## 1. 宏观硬约束（违反即打回）

> 这 8 条是本仓库的骨架，不随风格偏好改变。其余一切细则均为参考。

| # | 宏观原则                            | 一句话                                                                                                        | 兜底              |
| - | ------------------------------- | ---------------------------------------------------------------------------------------------------------- | --------------- |
| 1 | **架构主线：数据驱动 + 组件化**             | 角色 = base 场景 + 若干 `ComponentNormBase` 组件；状态本体在组件里，宿主只做转发，**不复制组件状态**                                       | 评审              |
| 2 | **组件只通过 `owner` / 信号 / 场景配置通信** | 禁止组件用 `get_parent()` 抓宿主改字段，禁止组件之间硬编码绝对路径                                                                  | 评审              |
| 3 | **生命周期入口固定**                    | 禁止子类重写 `_ready()` —— 重写 `ready_norm()` / `ready_show()` / `ready_garden()` / `ready_norm_signal_connect()` | 评审              |
| 4 | **类型映射一律走注册表**                  | `CharacterRegistry` / `BulletRegistry` / `MainSceneRegistry`；禁止业务代码散落 `preload` 类型映射                       | 评审              |
| 5 | **资源一律 `res://` 绝对路径引用**        | 移动 / 重命名必须连 `.uid` 一起带走并更新引用字符串，且**先关闭 Godot 编辑器**                                                         | 改名后全文搜 `res://` |
| 6 | **日志一律走 `Log.*`**               | 禁止裸 `print()` / `printerr()`（登记例外：`logger.gd` 整体、`test/autopilot_report.gd::line()`）                       | 打开游戏看控制台        |
| 7 | **改动触达玩法行为必须打开游戏（带窗口）实测**       | 改动较小 / 确定不会出问题 / 验证成本过高（**须在反馈里给出人工验证方法**）可免验证；判定见 [验证流程.md](验证流程.md)                                      | —               |
| 8 | **一关专属机制留在关卡脚本里，不进游戏本体**      | 只有一关（或极少数关）用到的特殊机制**必须**写在 `src/levels/mode_*/<关卡>.gd`（继承 `LevelScriptBase`）里；游戏本体不认识任何具体关卡 / 玩法名；该关**额外的专属脚本必须**与它同目录、文件名以它的文件名为前缀。被 ≥2~3 关复用时才上浮成通用字段 / 组件 / 规则（细则见 [D-07](参考存档/规范细则存档.md#d-07-关卡脚本-vs-游戏本体一次性机制的落位)）            | 评审              |

**应该**（默认遵守，例外在代码注释里写明理由）：

- **跨 Agent 记忆只落在文档里**：踩坑与流程结论**应该**写进 `docs/` —— 约束进本文件 §1，机制进专题文档，一次性过程进  
  [docs/工作记录/](工作记录/README.md)；只写在对话回复里等于没写（下一个 Agent 看不到）。

### 1.1 强制等级用语

| 标记          | 含义           | 出现的位置                                                  |
| ----------- | ------------ | ------------------------------------------------------ |
| **必须**      | 硬约束，没有例外     | 仅本文件 §1 这 8 条                                          |
| **应该**      | 默认遵守，例外需写明理由 | 本文件 §1 的补充项                                            |
| **参考 / 可以** | 可选做法，不做也不打回  | [具体规则存档](参考存档/规范细则存档.md)、[参考意见存档.md](参考意见存档.md) |

## 3. 维护约定

- **细则写进存档，不堆进本文件**：新增 / 修改具体规则直接改 [规范细则存档.md](参考存档/规范细则存档.md)，本文件保持「一屏可读」。
- **升级为硬约束要慎重**：只有真的反复踩坑、付出代价才加进 §1，并同步 [../AGENTS.md](../AGENTS.md) 的速查；细则仍在存档里。
- **改为参考的流程**：把 §1 里的条目移出时，正文搬进存档（措辞改「建议 / 不建议」），本文件 §2 保留目录行并标「参考」。
- **冲突时的优先级**：§1 > 专题文档 > 存档；存档与本文件冲突以本文件为准。
- **文档与代码漂移等同 bug**：代码行为变了要同步改对应文档。
- **文档分层**：**规则 / 方法论**放 `docs/` 顶层（`AGENTS.md`、`docs/README.md`、`项目规范.md`、`验证流程.md`、`AI调试通道.md`、`Agent协作协议.md`、`参考意见存档.md`）；**项目相关的机制 / 内容说明**放 [`docs/参考存档/`](参考存档/README.md)（明细见该目录 README §1），**不是**必读规范；**逐次任务的流程记录**放 [`docs/工作记录/`](工作记录/README.md)，三个目录不混排。
