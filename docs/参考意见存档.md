## 1. 怎么用这些意见

- **不是红线**：评审 / 自检**不会**因本文件的条目打回，提交前也**不必**逐条核对。
- **顺手一致**：新建文件、写大段代码时扫一眼 R-01 即可，不必回头改动历史文件。
- **不搞批量格式改写**：为了对齐本文件而重写既有文件（大 diff、易冲突）**不值得**。
- 想把某条**重新升级为硬约束**（真的开始因为踩坑付出代价了）→ 走 [E-01](参考存档/规范细则存档.md#e-01-新增一条规范)，不要在本文件里加「必须」。

## 2. 参考条目

### R-01 代码格式与注释（对应 S-01）

**状态**：参考。理由：排版与注释习惯不影响功能与架构，`.editorconfig` + `.gitattributes` 已配好，靠工具与习惯维持比靠强制更划算。

- **可以**用 **Tab** 缩进（当前绝大多数脚本如此，保持一致即可）。
- **可以**用 UTF-8 无 BOM、换行 LF、文件末尾保留一个换行（两处配置已声明）。
- **可以**不留行尾空格、空行不留缩进。
- **可以**用中文注释；成员文档注释 `##`、普通注释 `#`。
- **可以**用 `#region` / `#endregion` 分区（当前约 202 处），分区名写「这段在管什么」：

```gdscript
#region 组件状态访问
#endregion

#region 初始化相关
#endregion
```

- **可以**把 `@onready` 组件引用放在 `extends` / `class_name` 之后的第一块，其余成员用 `#region` 分节：

  `#region 子节点` → `#region 基础属性` → `#region 组件状态访问` → 各功能小节。
- **可以**让 `enum` / `signal` 紧贴使用它的属性或 `@export_group`，不强行凑固定顺序。
- **可以**给非平凡参数加一句注释：枚举成员、`@export` 配置项说明用途。

> **仍然必须**的是 [S-02 日志必须走 Log](参考存档/规范细则存档.md#s-02-日志必须走-log)（[项目规范.md](项目规范.md) §1 第 6 条）—— 那条是行为约束，不在这里。

### R-02 组件引用变量 `_component` 后缀（对应 C-01 一条）

**状态**：参考。理由：纯可读性收益，不影响 `%` 引用与任何运行机制。

```gdscript
@onready var sleep_component: SleepComponent = %SleepComponent   ## 可以：一眼看出是组件
@onready var sleep: SleepComponent = %SleepComponent             ## 也可以：不影响任何功能
```

> **仍然必须**的是「节点名与它的 `class_name` 一致」（`SleepComponent` 节点挂 `SleepComponent` 类）——
>
> 这条支撑 `%` 引用，仍在 [C-01](参考存档/规范细则存档.md#c-01-gdscript-标识符)。

### R-03 `src/` 与 `src/` 同名对应（源自 D-04 提示）

**状态**：参考（新增功能域时**可以**两边同时建同名目录）。理由：目录映射只影响「找不找得到」，不影响编译与运行。

- **可以**在新增功能域时同时建 `src/<域>/` 与 `src/<域>/`，按场景目录推导脚本位置。
- 只落一边也能跑，只是以后找脚本要多搜一次。

> 组件落位（[D-05](参考存档/规范细则存档.md#d-05-组件的落位)）与资源落位（[D-06](参考存档/规范细则存档.md#d-06-resources-的组织方式)）
>
> 同样是**参考**条目（正文见存档、目录见 [项目规范.md](项目规范.md) §2）。
