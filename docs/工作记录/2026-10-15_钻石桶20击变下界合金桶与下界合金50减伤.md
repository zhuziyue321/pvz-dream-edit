## 目标

改模组 `mods_builtin/more_armor/` 的**钻石桶 + 下界合金桶**：

- **钻石桶**：除了「挨打 20 次后变下界合金桶」外，其余与铁桶僵尸完全一致（**血量也从 1500 降到 1100**，与铁桶对齐）；
- **下界合金桶**：除了「本层防具 50% 减伤」外，其余与铁桶僵尸完全一致（**血量也从 2200 降到 1100**，与铁桶对齐 —— 减伤让「实际能挡的伤害」≈ 2200，效果不变）；
- 变身的口径：上限与当前血量都沿用旧防具。

## 步骤

3. 新增 `mods_builtin/more_armor/armor_diamond_bucket.gd`（`extends ArmorComponent`）：只多一件事 —— 累计挨打次数，满 20 次发 `sig_need_transform`；`absorb_damage()` 里在父类**之前**拍一张 `was_alive` 快照（让「第 20 击是破桶那一下」也计上），命中计数 + 阈值判定 + 发信号三步。

   - 加 `_transform_to_netherite()`：把整层防具换成下界合金桶那层，**继承旧防具的 `max_hp / curr_hp`**（基类 `_apply_armor` 先按继承的上限装好边界 / 贴图 / `curr = max`，再用 `armor.curr_hp = inherited_curr` 触发 setter 推进破损阶段）；

## 关键决策与理由

- **「效果长在防具上」已是定式** —— 铜桶的易伤、下界合金的减伤都在 `ArmorComponent` 子类里改 `absorb_damage()`，本体一行不用动；钻石桶的「挨打计数」也走这条 —— 跟伤害结算强相关的都长在防具上。
- **变身的触发计数长在防具组件，发信号给宿主换** —— 不在僵尸脚本里改 `absorb_damage()` 是因为宿主拿不到「这层吃了多少伤害」的判据；信号 + `call_deferred` 是「组件 → 宿主 + 帧末执行」的标准套路。
- **变身必须 `call_deferred()`** —— 钻石桶的 `absorb_damage()` 是被 `HpComponentZombie.hp_loss()` 调用的，那条函数正在 `for armor in armor_list:` 里遍历防具链；同步摘挂会改遍历目标。`call_deferred()` 推到帧末，结算已经走完。
- **继承口径：上限与当前血量都沿用** ——「防具血量继承」按用户口径理解为 max + curr 都沿用。优点：血条比例连续、破损阶段不跳变；缺点：变身后看似戴着一只「没怎么掉血的下界合金桶」，但这种小瑕疵是「换装」的固有代价。换成「只继承 curr，max 换成下界合金的 2200」会出现「刚换完立刻就看起来最破」的不连续感，所以选了前者。
- **下界合金桶自身上限也从 2200 改成 1100** —— 用户口径「下届合金桶也是 1100」。物理上等价（旧版 2200 平 vs 新版 1100 + 50% 减伤 = 有效 2200），但语义更清晰：「本模组三只桶防具血量一致 = 1100，特殊效果另算」。
- **基类加 `IRON_SPRITE_PATH` + 初始装配也换** —— 铁桶场景里 `IronNode` 自带铁器贴图，原本「被磁力菇吸走那一瞬」任何桶都顶着铁桶脸；现在统一在基类里按当前桶的完好贴图换，钻石桶变身后再换一次到下界合金。**这个修的是 pre-existing 瑕疵**，但变身路径必走这个节点，不修就会引入「同只僵尸被吸走那一瞬变身前是铁桶脸、变身后是下界合金脸」的新瑕疵。
- **count 在 `super` 之前** —— 钻石桶要算「第 20 击是破桶那一下」，所以在父类**之前**拍 `was_alive` 快照（破桶发生之后 `is_alive()` 才是 false）。宿主端的 `_transform_to_netherite()` 再判一次 `old.is_alive()` 兜底：真破了就跳过，留下「没桶的钻石桶」并打 `Log.warn`，不强行造一个「当前血量 = 0 的下界合金桶」。
- **减伤的「只减本层吃掉的部分」要走换算** —— 父类按「折小后的伤害」扣血得到 `absorbed`，但**往下传的是「原始伤害口径」** ⇒ `return remain - roundi(absorbed / (1 - 减伤率))`。如果只把父类的返回值原样上送，会把折小后的溢出当原始溢出传下去，本体吃的伤害就少了一半。
- **脚本比较用 `is_same()`** —— `Script == Script` 不可靠，preload 出来的同一份资源应该用 `is_same()` 判等。
- **血量从 1500 / 2200 调到 1100** —— 用户的口径是「其余与铁桶相同」+「下界合金桶也是 1100」，于是三只桶防具血量统一到 1100。战力 / 权重 / 阳光**没动**（6/8/3、1200/700/1600、175/225/100）—— 那是模组自己的稀有度阶梯，不属于本任务。

## 踩坑

1. **钻石桶 `was_alive` 快照的位置** —— 第一版写在 `super` 之后，结果永远是「这一击之后还活不活」（= 父类扣血之后的状态）。要的是「这一击之前还活不活」才能让「破桶那一下」也算上 ⇒ 必须在 `super.absorb_damage()` **之前**读 `is_alive()`。
2. **`absorb_damage()` 在伤害管线遍历防具链时被调用** —— 同步挂摘防具会改 `armor_list`，遍历跳 / 重。同步的 `sig_need_transform.emit()` 没问题（信号只是入队），**宿主的响应函数里**调 `add_armor()` / `remove_child()` 才有事。`call_deferred()` 把响应推到帧末，遍历已结束才动手。
3. **减伤「外溢到本体」的隐患** —— 父类按折小后的伤害扣血并返回「折小后的溢出」；如果把这个返回值原样上送，**本体吃到的伤害是折小后的**。正确做法是丢弃父类的返回值，根据 `absorbed` 换算回原始伤害口径再决定往下传多少。
4. **`halved` 至少为 1** —— `remain = 1, 0.5 减伤` ⇒ `halved = round(0.5) = 0`，父类按 0 扣会视作「没掉血」（父类的 `if curr_hp <= 0 or remain <= 0: return remain`）⇒ 一次 1 伤害会**免疫**。用 `maxi(..., 1)` 保住「极端小伤害至少要扣 1」。
5. **`user://` 下的脚本 `class_name` 不注册** —— 同上条，preload 的脚本与防具组件上挂的脚本 `==` 判等不可靠，统一用 `is_same()`。
6. **`probe` 里 `_check_diamond_transform` 必须 `await a.frames(2)`** —— 变身走 `call_deferred()`，不 await 帧末就立刻 `queue_free()` 的话断言会读到「变身前」的状态（与铜桶的「协程必须 await」同源）。
7. **首次跑探针发现新 `armor_diamond_bucket.gd` / `armor_netherite_bucket.gd` 的 `.uid` 还没生成** —— 不影响 probe（preload 用相对路径，不用 uid），但 Godot 编辑器第一次打开会自己生成。

## 给后来者的最简路径

1. **要给防具加自己的机制** → 在模组里写 `extends ArmorComponent` 的子类，重写 `absorb_damage()`；改伤害比例（×倍率 / ×折扣）时**务必按原始伤害口径往下传**（铜桶的「放大后夹回原始伤害」/ 下界合金的「扣血量换算回原始」是两种现成写法）。
2. **要触发变身 / 跨组件协作** → 在防具组件里累计条件 + 发信号，宿主用 `call_deferred()` 接收（不能在 `absorb_damage()` 同步换：血量组件正遍历防具链）。
3. **「铁器节点下那张桶」不在基类默认装配里**（原本是个 pre-existing 瑕疵）→ 加 `IRON_SPRITE_PATH` 常量进 `OreBucketZombieBase`，在 `build_runtime_parts()` 一起换；这样换装路径只需再写一次 `_set_sprite_texture(IRON_SPRITE_PATH, ...)` 就一致了。
4. **减伤 / 易伤的「只影响防具」口径**：调 `super.absorb_damage(mode, 折小/放大后的伤害)`，**然后丢弃返回值**，按本层 `absorbed` 换算回原始口径 `remain` 再 `return`。直接用父类的返回值会把折小后的溢出当原始溢出传下去。
5. **血量从「按矿石阶梯递增」改成「统一 1100 + 各自机制」** → 三只桶防具血量一致，特殊效果（易伤 / 变身 / 减伤）改机制不靠血量堆。物理上等价（旧 2200 = 新 1100 + 50% 减伤），但语义更清晰。
6. **收尾**：门禁 + `probe_more_armor_mod`（**核对断言条数**，多加了 `_check_netherite_dr` 与 `_check_diamond_transform`）+ 同步模组页文案 + [模组机制.md §6.3](../参考存档/模组机制.md) 三只桶的段落都按新口径重写。

## 人工验证方法（本次未开游戏）

1. 主菜单 → 选项 → 控制台 → 模组 → 打开「更多的防具」，看右侧文案：
   - 钻石桶：1100 + 「挨打 20 次后变下界合金桶」+「上限与当前血量都沿用」；
   - 下界合金桶：1100 + 「本层防具 50% 减伤」+「实际能挡 ≈ 2200」+「贴图四张，破损分四段」。
2. 开一关（出怪表已自动加入三只），盯一只钻石桶僵尸：
   - 放一棵豌豆射手（伤害 20），观察挨打 20 下后桶的颜色与贴图**瞬间**从钻石的变成下界合金的；
   - 换一株**伤害 60+** 的射手（寒冰菇 100 / 西瓜 80 / 玉米 80）：挨打约 14~18 下时钻石桶先掉到不足 1100 / 单击就破 —— **这种情况下不会变身**（防具没了就没东西可继承，会留一只没桶的钻石桶 + 一行 `Log.warn`），不期望看到变身。
3. 盯一只下界合金桶僵尸：
   - 用相同火力对比，**它应该比铁桶明显扛得久**（50% 减伤），看血条变化速度是否为铁桶的 ½；
   - 磁力菇吸桶的那一瞬，**僵尸本体血量不掉**（减伤只减本层吃掉的部分）。
4. 钻石桶变身后立刻被磁力菇吸走 —— 顶上来的应该是下界合金桶的脸（不是铁桶脸），验证基类铁器节点贴图也换对了。
