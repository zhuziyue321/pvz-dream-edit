## 关键决策与理由

- **第 6 项的对象池最终没做，只做了按需加载 + 生成收口** —— 因为发现 `bullet_parabola_base.gd` 被保护伞弹开时会执行 `area_2d_attack.queue_free()`，**把自己的攻击框子节点销毁了**。这种子弹一旦放回池里复用，第二次就没有攻击框，会静默失去伤害能力。而且收益与风险不成正比：高频的豌豆场景本就很轻，真正重的抛物线 / 玉米炮恰恰是不能池化的那批。结论已写进 §12.3-16。
- **第 8 项没有把 37 个事件回迁成 Godot 原生信号** —— 两个理由：① `minigame_*.gd` 关卡脚本正是靠 EventBus 的动态订阅来挂全局钩子（如 `minigame_12_column.gd` 订阅 `HAND_CARD_TAKE`），这是硬约束 §1-8「一关专属机制留在关卡脚本」的支撑机制；回迁后订阅方必须持有发布方引用、管理器跨关重建还得重新接线。② 回迁反而**引入**耦合（订阅方得知道谁在发布），与 §1-2 的方向相反。改用「签名表 + push 当下校验」，拿到了回迁的主要收益，成本只是一张可渐进补全的表。结论已写进 §12.3-17。
- **校验失败只打 `Log.error`、不拦下事件** —— 这条防线是为了「尽早暴露问题」而不是「替业务做决定」。万一签名表登记错了，直接拦下会让功能整个失效，那比原来的静默失效还糟；报错 + 继续，功能还在、日志也有据可查。
- **签名表要支持可选参数**：某个位置写 `TYPE_NIL` 表示「可选 + 跳过类型校验」，必填个数 = 从头数到第一个 `TYPE_NIL`。这是被 `CREATE_COIN` 逼出来的 —— 它的订阅方 `DIM_Coin.create_coin` 第三个参数带默认值，所以调用方传 2 个（`component_create_coin.gd`）或 3 个（`component_drop_item.gd`）都是合法的。
- **签名表只登记核实过的事件**（约 25 个），没登记的不校验：不为难存量代码，补一条就多一条保护。

## 踩坑

1. 写 `var path := some_typed_dict.get(key, 空串)` 会编译报错：The variable type is being inferred from a Variant value … (Warning treated as error)。原因是 **`Dictionary.get()` 的返回值恒为 Variant，哪怕字典本身是 typed 的**（当时的 `BULLET_SCENE_PATHS` 明明白白声明为 Dictionary[BulletType, String]）。**正解**：改用显式类型注解。
   连带教训：这个错误会沿依赖链冒泡成 Failed to compile depended scripts，报错文件（当时是 `lawn_mower.gd`）可能离真正的元凶（`bullet_registry.gd`）很远，别被误导去找错地方。
2. **不要假定一个事件只有一种 payload 长度** —— 订阅方参数带默认值时，同一事件的 arity 会不一致（`CREATE_COIN` 就是 2 参和 3 参并存）。登记签名前必须把所有调用点都看一遍。
3. 判断 payload 元素类型时，`.x` 这种成员访问不可想当然：`row_col` 是 `Vector2i` 时 `.x` 是 int，若是 `Vector2` 则 `.x` 是 float。本项目植物格子坐标是 `Vector2i`，所以 `JALAPENO_BOMB_*` 三个事件的 payload 登记为 int。

## 给后来者的最简路径

1. 想动战斗热路径（子弹 / 攻击组件 / 事件总线）时，**第一步永远是量化改动面**（搜调用点、看 extend 子树），规模常常会直接推翻原方案。
2. 遇到「某某要池化 / 要回迁」这类大改提议，先去找**具体的反例代码**（比如自毁子节点的那一行）来判断可行性 —— 比泛泛地评估利弊快得多，也更能写进文档说服后来者。
3. 改完这类基础设施，除了跑编译门禁，务必同步 `架构总览.md` 的这几处表格：§4.1 单例表、§4.3 注册表表、§4.5 生命周期、§5.3 组件表、§12.3 技术债表。本轮这 5 处全都漂移了，而仓库已无静态检查器会提醒你。
