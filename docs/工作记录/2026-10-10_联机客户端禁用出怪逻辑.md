# 联机：客户端彻底禁用出怪逻辑 + 出卡收归主机（波次只下发演出，僵尸交给快照）

> **[面向 AI Agent]** ｜ **触发条件**：要动 `src/mods/netplay/` 下任何一个文件，或要判断"某个新机制该走命令还是走快照"
> **读完你能**：知道为什么"出怪 / 出卡"不该留在客户端、改动落在哪几个文件、"连续量 vs 一次性事件"这条分流规则怎么用，以及**为什么动模组之后必须跑探针而不是只看门禁**
> **强制级别**：参考（流程记录） ｜ **关联**：[联机模组](../../参考存档/联机模组.md) §4.7 ｜ [联机模组规范](../../参考存档/联机模组规范.md) §3.2 ｜ [2026-10-09_联机波次同步与进关闸门](2026-10-09_联机波次同步与进关闸门.md)

## 1. 目标与结论

把"出怪"整件事从客户端拿掉。改完之后：

- 客户端**永远不开波**（`start_next_wave_gate` 恒 `false` + `stop_refresh()`）；
- 客户端**一个僵尸都不自己造** —— 场上僵尸全部由状态广播按 `entity_id` 补种；
- `wave_next` 命令只发**一次性演出**（波次号 / 升哪面旗 / 大波还是最终波）；
- 进度条改成走**每帧快照**（第二包 `pr` / `ws`），客户端不再自己算。

连带收益：`GameRng` 在"出怪"这条线上的依赖消失，中途加入不用补种子，珊瑚 / 蹦极 / 墓碑伏击那三批"从来没下发通道"的生成自动被覆盖。

## 2. 过程（含走过的弯路）

### 2.1 起点：一句质疑

用户问："理论上现在用 `GameRng` 的事情都应该由房主处理，为什么要下放 `GameRng`。"

这句话点破了架构矛盾：这套联机表面是主机权威，实际在"出怪"上是**两端各跑一遍确定性模拟** —— 客户端调的是本体同一个 `start_next_wave()`，主机只下发"开第 N 波"这个信号。

### 2.2 先看清客户端到底跑了多少

这一趟最关键的一步：**不是立刻改，而是先把客户端在跑的整条链路列出来**。列完发现比"抽个随机数"多得多：

| 客户端在跑的 | 含随机 | 备注 |
|---|---|---|
| `before_wave_spawn()` 关卡脚本按局势调出怪密度 | 依赖场上局势 | **两端局势一有偏差，连"随机调用了几次"都不同** |
| `create_curr_wave_zombie_list()` 抽怪清单 | `GameRng` | — |
| `create_norm_wave_zombies()` 自己选行 | `GameRng` + 雪橇队特殊选行 | — |
| `spawn_special_zombie_in_big_wave()` 珊瑚 / 蹦极 | `GameRng` | **不在 `wave_spawn` 清单里** |
| `call_tombstone_create_zombie()` 墓碑伏击 | `GameRng` | **不在清单里** |
| `GameRng.pick_random(携带解锁道具的那只)` | `GameRng` | — |

### 2.3 两条候选路径

**路径 B（下发清单）**：`wave_next` 带 `z_types / z_lanes / z_ids`，客户端按清单造。
本体其实**已经铺好了切口** —— 出怪是"清单 → 实例化"两段式：

```gdscript
# zm_zombie_wave_create_manager.gd
var wave_spawn: Array[CharacterRegistry.ZombieType] = create_curr_wave_zombie_list(wave, is_big_wave)
return level_script.create_wave_zombies(self, wave_spawn, wave)   # 关卡脚本可覆写进场方式
```

**路径 A（交给快照）**：客户端什么都不造，僵尸全靠 `NetplayStateSync` 的补种（那个能力本来就存在，`_spawn_zombie()` 带类型 / 行 / 位置 / 编号）。

**选了 A**。理由：珊瑚 / 蹦极 / 墓碑伏击那三批**不在清单里**，走 B 仍然覆盖不到，还得靠快照兜底；既然兜底能力本来就要有，就没有必要再开一条"主机下发清单"的通道（多一个通道就多一个"两边谁先到"的竞态）。代价只有僵尸晚约一个 RTT 出现（局域网几毫秒）。

> 弯路：一开始倾向 B（"零延迟"听起来更好）。把"哪些生成不在清单里"列出来之后才改的主意。
> **教训：先看"覆盖不到的那部分有多大"，再决定要不要为了延迟多开一条通道。**

### 2.4 进度条为什么走快照不走命令

一开始打算顺手塞进 `wave_next`。读了 `ZombieWaveManager` 才发现进度条是**连续量**：

```gdscript
battle_progress = curr_wave % max_wave_one_round * progress_bar_segment_every_wave   # 开波时跳一次
battle_progress += progress_bar_segment_mini_every_sec                                # 波次之间按秒爬
```

命令只在开波那一刻发一次 ⇒ **爬升那一段永远差着**。而且进度口径可被关卡脚本换掉（外部出怪器 / 僵王血量），所以采集走的是通用入口 `ZombieManager.get_battle_progress()`，不是直接读波次管理器的字段。

## 3. 踩坑

1. **⚠️ 主机不能读 `_flag_to_raise`** —— 那是**一次性**的（`take_flag_raise_index()` 读走即清）。主机若在下发前抢读，主机自己的进度条就升不了旗。
   → 正解：照本体口径自己算 `int(curr_wave % max_wave_one_round / 10.0)`，只在旗帜波 / 最终波算，其余发 -1。
2. **删掉常量要顺着搜引用** —— `ARG_ZOMBIE_IDS` 删了之后，`probe_netplay_session.gd` 里还有引用；`_host_wave_gate` 改名 `_client_wave_gate` 同样有探针引用。
   → 正解：改完立刻全仓搜一遍旧名字（编译门禁**抓不到**探针里的这类引用 —— 它只编译"被资源引用到"的脚本，见 `check_scripts.ps1` 头部 KNOWN LIMITATION 1）。
3. **GDScript 里 `\` 续行**在复杂布尔表达式里最好别用 —— 改成一个具类型的临时变量更稳（本项目把 `UNTYPED_DECLARATION` 当错误，`var x :=` 推断不出来会直接打回，所以临时变量要写明类型）。

  4. 客户端自己打不死僵尸（僵尸是木偶），血量/位置应跟着主机走。

## 6. 第二段：出卡同步（传送带流过来的是哪一张，由主机说了算）

同一轮顺手做的第二件事。起因是差距分析里找到的**最硬的一处不同步**：

```gdscript
# src/ui/card/card_slot/card_random_pool.gd:39
var random_weight: int = randi_range(1, _total_weight)   # 全局随机，不是 GameRng
```

传送带两端抽的是**不同的卡** ⇒ 客户端手里那一张主机没有 ⇒ 点下去主机重放时认不出它
（`execute()` 找不到这张卡）⇒ **这一下操作凭空消失**。

### 6.1 两条路，选了"主机下发"

| 路 | 做法 | 选 / 不选 |
|---|---|---|
| 改走 `GameRng` | 一行 `randi_range` → `GameRng.randi_range` | 不选：出怪那条线刚证明"两端各算一遍"有多脆弱（共享序列串位且**无任何报错**），出卡是同一类问题 |
| ★ **主机下发** | 本体加"闸门 + 指定身份出卡 + 出卡观测口"三件套，主机出一张发一张 | 选：与"生成一律归主机"这条已有纪律一致，顺带根治"客户端手里有主机没有的卡"这一整类问题 |

### 6.2 本体加的三件套（`card_slot_conveyor_belt.gd` / `card_slot_seed_rain.gd`）

```gdscript
var create_card_gate: Callable = Callable()       # 返回 false = 这一次不许本地出卡
signal card_created(reference, index)             # 出了一张卡
func spawn_card_by_reference(reference) -> Card    # 按**指定身份**出一张：不经闸门、也不走随机池
```

- 身份过网络用现成的 `ResourceCardReference.to_dict()` / `from_dict()`（三个标量字段），
  不用另发明序列化。
- 关卡配了 `conveyor_order` 的那几张本来就不走随机池（两端天然同一张），主机照样下发 ——
  省得再判一次"这一张要不要发"。
- ★ **种子雨（天降卡）只留槽位、不接管**：它是迷你游戏 04 的**一关专属玩法**，节点由关卡脚本
  自己挂（`minigame_04_seed_rain.gd`），按硬约束 §1-8 联机不碰。

### 6.3 ⊙ 一个必须记住的验证盲区

**编译门禁（`check_scripts.ps1`）覆盖不到整个 `netplay` 模组。**

- 模组入口是 `mod_manager.gd` 里的**字符串路径**
  （`ModIds.NETPLAY: "res://src/mods/netplay/netplay_mod.gd"`），运行时 `load()`
  ⇒ 不在资源管线的可达集里（门禁脚本头部的 KNOWN LIMITATION 1 写的就是这件事）。
- 实证：新增 `netplay_card_spawn_sync.gd` 之后门禁脚本数**没有增加**（改前 107 / 改后 106）。
- ⇒ **此前所有 `netplay` 改动都没有被门禁真正验证过**，真正兜底的是**探针**
  （`probe_netplay_session.gd` 会真的 `new()` 那些类，从而触发编译）。
- 所以要记住：**动模组之后必须跑探针，不能只看门禁 PASS。**

第一次跑就栽在这里：环境里有 3 个残留的 Godot 进程在抢输出文件
（"The process cannot access the file because it is being used by another process"）。

> **补充（同日稍后）**：隔一会儿重跑就通了 —— `[NETPLAY] result=PASS failed=0`。
> 所以那次**不是脚本的问题**，就是并发的 Godot 实例在抢同一个输出文件；
> 再遇到这个报错，等残留进程退出重跑一次即可，不要去改脚本。
> ⚠️ 顺带修掉一个自己踩的坑：`-Headless` **不是** `run_autopilot.ps1` 的参数
> （它默认就是无头，`-Windowed` 才是开窗口），传了会直接报"找不到参数"。

## 8. 第三段：补全快照（僵王 + 玩家阳光总量）

### 8.1 先判域，再动手 —— 省掉一项白做的

尾巴里原本列着"卡槽冷却 / 阳光总量 / 僵王"三项。动手前先按**战斗域 vs 本地域**判了一遍，
结果**砍掉一项**：

| 项 | 判据 | 结论 |
|---|---|---|
| 卡片冷却 | 两端各有自己的出战卡槽（`card_manager.card_slot_battle` 每局一个）、各点各的卡，**没有任何一个事件会同时影响两端的冷却** | ✗ **本地域，不该同步** —— 拉平反而打乱玩家自己的节奏 |
| 阳光总量 | 一颗阳光谁捡到都是**各自钱包各加一次**（`Sun.collect()` 在两端各跑一遍）⇒ 两端本该始终相等，靠一条条 `pick_sun` 命令堆出来 | ✓ **战斗域，该同步**（丢一条命令就永久分叉） |
| 僵王 | 场上实体，客户端不出怪 ⇒ 客户端压根没有僵王 | ✓ **战斗域，该同步**（不补种就是"主机在打、客户端看不见"） |

> 一开始就默认"三项都补"的话，卡片冷却那份是**白做的**，而且会引入一个真实的坏行为。

### 8.2 ⊙ 四个不查代码绝对猜不到的坑

| 坑 | 现象 / 正解 |
|---|---|
| 僵王**不在** `all_zombies_1d` | 挂在独立的 `%ZombieBossRoot`（`ZombieManager` 明确"僵王不加入普通僵尸列表"）⇒ 照僵尸那套遍历**一只都采不到**，必须单开一类 |
| `get_living_bosses()` **过滤掉已死的** | 用它采集的话，主机那只正在演死亡动画的僵王一条都发不出来 ⇒ 客户端永远收不到"它死了"，只能等缺席 90 帧凭空删掉，**死亡演出整个丢掉**。改遍历 `%ZombieBossRoot` 根节点 |
| 自动入口 `create_boss()` **每关只成功一次** | registry 里 `_auto_boss_spawned` 挡着，客户端补种时那一次早被主机用掉了 ⇒ 补种必须走**卡牌召唤**入口 `try_create_boss_from_card(type)`（每次返回新实例） |
| `ZB000Base` 上**没有任何类型字段** | 实测 `z_b_000_base.gd` 里没有 ⇒ 客户端补种无从知道造哪一种，**类型必须随快照发**。⚠️ 已知限制：取的是关卡参数 `game_para.boss_type`，僵王**卡牌**召唤的那只若本关没配自动出场就拿不到类型 ⇒ 补种不了（宁可不显示，也不造错一种） |

### 8.3 阳光总量那条的两个细节

- **只在值不同时才写回**：`sun_value` 的 setter 会遍历每张卡重判"阳光够不够"，每帧白跑一遍不值当。
- **没有出战卡槽时压根不发**：否则客户端 `snap.get(&"sv", 0)` 会把钱包**清零**。
- 采集走 `card_manager.card_slot_battle.sun_value`（⚠️ 不是 `DaySunsManagner.curr_sun_sum_value`
  —— 那只是"天降累计产量"，用来算下一次天降间隔的）。

### 8.4 验证

`powershell -ExecutionPolicy Bypass -File test/run_autopilot.ps1 -Scenario probe_netplay_session`
⇒ **`[NETPLAY] result=PASS failed=0`**（15 段全过，含本轮新加的僵王 / 阳光三条）。门禁 PASS。

⚠️ 但这轮的**新逻辑**只被"编译 + 不崩"覆盖，僵王 / 阳光的**实际对齐效果没有实机证据**
（要跑到僵王关才看得见）。真要验得开 5-10 或迷你 20 双开一局。

## 9. 第四段：客户端僵尸推进到「完全无行为逻辑」

### 9.1 关掉的不止攻击 —— 组件逐个过一遍

判据不是"名字里有没有 attack"，而是**它产不产生判定 / 效果**：

| 组件 | 类别 | 处理 |
|---|---|---|
| `attack_component` / `hurt_box_component` | 行为 | 关（第一轮已关） |
| **`move_component`** | **行为** | ★ 本轮关掉 |
| `detect_component` / `detect_component_pogo` | 行为（索敌） | 关 |
| `jump_component` | 行为（撑杆 / 跳跳 / 海豚） | 关 |
| `bomb_component_jackbox` | 行为（小丑爆炸**会炸掉植物**） | 关 |
| `hp_stage_change_component` | 表现（血量阶段换外观） | **保留** |
| `charred_component` | 表现（焦黑） | **保留** |
| `critical_value_component` | 表现（临界掉手 / 掉头） | **保留** |
| `drop_item_component` | 行为，但已被掉落闸门拦住 | 不重复关 |
| `swim_box_component` | 判定，但**不是** `ComponentNormBase` 子类（没有 `disable_component` 接口） | 没动，记一笔 |

⚠️ `critical_value_component` 名字像行为，实际只改外观，且由**血量**驱动（血量是主机下发的）
⇒ 该留。反过来 `bomb_component_jackbox` 看着像个"道具"，实际会在客户端自己炸掉植物 ⇒ 必须关。

### 9.2 ⊙ 先解决"截断僵住"，才敢关移动

2026-10-09 那条记录里"不动 `move_component`"的理由有**一条是真实且当时无解的**：
快照截断时那几只既收不到位置、又不会被回收，会僵在原地；本地移动正好盖住这个破绽。

所以本轮**必须先补采集侧**，顺序反了就是满屏僵住的僵尸：

**轮转采集**（`_z_cursor`）—— 截断时游标停在断点，下一帧**从没采到的那一只接着采**。
不轮转的话每帧都从头采、被截断的永远是排在后面那同一批 ⇒ 那几只**永远收不到位置**。

> 这是本轮唯一一处「为了改 A 必须先改 B」的地方 —— 光关移动不补轮转，等于把破绽掀开给人看。

⚠️ **代价**：移动组件顺带管着屋顶斜面 / 爬梯的 y 修正（`move_y_correct_slope` / 爬梯），
关掉后客户端的僵尸**不走斜面修正**。位置本身（含 y）仍然是主机下发的，缺的只是贴合斜面那点偏移。

### 9.3 ⊙ 探针 PASS ≠ 没有脚本错误（差点漏掉）

把 `_has_anim_prop` 改名成 `_has_prop` 之后跑探针，**stdout 报 `result=PASS failed=0`**，
但 **stderr 里躺着**：

```
SCRIPT ERROR: Invalid call. Nonexistent function '_has_anim_prop' in base 'Node (NetplayStateSync)'.
```

探针里有一处还在调旧名，而**断言块里抛的错不会计入 `failed`** ——
于是"PASS"与"有一整段断言根本没跑"同时成立。

⇒ **跑完探针必须单独看 stderr**，只盯那行 `result=PASS` 会被骗过去：

```powershell
$o = powershell -ExecutionPolicy Bypass -File test/run_autopilot.ps1 -Scenario probe_netplay_session 2>&1
$o | Select-String -Pattern "NETPLAY\] result"
$o | Select-String -Pattern "SCRIPT ERROR|Parse Error|Nonexistent function"   # 这一行必须为空
```

（这正好印证 [AI调试通道](../../docs/AI调试通道.md) 第〇节：无头只证明"跑得完"。）

### 9.4 ⊙ "禁了"不等于"停了"

`ComponentNormBase` 只是个**标记** —— 基类**并不统一拦** `_process` / `_physics_process`，
禁用到底有没有效**取决于每个子类自己判不判这个标记**。

`MoveComponent` 是在自己的 `disable_component()` 里把 `is_enabling` 桥接到
`move_factors[E_MoveFactor.IsDisable]` 上、`_process` 里再判 `is_move` 才真的停住的。

⇒ **换一个组件要重新确认它读不读这个标记**，不能假定"调了 `disable_component` 就一定停"。
