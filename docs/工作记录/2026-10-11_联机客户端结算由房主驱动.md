# 2026-10-11 · 联机同步 · 客户端不自行结算，房主结算时客户端才结算并写通关存档

> **任务类型**：其它（联机同步 / 结算线）
> **推荐度**：**推荐**（"要拦就拦在'这一下算不算数'的入口，不要只拦下游的写档"这条可直接照用）
> **耗时与成本**：约 1 轮对话，未开游戏（门禁 PASS + lint 0，已给双实例人工验证方法）
> **验证方式**：免验证 + 已给出人工验证方法（改动只落在结算时机，双实例才验得到）
> **补充自**：无（顺着 [2026-10-10 联机快照渲染状态](2026-10-10_联机快照渲染状态.md) 那条"客户端只渲染"的口径往下做）

## 目标

1. 客户端**不能自己结算**（自己点开奖杯不算数）；
2. 房主结算的那一刻，客户端跟着结算；
3. 客户端**一定要写通关存档**（含解锁植物 / 道具 / 钉耙 / 跳商店）。

## 步骤

1. 先摸清现有链路（不要直接改）：`MgmRewardManager.win_main_game()` 是结算唯一出口，
   里面 `update_level_state_data_success()` 是**全仓唯一**写 `IsSuccess` 的地方。
2. 本体加一个通用的「结算时机」问询口 `MgmRewardManager.level_settle_gate`（不带联机字样，默认空 = 照旧），
   判在 `win_main_game()` 里 `is_win_settled` 判重**之后**、置位**之前**（被拦时不能置位，否则后面调不进来）。
3. 模组在 `install_to_main_game()` 里占住它：`_settle_gate()` —— 房主照旧，客户端**只有
   `_host_verdicts` 上榜**才放行，否则停在原地并在控制台写一行"等房主结算"。
4. 客户端收到房主那句 `level_result`（它同时是结算指令）：还在关里 ⇒ 直接
   `reward_manager.win_main_game()` 走本体同一条线；已离场 ⇒ 原有兜底
   `_apply_host_verdict_outside_level()` 补写"通关 + 顺带解锁的植物"。
5. 同步文档：[联机模组.md §4.4](../参考存档/联机模组.md)（两道闸门 + 收尾口径）、
   [联机模组规范.md §2.4](../参考存档/联机模组规范.md)（规则层）。
6. 跑编译门禁 `powershell -ExecutionPolicy Bypass -File test/check_scripts.ps1`（real compile errors = 0）。

## 关键决策与理由

- **拦"结算"而不是只拦"写档"** —— 因为只拦写档时 `win_main_game()` **照样会切场景**，
  客户端先回选关页，房主的指令到时人已经不在关里 ⇒ 只能靠兜底补写，钉耙消耗 / 多轮重置 / 跳商店
  全对不上，而且"这一关通没通"要等下一次重打才补得上（旧实现真正的时序洞）。
- **客户端结算直接调 `win_main_game()`，不自己抄一遍写档** —— 结算线上还有多轮重置、
  跳商店 / 跳图鉴，抄一遍就会跟房主走出不同的收尾。
- **保留 `_apply_host_verdict_outside_level()` 兜底** —— 客户端被房主带去下一关时指令会晚到一步，
  那时没有本局节点可调 `update_level_state_data_success()`，只能直接写 `Global.global_game_state`。
- **沿用现成的 `level_result` RPC，不加新指令** —— 房主写档与"通知大家结算"本来就是同一刻同一件事。

## 踩坑

1. **读到的是过期的文件内容** —— 第一次 `read_file` 拿到的 `netplay_mod.gd` 里没有
   `_apply_host_verdict_outside_level()`，按那份内容写的替换直接失配。
   → **正解**：改之前那次读取若与后续编辑间隔较久（或中间被别的 agent 改过），替换前**重读一遍**再动手。
2. **闸门被拦时不能置"已结算"标志** —— `is_win_settled = true` 若写在 gate 之前，
   客户端被拦一次就永远结算不了。**正解**：判重在前、gate 在中、置位在后。
3. **光拦下游写档 = 拦了个寂寞** —— 见「关键决策」第一条，判据是
   "这一段代码有几条会跑出去的副作用"，不是"闸门装上了没有"（同 [规范 E-02](../参考存档/规范细则存档.md#e-02) 那条口径）。

## 给后来者的最简路径

1. 找结算的唯一出口（`win_main_game()`），在它开头加一个通用 `Callable` 闸门（本体不认玩法名）。
2. 模组占住：房主放行 + 下发指令；客户端等指令。
3. 客户端收到指令 ⇒ 调本体同一个函数（不要抄写档），离场时另备兜底。
4. 人工验证：双实例进同一关，客户端先点开奖杯 ⇒ 应停在白屏（控制台"等房主结算"）；
   房主点开奖杯 ⇒ 两端同时切场景，且客户端的选关页上这一关显示已通关（解锁植物也在）。

## 补充（同日，另一半）：客户端得先"走得到该等的那一刻"

> **补充者**：同批并发的另一个 agent ｜ **双向引用**：本文 §「关键决策」第 3 条提到的
> `_apply_host_verdict_outside_level()` 兜底就是这一半加的；这一半的机制文档在
> [联机模组.md §4.7.1](../参考存档/联机模组.md)（不是 §4.4）。

**起因**：用户报的两件事里还有一件 —— 日志刷
`关卡脚本：主游戏 / 通关结算子管理器不存在，判胜已跳过`，而客户端打完 1-2 拿不到樱桃炸弹。
上面那条闸门只解决"**别提前结算**"，但它**治不了"客户端根本走不到判胜那一步"**：

`start_battle` 判"本段打完了吗"问的是 `is_end_wave and curr_zombie_num == 0`，
而这两个数在客户端**各缺一半**：

| 判据 | 客户端为什么凑不出来 |
|---|---|
| `ZombieManager.is_end_wave` | 客户端**一次波都不开**（`start_next_wave_gate` 恒 false），本地这一位**永远变不成 true** |
| `ZombieManager.curr_zombie_num` | 僵尸是快照补出来的木偶，退场走 `_delete_zombie()` 的 `queue_free()`，**不走本地死亡流程** ⇒ 只增不减 |

⇒ 客户端的关卡流程**一直卡在开战那一步**，直到房主离场把这一关拆掉才醒过来，
醒来时 `Global.main_game` 已经是 null ⇒ 就是那句 ERROR；
而 `gain(level_complete_loot)` 被跳过 ⇒ **客户端永远拿不到本关给的植物**。

**做法**：主机在自己那一局推 `EventBus "battle_finished"` 的当下把这一刻**下发**
（一次性事件 ⇒ 走 `battle_op` 可靠命令，新增 `NetplayCommand.OP_BATTLE_FINISHED`）；
客户端收到只改 `is_end_wave` / `curr_zombie_num` 两个字段，让关卡流程能往下走；
顺手把 `_delete_zombie()` 的计数减回去（客户端的僵尸增减要配成对）；
那条 ERROR 在"本关自己的主游戏已被销毁"时降级成 debug（那只是关卡被拆了，不是错误）。

**⊙ 踩坑（这一半最值钱的一条）**：第一版走的是**快照**（把 `is_end_wave` 当状态塞进第二包的 `ew`），
写完才意识到有**假阳性窗口** —— `ew` 在第二包、僵尸名册在第一包，ENet 不可靠包会乱序 / 丢包，
主机刚开最后一波的那一帧客户端可能读到"最后一波 + 僵尸 0" ⇒ **提前判完本段**，
客户端会在主机还在打的时候就自己结算离场。
⇒ 正解是让主机把**结论**发下来：一次性事件走命令，本来就不丢包也不乱序。
**教训：§4.7 那条"一次性事件 vs 连续量"的分流规则不只是归类，它同时决定有没有竞态。**

**⊙ 第二个坑**：客户端**别本地补推** `battle_finished` 事件 —— 那一下还会触发多轮关卡的切轮
（`MgmRewardManager.on_battle_finished` → `start_next_round_game`），切轮归主机，
客户端自己切会跟主机的摆场打架。只改那两个字段就够了（流程问的就是它们）。

**留给下一轮**：砸罐子仍未覆盖 —— 它问的是 `plant_cell_manager.curr_pot_num == 0`，
这一位还没同步，客户端的罐子关仍会卡在开战那一步（同样的后果）。
多轮关卡的切轮也仍归主机：客户端收到 `battle_finished` 后若还有下一轮，
会停在 `start_battle` 末尾"等轮次 +1"那一步（与改之前一样，不新增问题）。

**验证**：门禁 PASS + `probe_netplay_session` PASS failed=0 且 stderr 干净
（新增两条 `OP_BATTLE_FINISHED` 命令断言）。人工方法同上，另加一条：
客户端应**看得到**樱桃炸弹种子包掉出来（不只是存档里有）。
