
# 2026-10-03 · 关卡与地图 · 1-1 新手教程拆成逐个事件（逐步模式），并排在开战之前

> **任务类型**：关卡与地图
> **推荐度**：**推荐**（下次同类任务照这个走）
> **耗时与成本**：约 4 轮对话，未开游戏（跑了无头探针 `probe_tutorial` 全 PASS；提示框/箭头只有打开游戏才看得见，**还需人工实测**）
> **验证方式**：跑了无头探针（`-Scenario probe_tutorial`，20 项全 OK）+ 给出人工验证方法
> **补充自**：[2026-10-03_关卡流程数据改run_flow传参.md](2026-10-03_关卡流程数据改run_flow传参.md)（把「教程由彩票数据」「教程由流程场景」这条往前又推了一步）

## 目标

把 1-1 的教程从「一串 `ResourceTutorialStep`，由 TutorialManager 自驱跑」改成
「每一个分句一个事件，写在 `run_flow()` 里逐个 await」，并把整段教程**排在「允许操作」之后、「开战」之前**：

```
预览 → 选卡 → 移回视角 → 允许操作 → [箭头(种子包) → 教程(捡起) → 等待捡起 → 箭头(空)
  → 教程(种下) → 等待种下 → 教程(干得漂亮) → 等 4 秒 → 生成阳光 → 箭头(阳光)
  → 教程(收阳光) → 等待点击阳光 → 生成阳光 → 教程(继续收集) → 等待阳光足够
  → 教程(太好了) → 等 4 秒 → 教程(再种一棵) → 等待种下 → 教程(别让僵尸靠近房子)
  → 等 4 秒 → 教程(空)] → 战斗
```

## 步骤

1. **先摸清「能不能操作」的判据**（这一步决定整个方案）：
   `Card._on_button_pressed` / `HandManager._on_main_game_progress_update` 都只看
   `main_game_progress == MAIN_GAME` —— 教程要玩家动手，就必须先进入 MAIN_GAME；
   而出怪 / 天降阳光又在 `main_game_start()` 里。→ 结论：**把两者拆开**，新增一个只做「放行」的事件。
2. `MainGameManager.allow_lawn_operation()`：置 `MAIN_GAME` + `card_slot_update_main_game()`
   + 收回预览僵尸；`main_game_start()` 保留原样（开战还是它）。
3. `TutorialManager` 加**逐步模式**：`begin/end_stepped_mode()`、`show_advice_text()`、`point_to()`、
   `spawn_sun()`、`wait_take_card()` / `wait_plant()` / `wait_collect_sun()` / `wait_sun_at_least()`、`has_steps()`。
   等待条件**不重写**：临时 new 一个 `ResourceTutorialStep` 交给现成的
   `_is_step_condition_satisfied()` / `await _signal_step_finished` 判定。
4. `MainGameManager.ensure_tutorial_stepped_mode()`：幂等地取/建 TutorialManager 并进入逐步模式。
5. 9 个事件脚本 + `LevelPrefabs` 对应的一行式方法。
6. 重写 `adventure_01_01.gd`（删掉 `_build_tutorial()`，改成 `_tutorial_flow()`）。
7. 同步探针 `probe_tutorial.gd`（判据从「步骤下标」改成「提示文本」）。
8. 同步文档：[新手教程.md](../参考存档/新手教程.md)、[关卡时间轴.md](../参考存档/关卡时间轴.md)。

## 关键决策与理由

- **等待条件复用现成判定，不写第二套**：每次等待临时造一个 step 塞进 `_curr_step`，
   `_on_hand_card_take` / `_on_plant_create` / `_on_add_sun_value` / `_process` 那套逻辑一行不用动。
   新加的只有「把上一次 `point_to()` 的目标带进这个临时 step」—— 否则箭头会跳回 None。
- **不新建第 10 个 autoload、不动 `main_game_progress` 枚举**：加一个枚举值会让所有
  `match main_game_progress` 处漏判；用独立 bool + 复用 MAN_GAME 阶段，判据集中在一处。
- **`end_tutorial()` 单独一个事件，不顺手塞进 `advice("")`**：
   `advice("")` 在原版语义就是 hid()，跟「收起整个教程」不是一回事；
   提示框节点不摘会一直挂在 UI 层压着草坪，`TutorialManager` 还会继续每帧解析箭头目标，
   所以收尾必须是流程里看得见的一步。
- **没有教程数据的 TutorialManager 要能存在**：`init_tutorial_manager()` 靠
  `should_run_tutorial()` 决定是否创建，而逐步模式下该剧集(「已通关就不播」)由 `run_flow()` 自己判，
  所以 1-1 把 `should_run_tutorial()` 覆写为 true，否则已通关的存档进关时 TutorialManager 不会被创建、
  所有教程事件都空转。

## 踩坑

1. **`replace_all` 把右括号一起删了**（`P001PeaShooter)` → `P001PeaShooterSingle`），
   4 处 `await prefab.xxx(...)` 少了 `)`，GDScript 报
   `Parse Error: Expected closing ")" after call arguments`；
   补括号时又因为 old_str 结尾带了 `\n`，把下一行注释并到了同一行（`await ...)` + `## 注释`）。
   → **正解**：改完带 `replace_all` 的替换后，**重读一遍文件**再跑探针；缺符号的 parse error 报在行号上很好定位。
2. **`should_run_tutorial()` 不覆写就会静默失效**：不是报错，是上网教程一句都不播（探针才会 NG）。
   → 判据：逐步模式下「管理器不存在」= 全部事件空转，这条要留在注释里提醒后来者。
3. **无头探针是发现 parse error 最快的方式**：运行 `--editor --quit-after` 全项目扫描不会报脚本错误，
   只有真正加载脚本的场景才会炸。
4. **Windows 路径带空格**：`Start-Process -ArgumentList '--path','c:\Users\a a\...'` 会被拆成两个参数
   （报 `Invalid project path specified: "c:\Users\a"`）→ **正解**：写成 `'--path="c:\Users\a a\..."'`。

## 补充：按反馈再调的三处（同一任务的第二轮，不新建文件）

承接上文 §「目标」，人类看完第一轮结果给了三条调整：

1. **「太好了」之后不再固定等 4 秒再教「再种一棵」** —— 改成**先直接等玩家种，
   只在玩家 4 秒内没动手时才补那句教学**（原版就是这样，第一次写成了「等 4 秒 → 提示」。
   台词也同步改成 `"太好了！你已经收集到了足够\n进行下一次种植的阳光！"`。
2. **已通关 1-1 的分支要补上「准备…安放…植物」红字** —— 那条分支原本直接开战，
   于是普通重玩显得比教程首通还少一段。现在：
   `未通关 → 教程` / `已通关 → ready_set_plant()`，**两条分支共用 `allow_operation()` 与 `start_battle()`**。
3. 隐患澄清（人类给的口径，已写进关卡脚本文件头注释）：**首通 1-1 的玩家只有豌豆射手一张卡**
   （选卡阶段「卡槽数 >= 拥有植物卡数」时系统锁卡），所以教程敢写死 `P001PeaShooterSingle`，
   不用为了「玩家没带上豌豆射手」加保险。

**因此新增一个 API**：`TutorialManager.wait_plant_timeout(count, plant_type, timeout) -> bool`
+ `LevelPrefabs.wait_plant_timeout(...)`（事件侧是 `LevelTimelineEventTutorialWaitPlant.timeout` + `is_planted`）。
两个坑：

- **种植次数不能用 `_is_step_condition_satisfied()` 判** —— 那张表里只有
  `TakeCard / SunValueAtLeast / TakeShovel / DigAllPlants` 四种，`PlantCount` 走的是
  `_on_plant_create()` 里累加 `_plant_done_num`。限时等待只能轮询这个计数。
- **抽了 `_begin_condition_step()` / `_end_condition_step()`**：等待结束要把 `_curr_step`
  换回占位步骤（`_idle_step`），否则按帧判定会继续对着旧 step 反复发射「完成」。

**其余关卡没改**（1-2 / 1-5 仍走自驱 steps）：1-5 依赖 `is_opening_tutorial` +
步骤上的 `start_conveyor_belt` / `dave_dialog` 附加动作，逐步事件这套还没有对应的东西，
为它补齐不划算 —— **两条跑法并存是刻意的**（判据：`TutorialManager.has_steps()`）。

探针 `probe_tutorial.gd` 同步：STEP5 改成「故意先等 5 秒」专门走超时那条分支，
STEP8 多了「已通关分支也能正常开战」；跑出来 **24 项全 OK**，
八句提示顺序实测 = 点击种子包 → 点击草地 → 干得漂亮 → 点击收集 → 继续收集 → 足够阳光 → 再种一棵 → 别让僵尸。

## 补充 2：人类开窗实测报回来的两个 bug（同一任务第三轮）

第二轮交出去之后的人类实测反馈：**提示框高度异常**（「点击种子包」那句）+ **箭头没显示**
+ **退回主菜单时报 `previously freed ... is not a subclass of`**。
三个都复现成功了（无头探针也能测到前两个），根因如下：

1. **5008 高的黑框**：上一轮为了让带 `\n` 的长句不被裁，我改成
   `advice_panel.size.y = maxf(80, advice_panel.get_minimum_size().y)` —— 这就是祸根。
   Label 还没拿到布局宽度时 width 是 **1px**（不是 0），minimum_size 按「一个字一行」算，
   12 字 → 12 行；Godot 还会把 Control 的 size 钳到不小于 minimum_size，于是第一次显示必是 5008。
   → 改成**宽度按面板算**（`advice_panel.size.x - 28`），高度自己按字宽估行数；
   `_ready()` 里先钉宽度、`Label.resized` 时再校准一次。
2. **箭头被每帧按没**：`TutorialAdviceUI._process()` 本来是给「第一次掉金币」的一次性提示用的，
   它每帧 `_update_once_pointer()`，`_once_target` 为 null 时调 `hide_pointer()`。
   步骤教程每帧由 `TutorialManager` 喂 `update_pointer`，两者叠加 = 点亮→按没→点亮→按没。
   日志是这个节奏：`update_pointer ptr_before=false` → `hide_pointer visible=true` → 下一帧重复。
   → `_process` 只在 `_once_target` 有效时干活，目标消失后收一次箭头就 `set_process(false)`。
   （同类的还有一个：`TutorialPointer._ready()` 里的无条件 `visible = false` 比同一帧的
   `point_to()` 晚跑，也改成看 `_has_target` 了。）
3. **退回主菜单的已释放对象**：教程协程挂在「等玩家 XX」上时 `MainGameManager` 被释放，
   signal / timer 唤醒协程后继续 `prefab.xxx()`，参数就是个 freed 对象。
   → 闸门加在 `LevelPrefabs._run()`（`is_instance_valid(mg)`），顺带把 TutorialManager 里
   `main_game != null` 的写法全换成 `is_instance_valid()`（对 freed 对象 `!= null` 仍是 true）。
   探针加了 STEP9：**教程卡在等捡卡时退回主菜单**，专门盯这条。

**这一轮最值钱的一步**：先把两个 bug 变成探针断言（`箭头可见` / `提示框高度没撑爆`），
无头就能复现 —— 否则「箭头不显示」这种事只能靠人在窗口里看。
两个坑已写进 [新手教程.md](../参考存档/新手教程.md)（提示 UI 那两个框 + 注意事项第 6 条）。

探针现在 **27 项全 OK**；1-2 / 1-5 复跑无回归（那两个探针的 `LEVEL_PATH` 还指向旧的 `.tres`，
日志里那行 `set_choose_level in base 'null instance'` 是迁移遗留，与本次改动无关）。

## 补充 3：提示 UI 从小黑框改成屏幕下方的通栏提示条（同日，另一任务）

接到「删除教程小框，统一改为屏幕下方的提示」，改动集中在这 5 处：

1. `src/ui/tutorial_advice_ui.tscn`：`AdvicePanel` 从「写死的 360×80 黑框（`offset_left=353`…）」改成
   **Bottom Wide 锚点**（左右各留 24、距底 20），字号 22 → 26，边框 3 → 2、圆角 6 → 10，初始 `visible = false`。
2. `src/ui/tutorial_advice_ui.gd`：删掉 `set_advice_position()`；高度改成 `offset_top = offset_bottom - 高度`
   （**锚点布局下直接写 `size.y` 会被下一次布局覆盖**，`size.y` 那套写法只在原来那种「写死 position」的形态下有效）；
   `get_advice_box_center()` 改走 `get_global_transform_with_canvas()`（锚点模式下 `position` 不是屏幕位置）。
3. `TutorialManager._create_advice_ui()`：不再传坐标；`ResourceTutorialData.advice_box_position` 字段一并删除。
4. `MainGameManager._on_first_coin_drop()`：删 `ADVICE_BOX_POSITION` 与 `set_advice_position()` 调用
   —— 「第一次掉金币」那条一次性提示自然跟着变成底部提示条。
5. 探针 `probe_tutorial.gd`：面板高度下限 80 → 64（底部条更宽，长句在 26 号字下最多两行，实测 85）。

**踩到的坑**（已写进 [新手教程.md](../参考存档/新手教程.md) 提示 UI 那节的坑 3）：锚点布局 ≠ 绝对布局，
`size.y` / `position` 两处写法要换成 offsets 与画布变换。顺带把脚本、关卡脚本、文档里的「提示框」统一改成「提示条」。

**验证**：无头 `probe_tutorial` / `probe_tutorial_1_5` / `probe_first_coin_advice` 全 PASS，
并按规范用 `-Windowed` 开了一次窗口跑 `probe_tutorial`（27 项全 OK，提示条实测 `(1018.0, 64.0)`、
多行那句 `85.0`、箭头指向卡片正常）。

**得到的经验**：这类「只挪位置」的 UI 改动，探针里的尺寸断言（`get_advice_panel_size()`）能替眼睛查住一半问题
（宽度对不对、有没有撑爆），但**「是不是真的贴在屏幕底部」必须开窗口**，无头只能证明数值算得出来。
