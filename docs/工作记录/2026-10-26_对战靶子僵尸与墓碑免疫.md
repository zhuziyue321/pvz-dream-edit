# 2026-10-26_对战靶子僵尸与墓碑免疫（小推车 / 魅惑僵尸）

> **本次任务**：用户要求「靶子僵尸，墓碑免疫小推车等，被魅惑僵尸无视」——
> 即对战里两只**建筑型僵尸**（靶子僵尸 `pb_target_zombie`、产脑光墓碑 `zombie_card_vsgravestone`）
> 要和原版墓碑同一套待遇：
> ① 小推车 / 屋顶清洁车从身上开过去不结算；② 魅惑僵尸索敌时无视它们。
> **验证**：`check_scripts.ps1` PASS（real compile errors = 0，scenarios 170 个全编译）；
> 运行期探针**没跑**（机上有 `godot - man` 进程，按 `run_autopilot.ps1` 的 STALE_PROCESS 规矩不杀）。

## 改了什么

| 文件 | 改动 |

| `src/entities/character/components/detect_component/component_detect.gd` | `_judge_enemy_is_can_be_attack()` 的僵尸分支加一句：宿主是僵尸（= 魅惑僵尸）且目标 `is_targetable_by_hypno_zombie()` 为 false 时返回 false |

## 为什么落在这两处

**① 小推车**：`LawnMover` 有两条路径会碾人 ——
`_on_lane_zombie_enter()`（跑动中撞上，直接 `be_mowered_run`）与
`_mower_run_all_zombie_on_start()`（启动那一下扫重叠框）。两条最终都走
`Zombie000Base.be_mowered_run()`，所以**只覆盖这一个方法**就够，不用改推车脚本。
先例：`zb_base.gd` 的僵王早就这么干了（「车体从它脚下开过去不做任何结算」）。

**② 魅惑僵尸索敌**：魅惑僵尸的啃食 / 巨人砸 / 冰车碾都读
`detect_component.enemy_can_be_attacked`，而这个值统一由
`DetectComponent._judge_enemy_is_can_be_attack()` 产出 —— 一个口子管住全部攻击方式。
判定放在**阵营过滤之后**：普通僵尸（僵尸阵营打僵尸 = 非敌人）根本走不到那行，所以
`owner is Zombie000Base` 一旦成立就必然是魅惑僵尸，不用再判 camp。

**为什么不写成「全局无敌」**：靶子僵尸要能被植物打死（击破 3 只判胜）、
墓碑要能被植物打烂（放开占格），所以只挡「僵尸打僵尸」这一条通道。

## 坑

- **靶子僵尸的「触发」一侧不用管**：`LawnMover.start_trigger_filter()` 只在僵尸走到车跟前
  才启动推车，靶子站着不动且在第 10 列（草坪外右侧），永远走不到 —— 只挡「碾压结算」即可。
- **别在 `be_bomb()` 上动手**：灰烬 / 灌木爆炸是通用伤害管线，挡了会把「炸弹炸不死靶子」一起做出来。
- **本体墓碑不是角色**（`tombstone.tscn` 是场景物件），天然没这两个问题 —— 所以本次只处理
  两只**被做成僵尸**的 DLC 对战单位。下次再往对战里加「建筑型僵尸」，照这两个覆盖抄。
- **范围伤害仍会波及**：魅惑僵尸的小丑盒 / 爆炸类走 area 扫描而不是索敌，靶子挨到还是会掉血
  （原版墓碑不是角色、炸不到）。用户这次只要求「无视」，没提范围伤害，先不做。

## 人工验证

1. 开「玩家对战：白天」，僵尸方（或调试窗口）叫一只魅惑僵尸（催眠菇啃一只普僵）——
   它应该跳过第 10 列的靶子继续往左走，不会停下来啃；
2. 让僵尸方触发小推车（放一只僵尸走到最左），车体一路开过第 10 列的靶子 ——
   靶子血量不变、不倒地、不消失；
3. 植物照常能打靶子（击破 3 只判胜流程不变）；
4. 墓碑：放下产脑光墓碑，魅惑僵尸经过不啃它；推车碾过不炸；植物仍能打裂它（break1~5）。
5. 探针命令（关掉那个 Godot 进程后）：
   `powershell -ExecutionPolicy Bypass -File test/run_autopilot.ps1 -Scenario probe_player_battle_scenery_immunity -Windowed`

## 补充（同日二轮：小推车改成「一种特殊伤害」）

用户要求：**本体的小推车改为一种特殊伤害，僵尸免疫小推车用「修饰伤害」的逻辑** ——
也就是别在角色脚本里写「压不动」的空覆盖，改成免疫一类伤害。

### 改法

| 位置 | 改动 |
|---|---|
| `ConstDamage.E_DamageCause` | 新增 **`Mower`**（加在**末尾**：枚举值会随 `DamageInfo` 进日志 / 联机包，中间插一项会让存量对不上） |
| `Zombie000Base.be_mowered_run()` | 不再直接调表现工具：把碾压包成 `DamageInfo{ cause = Mower, is_instant_kill = true, is_drop_on_death = false, trigger_sfx = false }` 走 `apply_damage()`；`result.is_applied == false`（被修饰器取消）就**直接返回**，连压扁演出都不播 |
| `ZombieMowerRunUtil` | `run()` → **`play_crush()`**：不再结算血量（致死交给管线），只编排「停移动 / 停动画 / 自爆 / 压扁 / 掉肢体 / 删节点」；`lawn_mover` 允许为空（掉在原地） |
| 新增 `ComponentImmuneMower`（`DamageModifierComponent` 子类） | `modify()` 里先 `info.target != owner_character → return true`，再 `cause == Mower → return false` |
| 场景 | `zombie_target.tscn` / `zombie_vsgravestone.tscn` / `zombie_boss_base.tscn` 各挂一个 `ImmuneMowerComponent` 节点；靶子 / 墓碑脚本里的 `be_mowered_run()` 空覆盖、僵王 `zb_base.gd` 里的空覆盖**全部删掉** |
| 文档 | `docs/参考存档/伤害系统.md`：`E_DamageCause` 列表、§6「谁发起 / 什么模式 / 什么来源」表、§10 修饰器示例点名本组件 |

### 坑（这轮新增）

- **修饰器是全局注册的**：`modify()` 在**全场每一次伤害**上都会跑。第一版没判 `info.target`，
  症状会是「场上只要有一只免疫单位，别处的同款伤害一起被取消」—— 现在组件第一句就认领自己的包。
- **未入树的僵尸调 `be_mowered_run()` 会真的被压死**：修饰器是在组件 `_ready()`（`component_ready()`）
  里注册的，探针里 `instantiate()` 完不入树就调，等于没有免疫。探针对墓碑只查「组件挂上了没」。
- **`is_can_death_language` 要存原值**：入口先置 false（死亡信号在管线里同步发出、压扁的僵尸不该触发亡语），
  被免疫取消时必须**还原成原值**而不是硬写 true，否则会把「本来就不触发亡语」的僵尸误开。
- **灭活路径要跟着走**：`hp_loss_to_death()` 本来就是走管线的（cause = Death），所以这轮只多了
  「cause 能区分是不是车」这一层，不会出现「一半走管线一半不走」的分叉。
