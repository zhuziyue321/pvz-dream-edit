> **推荐度**：**推荐**（下次「某个一关专属道具要进手持物体系」照这个走）
> **耗时与成本**：约 2 轮对话，带窗口跑 4 个探针（`probe_hammer_zombie` / `probe_hand` / `probe_init` / `probe_tutorial_1_5` 全 PASS）
> **验证方式**：打开游戏实测（带窗口，`[HAMMER] result=PASS failed=0`，44 断言）
> **补充自**：[2026-10-05\_回迁旧版四项优化.md](2026-10-05_回迁旧版四项优化.md#补充--评价2026-10-05--锤子改成手持物hud-入口随之撤掉)（那次回迁的「HUD 锤子入口」本次撤掉）、[2026-10-04\_锤僵尸玩法搬出本体.md](2026-10-04_锤僵尸玩法搬出本体.md#补充--评价2026-10-05--锤子从规则生成的光标改成手持物)（那次把锤子搬出本体，本次把它接进手持物体系）

## 目标

打僵尸（迷你游戏 15「打僵尸」/ 冒险 2-5「打地鼠」）里的锤子**由关卡脚本驱动**，
并且**取代原先的空手** —— 那两关玩家的「空手」就是锤子：进 MAIN_GAME 自动在手上、
种完植物 / 放下铲子后回到锤子、非游玩阶段收起。锤子不再是一个独立于手持物体系的自定义光标。

用户当场定下两个取舍（动手前问的，别自己猜）：

1. **撤掉 HUD 锤子入口**（10-05 才回迁的 `UIHammer` 按钮 + H 键）——锤子全程在手上，不需要切换。
2. **挥锤保持现状**：仍走 `hammer.gd` 的 `_unhandled_input`（点屏幕任意非 UI 处都挥），
   不改成格子的 `click_cell` 派发（僵尸走到草坪外也点得到）。

## 步骤

1. `HandComponentBase.E_HandComponentType` **末尾**加 `Hammer`（改中间会动到已有 int 值）。
2. 新增 `src/managers/hand_manager/component/hand_component_hammer.gd`：默认禁用，
   `enter/exit_hand()` 只负责 `RealHammer.set_is_used(true/false)`；`click_cell()` 恒返回 false。
3. `HandManager` 加一个通用口子 `set_idle_hand_type(类型)`：**空闲手持物**取代空手 ——
   `drop_hand()` 回到它，进可操作草坪的阶段也补上它；空闲手持物不算「手持中」（`is_holding_hand()` 为 false，
   右键取消对它无效）。`is_holding_hand()` / `_drop_to_null()` / `_on_main_game_progress_update()` 随之改。
4. `hammer.gd` 去掉自驱动：删 `main_game_progress_update` / `main_game_click_hammer` 订阅、
   删 `Input.set_mouse_mode` 与两条 HUD 事件推送；`set_is_used()` 改由组件调；冷却改成「收起美术、走完自动回来」。
5. `LevelRuleHammerZombie.install()`：`_install_hud()` 删掉，新增 `_install_hand()`
   （启用组件 + `set_idle_hand_type(Hammer)`），`_install_cursor()` 只剩打开自定义光标开关。
6. `main_game_base.tscn`：加 `HM_Hammer`（HandManager 下）与 `RealHammer`（CanvasLayerTemp 下，实例 `hammer.tscn`）；
   删 `UIHammer` 子树 + 2 条 ext_resource + 1 条 connection；`load_steps` 不动（ext 一进一出 = 83）。
   删 `src/ui/card/hammer_in_ui.gd`（连 `.uid`）、`project.godot` 的 `ShortcutKeys_Hammer`、
   `SceneRegistry.HAMMER`（改由场景常驻后没人用）。
7. `MainGameManager`：`main_game_progress` 的 setter 里按阶段切系统鼠标（自定义光标模式下
   可操作草坪=隐藏、其余=可见）—— 补上原来靠 hammer.gd 做的那一步。
8. 探针：`probe_hammer_zombie` 改成验「锤子美术常驻 + 空闲手持物 = 锤子 + 放下回到锤子 + 失败回空手」；
   `probe_hand` 的「组件节点数」4 → 5。

## 关键决策与理由

- **本体只加一个「空闲手持物」口子，不加 `if 锤子关` 分支**：一关 / 两关专属的东西留在关卡侧规则里，
  本体只认一个 `E_HandComponentType`（硬约束 §1-8）。这也是延续
  [三消那次](2026-10-04_僵尸迷阵三消整包搬出本体.md)「本体给的必须是回调口子 / 开关」的思路。
- **锤子 = 空闲手持物，而不是「默认拿着的道具」**：`is_holding_hand()` 对它返回 false，
  语义上它就是那两关的空手 —— 教程的「已拿卡」判定、右键取消这类通用逻辑都不用为它加特例。
- **启用走 `register_level_init_callback()`**：手持物组件要等 `HandManager.init_manager()` 注册完才存在，
  而 `init_level_items()` 跑在它之前（与出怪器正好相反，出怪器必须赶在 `ZombieManager` 初始化**之前**）。
  同一个关卡脚本里两种时机并存，取决于「要赶在子管理器初始化之前还是之后」。
- **挥锤不改派发方式**：锤子是光标类道具（跟着鼠标，不是针对格子），改走 `click_cell` 会让
  草坪外的僵尸点不到，行为回归也没有收益。
- **冷却能力保留、HUD 撤掉**：`cool_time` 仍是导出参数（挥中后收起美术、走完自动回来），
  只是不再往 HUD 推事件（没有订阅者了）。

## 踩坑

1. **无头跑出 `HandManager: 缺少空手组件，无法放下手持物`（3 次）** —— 阶段事件
   （`main_game_progress = CHOOSE_CARD`）比 `init_manager()` 先到，新写的 `_drop_to_null()` 在组件还没注册时
   就打错误日志；原来的 `drop_hand()` 靠 `is_holding_hand()` 挡住了这种情况。
   → **正解**：`_drop_to_null()` 开头先 `if curr_hand_component == null: return`（手上本来就没东西，静默返回）。
2. **`probe_hand` 断言「组件节点数 = 4」变 NG（count=5）** —— 新增手持物会让这条硬编码失败。
   → **正解**：改探针期望值 4 → 5。**每加一个手持物都要同步这条**。
3. **`change_hand_component_enable(Hammer, true)` 在 `init_level_items()` 里静默失效**（组件还没注册，
   `get_hand_component()` 返回 null，函数直接 return）。→ **正解**：改走 `register_level_init_callback()`。
4. **锤子不管鼠标之后系统鼠标再也没人藏** —— 原来靠 `hammer.gd::set_is_used()` 的 `set_mouse_mode`，
   本体的自定义光标开关只在「悬停控件进出」时切，缺了「进阶段就藏」那一步。
   → **正解**：`main_game_progress` 的 setter 里统一按阶段切（离开关卡还能把鼠标交还给玩家）。
5. **主场景里有一条指向已删节点 `Manager/ZombieManager/HammerZombieManager` 的 connection 残留**
   （10-04 删节点时没一起删连接，每次加载都会报一次）。→ **正解**：顺手删掉；删节点要连 connection 一起清。

## 给后来者的最简路径

1. 先问清两件事：**HUD 入口要不要留**、**触发方式要不要改派发**（本次两个答案决定了三分之一的改动量）。
2. 手持物四步（枚举末尾加 → 写组件 → 场景挂组件节点 + 美术 → 规则启用），
   完整正例见 [手持物实现.md](../参考存档/手持物实现.md) §六。
3. 「取代空手」= 规则里调一次 `set_idle_hand_type(类型)`，本体不用再动。
4. 一关专属道具的**启用时机**先确认排在哪个子管理器初始化的前面 / 后面，再决定用
   `init_level_items()` 还是 `register_level_init_callback()`。
5. 收尾必跑 `probe_hand`（手持物链路）+ 玩法自己的探针；新增手持物记得改 `probe_hand` 的组件数断言。
