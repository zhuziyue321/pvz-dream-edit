## 目标

花园三个背景页（温室 / 蘑菇园 / 水族馆）的背景贴图从 **1066×600** 换成 **800×600**，
且 `bg_00/bg_01/bg_02` 里手摆的 **48 个植物格子**要与新背景上画出来的种植位**对齐**（不能错位）。

## 步骤

1. 现状（`assets/image/garden/`）：`Background_Greenhouse_New.png` / `Background_MushroomGarden_New.png` /
   `aquarium1_new.png` 都是 **1066×600**，被 `src/garden/bg_0*.tscn` 的根 `Sprite2D` 直接引用；
   同目录另有原版 `Background_Greenhouse.jpg` / `Background_MushroomGarden.jpg` / `aquarium1.jpg`（**800×600**，无人引用）。
   视口已是 800×600 → 1066 宽的图右侧 266px 被裁掉，温室第 8/16/24/32 号格子（x=787/800/824/830）根本点不到。
2. ~~用「平均灰度差（MAD）」比较两套图，判定 1066 是 800 的横向拉伸；把格子 x 乘 `800/1066`~~
   → **放弃原因**：结论是错的，改完**植物整体错位**（见「踩坑 1」）。
3. 改用**高通滤波 + ZNCC** 做图像配准，在「1:1 不缩放」的前提下扫描横向裁剪偏移 `dx`：
   温室 `dx=133`（ZNCC 0.987）、蘑菇园 `dx=133`（ZNCC 0.996）、水族馆 `dx=130`（ZNCC 0.69，峰值较平缓）。
4. 结论：**`*_New.png` = 原版 800×600 图 1:1 居中放置 + 左右各补 133px 背景**（`1066 - 800 = 266`，居中即 133）。
5. 坐标改法：`x_800 = x_1066 - dx`（**平移，不是缩放**），`y` 不变（两套图高度都是 600）。
6. 生成「坐标叠加预览图」（在 800×600 目标图上画出 48 个格子 rect）目视确认
   —— 温室 32 个框全部精确落在 32 个木质种植台上 → 写回 `.tscn`（贴图 ext_resource 的 path/uid 一并换成 jpg 的）。

## 关键决策与理由

- **用仓库里现成的原版 800×600 jpg，而不是把 `*_New.png` 压缩到 800** —— 用户要的就是 800×600 的贴图，
  且原版 jpg 就在同目录，压缩 `_New` 会把画面横向压扁 25%。
- **格子保持 75×75 不变** —— `plant_cell_garden.tscn` 的 `RectangleShape2D` 是 `Vector2(75, 75)`，
  若跟着缩放 x，点击区会变成 56×75 的扁矩形。
- **三张图分别取各自实测的 `dx`（133/133/130），不强行统一** —— 水族馆实测偏 3px，视觉影响可忽略，但按实测值更忠实。

## 踩坑

1. **用平均灰度差判断「两张图是不是同一张的缩放版」会得出错误结论**：
   把 1066 压到 800 与 jpg 的 MAD = **37.94**，左对齐不缩放 MAD = **134.80** → 看起来「拉伸假设」完胜，
   于是按 `x * 800/1066` 缩放坐标 → **植物全部错位**。
   → **正解**：跨来源的两套素材整体亮度/色调差异很大，MAD 会被这种低频差异带偏。
   改用 **高通滤波（luma 减去盒式模糊，半径 4~6）+ ZNCC**，只比结构；可信的匹配是
   **峰值 > 0.9 且两侧快速衰减**（本例 dx 从 0.48 一路升到 0.959 再回落，峰形尖锐）。
2. **同时搜「缩放 α + 平移 β」两个参数会得到撞边界的无意义解**：
   α ∈ [0.68, 0.82] × β ∈ [-50, 50] 自由搜索时，ZNCC 只有 0.52 / 0.21 / 0.57，最佳 α 撞在搜索边界上。
   → **正解**：先用整数线索把「缩放」定死（`1066 - 800 = 266` 正好可整除居中，
   且高度同为 600），把它退化成**单参数（dx）**问题再扫，峰值立刻从 0.5 升到 0.99。
3. **原 tscn 里的格子 x（169..905）本就不是「1066 图专用坐标」**：它们 = **原版 800×600 的坐标 + dx**（温室 / 蘑菇园 +133、水族馆 +130），
   所以减去 133 后全部落在 `0..772` 内，正好进屏 —— 这是「平移」假设的独立佐证
   （若真是拉伸关系，缩放后不会这么整齐地全部落回屏内）。
4. **用 PowerShell 改 `.tscn` 会把行尾写成 CRLF**：`[System.IO.File]::WriteAllLines` 用 `Environment.NewLine`，
   而仓库 `.tscn` 是 LF → 整个文件在 git 里显示为全量改动。
   → **正解**：写完用 `ReadAllText` / `Replace` / `WriteAllText` + `UTF8Encoding($false)` 落回 LF、无 BOM。

## 给后来者的最简路径

1. 遇到「同一场景两套不同分辨率的素材」，**先按 1:1 平移假设**用
   [tools/image_crop_offset.ps1](../../tools/image_crop_offset.ps1) 扫裁剪偏移：

   ```powershell
   powershell -ExecutionPolicy Bypass -File tools\image_crop_offset.ps1 `
       -Source assets\image\garden\Background_Greenhouse_New.png `
       -Target assets\image\garden\Background_Greenhouse.jpg
   ```

2. 峰值 **ZNCC > 0.9 且尖锐** → 用 `x_new = x_old - dx` 改坐标；
   峰值平缓（< 0.8）→ 两套素材内容本来就不同，**别硬套公式**，直接在两套图上目视。
3. 改完**务必**生成「坐标叠加预览图」（在目标贴图上按新坐标画格子 rect）目视确认，再写回 `.tscn`。
   这一步比开游戏更快、更准，且能直接看出偏移方向。
4. 顺手检查：贴图 `ext_resource` 的 **uid 要和目标文件 `.import` 里的一致**，漏改会让 Godot 报资源丢失。

## 补充（同日）：花园顶部 UI 在 800 宽下重排

用户反馈「顶部的 UI 也偏了」。顶部这一排在 1066 时代是**右对齐铺满**的
（工具条 `184..778` → 翻页 `798..858` → 页码 `868..959` → 主菜单 `976..1066`），
内容总宽 `882 > 800` 放不下；而 `Next` 的页码 `Label` 是**挂在按钮右侧**的（相对 offset `70..161`），
把 `Next` 当普通右锚按钮去贴右边，页码会整体落到 `808..899` —— **完全出屏**。

改法（`src/garden/garden.tscn`）：

| 元素 | 原（1066 时代） | 现（800） | 说明 |
| --- | --- | --- | --- |
| `PanelUI` 工具条（8 槽） | `184..778` | **`25..619`** | 右边缘让出翻页组的位置 |
| `Next` 翻页按钮 | `798..858` | **`639..699`** | 右锚 `-62/-2` → `-161/-101`（给右侧 91 宽的页码让位） |
| 页码 `Label` / `Label2` | `868..959` | `709..800` | 跟随 `Next`，改父节点偏移即可，自身不动 |
| `StoreEnterKey` 商店 | `982..1061`, y `59..101` | `716..795`, y **`80..122`** | 下移 21px 避开页码 |
| `ReturnStartMenu` 主菜单 | `976..1066`, y `0..40` | **`0..90`, y `560..600`** | 右上角被翻页组占满，移到左下角（preset `1` → `2`） |

**验证**：把上述 6 个元素的矩形画在花园背景图上生成预览图目视 → 两两不重叠、全部在 `0..800` 内。

**踩坑（本轮自己犯的）**：`Next` 不是单纯的图标按钮，它是「箭头按钮 + 右侧两行页码」的**组合**
（页码 `Label` 是它的子节点，相对 offset `70..161`）。
改分辨率时按「右锚贴边」的思路把按钮设成 `-62/-2`，页码就跟着出屏了。
→ **正解**：这类「按钮 + 附属文字」的组合，右锚偏移要按**组合总宽**算（`60 + 10 + 91 = 161`），
改完**必须**把组合里所有子节点的屏幕矩形都画出来看一眼，不能只看按钮本身。

**同样的教训**：`PanelUI` 也是「容器 + 8 个 75×75 子按钮」的组合，容器宽 594 是子按钮撑出来的 ——
改容器 offset 时要按 594 算，不能只改一个数。
