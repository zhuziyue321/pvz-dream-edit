## 1. 目标

`mods_builtin/pvz2/` 里已经导入了两株豌豆的动画（`firepeashooter/` / `peapod/`，各 4 个 `.pam.bin`
+ 图集 + `*_anim.tscn`），探针 `probe_pvz2_pea_anim` 只证明「数据能播」，场上**种不出来**。
本轮把它们做成和潜伏芹菜一样能上场的一株：

- **火焰豌豆射手**：本行直线射手，吐火豌豆（`BulletIds.PEA_FIRE`，一发 40）。
- **豌豆荚**：同格最多叠 5 层，攻击时按层数连发（1~5 颗），每颗 20。

## 2. 做了什么

1. `firepeashooter/firepeashooter_plant.gd` + `plant_firepeashooter.tscn`：
   PAM 待机 `idle`/`idle2` 接龙、`attack` 第 8 帧发一颗火豌豆、`AttackCdTimer` 1.4 秒。
2. `peapod/peapod_plant.gd` + `plant_peapod.tscn`：
   1~5 层待机 `idle`~`idle5` / 攻击 `attack`~`attack 5`，第 8/11/14/17/20 帧各发一颗；
   层数进存档。
3. **本体加了一个通用叠层口子**（本体不认识豌豆荚）：
   `Plant000Base.max_stack_layers` / `can_stack_up()` / `try_stack_up()` +
   `ResourcePlantCondition.judge_is_can_plant()` 放行同种可叠 +
   `PlantCell.create_plant()` 改调 `try_stack_up()`（不新建第二株）。
4. 两株各自的配方（子类，只覆盖 `build_card_face()`）+ 卡面定格场景（复用 `pam/pam_static_frame.gd`）。
5. `pvz2_mod.gd`：四株一个数组（四张配方 / 四条图鉴 / 装 / 卸一起走），详情页与描述同步。
6. `test/scenarios/probe_pvz2_pea_plants.gd`（新探针，无头 PASS failed=0）。
7. 文档：`模组机制.md` §6.7 / §6.7.3、`运行期植物.md` §5.1、`mods_builtin/README.md` 那一行。

## 3. 关键决策与理由

### 3.1 为什么两只都自己挂 Timer，不用本体的 `AttackComponentBulletBase`

那条路的攻击节奏靠 `AnimationTree.set("parameters/OneShot/request")` 驱动，而 PAM 播放器没有
`AnimationTree`；组件里的 `@onready var animation_tree: AnimationTree = $"../AnimationTree"` 在
PAM 植物场景里会在加载时报 `Node not found`。所以照菜问的做法：`DetectComponent` + `AttackCdTimer`
自己管节奏，发射直接走 `BulletRegistry`，参数口径照抄 `get_bullet_paras()`。

### 3.2 发射帧是量出来的，不是按时间猜

用 `tmp/analyze_pea_bin.py`（解析 `.pam.bin`、递归累乘变换算每帧包围盒）量的：

- 火焰豌豆 `attack` 31 帧：第 8 帧嘴前火苗最亮 → 这一帧发射。
- 豌豆荚 `attack*` 30~31 帧：第 8 / 11 / 14 / 17 / 20 帧各一颗，5 层刚好在段内发完。
- 豌豆荚 1~5 层的状态对应关系也靠部件数确认：`idle`~`idle5` 部件数 25/29/33/37/41（每层 +4），
  `attack`~`attack 5` 27/33/39/45/51（每层 +6）。
  ⚠️ `idle6`（+10 个部件）与 `idle7`（包围盒撑到 4009×3431）**不是第 6/7 层**，别拿来用。

### 3.3 豌豆荚的叠层走本体通用口子

叠层不是「在本体里写死豌豆荚」，而是三处各加一条通用判定（见 §2.3）：
`judge_is_can_plant()` 决定虚影放不放行、`create_plant()` 决定新建还是叠层、
`Plant000Base` 决定一株最多几层。本体只知道「这株植物说自己还能叠」，不知道它是豌豆荚。

## 4. 踩坑

1. **叠层要同时改三处，只改 `create_plant` 会「虚影不亮」**：手持虚影走的是
   `ResourcePlantCondition.judge_is_can_plant()`，不改它，第 2 层根本点不下去（表现为卡在手上）。
2. **叠层植物的 `create_plant()` 不要发 `signal_plant_create` 两次**：叠层路径发一次即可，
   否则监听方（玉米炮后轮那类）会收到两条。
3. **`not x in arr` 的优先级**：写成 `if not String(state) in ATTACK_ANIMS:` 会被解析成
   `(not String(state)) in ...`（编译能过、逻辑错），要写 `if not (x in arr):`。
4. **PAM 播放器的 `state_frame_changed` 在卡顿时会跳帧**：豌豆荚按「到这一帧为止该发几颗」
   的循环补发（`while _shots_fired < target`），不要写成「帧号相等才发」。
5. **探针退出前 `PAMAnimator.clear_cache()`**：不清会让静态字典把贴图留到进程结束
   （引擎打 `resources still in use`）。不过旧的 `probe_pvz2_mod` 同样有 3 resources 告警，
   属既有现象，不是本轮引入。

## 5. 给后来者的最简路径

1. 先过一遍 `probe_pvz2_pea_anim` 确认 bin / 图集 / 状态都在。
2. 用 `tmp/analyze_pea_bin.py <bin> <state>` 量出：脚在哪（pivot）、嘴在哪里（Marker）、
   哪一帧最伸展（发射帧）、各层部件数（层数与状态对应）。
3. 场景照 `plant_firepeashooter.tscn` 抄：`AnimComponent` 换 `component_anim_empty.gd`、
   `Body` 下挂 PAM 播放器 + `Marker2D`、`DetectComponent` 用本体豌豆射手那条一整行（1000×5）。
4. 脚本照 `firepeashooter_plant.gd`：`ready_norm()` / `ready_norm_signal_connect()` / `ready_show()`，
   **不要重写 `_ready()`**（硬约束 1-3）。
5. 卡面：照 `*_recipe.gd` 覆盖 `build_card_face()` + 一个 `*_card_face.tscn` 定格节点。
6. 注册：`pvz2_mod.gd` 的四株数组 + 图鉴条目。
7. `check_scripts.ps1` 过了再跑探针（本机编辑器进程会挡 `run_autopilot.ps1`，
   改用独立 `$env:APPDATA=<tmp>` + `godot --headless --path ... -- --scenario=res://...`）。

## 6. 人工验证方法（画面类，机器只能证明「数据对」）

1. 开游戏 → 模组页面打开「PVZ2」→ 进任意关卡。
2. 选卡界面最后应多出**火焰豌豆射手**与**豌豆荚**两张卡，卡面分别是站着的火豌豆 / 单层豌豆荚
   （不该空白，也不该借用别的植物的脸）。
3. 火焰豌豆：种在草地上，僵尸进入本行后它播喷火动作、嘴前飞出火豌豆，命中掉血；
   **关注比例**（约 132×89 px）与**站位**（脚落在格子里）。
4. 豌豆荚：种一株 → 同一格子再点一次卡 → 应该**变高一层而不是多出一株**，最多 5 层；
   僵尸来了按层数连发（5 层一次 5 颗）。**关注**：叠层时卡片照常扣阳光 / 走冷却、
   铲子铲一次整株移除、读档后层数还在。
5. 两株都看一眼层次：不该压住血条 / 卡片冷却遮罩。
