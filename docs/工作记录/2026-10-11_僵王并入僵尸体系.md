# 2026-10-11 · 其它 · 把僵王博士改成一个正规僵尸（`ZB000Base extends Zombie000Base`）并完整并入僵尸体系

> **任务类型**：其它
> **推荐度**：**推荐**（下次做「把 A 角色并入 B 体系」照这个走）
> **耗时与成本**：约 6 轮对话，**未开游戏**（用户的 Godot 编辑器正开着项目，多实例会争抢 `.godot/`，实测结果不可信 —— 详见踩坑 11）
> **验证方式**：免验证 + 已给出人工验证清单（编译门禁 `check_scripts.ps1` PASS，`real compile errors = 0`）
> **补充自**：无。但**同一批坑的相关记载**见 [2026-10-06_修复僵王伤害异常.md](2026-10-06_修复僵王伤害异常.md)（那条已提出「`lane` 恒为 -1 导致整只漏掉」，本次是从另一侧——并入 `all_zombies_2d`——再次撞上同一个根因）

## 目标

僵王博士原本是 `extends Character000Base`，绕开了整条 `Zombie000Base` 继承链。改成 **`extends Zombie000Base`** 并满足用户指定的三件事：

1. 受击窗口改用僵尸标准口径 `curr_be_attack_status`（低头 `IsNorm` / 抬头不可打），替换原来直接改 `hurt_box_component.is_enabling` 的做法；
2. **完整并入僵尸体系**：登记 `ZombieType`、进 `all_zombies_2d`、参与敌方计数；
3. **免疫小推车**（明确要求）。

可判定：编译门禁 PASS + 5-10 关卡里低头能掉血 / 抬头免疫 / 小推车穿身而过。

## 步骤

1. **先做可行性分析（这一轮不能省）** —— 用 code-explorer 把 `Zombie000Base` 的结构、强制组件、`ZB000Base` 对父类成员的依赖全部列出。**结论是不能只改一行 `extends`**，有 4 类卡点（编译错误 / 组件缺失 / 静默改坏 / 判定反转）。
2. **给用户选深度** —— 用 `ask_followup_question` 确认「并入到哪一层」和「受击窗口怎么承接」。这一步决定了后面全部工作量，不要自己猜。
3. 改继承链 + 删两处 **GDScript 成员遮蔽**（`zb_base.gd` 的 `signal_status_update`、`zb_doctor.gd` 的 `hp_stage_change_component`）。
4. **场景改 instance 源**：`zombie_boss_base.tscn` 从实例 `character_base.tscn` 改成实例 **`zombie_base.tscn`** —— 一句话补齐 5 个强制组件，比手写节点省事且配置现成。
5. `ZB000Base.ready_norm()` 里 `super()` 之后：撤销坡面位移、永久禁用 5 个组件、隐藏继承来的血条。
6. `can_attack()` 把 `ZB000Base` 分支**提到 `Zombie000Base` 之前**并只比 `IsNorm` 一位。
7. 登记 `ZombieType.Z999ZombossDoctor`（**只登 `ZOMBIE_INFO`，不登出怪权重**）。
8. `ZmBossRegistry` 补 lane 合法化 + `all_zombies_2d` / `all_zombies_1d` 增删同步。
9. `ZombieManager` 三处去重。
10. 每批改完跑一次 `test/check_scripts.ps1`（**逐批跑**，一次性改完再跑会分不清是哪批引入的错误）。

## 关键决策与理由

- **【最省的一步】场景改 instance `zombie_base.tscn`，而不是手补组件节点** —— `Zombie000Base` 有 6 个 `@onready %XXX` 强取，`AttackComponent` 还依赖 `DetectComponent/Area2d/CollisionShape2D` 三层子节点。手写极易漏，改一行 instance 源全都有。**代价**是会连带继承普通僵尸的血条 UI 和 `CriticalValueComponent`，需在代码里显式关掉（见踩坑 7、8）。
- **受击口径不用「新增第 64 位拼掩码」，改成「对 `ZB000Base` 短路、只比 `IsNorm` 一位」** —— 因为撞上了既有 bug：仙人掌那句 `can_attack_zombie_status = ~8` 是**全掩码**，`64 & -9 = 64` 照样命中。只比一位天然绕开，不用改那行既有代码（符合「顺手改别人代码要谨慎」）。第 64 位仍然加了，用于未来有人绕过 `can_attack()` 直接比掩码时的兜底。
- **禁用组件用 `E_IsEnableFactor.Default` 而不是 `InitType` / `Character`** —— `Default` 的语义就是「该角色不使用此组件」；`InitType` 是「正常/展示/花园」、`Character` 留给状态机的临时开关，用它们会和现有关开关打架（相消后八字不合导致僵王提前失去行动能力或反过来提前挨打）。
- **编号用 `Z999` 而不是 `Z026`** —— `Agent协作协议.md` 写「Z001–Z024 已用；Z999 boss 特殊占用」，但配额文档已过时（实际 Z026、Z031–Z044 已被占用）。`Z999` 是 boss 段、语义明确且不冲突。
- **只登 `ZOMBIE_INFO`，刻意不登 `ZOMBIE_SPAWN_POWER` / `ZOMBIE_SPAWN_WEIGHTS`** —— 保证永远不会被自然刷怪抽到，出场仍只由关卡 `boss_type` 驱动。这是「登记进 `ZombieType`」和「让谁都能刷它」的区别。
- **敌方计数不加，保持 `ZmBossRegistry` 独占** —— 查过之后发现 `register_boss()` 早就在做 `curr_zombie_num += 1`。如果顺手在 `_on_zombie_dead` 里再减一次会变成负数（见踩坑 6）。

## 踩坑

1. **`.tscn` 的注释是 `;` 不是 `##`** —— 第一版场景文件写了 GDScript 注释，报 `Parse Error: [zombie_boss_base.tscn:9]`。**正解**：`.tscn` 用 `;`。**容易看错方向的是**：它同时级联出 `Could not resolve external class member "ZombieInfo"`，看起来像注册表坏了，实际根因在最前面那条场景解析失败。
2. **循环依赖（最绕的一个）** —— 在 `zombie_info_data.gd` 里 preload doctor 场景后，形成环：`character_registry.gd` → `zombie_info_data.gd` → `zombie_boss_doctor.tscn` → 场景内脚本编译期引用 `CharacterRegistry.ZombieInfo` → 回到 `character_registry.gd`。现象是 `Could not resolve external class member "ZombieInfo"` + `Failed to load script zb_doctor_state_spawn.gd`。**正解**：把 doctor 子树里对 `CharacterRegistry` **常量成员**的访问改成 `Global.character_registry.X`（autoload 实例成员，运行期解析）即可断环。只改 `zb_doctor_skill_spawn.gd` 一个文件的 6 处就够了 —— **不要试图把 doctor 子树里所有 `CharacterRegistry` 都改掉**（连枚举引用都改是徒劳且无必要的）。
3. **判定反转（本次最危险的坑，靠分析阶段预判发现）** —— `ZB000Base` 一旦变成 `Zombie000Base` 的子类，`component_can_attack_status.gd` 里 `elif enemy is Zombie000Base:` 会**先命中**，僵王那个分支变成死代码；而僵王的 `curr_be_attack_status` 恒为 `IsNorm=1`，`(1 & 1) != 0` 恒真 → **低头受击窗口彻底失效，僵王全程可被任意植物打**。**正解**：把 `ZB000Base` 分支提到最前面。
4. **仙人掌 `can_attack_zombie_status = ~8` 是全掩码** —— 见上面关键决策。`64 & -9 = 64 ≠ 0`，所以「加个高位的免疫位」这个思路本身不够。
5. **`all_zombies_2d` 按 lane 下标索引，僵王 lane = -1** —— GDScript 允许负下标（会取到最后一行），**不报错**但语义完全错。**正解**：生成时由 `ZmBossRegistry` 固定给 lane = 0。这也解释了 2026-10-06 那条记录里「子弹同行判定把它整只漏掉」的根因 —— 同一个 lane=-1，两个 symptom。
6. **差点重复计数** —— 本以为「参与敌方计数」要新加，回读 `zm_boss_registry.gd` 才发现 `register_boss()` 里早有 `manager.curr_zombie_num += 1`、`_on_boss_dead` 里 `-= 1`。**正解**：并入列表时**不要**再连 `_on_zombie_dead`，列表增删单独抽一个 `_sync_boss_to_zombie_lists()`。教训：**动手前回读一遍，别假设当前缺失**。
7. **`CriticalValueComponent` 会自己掉血** —— 从 `zombie_base.tscn` 继承来的，默认 `is_drain_hp = true`，低于 `death_hp` 后每秒自动掉 1 血。博士的破损只换贴图，绝不该有残血流失。**正解**：显式禁用。这是「改 instance 源」这条路最需要注意的连带副作用。
8. **`zombie_base.tscn` 的 `max_hp` 是 270** —— 关卡不配 `boss_hp` 时僵王会只有 270 血（原先僵王场景自带的是 40000，改成实例 `zombie_base.tscn` 后被它的默认值顶掉了）。**正解**：在 `zombie_boss_base.tscn` 里用 `[node name="HpComponent" parent="."]` 覆盖回 40000。
9. **进了 `all_zombies_2d` 之后三处会重复结算** —— ① `ice_all_zombie()` 原来额外遍历 `get_living_bosses()`，现在全场遍历已覆盖 → 不删会**冻两次**；② `jalapeno_bomb_lane_zombie()` 行循环会打到僵王 → `be_bomb` 是普通僵尸的灰烬+立即删除，会把正在播死亡演出的博士直接抹掉；③ `death_all_zombie()` → 一键清场会把博士连同奖杯结算一起抹掉。**正解**：①删专属循环，②③行循环里 `if zombie is ZB000Base: continue`，辣椒交给专用 `be_jalapeno` 接管。
10. **`Zombie000Base.ready_norm()` 会按地图坡度修正 y** —— 屋顶关会把 x=-80 的僵王拽走。**正解**：量出 `super()` 前后的 y 差值，用 `move_y_zombie(-delta)` 精确撤销（`move_y_zombie` 会同步处理 `node2d_detect_in_slope` 里的检测节点，反向调用即可连同它们一起复原）。
11. **跑不了 autopilot，差点误判成改造失败** —— PowerShell 报 `The process cannot access the file because it is being used by another process`，读取到的 STDOUT 是**上一次**（`probe_custom_level_mod`）的残留输出，`exitCode=1`。查进程发现用户的 Godot 编辑器 PID 29744（窗口标题 `PVZ-Dream-Edit`）正开着项目，另有 2 个无窗口残留进程。**正解**：用 `Get-Process -Name 'Godot*' | Select-Object Id,MainWindowTitle,MainWindowHandle` 区分编辑器 vs 僵死进程，**不要**杀带 `MainWindowHandle != 0` 的那个；这种情况下改用编译门禁 + 人工清单。
12. **Windows 下 `timeout` 是 `TIMEOUT.EXE`** —— `timeout 300 powershell ...` 报 `Invalid syntax. Default option is not allowed more than '1' time(s)`。**正解**：别用 `timeout` 前缀，直接跑。

## 给后来者的最简路径

把某个「绕开继承链的正式角色」并入它本该在的体系时，按这个顺序做，每批跑一次 `test/check_scripts.ps1`：

1. **先做可行性分析**，把目标基类的「强依赖列表」全部列出（`@onready %XXX` / 必须实现的方法 / 生命周期入口）。结论往往不是改一行，而是有一整套连带项。
2. **场景改 instance 源**（补组件最快的一步），然后在代码里逐个关掉连带副作用 —— 尤其注意**会自动做事的组件**（本例的 `CriticalValueComponent`）和**被覆盖的数值**（本例 `max_hp`）。
3. **全局搜索「对本类的 `is` 判定」**，改成继承后会命中**父类分支**，凡是 `elif` 顺序受影响的地方都要重排。这是最危险、也最容易被漏掉的一类。
4. **处理重名成员**（GDScript 禁止遮蔽）→ **跑门禁**。
5. 并入「第二张表」时（本例 `all_zombies_2d`）：先确认**计数归谁管**（别重复加减），再审全场遍历的所有站点有无重复结算。
6. 最后再登记类型 / 编号。**只登信息表、不登权重表**，除非真的想让它被自然刷出来。
