# 2026-10-05 · 排查调试 · 修复锤僵尸墓碑出怪：出怪器 Timer 没连信号，整局只出一组僵尸

> **任务类型**：排查调试
> **推荐度**：**推荐**
> **耗时与成本**：约 1 轮；**开了游戏**（带窗口探针），中间被别的 agent 改仓库打断过 2 次
> **验证方式**：打开游戏实测（`probe_hammer_spawn_trace` / `probe_tombstone_respawn` / `probe_hammer_zombie` 三条全 PASS）
> **补充自**：无（关联旧记录 [2026-10-04\_锤僵尸玩法搬出本体.md](2026-10-04_锤僵尸玩法搬出本体.md)）

## 目标

用户反馈「锤僵尸的墓碑出怪不对」。要把它查到**具体成因**并修掉，而不是凭代码印象猜。
判定标准是实机上能看到出怪按波次持续推进。

## 步骤

1. **先读已有文档和实现，不猜**：`docs/参考存档/墓碑机制.md` + `zm_hammer_zombie_manager.gd` + `tombstone.gd`。
2. **第一版猜测是错的**（见踩坑 1）：怀疑「僵尸冒头途中被锤死 → 墓碑永久锁死」。写了 `probe_tombstone_respawn` 验证 —— **PASS**。
   又把「解锁兜底」摘掉重跑，**依然 PASS** —— 说明**这个 bug 不存在**，Godot 会把已释放对象判为无效引用。
   👉 **这一步最值钱：花两次跑批证明自己猜错了，而不是把错的分析写进代码注释。**
3. **改用观测型探针找现象**，不再找解释：写 `probe_hammer_spawn_trace`，按 2 秒一格打印
   `wave/小组、墓碑数(忙碌数)、累计出怪数`。
   结果一眼致命：`wave/grp` 永远停在 `0/0`，`created` 一直是 0 —— **出怪器只出了第一组就停摆**。
4. **顺着「为什么第二组不来」排查**：出怪循环靠 `hammer_zombie_timer.start()` 驱动，
   但 `zm_hammer_zombie_manager.tscn` 里只有一个 Timer 节点、**没有 `[connection]` 段**，`_ready()` 也没 `connect`。
   👉 只有 `start_first_wave()` 手动调的那一次起作用，之后 timeout 无接收者。
5. 在 `_ready()` 里显式 `connect`，重跑观测探针：`wave` 0→4 持续推进、墓碑每大组 +1（10→14）、累计出怪 143 只。
6. 顺手把验证过程中确认成立的两个次要点也修了（见「关键决策」第 2、3 条）。
7. 跑 `probe_hammer_zombie` 回归（44 断言全 PASS，含 2-5 戴夫对话 / 失败流程）。

## 关键决策与理由

- **把 connect 写在 `_ready()` 里，不去改 `.tscn`** —— 这个出怪器本来就是运行期 `instantiate()` 出来的
  （由 `LevelRuleHammerZombie` 注入 `ZombieManager`），显式 `connect` 比依赖场景文件的连线更抗改，也更好读。
- **`create_one_group_min_zombie()` 改成只从「空闲墓碑」里挑** —— 原来是在全部墓碑里 shuffle 后取前 N 个，
  抽到正在冒头的那块会被**静默跳过**（只有一行 debug 日志），本组实际出怪数比配置少。
  顺带让 `create_new_zombie()` 返回 bool，调用方能知道这一只到底放没放出去。
- **`await create_one_group_min_zombie()`** —— 它内部在「没有墓碑」时会先补墓碑并等 2 秒，
  不 await 的话这段等待会和后面的「停顿 → 补墓碑 → 起下一组」并发，节奏串在一起。
- **大波补了 20 只上限** —— 头注本来就写「最后 1 波…不超过 20 只」，代码里没有，补上对齐注释。

## 踩坑

1. **我的第一版根因分析是错的，而且看起来很合理** —— 「协程遇到僵尸被销毁就永不返回 → 墓碑永久锁死」。
   Godot 4 里僵尸 `queue_free()` 之后引用变成**已释放对象**，`is_instance_valid()` 转 false，
   所以墓碑**不会**永久锁死。**正解**：先用探针证伪再下结论，代码注释也要跟着改成诚实版本
   （我把「永远卡死」的说法从 `tombstone.gd` 注释里删掉重写了）。
2. **`probe_hammer_zombie` 抓不到这个 bug** —— 它只验「25 秒内出现过僵尸」和「清场出奖杯」，
   **第一组僵尸就足够让它全绿**。要抓「出怪停摆」必须**按时间打点看会不会推进**。
   **正解**：改出怪 / 波次逻辑时，补一条按时间采样的观测探针，别指望一次性断言。
3. **观测探针里不代打会 GAME_OVER** —— 第一版跑到 48 秒就「卡住」了，其实是游戏已经失败（僵尸进家），
   所有 `create_timer` 被 TreePause 冻住。**正解**：观测循环里每秒把逼近家的僵尸清掉，并检测
   `main_game_progress != MAIN_GAME` 就提前收尾。
4. **统计出怪数不能连 `zombies_root.child_entered_tree`** —— 僵尸是挂在各条 `ZombieRow` 下的，
   连 `row.child_entered_tree` 才数得到（`created` 一直是 0 就是这么来的）。
5. **多 agent 并行时会被别人的编译错误污染** —— 中途连续 2 次跑批失败，报
   `Identifier "CharacterShowFactory" not declared`（别的文件正在改的中间态），跟本次改动无关。
   **正解**：先看报错落在哪个文件，不在自己改动范围内就等 1~2 分钟重试。

## 给后来者的最简路径

1. 改任何**出怪 / 波次**逻辑前，先确认驱动循环的 Timer **真的连了 timeout 信号**
   （`.tscn` 的 `[connection]` 段或 `_ready()` 里的 `connect`，两者至少有一个）。
2. 写一条**按时间打点**（wave / 小组 / 累计出怪数 / 场上单位数）的观测探针跑一遍，
   确认它会持续推进 —— 这一步能挡住「只出第一组」这类一次性断言抓不到的故障。
3. 跑批失败先看报错文件属不属于自己；多 agent 并行时等 1~2 分钟重试。
4. 分析出「必然会发生」的结论后，**先写探针证伪**，跑通再改代码注释。
