> **任务类型**：其它
> **推荐度**：**推荐**（下次做"把本体某条流程收归联机"照这个走）
> **耗时与成本**：约 2 轮，未开游戏（无头探针 `probe_netplay_session` 11 段全过 + 编译门禁 PASS）
> **验证方式**：免验证 + 已给出人工验证方法（双实例开游戏，见文末）
> **补充自**：[2026-10-08_为联机模组做准备.md](2026-10-08_为联机模组做准备.md)（地基那次；本次是它的第二阶段）

## 目标

把联机从"操作同步"推进到"**两端真的在打同一局**"：每一波由主机下发（客户端不再按本地定时器开波），并落实 [联机模组规范](../参考存档/联机模组规范.md) §2.5 的「客户端不得自行进关」。

## 步骤

1. 先摸清波次系统：`zm_zombie_wave_refresh_manager`（波长 Timer）/ `zm_zombie_wave_manager.start_next_wave()` / `zm_zombie_wave_create_manager`（抽怪 + 选行）。**关键发现**：波次刷新靠的是真实时间的 Timer + `randf_range(25,31)`，两端各跑各的，连第一波都不在同一刻。
2. 本体加两个通用口（`zm_zombie_wave_manager.gd`）：`start_next_wave_gate: Callable`（返回 false = 不许本地开波）+ `signal wave_started(wave)`。命名不带联机字样（边界规则 2）。
3. 模组新增 `netplay_wave_sync.gd`：主机连 `wave_started` → 复用 `battle_op` 通道下发 `wave_next(波次号)`；客户端占住闸门 + `stop_refresh()`，收到命令才放行开波。
4. 把**影响波次的判定随机**换成 `GameRng`（波次时长 / 残半阈值 / 墓碑数量与伏击类型 / 珊瑚与蹦极抽取 / 多轮出怪表），两端同一串 `start_next_wave()` → 随机序列一致。
5. 落实「客户端不能自己进关」：本体加 `GlobalUtils.enter_level_gate`，`choose_level.gd` 进关前过一遍；模组在 `install()` 里占住、`uninstall()` 里交还。
6. 探针补第 11 段（波次同步 + 进关闸门，10 条断言）；跑 `probe_netplay_session` + 编译门禁。
7. 同步三份文档：[联机模组.md](../参考存档/联机模组.md)（§三.1 判据 / §4.7 / §五 阶段表 / §六 槽位清单 / §七 探针段数）、[联机模组规范.md](../参考存档/联机模组规范.md)（§2.5 现状差距 / §3.2 僵尸项 / §四 验收 / §五 未决）。

## 关键决策与理由

- **没走"主机下发波次的 `ZombieWaveSourceBase`"**（原计划的做法）—— 注入出怪器会把**整关怎么出怪**连带关卡脚本覆写的进场方式一起接管掉；这里只要"**什么时候开下一波**"这一件事，一个闸门 + 一个观测口正好，本体其余一行不改。
- **波次用 `battle_op` 那条既有通道下发**，不另开 RPC —— 波次本来就是"主机上已经发生了的事实"，与操作重放同语义。
- **阳光 / 掉落刻意不换 `GameRng`**（推翻了原计划"待替换"清单里的三条）—— `GameRng` 是一条共享序列，天降阳光走自己的 Timer、掉落由"某只僵尸死了"触发，两端调用**时机与次数都不保证相同**，换过去只会把波次序列打乱（比不同步更糟）。判据已写进 [联机模组.md](../参考存档/联机模组.md) §三.1。
- **`setup()` 里用 `call_deferred`** ——模组 `install_to_main_game()` 排在 `zombie_manager.init_manager()` **之前**（`main_game_manager.gd` 397 行 vs 399 行），那一刻 `monster_mode` 还没赋值，判断不了"接不接管"。帧末再接线，开战远在后面几帧，来得及。
- **中途加入 / 丢包**：命令带波次号，对不上就把 `curr_wave` 对齐到主机（补不回中间几波的僵尸，但后面每一波同步）。

## 踩坑

1. 探针的子函数里写了 `await a.frames(2)` → `run()` 没 `await` 它，**函数在 await 处直接返回，后面的断言一条都没跑**（日志里那一段只剩标题，还伪装成 PASS）。
   → **正解**：探针子函数里不要用 await；要触发延迟逻辑就直接喊那个被 defer 的函数（这里喊 `sync._install()`）。
2. `ReadLints` 与编译门禁都 PASS，但**门禁抓不到没人 import 的新脚本**（`netplay_wave_sync.gd` 就属于这类）→ 必须靠探针把它真的跑一遍。

## 给后来者的最简路径

1. 找本体那条流程的**唯一入口**，加一个 `xxx_gate: Callable`（默认空 = 单机零影响）+ 一个观测信号。
2. 模组里一端连观测信号下发、另一端占住闸门按命令放行；命令走既有的 `battle_op` 通道，只加一个 op。
3. 接线时机若在子管理器初始化之前 → `call_deferred`。
4. 随机只在"两端调用次数必然相同"的场合换 `GameRng`，其余留本地。
5. 探针补一段（别用 await），跑 `probe_netplay_session` + 门禁，再同步三份文档。

### 做了什么

- 新增 `src/mods/netplay/netplay_state_sync.gd`：主机 `_physics_process` 采快照 → `state_snapshot`
  **unreliable** 广播；客户端按 `entity_id` 对齐（缺的补 / 多的删 / 位置血量覆盖）。
- 快照 = **僵尸（id/类型/行/位置/血量）+ 植物（id/血量）**，一律 `Packed*Array` 编码。
- `NetplaySession` 加 `state_snapshot` RPC + `send_state_snapshot()` + `state_snapshot_received` 信号。
- `wave_next` 命令多带一份 `z_ids`（主机这一波每只僵尸的编号），客户端开波后按顺序贴号。
- 探针补第 13 段（8 条断言）：没连线不广播 / 没本局不崩 / 只有主机开物理帧 / 缺席够久才删等。

### 关键决策

- **不用 reliable**：快照是"最新真相"，重传只会把**旧**数据迟到送到 —— 与 `battle_op` 正好相反。
- **不用字典数组**：30 只僵尸的字典约 3KB，超 ENet 不可靠包的 MTU（约 1400B）会被**整包丢弃**；
  改成 `Packed*Array` 后约 24 字节/只。
- **不管阳光**：已有 `NetplaySunSync`，且它明确让客户端自己长的阳光**故意不同步** —— 快照按
  "主机没有就删"处理，会把玩家的向日葵阳光当场抹掉。
- **连续缺席 90 帧才删**：主机包还没到就删，客户端刚出生的僵尸会闪一下。
- ★ **编号必须主机下发**：两端各自自增的 `entity_id` 会错位（谁先多生一颗阳光就整体错开），
  快照会把整波僵尸判成"主机有、本地没有"而**再生成一遍 —— 场上僵尸直接翻倍**。这是本次最大的坑。

### 踩坑（三条都是编译门禁抓不到的）

1. **`PlantCell.get_plant()` 没标返回类型** → `var plant := cell.get_plant(place)` 报
   "Cannot infer the type"（仓库把这条警告**当错误**）。必须写 `var plant: Plant000Base = ...`。
2. **全局 `min()` / `max()` 返回 Variant** → `var count := min(a, b)` 同样被当成错误打回。
   写 `var count: int = ...`，或直接别用。
3. **编译门禁 PASS 但脚本根本编译不过**：门禁只编"被某个资源引用到"的脚本，模组脚本是运行时
   `load()` 的，解析错误只有**跑一遍探针**才会暴露（`netplay_mod.gd` 加载失败 →
   `NetplayWaveSync.new()` 报 "Nonexistent function 'new'"）。
   → **给模组加新脚本后，必须跑一次探针**，不能只看门禁。
