# docs/工作记录/ —— 目录索引与记录模板

> **[面向 AI Agent]** ｜ **触发条件**：① 任何有实质产出的任务**收尾时**（**应该**在本目录建一条记录）② **开工前**找同类任务的最简路径 ③ 照某条旧记录做完后，要给那条记录**追加补充 / 评价**
>
> **读完你能**：按 §3 模板在本目录新建一条合格记录；按 §2 索引捞出同类历史流程，挑出**最适合 / 最简单**的那条照做；按 §5 给旧记录追加评价并同步索引里的推荐度
>
> **强制级别**：**应该**（收尾归档）/ **可以**（开工查阅） ｜ **不读的风险**：重复踩坑、重复摸索，同一个任务每次都从零试错
>
> **关联**：规范卡片 [E-05](../参考存档/规范细则存档.md#e-05-工作流程归档每次任务结束必做) ｜ 文档地图 [../README.md](../README.md) ｜ 仓库入口 [../../AGENTS.md](../../AGENTS.md)

> 本目录是**唯一**的工作记录落点：**一次任务 = 一个文件**，索引集中在本文 §2。
>
> **不建议**在 `docs/` 下另建 `agent_notes*.md` / `我的流程.md` 之类散落文件。
>
> 只记**可复用的工作流**（步骤、决策、踩坑、成本），不复述代码内容与机制说明 —— 那些是**项目相关参考文档**，住在
> [`docs/参考存档/`](../参考存档/README.md)（如 [地图实现](../参考存档/地图实现.md) / [子弹说明](../参考存档/子弹说明.md)），本目录不再混排这两类文件。

## 1. 怎么用这个目录

**写（收尾时，建议做）**

1. 在本目录新建 `docs/工作记录/<YYYY-MM-DD>_<主题>.md`（命名规则见 §4）。
2. 复制 §3 模板填好，**缺项写「无」**。
3. 在本文 §2 索引表**补一行**（不补 = 后来者捞不到这条）。
4. 不改他人已归档文件的事实；发现过时就在该文件顶部加 `> **已过时**：<失效原因 + 替代做法>`，**不要**删。
5. 中途换方案的**弯路也要记**（"试过 X，因为 Y 放弃"是后来者最需要的信息）。
6. **可以**在收尾时给同源的旧记录**追加**「补充 / 评价」区块（见 §5）—— 只追加不改正文、双向引用、**不占索引新行**；若结论推翻了旧评价，**可以**去改 §2 该行的「推荐度」。

**读（开工前，应该）**

1. 在 §2 索引按「任务类型」找同类条目。
2. 优先选**推荐度最高且未标记过时**的那条；同类多条时比「耗时 / 踩坑数」。
3. 照抄前先验证记录里的路径、脚本名是否还存在 —— 不存在即已漂移，按上面第 4 条就地标注。

**判断一条记录是否还适用**

- 记录中的文件路径 / 脚本名 / 命令在仓库里仍然存在；
- 没有被标 `已过时`；
- 涉及的规则编号（如 `K-05`）在本目录的 [规范细则存档.md](../参考存档/规范细则存档.md) 里仍能查到。

## 4. 文件命名规则

- 格式：`<YYYY-MM-DD>_<主题>.md`，主题是**一句话目标的压缩**（中文、10 字以内最好）。
- 同一天多条：`2026-10-01_主题.md`、`2026-10-01_主题-2.md`（**不要**用时间，检索时没有语义）。
- **禁止**用 `新建文档.md` / `记录1.md` 之类看不出内容的名字 —— 索引表里等于一行废话。
- **补充 / 评价不建新文件**：追加在目标记录文件里（§5），文件名保持原样、**不**改成 `-补充` 之类。

## 5. 给旧记录追加「补充 / 评价」

> 场景：照某条旧记录做完一遍任务，发现它漏了一步、某步已漂移、或者有更省的做法 —— 这条经验属于**那条旧记录**，不是新的一次任务。

**规则**

- **追加，不改写**：只在目标记录文件**末尾**追加一个区块，**不删改**原有的标题、步骤、踩坑、推荐度字段。  
  整条记录已不再适用时，另在文件**顶部**加 `> **已过时**：<失效原因 + 替代做法>`（§1 第 4 条）；两者可以并存，不冲突。
- **双向引用**：追加区块里**必须**链回本次任务的记录文件；本次任务的记录文件里也**必须**链回被补充的旧记录（带锚点）—— 从任一端都能跳到另一端。
- **不进索引**：补充区块**不**在 §2 索引表新增行。索引的意义是「一次任务一个文件」，追加不是新任务。
- **推荐度可以改**：若追加的结论推翻了旧评价（照做不顺利 / 有更优路径），**可以**改 §2 该行的「推荐度」列；  
  **不建议**顺手改日期 / 任务类型 / 目标 / 文件名 —— 那些是原始事实，改了就查不到当初到底干了什么。  
  改完**建议**在追加区块里写明「推荐度已于 <日期> 调整为 <值>」，让后来的 Agent 知道这一列被动过、为什么动。

**追加区块模板**（贴在目标记录文件末尾，缺项写「无」）

```markdown
---

## 补充 / 评价（<YYYY-MM-DD> · <本次任务一句话>）

> **本次记录**：[<本次记录文件名>](<本次记录文件名>) ←→ 被补充：<本文件>
> **索引推荐度**：<原值> → <新值>（已同步 / 未改）

- **补充**：<原记录漏掉或已漂移的一步，写出新事实，如「第 3 步的脚本已改名为 <新名>」>
- **评价**：<照做的真实结果，如「能跑通，但 4 步里有 2 步多余」>
- **更省的做法**：<一句话；没有写「无」>
```

**正例**

```
docs/工作记录/2026-10-01_资源改名.md          ← 末尾追加了「补充 / 评价（2026-10-02 …）」，链向本次记录
docs/工作记录/2026-10-02_资源改名-2.md         ← 文件里反向链回上一条的 #补充--评价 锚点
docs/工作记录/README.md                        ← 索引里 2026-10-01 那行的推荐度改为「可用」，行数不变
```

**反例**

- 把评价写成新文件 `2026-10-02_对上次的评价.md` —— 又多一个待维护的小文件，且读者不一定先看到它。
- 直接改写旧记录的「步骤」让它变成正确版本 —— 原始事实被抹掉，后来者无法知道「曾经有一条更好 / 更差的路」。
- 只在一边放链接（旧 → 新 或 新 → 旧 任选其一）—— 从旧记录跳过去后回不来，读者会怀疑这是不是最新结论。
