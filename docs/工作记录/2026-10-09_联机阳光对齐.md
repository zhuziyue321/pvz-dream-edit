## 1. 起点：先盘清楚"哪儿没对齐"

按 [联机模组.md](../参考存档/联机模组.md) §五 的阶段表：一 / 二 / 三 都已 ✅，
阶段四（状态下行）还是空的。盘下来**最显眼、也最容易验**的一处是阳光：

| 现象 | 为什么 |
|---|---|
| 天上掉的阳光两端不一样 | `DaySunsManagner` 是 `Timer` + `randf_range`，两端各摇各的 —— 连"有没有这一颗"都对不上 |
| 客户端点了阳光，主机那颗还在 | `EventBus` 上只有 `ADD_SUN_VALUE`（**加了多少点**），说不清"**点了哪一颗**"，主机只能加数值，摘不掉自己场上的那一颗 |

判据（机制文档 §三.1 已经写过）：**只有"两端调用次数必然相同"的随机才换 `GameRng`**。
天降阳光由本地定时器触发，次数与时机都不保证相同 —— 换 `GameRng` 只会把波次的共享序列打乱（比不同步更糟）。
正解是**换同步方式**：主机掉一颗就下发一颗，客户端的定时器干脆不掉。

## 2. 做法：照抄上一刀的「闸门 + 观测口」

上一刀（波次）验证过的一套，这一刀**原样再来一遍**，本体只多两个通用问询口（都不带联机字样）：

| 位置 | 加的东西 | 谁用 |
|---|---|---|
| `day_suns_manager.gd` | `spawn_sun_gate` + `signal sun_spawned` | 客户端占住闸门（本地不掉）；主机连信号（掉一颗发一颗） |
| `global_utils.gd` | `sun_click_gate`（回调 `func(sun: Sun) -> bool`） | 客户端占住：点阳光 = 上行一次请求 |
| `sun.gd` | `entity_id` + `assign_entity_id()`、`spawn_target`、`collect()` | 两端对上"哪一颗" / "落在哪儿" |
| `netplay_command.gd` | `OP_SUN_SPAWN`（编号 / 值 / 起点 / 落点）；`OP_PICK_SUN` 改成带**编号** | 新增 `netplay_sun_sync.gd` 处理 |
| `netplay_battle_sync.gd` | `_replay_pick_sun()` 改成按编号找那一颗再 `sun.collect()` | 重放表仍然只有这一份 |

三条关键决定，都不是一眼能想到的：

1. **`ADD_SUN_VALUE` 从命令表里摘掉**（`op_from_event()` 不再认它）。
   那条事件说不清"哪一颗"，留着只会让主机重放时**双加一次**（`Sun.collect()` 内部本来就会推一次）。
2. **拾取只接管"有身份的"阳光**。客户端自己长的（向日葵产 / 僵尸掉）主机那局上根本没有，
   接管 => `pick_sun` 上行 => 主机找不到 => 跑不动 => 客户端**点都点不动**。
   所以用一个 `_known_sun_ids` 放行它们回本机的老路：**不同步，但照样能收**。
3. **闸门放在生成点（ `DaySunsManagner` ）而不是 `Sun` 自己身上**。
   挂到 `Sun._ready()` 里能一处盖住四种来源，但那时已经 `add_child` 完了，
   `queue_free()` 之后 `spawn_sun()` 后半段还在给一个待释放的对象建 tween —— 不敢赌。
   放在生成点只盖住定时器与时间轴两条入口（`LevelTimelineEventSpawnSun` 也是调 `spawn_sun()`），够用且稳。

## 3. 弯路 / 踩坑

- **探针里 `await` 的函数忘了 `await` 调用** —— `_check_sun_sync()` 内部有 `await a.frames(1)`，
  `run()` 里写成 `_check_sun_sync(a)`（没 await）⇒ `run()` 一路跑到 `_finish()` 提前收尾，
  后半段断言**根本没跑**，却照样打印 `result=PASS failed=0`。
  → **正解**：`await _check_sun_sync(a)`。**探针报 PASS 时，先看一眼断言条数对不对**，
  别只看那行汇总 —— 这也是编译门禁抓不到的那类（门禁不跑探针）。
- **`var root := a.get_node_or_null("/root")` 编译不过** —— `a` 是 Variant，`:=` 推不出类型。
  → 写明 `var root: Node = ...`。
- **并行 agent 撞进同一个目录**：写的过程中 `src/mods/netplay/netplay_state_sync.gd`（阶段四快照）
  被另一个 agent 新建并接进 `netplay_mod.gd`，当时它有两处 `var plant := cell.get_plant(place)`
  编译不过（`get_plant()` 返回 Variant），连带 `netplay_mod.gd` **整份加载失败**。
  → 处理：**不去改别人的文件**，只在探针与文档上把自己的部分做完；编译门禁当时仍 PASS
  （门禁只编译"被资源引用到"的脚本，没人 import 的新脚本会整份漏掉，见 `check_scripts.ps1` 头部），
  但**实际运行会整份挂掉** —— 门禁 PASS ≠ 能跑，这条再记一次。

## 4. 与 `NetplayStateSync`（并行中）的重叠

两边都以 `entity_id` 为键，**当前不冲突**：

- `NetplaySunSync`（本条）：管"天上掉下来"和"被谁捡走" —— 事件驱动、一次性。
- `NetplayStateSync`（那条）：管"现在是什么样" —— 定期快照、位置 lerp、补齐 / 回收。

`NetplaySunSync._spawn_from_host()` 生成前会先按编号查一遍（已有就不重复造），
所以快照先造出来时它会自动让开。真要合并时，**天降下发可以并进快照的 `_align_suns()`**
（位置本来就在快照里），但拾取的请求 / 事实那条链路得留着 —— 快照拉不平"这一颗被谁点了"。

## 7. 补充 / 第二刀（2026-10-09 同一天）：闸门统一 + 向日葵也收归主机

> 与上面同一主题，按「补充不新建文件」的约定追加在这里。

### 7.1 第一刀留了个真 bug：闸门装了，但没人读

收尾后复查代码时发现：本体加的是 `DaySunsManagner.spawn_sun_gate`，模组装的却是
`GlobalUtils.sun_spawn_gate` —— **两回事**。结果客户端的天降阳光**根本没被拦住**，
而探针照样报 PASS：它只验了"闸门装上了、调用返回 true"，没验"**谁在读它**"。

> 这类 bug 的典型形状：**同名 / 近名的两个口，只装了一个**。
> 防法：要么只留一个口（本次选的），要么探针里加一条"另一个口不存在"的反向断言。
> 我现在两条都做了：`DaySunsManagner.spawn_sun_gate` 删掉，
> 探针加 `dsm.get("spawn_sun_gate") == null`（`Object.get()` 取不到就返回 null）。

### 7.2 这一刀做了什么

| 改动 | 说明 |
|---|---|
| 闸门收成一个 | 天降与向日葵共用 `GlobalUtils.sun_spawn_gate`；`DaySunsManagner.spawn_sun_gate` 删掉 |
| 向日葵产阳光收归主机 | `CreateSunComponent._spawn_sun()` 开头问同一个闸门 |
| 观测口改成全局事件 | 新增 `ConstEventName.SUN_SPAWNED`（payload `[Sun]`），主机一处订阅盖住所有生成点；删掉 `DaySunsManagner.sun_spawned` 信号 |
| 下落时长也下发 | `Sun.spawn_fall` + `ARG_FALL` —— 天降是"距离 / 速度"，向日葵是固定 0.9 秒，客户端自己算会把后者压成一闪而过 |

**踩坑**：`SUN_SPAWNED` 一开始想在 `Sun._ready()` 里推（一处覆盖所有来源），
但那一刻生成方还没把 `spawn_target` 写进去（`add_child` 同步触发 `_ready()`，落点是之后才设的）
⇒ 推下去的是空落点。改成**由生成点在写完落点之后推**。

### 7.3 第三刀（同一天）：补上漏掉的三个生成点 —— 顺带发现上一刀的目标写错了

上一刀结尾写"还差僵尸**掉落**的阳光"。这一刀动手前先去核 `component_drop_item.gd`，
发现它只掉**金币 / 花园植物 / 巧克力**，根本没有阳光 ——
那句话是从更早的分析里沿用的，**没有核实就写进了两份文档**。已删并加反向说明，
免得后来的 agent 去找一个不存在的东西。

真正的生成点有**五处**（`SceneRegistry.SUN.instantiate()` 全局搜一遍就出来），
其中三处之前漏了，而它们全都往 `main_game.suns` 里加、`NetplaySunSync` 也挂在 `main_game` 上
⇒ **客户端在这些模式里会被全局闸门拦掉，又收不到主机下发 ⇒ 永远不出阳光**。这是真隐患，不是理论问题。

| 生成点 | 上一刀 | 这一刀 |
|---|---|---|
| 天降 `DaySunsManagner` | ✅ | ✅ |
| 植物产 `CreateSunComponent` | ✅ | ✅ |
| 水族馆 `ZombiquariumManager` | ❌ 漏 | ✅ 补 |
| 宝石迷阵 `BeghouledManager` | ❌ 漏 | ✅ 补 |
| 锤子小游戏 `Hammer` | ❌ 漏 | ✅ 补 |

四处（除天降）的 tween 是**同一串数字**（弹 -15、落 +45、横向 ±30、0.9 秒），
原来四处各抄一遍 —— 收成 `Sun.mark_pop_up(offset_x)`，落点与用时只在一处定义。

> 教训：**"还差什么"这种结论要先核实再写进文档**。
> 我上一刀凭印象写了个不存在的生成点，还写进了两份 md。
> 查法很便宜：`SceneRegistry.SUN.instantiate()` 全局搜一遍就是全部生成点。

### 7.4 第四刀（同一天）：掉落物也收归主机 —— 用户提的原则「客户端不该处理战斗逻辑」

用户看了阳光那刀之后提了一条**原则性**要求：「客户端不应该处理战斗逻辑，包括掉落阳光」。
测绘后确认：**掉落确实完全没同步**，而且比想象的更糟 ——
`DropItemComponent.drop_coin()` 摇一次 `randf()` 定掉不掉，
`DIM_Coin.create_coin()` 再摇一次定**掉银币还是钻石**，落点也是默认参数里的 `randf_range`。
客户端自己掷，就掷出另一枚。

按用户的选择做了两件事：① 掉落物收归主机；② 拾取也走主机权威（所以掉落物要先有编号）。

| 改动 | 说明 |
|---|---|
| 掉落物加编号 | `Coin` / `ChocolateDrop` 加 `entity_id`（与角色共用 `Character000Base` 那份自增分配器）+ `assign_entity_id()` |
| 两个新闸门 | `GlobalUtils.drop_gate`（客户端一件都不掉）、`drop_click_gate`（点一下只是请求） |
| 新观测口 | `ConstEventName.DROP_ITEM_SPAWNED`，由生成点在写完落点后推 |
| 新命令 | `OP_DROP_ITEM`（编号 / 种类 / 起点 / 落点）、`OP_PICK_DROP`（编号） |
| 本体一个重建口 | `DropItemManager.create_drop_of_kind()` —— 一个随机数都不摇，照数据原样长 |
| 新文件 | `netplay_drop_sync.gd`（仿 `netplay_sun_sync.gd`） |

**范围上刻意排除 `Present`（礼包）**：它是解锁道具 / 战利品 / 关卡结算线，
时机由**关卡数据**决定（确定性），拾取还要写存档、触发本关结算 —— 拦了会断关卡流程。
同理 §4.9 的快照也不碰它。

**仍然没做的那一档（更大）**：僵尸的 AI / 啃食 / 掉血 / 死亡判定、植物的开火、
子弹的飞行与命中，客户端**都还在本地跑**，只靠快照事后拉齐。要转成真正的 dumb client，
快照得先把**动画状态**（走 / 啃 / 死）带上，否则停掉本地 AI 后僵尸不会啃东西 ——
这一档与并行 agent 的 `NetplayStateSync` 强耦合，等快照协议扩展后再做。

### 7.5 「僵尸 / 植物转只渲染」的可行性测绘：**不能靠加一个开关完成**

用户选了更大一档（客户端只渲染），测绘后的结论是**这一档的前置是快照协议扩展，不是加个开关**。
把证据记下来，免得下次从头再查一遍。

**好消息：`disable_component()` 是真的能停逻辑的**（原来担心它只是置个标志）。实测：

| 组件 | 禁用后确实停了什么 |
|---|---|
| `MoveComponent` | `disable_component` → `update_move_factor(true, IsDisable)`：不再移动 |
| `DetectComponent` | `_process` 里 `if need_judge and is_enabling`：不再索敌；`disable_component` 还会发 `signal_not_can_attack` |
| `AttackComponentBase` | `disable_component` → `update_is_attack_factors(false, Enbale)` → `attack_end()` |
| `HurtBoxComponent` | `disable_component` → 所有 Area2D `monitorable = false`：子弹打不进来 |

也就是说项目里**已经有**"只渲染"的现成范式：`ready_show()` 就靠
`move_component.disable_component(E_IsEnableFactor.InitType)` 让展示用僵尸站着不动。

**坏消息：判定与表现是长在同一个组件上的，拆不开。**

1. **啃食绕过受击框。** `AttackComponentZombieNorm._physics_process()` 直接调
   `enemy.be_zombie_eat(...)` —— 不走 Area2D、不经 `HurtBoxComponent`。
   ⇒ 只禁受击框是**假收口**：子弹伤害挡住了，啃食伤害照样本地结算。
2. **关掉伤害总闸会让僵尸"站着 0 血再凭空消失"。** 所有伤害最终汇到 `HpComponent.Hp_loss()`
   （`be_bomb` / `be_chomper_eat` / `be_squash` / 子弹全都走它），在那里加闸门最集中。
   但客户端一旦不掉血，就永远走不到本地死亡流程 —— 而快照的删除要等**连续缺席 90 帧**
   （`MISS_FRAMES_BEFORE_DELETE`，约 1.5 秒）。结果：僵尸 0 血还在走，1.5 秒后凭空消失，
   没有倒地 / 掉头动画。**必须先同步死亡状态**才能开这个闸门。
3. **子弹是个死结。** 客户端植物若不开火 ⇒ 场上没有豌豆（视觉断档）；
   若照旧开火而僵尸受击框被禁 ⇒ 豌豆穿过僵尸飞出屏幕（视觉也断档）。
   ⇒ **子弹必须纳入同步**（生成 + 位置 + 消失），否则两头都不对。

**结论**：这一档真正的前置是给快照加**三样东西** —— 死亡状态、动画 / 攻击状态、子弹。
在那之前开任何一个"客户端停逻辑"的开关，都是在用一个**无头探针验不出来、也无法目视验证**的
视觉回退，换一个纸面上的架构纯度。所以这一轮**没有**开那个开关。

### 7.6 探针验不到的那段（别误以为验过了）

主机"推一条事件 ⇒ 发一条命令"这一段在单进程探针里**验不到**：
`request_battle_op()` 走 `rpc`，没有对端时本地不回调，`battle_op_received` 收不到
（实测收集到的 `sent` 恒为空）。曾想写一条断言，跑出来必然 FAIL，改成明说"这段要开双进程才验得到"。
**结论**：联机的"真同步"只有阶段五的双进程验证能证明，单进程探针能验的只是**闸门语义**与**命令格式**。

## 8. 第三刀（2026-10-09 同一天）：快照协议扩展 —— 死亡 / 动画状态

接着 §7.5 的结论做前置。这一刀**不改任何运行时开关**，只把快照能表达的真相变多。

### 8.1 关键发现：动画由本体字段直接驱动

原本担心"要让客户端跟着主机啃食，得另发明一套动画协议"。查下来不需要：
`zombie_norm.tscn` 的 AnimationTree 用 `advance_expression` **直接读本体字段** ——
`is_death` / `is_attack` / `is_swimming` / `is_idle` / `walk_status` / `idle_status` / `death_status`。

⇒ 把 `is_death` / `is_attack` / `is_swimming` 三个开关随快照下发，客户端的动画就跟着主机走。

> 顺带一个没去管的小事：`zombie_norm.gd` 在初始化时 `randi_range(1, 2)` 挑
> `walk_status` / `idle_status` / `death_status`（走 / 站 / 死的**变体**），两端挑的不一样。
> 两个变体都是合法的走路动画，所以不算错，只是两端不完全一致。要对齐得再多带 3 个小整数，
> 性价比不高，先记着。

### 8.2 状态位挤在 `z_lane` 的高 8 位

每只僵尸再开一条数组 = +160 字节，而快照已经贴着 ENet 的 MTU（约 1400B，见文件头注释）。
行号只用到 0..5、状态位只有 3 个 ⇒ 挤进同一个 int，**零新增字节**。

代价就是那条警告：**读 `z_lane` 必须走 `_unpack_lane()`**，直接当下标用会把僵尸挂到错误的行上。
这正是 §7.1"两个同名的口只装了一个"的同款隐患，所以探针里加了**打包 / 解包往返**断言守着
（不是只验"常数存在"，而是真的走一遍 `_pack_lane_state()` 再解回来）。

### 8.3 死亡表现改由主机触发

```
主机说它死了 && 本地还活着 ⇒ 客户端补一次 Hp_loss_death(false)
```

- 僵尸：走快照的状态位（上面那三个之一）
- 植物：**没有专门的死亡位**，用血量 ≤ 0 推断 —— 再开一条数组要多 256 字节，不值当

有了这一句，§7.5 里那个"客户端不结算伤害 ⇒ 僵尸 0 血站着走 1.5 秒然后凭空消失"的回退
就不存在了：**关掉本地 `Hp_loss()` 之后，死亡表现仍由主机的快照触发**。
也就是说"客户端不处理战斗逻辑"的前置，三样里已经齐了两样。

### 8.4 子弹没做，原因记下来

子弹工厂是现成的（`Global.bullet_registry.create_bullet(BulletType)`），同步本身不难，
卡在**编号怎么发**：`Bullet000Base` 有 **7 个子类重写 `_ready()`**
（bowling / cactus / cob_cannon / norm_base / parabola_base / pea_fire / track_base / winter_melon）。

照角色那套"`_ready()` 里自动领号"加到基类会**静默失效**：没调 `super()` 的那一批拿不到编号
⇒ 不进快照 ⇒ 不同步**且无任何报错**。这就是 §7.1 那次 bug 的形状，不能再踩。
建议改由**生成点**在 `add_child` 前显式赋号（与阳光 / 金币同一套路）。

所以子弹留作独立一轮（设计已写进 [联机模组.md](../参考存档/联机模组.md) §4.11）。

### 8.5 验证

- 编译门禁 PASS（`real compile errors = 0`）
- 联机探针 13 段全过，其中新增 4 条断言**确认真的执行了**（日志里能看到 `[OK]`）：
  死亡位不串到行号上 / 死亡位解得回来 / 啃食+游泳两位一起带过去 / 本体字段往返一致
- `probe_first_coin_advice` / `probe_zombie_drop_chocolate` / `probe_tutorial` 全过
  —— 本体行为不变（快照只在联机连上时才跑）

⚠️ **仍未开游戏**：这一刀改的是快照内容，只有两端真连上才看得到效果，
单进程探针能验的只是"打包解包对不对"，验不到"两端动画是否真的同步"。

## 9. 第四刀（2026-10-09 同一天）：子弹进快照 + 修掉一个既有的误删 bug

### 9.1 编号：领号放在唯一的创建口，不碰 `_ready()`

§8.4 记过这个隐患：`Bullet000Base` 有 **7 个子类重写 `_ready()`**，在基类加自动领号会静默失效。
实际做法是把领号放进 `BulletRegistry.create_bullet()` —— 全部 **9 处**创建点都过这一个口，
一处覆盖，绕开 `_ready()`。

### 9.2 一个差点埋进去的 bug：重建路径被自己的闸门挡住

客户端要占住"不造子弹"的闸门，而重建子弹也走 `create_bullet()` ——
闸门一占，**客户端一颗都造不出来**，场上会完全没有豌豆。

⇒ 加了 `create_bullet(type, is_ignore_gate)`，只有 `NetplayStateSync` 那条重建路径传 true。

> 这是"闸门 + 重建走同一个工厂"必然碰上的结构性问题，阳光 / 金币那两刀没有，
> 因为它们各有独立的重建入口（`create_drop_of_kind()`）。

### 9.3 只拦造子弹，不拦开火动画

`AttackComponentBulletBase._shoot_bullet()` 拿不到子弹就返回，但**开火动画仍由本地攻击组件驱动**
（`_on_bullet_attack_cd_timer_timeout()` 设 OneShot 请求）。判定与表现不能一起停 ——
停掉攻击组件会连发射动画一起没了。

### 9.4 顺手修掉的**既有** bug：截断会把实体误删

加子弹时发现：光靠"条数上限"**算不出真实体积** ——
40 只僵尸（24B）+ 64 株植物（8B）就已经 1472B，超过 ENet 的 MTU（约 1400B）会被整包丢弃。
也就是说**加子弹之前这个 bug 就存在**。

改法两条：

1. **按字节排上限**（`BYTE_BUDGET`），并给后面的类留保底 ——
   否则僵尸一多植物就一条都发不出去，客户端的植物永远死不了。
2. **截断时不回收**：填不下就打 `z_cut` / `b_cut`，客户端见到截断就不回收。
   ⚠️ 这一条才是真修 bug：原来僵尸超过 40 只时，客户端会把多出来的那批
   判成"主机那边没有"而**删掉**。

### 9.5 已知代价

客户端的子弹是**木偶**（`set_physics_process(false)`）：位置每帧由快照写，
自己不再算飞行与命中。代价是子弹自身的动画 / 旋转（如抛物线的翻滚）不走了。

### 9.6 验证

- 编译门禁 PASS（`real compile errors = 0`）
- 联机探针 13 段全过，新增 10 条断言**逐条确认真的执行了**（日志可见 `[OK]`）
- `probe_first_coin_advice` / `probe_zombie_drop_chocolate` / `probe_tutorial` 全过
- ⚠️ 仍未开游戏

### 9.7 第五刀：动画状态改由主机整份下发

上一版只发了 3 个开关（`is_death` / `is_attack` / `is_swimming`），并且**挤在 `z_lane` 的高 8 位**。
改成独立的 `z_anim`，把 AnimationTree 读的 **7 个字段全发**：

```
is_death / is_attack / is_swimming / is_idle
walk_status(1..2) / idle_status(1..2) / death_status(1..3)
```

三个变化：

1. **补上了变体。** 实测 `zombie_norm.tscn` 的 `advance_expression` 还读了
   `walk_status` / `idle_status` / `death_status`，而 `zombie_norm.gd` 在 `_ready()` 里
   `randi_range(1, max)` 各挑一个 —— **两端挑的不是同一个**。两个变体都合法所以不算错，
   但两端画面不一致。要一致就得发。
2. **`z_lane` 回到纯行号。** 上一版"行号塞在 `z_lane` 高位"的做法本身没错（省了 160 字节），
   但它把一个新隐患塞进了最基础的字段：读 `z_lane` 必须走解包，直接当下标用会挂错行。
   换独立的 `z_anim` 后这个隐患消失，代价是每只 +4 字节（僵尸上限从 30 变 25，
   截断时不再回收所以是优雅降级）。
3. **变体字段不是每类僵尸都有。** 只在 `Zombie001Norm` 上，读写都走 `_has_anim_prop()` 兜底 ——
   `set()` 到不存在的属性会**报错**，不能裸写。

### 9.8 踩到的两个坑（都写进注释了）

| 坑 | 现象 |
|---|---|
| `get_class()` 返回的是**引擎基类** | 用它做属性探测缓存的键，普僵和僵尸基类共用同一个键 ⇒ 先查的那只把结果污染给另一只 ⇒ 普僵被判成"没有走路变体"，变体永远同步不过去。改成按**脚本路径**做键 |
| `var script = get_script()` 是 Variant | 后面 `var path := script.resource_path` **推断不出类型**，整份脚本解析失败。必须写死 `var script: Script` |

⚠️ 顺带一个**流程警讯**：第二个坑发生时门禁报了 `real compile errors = 0`
（把那条 Parse Error 当成"预期噪声"放行了），是探针输出里的 `SCRIPT ERROR` 才暴露出来。
⇒ **不能只看门禁的 PASS**，跑完还要扫一眼输出里的 `SCRIPT ERROR`。

### 9.9 第六刀：客户端僵尸转"只渲染"（这一档收口）

前置（死亡 / 动画 / 子弹）齐了，于是把客户端僵尸的判定整体关掉：

```
z.attack_component.disable_component(Netplay)   → 连带禁用它内部的 detect_component
z.hurt_box_component.disable_component(Netplay)
```

用**新增的** `E_IsEnableFactor.Netplay` 因素，不复用 `Global` / `Death` 等。

**为什么这道闸门必须是"粘的"**（这条最关键）：`disable_component` 把 Netplay 因素置 false，
而 `is_enabling` 是**所有因素的与** —— 所以之后任何人 `enable_component(别的因素)` 都拉不回来。
死亡 / 魅惑 / 睡眠这些正常流程都在调 `enable_component`，如果闸门是能被顶开的，
客户端跑一会儿就又开始自己判定了。探针里有专门的断言守着这条。

**两处刻意没动**（都写进注释了）：

| 不动 | 原因 |
|---|---|
| `move_component` | 位置每帧被快照拉齐，本地多走的那点立刻被拉回（60fps 下半像素级），收益很小；而停掉它的代价很具体 —— 快照**截断**时那几只既收不到位置、又不会被回收，会**僵在原地**。移动组件还管地面 / 斜坡表现 |
| 植物 | 开火动画长在攻击组件里，停掉它植物只剩静止贴图；"客户端不自己造子弹"已由 `bullet_spawn_gate` 兜住 |

所以严格说僵尸现在是**判定归主机、移动仍本地（但被拉齐）**，不是 100% 的 dumb client。
剩下的"植物开火与命中"动不了（上面第二行），除非把开火动画也改成主机下发。

### 9.10 下一刀

三样前置（死亡状态 / 动画状态 / 子弹）**已全部齐**。剩下真正落下那一刀：
把客户端的 `move` / `attack` / `detect` / `hurt_box` 整体 `disable_component()`
（实测这四个都真的检查 `is_enabling`）。这一刀会**改变运行时行为**，要单独验。
