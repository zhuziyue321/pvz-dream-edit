## 关键决策与理由

- 降级范围只取「违反后功能与依赖完全一样」的三类（排版、变量后缀、目录同名）—— 日志走 `Log`、UI 坐标、注册表、`.uid`、字典读取、验证一类的**行为约束一律不降**，它们违反后是静默出错，不是不好看。
- 红线编号重排而不是留空号 —— 留空号会让「第 N 条红线」的引用长期指向错条目；重排后全仓 grep 一遍即可确认。
- 原卡片不删除、只留「已降级 + 链接」—— 后来者看到标题才知道这条曾经存在、现在去哪了，避免重新猜一遍。

## 踩坑

1. 降级后 `grep "行尾空格|4 空格缩进"` 才发现 [Agent协作协议.md](../Agent协作协议.md) §5 里还写着「S-01，红线第 9 条」→ 只改项目规范.md 会留下第二处强制 → **正解**：降级类改动收尾前必须**全仓 grep 关键词**，而不是只改规范本体。
2. 删红线会连带改编号与多处「N 条红线」计数文案 → 只删行不动编号会让后续引用全部错位 → **正解**：删行 → 重排 → 再 grep `条红线` 复核计数。

## 给后来者的最简路径

1. 判定：违反后会不会崩 / 依赖会不会断？不会 → 可降级。
2. 原文搬进 [参考意见存档.md](../参考意见存档.md)（下一个 `R-<编号>`），规范原位置留「已降级为参考 + 链接」。
3. 全仓 grep 该条目关键词 + `条红线`，逐处摘掉「必须 / 禁止」并修正编号与计数。
4. 在 [参考意见存档.md](../参考意见存档.md) §3 降级记录补一行。
