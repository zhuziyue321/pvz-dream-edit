## 一、目标与形态（先定死，别边做边改）

- **玩法形态**：多人**合作共守一块草坪** —— 同一张地图、同一批僵尸，大家一起种。
- **同步方案**：**主机权威 + 命令上行 + 状态下行**。
  - 主机跑完整的关卡逻辑（波次、出怪、伤害、掉落），是唯一的事实来源；
  - 客户端只把"我点了什么"发给主机；
  - 主机定期下发状态（实体位置 / 血量 / 阳光 / 卡槽），客户端照着画。
- **为什么不是帧同步**：本体的关卡流程是 `await` 协程链 + `Timer`（见 [关卡时间轴.md](关卡时间轴.md)），
  **没有 tick / 帧号概念**，波次时长是 `randf_range(25,31)` 秒的真实时间。
  帧同步要求"同样的输入 + 同样的步进 = 同样的结果"，得先把全仓库的 Timer 与 `await` 换成固定步长 tick 驱动，
  改造面是整个关卡系统 —— 而状态同步只需要"主机算、客户端画"，与现有计时器天然相容。
- **为什么是模组**：原版《植物大战僵尸》没有联机 → [模组机制.md](模组机制.md) §一 的判据「原版没有 → 做成模组」。
  开关在 `data/mods/mod_config.tres`，**默认关闭**。

> ★ **本文只讲现状与实现**。三条顶层约定（房间机制 / 关卡只由房主打开退出 / 进关后战斗域 vs 本地域）的规范版在
> [联机模组规范.md](联机模组规范.md)；两份冲突时以那份为准，并回来改本文对应段落。

## 二、现状盘点：哪些地方挡着联机

| 维度 | 现状 | 联机能不能绕 | 处理 |
|---|---|---|---|
| **随机** | 全仓库 0 处 `seed()` / `RandomNumberGenerator`，164 处 `randi*/randf*`，Godot 启动时自动播种；出怪类型 / 出怪行 / 波次时长全随机 | 不能绕：两端必须抽到同一批怪 | ✅ 已加 `GameRng`（可播种），抽怪入口已接（见 §三.1） |
| **主循环** | `MainGameManager._ready()` → `await level_timeline_manager.run_timeline()`；波次靠 `WaveNormRefreshTimer` 等 Timer 推进，**无 tick** | 可以绕：主机权威不需要固定步长 | ⏸ 不动（状态同步的前提就是"主机说啥是啥"） |
| **玩家输入** | 点卡 / 铲子 / 捡阳光已经是 `EventBus` 事件：`MAIN_GAME_CLICK_CARD` / `MAIN_GAME_CLICK_SHOVEL` / `ADD_SUN_VALUE` | 好收：天然就是"命令" | ✅ 已加 `EventBus` 拦截器（见 §三.2） |
| **出怪权** | `ZombieManager.set_wave_source()` 已能把出怪器整体换掉（锤僵尸关就在用） | 现成扩展点 | ✅ **波次已由主机下发**（走的是 `ZombieWaveManager.start_next_wave_gate` + `wave_started`，没动出怪器 —— 见 §4.7） |
| **实体标识** | 只有 `get_instance_id()`（进程内、非稳定、释放即失效）；`create_norm_zombie()` 还有个不可序列化的 `Callable` 参数 | 不能绕：得说清"哪一只" | ✅ 已加 `entity_id`（见 §三.3）；`Callable` 参数待改成枚举 id |
| **单例** | `GameContext.curr_main_game`（静态）、`Global.game_para`、`EventBus` 订阅表、`TreePauseManager`（全树 paused）都是进程级全局 | **只在"一进程跑两局"时才挡路** | ⏸ 合作共守是"一进程一局 + 两端两个进程"，暂时不用动 |
| **验证** | `DebugChannel + autopilot`（`test/scenarios/` 100 个探针）能脚本化种植物、读回场上状态，但 `run_autopilot.ps1` 只起一个进程 | 双进程验证要另做 | ✅ 已有 `probe_netplay_pair_host` / `_client` 两个探针（手动开两个实例跑）；一键跑批仍待做 |

一句话：**真正必须先解决的只有"随机"和"实体标识"两件**，其余要么有现成扩展点，要么状态同步天然绕开。

## 三、已落地的本体扩展点（都在通用能力名下，本体不认识联机）

> 命名纪律同 [模组机制.md](模组机制.md) §五 边界规则 6：本体 API 不带模组名字。
> `GameRng` / `entity_id` / `拦截器` 都是通用能力，单机回放、录像、自动回归也能用。

### 3.1 `GameRng`：可播种随机（`src/core/game_rng.gd`）

```gdscript
GameRng.set_seed(12345)      # 两端同一个种子 → 同一串随机数
GameRng.randf_range(25, 31)  # 与全局 randf_range 同名，替换时只换前缀
GameRng.clear_seed()         # 回到默认（每次运行不同）
```

- 不调 `set_seed()` 时行为与原来**完全一致**（同样的 PCG 算法、同样每次运行不同）—— 单机零影响。
- **已接线**（影响判定的那几处）：
  - `src/core/autoload/random_picker.gd` —— 抽怪类型的唯一入口（`zombie_choose_random_pool`）
  - `src/managers/zombie_manager/zm_zombie_choose_row_system.gd` —— 出怪行（加权轮盘 + 兜底 `pick_random`）
- **已替换**：波次时长与残半阈值 `zm_zombie_wave_refresh_manager.gd`、墓碑数量 / 伏击类型
  `zm_zombie_wave_manager.gd`、解锁道具携带者（同上）、珊瑚与蹦极的抽取
  `zm_zombie_wave_create_manager.gd`、多轮出怪表 `zombie_manager.gd`。
- **不替换**（与早先的计划相反，见下面那条判据）：植物产阳光 `component_create_sun.gd`、
  僵尸掉落 `component_drop_item.gd`。
- **改由主机下发**（不换 `GameRng`，换同步方式）：天降阳光 `day_suns_manager.gd` ——
  主机掉一颗就下发一颗，客户端的定时器干脆不掉（见 §4.8）。
- **不用改**：纯表现随机（眨眼、断肢弹道、音效、花园、砸罐子摆位）—— 不同步也不影响胜负。

> ★ **判据（重要）**：只有"**两端调用次数必然相同**"的随机才换 `GameRng`。
> `GameRng` 是一条**共享的随机序列**，任何一端多调一次 / 少调一次，后面全串位。
> 波次那几处安全，是因为两端跑的是同一串 `start_next_wave()`（见 §4.7）；
> 而天降阳光走自己的 `Timer`、掉落由"某只僵尸死了"触发 —— 两端的调用**时机与次数都不保证相同**，
> 换成 `GameRng` 只会把波次的序列打乱（比不同步更糟）。这类要么保持本地随机，要么等阶段四由主机下发。

### 3.2 `EventBus` 拦截器（`src/core/autoload/event_bus.gd`）

```gdscript
EventBus.add_interceptor(func(event_name: String, payload: Array) -> bool:
    ...
    return true   # true = 我接管了，本体不再本地派发
)
EventBus.remove_interceptor(回调)
```

- 派发前过一遍，返回 `true` 则跳过本地订阅方；没有拦截器时只多一次 `is_empty()` 判断。
- 为什么是这个点：玩家操作天然是总线上的几条事件，在这里挂钩**一处就够**，不碰任何 UI 与管理器。
- ⏸ **联机现在不再用它采集操作**：拦截器只能采到"有事件"的那两种（点卡 / 点铲子），
  点格子 / 捡阳光 / 捡掉落物另有入口 —— 四条上行路径各装各的，加一种操作就得新开一个本体口。
  现已一律改走本体的**统一上报口** `GlobalUtils.player_action_gate`（见 §4.6）；
  拦截器作为通用能力仍留在本体（单机回放 / 录像可用），模组不再装它。

### 3.3 `Character000Base.entity_id`：实体稳定标识

```gdscript
character.entity_id                      # 0 = 未分配
Character000Base.reset_entity_id_allocator(1)   # 新的一局从 1 开始
zombie.assign_entity_id(主机下发的 id)     # 客户端入树前塞进去，_ready() 就不再自动分配
```

- 出战角色（`character_init_type == IsNorm`）在 `_ready()` 里自动领一个自增 id；展示 / 花园态不领。
- 只做标识，**不参与任何玩法判定** —— 单机行为完全不变。

### 3.4 出怪器注入（原本就有，无需改造）

`ZombieManager.set_wave_source(ZombieWaveSourceBase)` 可以整体替换出怪器（现成用法见
`src/levels/core/hammer_zombie/level_rule_hammer_zombie.gd`）。下一阶段的"主机下发波次"就走这个口子。

### 4.1 房间：房主进关 ⇒ 全屋跟进

需求是"房主进入某关，所有玩家都进入"。**方位由房主独裁**（客户端喊了会被丢掉），流程只有一跳：

```
房主 MainGameManager.init_manager()
  → ModManager.install_mods_to_main_game() → NetplayMod.install_to_main_game(mg)
      → NetplaySession.request_enter_level(_level_key_of(mg.game_para))   ← 只有 is_host() 时成立
          → enter_level.rpc(level_key)                                    ← one-to-many 下行
客户端 NetplaySession.enter_level()
  → signal level_enter_requested → NetplayMod._on_level_enter_requested()
      → LevelRegistry 取关 → set_choose_level(三件套) → Global.game_para = para
      → GlobalUtils.change_scene(MainScenesMap[para.game_sences])
```

| 要点 | 说明 |
|---|---|
| 键值内容 | `id`（`LevelRegistry` 的 id = 文件名 basename）+ `path` + 选关三件套（`mode` / `page` / `level_id`） |
| 三件套不能省 | `set_choose_level()` 是 `save_game_name` 的唯一来源，不补齐会把通关存档写到默认键上 |
| 为什么要带 `path` | 有的导出包里 `LevelRegistry.rescan()` 扫不到内置关卡（日志里是 0 关），客房按 id 找不到 → 退回路径，但仍用 `LevelRegistry.is_level_script()` 过白名单 |
| 后加入的人 | `NetplaySession._on_peer_connected()` 里房主给新 peer 单独补发一次当前关卡 |
| 面板反馈 | 控制台「房间关卡」一行显示房里正在打的这一关（房主还没进关时显示占位） |

> 注意：**不要**把进关做成 `NetplayCommand` 的一个 op —— 命令是"客户端 → 主机"的上行，
> 进关是"主机 → 客户端"的下行，方向相反，混进命令表会让阶段三的重放逻辑多一层"这条命令要不要在本地重放"的分支。

### 4.2 选卡：不跳过 + 不重复 + 撞车让路

用户的原话需求：**"选卡无论如何都不跳过，因为双方不能选重复的卡，需要协商"**。

#### 4.2.1 不跳过（强制找回选卡界面）

原版有一条"没有选择权就跳过选卡"（`ResourceLevelData.is_no_choose_permission()`）：已拥有植物 ≤ 卡槽数时系统替玩家全选。这在联机里不成立 —— **谁带哪张必须由两边当面挑**。

```
MainGameManager._ready()
  game_para.init_para()          ← 这一句里算出 is_locked_card_slot / prechosen_cards
  ModManager.notify_level_para_ready(self)   ← ★ 新加的通用钩子（见 ModBase.on_level_para_ready）
      → NetplayMod.on_level_para_ready() → keep_choose_card_ui()
          para.is_locked_card_slot = false; para.prechosen_cards.clear()
  init_manager()  → card_manager.init_manager()  ← 卡槽照着（已清空的）预选卡建，UI 正常出现
```

> ★ 这个钩子为什么必须加在本体：**晚了就来不及**。`card_manager.init_manager()` 里已经
> `CardSlotController.create()` → `CardSlotNorm.init_card_slot_norm()` → `init_pre_choosed_card()`
> 把预选卡塞进出战卡槽、待选区对应卡隐藏，回头再改字段没人看。原先唯一的钩子
> `install_to_main_game()` 排在 card_manager **之后**，做不到。

界限：传送带 / `can_choosed_card == false` 的关本来就没有选卡界面（`card_slot_norm` 是 null），
**不去碰**（硬掰会弄坏这批关）；单机不联网时也完全走原路（探针有断言守着）。

#### 4.2.2 不重复（协商）

`NetplayCardSync`（每局由模组挂到本局上，随场景灭）：

| 环节 | 做法 |
|---|---|
| 本机选了什么 | 每帧比对 `card_slot_battle.curr_cards` 的**全量快照**，变了就 `card_selection.rpc()` 广播（元素=`ResourceCardReference.to_dict()`，天然可进 RPC） |
| 对面挑走的卡 | **留在原处压暗 + 点不动**（`card.modulate` + `mouse_filter_stop()`） —— 要看得见"他挑走了哪张"，所以**不用** `set_plant_card_banned()`（那套是关卡禁选用的，会把卡整张撤走） |
| 对面又放了手 | 同样遍历一遍把颜色与点击恢复。选卡阶段结束也会整体还原一次 |
| 撞车（几乎同时挑同一张） | **`must_yield()`：peer id 大的一方让**，自动点掉自己那张。两端按同一条规则算，结论必然一致，不需要再多一次往返 |
| 模仿者 | `content_id` 就是被模仿的那株植物，去重时按**同一张**算 |

#### 4.2.3 以后要摆平的（阶段三）

双方卡组仍各自来自**自己的存档**（`Global.global_game_state.curr_plant`）—— 置灰只保证**不重复**，
不保证两边阵容对等（房主解锁了 30 张、客户端只有 1 张时，客户端就是在用自己那一两张硬撑）。
真做主机权威时，卡池要由房主下发（已列入 §八 已知风险 7）。

### 4.3 同进同出：房主退关 ⇒ 客户端也退

进一起进，退也一起退：

```
房主 MainGameManager.tree_exited  →  NetplayMod._on_main_game_exited()
  → NetplaySession.request_leave_level()      ← 只有 is_host() 喊得动
      → leave_level.rpc()  → signal level_leave_requested
客户端 NetplayMod._on_level_leave_requested()
  → GlobalUtils.change_scene(那一关所属的选关页)
```

- **退回哪一页不用维护对照表**：`ResourceLevelData.game_mode` 存的就是它所属选关页的场景 id
  （`MainSceneRegistry.MainScenes.ChooseLevel*`）。认不出时**留在原地**，不猜不乱跑。
- 连续换关时旧节点的 `tree_exited` 也会响一次，紧接着新的那一局又会把大家拉进去 ——
  中途那次多余的"退"会被紧随其后的"进"盖掉，不会闪过一个多余的画面。

### 4.4 通关与否以房主为准

**判决点选在 `MgmSaveManager.update_level_state_data_success()`** —— 全仓唯一写 `IsSuccess` 的地方，
通关解锁植物 / 解锁道具 / 消耗钉耙也都在它里面。锁住它 = **下游所有解锁自动跟着停**
（选关页、商店、图鉴、花园、铲子的解锁都是从通关进度推导的，没有第二份来源）。

本体留一个通用问询口（不带联机字样，默认永远是"照旧写"）：

```gdscript
# mgm_save_manager.gd
var level_success_write_gate: Callable = Callable()   # 返回 false = 这一次的通关不写档

func update_level_state_data_success():
    if level_success_write_gate.is_valid() and not level_success_write_gate.call():
        return
```

模组把它占住，规则只有两行：

| 角色 | 行为 |
|---|---|
| 房主 | 照旧写（我就是事实来源），写完顺手 `request_level_result(save_game_name, true)` 把裁决发下去 |
| 客户端 | **只有房主裁决过这一关才写**（`client_may_write()`）；自己打通不算数。裁决到了就补写一次本体的同一条函数，解锁口径与房主完全一致 |

还差一步（属阶段三）：客户端自己的**结算画面 / 失败表现**仍走本地 —— 状态同步到位之前
"这一局到底赢了没有"本来就是各跑各的。裁决口保证的是**存档进度**跟着房主走，不等于表现也跟着房主走。

### 4.5 选卡收工：客户端报准备，人齐了房主才开始

选卡阶段那颗按钮（`card_slot_norm.tscn` 的 `CardSlotCandidate/TextureButton`）**文字是烘焙在贴图里的**
（`SeedChooser_Button_Glow.png`，一个 Label 都没有），改不了文案 —— 所以做法是：
**把原版那颗藏起来，照它的位置尺寸补一颗**（与本体「开始战斗！」那颗同一份 `pvz_theme.tres`
同一个 `PanelButtonBG` 变体，中文字体现成可用）。

```
原按钮 TextureButton（visible = false，数据一概不动）
 └ 同位置同尺寸补一颗 BaseButton + Panel(PanelButtonBG) + Label ← 同一份主题
```

按键之前的协商只是"谁准备好了"：

| 角色 | 按钮上写什么 | 按下去做什么 |
|---|---|---|
| 客户端 | `准备` / `已准备（等房主开始）` | 切换自己的准备状态（`session.declare_ready()`），**永远不开始** |
| 房主 | `开始` / `等准备 n/m`（n/m 不全时按钮是灰的） | 人齐 ⇒ 广播"收工"+ 本体照常推进；不齐 ⇒ 提示还差谁，留在本界面 |

**闸门锁在 `MainGameManager._on_card_slot_norm_start_game()`**（本体唯一的收工汇合点：点按钮 /
跳过选卡 / 调试入口都经过它），本体留的口还是那个套路：

```gdscript
# main_game_manager.gd
var choose_card_start_gate: Callable = Callable()   # 返回 false = 这一次不许收工

func _on_card_slot_norm_start_game() -> void:
    if choose_card_start_gate.is_valid() and not bool(choose_card_start_gate.call()):
        return
```

房主这一把自己的开局仍然是**本地发起**的（`_press_start()`：存选卡 + push
`CARD_SLOT_NORM_START_GAME`），客户端收到 `choose_card_start_requested` 之后照做同样的两步 ——
两边走的是同一条本体路径，不会出现"房主打起来了、客户端还站在选卡界面"。

- 客户端**没走上选卡界面**的那一局（传送带 / 没有选卡权）会自动替本机报一次准备：
  那种关卡根本没有「准备」可以按，不然房主会永远等一个不可能按键的人。
- ⚠️ 现在的等待是**无条件的**：客户端必须先跟着房主进到同一局才报得上准备，
  还留在菜单里的同伴会让房主一直等（超时 / 房主手动跳过属于下一阶段的事）。

### 4.6 战斗同步：**主机权威**（上行的是请求，下来的才是事实）

一句话规则：**客户端按下的一次操作不在本地生效**。两端不做两份局面，只做主机那一份：

```
client 按键 ──上行"请求"──▶ host 在自己这一局上跑一遍 ──下行"事实"──▶ 屋里的每一个人重放
host  按键 ────────────────▶ host 在自己这一局上跑一遍 ──下行"事实"──▶ 客户端重放
```

所以两端看到的是**同一串**操作，而不是各自跑各自的那一份。关键是"**跑得成**"才下发 ——
主机上跑不动（卡在冷却 / 阳光不够 / 下标对不上）就当这一下没发生，两端都不会记这一笔，
不会出现"客户端记了、主机没记"的歪账。

**唯一的重放表**在 `NetplayBattleSync.execute()` 里（纯数据 → 本体动作）：

| 操作 | 参数 | 重放时怎么落 |
|---|---|---|
| `click_card` | 卡槽下标 + 植物类型 | 取出那张 `Card`，推**本体的同一条事件** `MAIN_GAME_CLICK_CARD` |
| `click_shovel` | 空 | 推 `MAIN_GAME_CLICK_SHOVEL` |
| `click_cell` | row / col | 调 `hand_manager._on_click_cell(cell)`（种植物与铲植物是同一枚入口） |
| `pick_sun` | 阳光值 | 推 `ADD_SUN_VALUE` |

**重放为什么尽量推本体的同一条事件**，而不是替本体调 API：推同一个事件就还是本体的
同一条链路 —— 音效、生命周期、冷却 / 阳光够不够的校验全都不用模组再抄一遍。

**客户端从哪儿把操作发出去**：本体只留**一个**口，模组只在**一处**翻译与发送 ——

```gdscript
# global_utils.gd：玩家的每一个操作在落下去之前都先问这一位
var player_action_gate: Callable = Callable()   # func(action: E_PlayerAction, payload: Array) -> bool
func submit_player_action(action: E_PlayerAction, payload: Array = []) -> bool
```

`NetplayActionGateway` 占住它，按 `E_PlayerAction`（`ClickCard` / `ClickShovel` / `ClickCell` /
`PickSun` / `PickDrop`）翻成命令，再交给 `NetplayBattleSync.handle_local_command()` ——
**那是模组唯一的发送出口**（客户端上行请求 / 主机跑成后下行）。

> ★ 为什么要收成一个口：早年上行分散在四处（事件拦截器采点卡 / 点铲子、
> `HandManager.cell_click_gate` 采点格子、`GlobalUtils.sun_click_gate` 采捡阳光、
> `drop_click_gate` 采捡掉落物）—— 每加一种操作就要新开一个本体闸门、还得记得来装它，
> 漏装的那一个正是"闸门装了没人读"的同款坑（装上 ≠ 生效）。现在新增一种操作
> = 多一个枚举值 + 网关里一支 `match`，**没有第二处要改**。

**随机同源**：主机每开一关换一颗种子（`request_battle_seed()` → `sync_battle_seed.rpc`），
两端 `GameRng` 种同一颗 —— "这一波出什么怪 / 落在哪一行"这类抽奖型的随机才会抽到同一份结果。
后加入的人由 `_on_peer_connected()` 补发。

⚠️ **这一阶段同步的是"操作"，不是"状态"**，所以还差一件事（属阶段四）：

1. ~~**实体增删不对齐** —— 客户端点了阳光，它自己那颗阳光已经本地消失（节点在 `sun.gd` 里
   `queue_free()`），数值要等主机回话才加；主机这一侧则**没有**被摘走的那一颗。~~
   **已解决**（§4.8）：阳光有了 `entity_id`，拾取按编号走，两端摘的是同一颗。
2. **客户端的手感有半个 RTT 的延迟** —— 按下到"主机回话"之间本地一动不动（没有预测 / 回滚）。
   （§4.9 的状态广播把"场上长什么样"每帧拉齐，**分叉**治好了，**手感延迟**仍在 —— 那是预测 / 回滚的事。）

### 4.8 阳光同步：**天降 + 向日葵都由主机下发，拾取按编号走**

操作层对齐之后，阳光还是各跑各的：天降是 `DaySunsManagner` 的 `Timer` 摇出来的
（`randf_range` 落点 + `randf_range` 间隔），向日葵是每株一个 `CreateSunTimer`
（首产 `randf_range(3, 12.5)`）—— 两端连"场上有没有这一颗"都对不上；
拾取则更糟 —— `EventBus` 上只有"加了多少点"，说不清"点的是哪一颗"，
主机那一局上被摘走的**不是**客户端点的那一颗。

两步各补一个**闸门 + 观测口**（与 §4.7 的波次同一套，本体只多两个通用问询口）：

```
host   任一生成点 ──▶ SUN_SPAWNED(sun) ──▶ battle_op(sun_spawn: 编号/值/起点/落点/时长)
client              GlobalUtils.sun_spawn_gate 占住：本地一条都不长
                    收到 sun_spawn ⇒ 照着数据在同一处、同样快地长出同一颗

client 点一颗 ──上行 pick_sun(编号)──▶ host 摘掉自己那颗 ──下行──▶ 屋里的每一个人摘同一颗
```

| 要点 | 说明 |
|---|---|
| 落点与时长 | `Sun.spawn_target` / `Sun.spawn_fall`（生成方写入）—— 下发起点 + 落点 + 用时，客户端落在同一处、**掉得一样快**（天降是"距离 / 速度"，向日葵是固定 0.9 秒；客户端自己按速度算会把后者压缩成一闪而过） |
| **★ 生成闸门只有一个** | `GlobalUtils.sun_spawn_gate`，天降与向日葵共用。⚠️ 第一版在天降管理器上另开了一个 `spawn_sun_gate`，模组却只装了全局那个 ⇒ 客户端的天降**根本没被拦住**；探针只验了"闸门装上了"、没验"被谁读"，照样报 PASS |
| 观测口是全局事件 | `ConstEventName.SUN_SPAWNED`（payload `[Sun]`），主机一处订阅盖住所有生成点。⚠️ 由**生成点**在写完落点之后推，**不要**在 `Sun._ready()` 里推 —— 那一刻 `spawn_target` 还是空的 |
| 拾取为什么改成编号 | 只带数值的话，主机只能"加 25 点"，摘不掉自己场上那一颗 —— 两端会各记一笔不一样的账 |
| 拾取走统一上报口 | 本体侧是 `GlobalUtils.submit_player_action(E_PlayerAction.PickSun, [sun])`；网关先问 `NetplaySunSync.is_host_spawned(sun)`（只有**主机下发过的**才上行），再交给 `NetplayBattleSync` 发出去。`ADD_SUN_VALUE` 那条事件说不清"哪一颗"，不再作为操作上报 |
| 本体新增的口 | `GlobalUtils.sun_spawn_gate`（生成，不带联机字样）；拾取那一下走玩家操作的统一口 `GlobalUtils.player_action_gate` |

**阳光生成点全景**（五处，全部已收归主机 —— 少一处客户端就会"被拦掉却收不到下发"）：

| 生成点 | 场合 |
|---|---|
| `DaySunsManagner.spawn_sun()` | 天降（定时器 + 关卡时间轴两条入口） |
| `CreateSunComponent._spawn_sun()` | 向日葵 / 阳光菇 / 双子向日葵（含"我是僵尸"模式） |
| `ZombiquariumManager._on_pet_produce_sun()` | 禅境花园水族馆的宠物产阳光 |
| `BeghouledManager._drop_one_sun()` | 宝石迷阵 |
| `Hammer.spawn_sun()` | 锤子小游戏 |

> ⚠️ 后四处都是"弹起来再落下"同一套表现（弹 -15、落 +45、横向 ±30、0.9 秒），
> 落点与用时收在 `Sun.mark_pop_up()` 一处 —— 改一个忘三个的话，两端就会落在不同地方。
> ⚠️ 别去找"僵尸掉落的阳光"：**不存在**。`DropItemComponent` 只掉金币 / 花园植物 / 巧克力。
> （上一版文档里写过这一条，是没核实的误记，已删。）
| 重放走的还是本体入口 | `Sun.collect()` —— 音效 / 飞向收集点 / 卡槽加数值全都不用模组再抄一遍 |

> 与 `NetplayStateSync`（§4.9，按 `entity_id` 每帧拉齐位置 / 补血 / 回收）**不冲突**：
> 那一位管"现在是什么样"，这一位管"天上掉下来 + 被谁捡走"；两边都以 `entity_id` 为键。
> ★ 而且**快照刻意不碰阳光**：五处生成点已经有主机编号、由命令同步管，
> 快照再插一手只会跟命令打架。

**新增一个生成点时要做两件事**，否则客户端会"本地被拦、主机又不下发" ⇒ 永远不出阳光：
① 生成后调 `Sun.mark_pop_up()`（或自己写 `spawn_target` / `spawn_fall`）；
② 在落点写完之后 `EventBus.push_event(ConstEventName.SUN_SPAWNED, [sun])`。
（`Sun._ready()` 里**不要**推 —— 那一刻 `add_child` 刚触发，生成方还没写落点。）

### 4.10 掉落物同步：**掉不掉、掉哪一种由主机下发**（客户端不掷骰）

"这只僵尸死了掉什么"是一次掷骰：`DropItemComponent` 摇 `randf()` 定掉不掉、再摇一次定
落点，`DIM_Coin` 又摇一次定**掉银币还是钻石**。客户端自己掷，就会掷出另一枚 ——
掉的种类、位置、时机全对不上，两端的钱数各记一笔。

与阳光**完全同一套**（闸门 + 观测口），见 `NetplayDropSync`：

```
host   生成点 ──▶ DROP_ITEM_SPAWNED(drop) ──▶ battle_op(drop_item: 编号/种类/起点/落点)
client            GlobalUtils.drop_gate 占住：本地一件都不掉
                  收到 drop_item ⇒ 照着数据在同一处长出同一枚

client 点一枚 ──上行 pick_drop(编号)──▶ host 收走自己那枚 ──下行──▶ 屋里的每一个人收同一枚
```

| 要点 | 说明 |
|---|---|
| 掉落物也要有编号 | `Coin` / `ChocolateDrop` 加了 `entity_id`（与角色共用 `Character000Base` 那份自增分配器）—— 点一枚金币跟点一颗阳光一样，上行的是**编号**而不是钱数 |
| 种类要下发 | `DropItemManager.E_DropKind`（银 / 金 / 钻 / 巧克力）+ `Coin.drop_kind`：光说"掉了个金币"分不出银币还是钻石 |
| 重建走本体入口 | `DropItemManager.create_drop_of_kind()` —— **一个随机数都不摇**，编号 / 种类 / 起点 / 落点全由调用方给定 |
| 重放走本体入口 | `Coin.collect()` / `ChocolateDrop._on_texture_button_pressed()` —— 音效、飞向钱袋、入账都不用模组再抄一遍 |
| **礼包 `Present` 不归这里管** | 那是解锁道具 / 战利品 / 关卡结算线，时机由**关卡数据**决定（确定性），拾取还要写存档、触发本关结算 —— 拦了会断关卡流程 |

### 4.7 波次同步：**每一波由主机下发，客户端一个僵尸都不自己造**

操作层对齐之后，波次还是各跑各的 `Timer` —— 两端的第一波都不在同一刻来，
"我们在打同一局"这句话只成立一半。这一步把波次也收归主机（见 [联机模组规范](联机模组规范.md) §3.2）。

★ **这一层只下发"演什么"，不下发"出什么怪"** —— 客户端**彻底没有出怪逻辑**：

```
host  start_next_wave() ──▶ wave_started ──▶ battle_op(wave_next: 波次号/大波/升旗) 下行
client                                    ──▶ 只播演出（升旗 +「一大波僵尸正在接近」）
host  场上的僵尸 ────────▶ 每帧快照 ────────▶ client 按 entity_id 补出来（见 §4.9）
```

本体留的两个通用口（都不带联机字样，见 §六-2）：

```gdscript
# zm_zombie_wave_manager.gd
var start_next_wave_gate: Callable = Callable()   # 返回 false = 这一次不许本地开波
signal wave_started(wave: int)                    # 一波已经开起来
```

| 要点 | 说明 |
|---|---|
| ★ 客户端 | **永远不开波**（闸门恒 `false` + `stop_refresh()`），也不造僵尸 —— 僵尸全部由 §4.9 的快照按 `entity_id` 补种 |
| `wave_next` 发什么 | 波次号 + `flag`（升哪面旗，-1 = 不升）+ `big` / `final`（播哪一版演出）。**不带**出怪清单，连 `z_ids` 也一并去掉了 |
| 主机 | 连 `wave_started`，每开一波下发一次；走的还是 `battle_op` 那条可靠下行通道 |
| 进度条 | **走快照，不走命令**（第二包的 `pr` / `ws`）—— 它是**连续量**，开波跳一次之后波次之间还按秒慢慢爬，命令只在开波那一下发，爬升那一段永远差着 |
| ⚠️ 升旗别读 `_flag_to_raise` | 那是**一次性**的（`take_flag_raise_index()` 读走即清），主机抢读了主机自己的旗就升不起来。序号照本体口径自己算：`int(curr_wave % max_wave_one_round / 10.0)` |
| 只接管普通关 | `monster_mode == Norm` 且没有外部出怪器；锤僵尸这类一次性玩法不碰（§1-8） |
| 中途加入 | 进来就开始收快照，僵尸自己补齐，**不用补种子、也不用对齐 `GameRng` 的序列位置** |
| 接线时机 | `NetplayWaveSync.setup()` 里 `call_deferred` 到帧末 —— 模组装在 `zombie_manager.init_manager()` **之前**，那一刻 `monster_mode` 还没赋值 |

**为什么不让客户端照着清单造（而交给快照）** —— 客户端只要还在跑 `start_next_wave()`，
就得一直赌两端的随机序列一致：

1. `GameRng` 是一条**共享序列**，一端多调一次就全串位，而且**没有任何报错**，只表现为两端的怪不一样；
2. `before_wave_spawn()` 让关卡脚本按**场上局势**调出怪密度 —— 两端局势一有偏差，
   连"随机调用了几次"都不同，串得毫无规律；
3. 珊瑚 / 蹦极 / 墓碑伏击那几批"额外生成"根本不在 `wave_spawn` 清单里，**从来就没有下发通道**，
   以前只能靠 `GameRng` 撞运气 —— 它们带 `entity_id`，交给快照后自动覆盖。

代价只有一个：僵尸出现比主机晚约一个 RTT（局域网几毫秒）。
收益是"出怪"整件事彻底归主机，上面三条全部消失。

> 为什么没走"主机下发波次的 `ZombieWaveSourceBase`"：注入出怪器会把**整关怎么出怪**都接管掉，
> 包括关卡脚本覆写的进场方式；而这里只要"**什么时候开下一波**"，
> 一个闸门 + 一个观测口正好，本体其余部分一行都不用改。

### 4.9 状态广播：**主机每帧把"场上现在长什么样"整份广播**

命令同步（§4.6）管的是"**做了什么**"，波次 / 阳光（§4.7 / §4.8）管的是"**什么时候、掉哪一颗**"，
但两端各自的本地模拟（僵尸 AI、啃食、减速、掉血）仍会慢慢分叉。这一层是兜底：
主机每帧采一份快照广播出来，客户端照着对齐，分叉就被抹平了。

```
host   _physics_process ──▶ 采一份快照 ──▶ state_snapshot（unreliable）广播
client 收到 ──▶ 按 entity_id 对齐：缺的补、多的（连续缺席 90 帧）删、位置/血量覆盖
```

| 要点 | 说明 |
|---|---|
| 广播频率 | **每秒 60 次**（控制台「快照频率」滑条可调，1~60）—— 按**时间**攒够一个间隔才发，不是按帧数取模（帧率改了频率不会跟着变）；上限是物理帧率，一帧最多发一次 |
| 为什么 unreliable | 快照是"最新真相"，丢一帧下一帧就补上；重传只会把**旧**数据迟到送到。与 `battle_op`（reliable）正好相反 |
| 编码 | 一律 `Packed*Array`，不用字典数组 —— 30 只僵尸用字典是 3KB，超 ENet 不可靠包的 MTU（约 1400B）会被**整包丢弃** |
| 对齐的键 | `entity_id`；**波次那一批的编号由主机随下发指定**（下面那条） |
| ~~不管阳光~~ **已改：阳光进快照** | 早先的理由是"周岁僵尸掉的阳光两端各自生成、编号不同，对齐会误删"。**这条不成立**：实测 `component_drop_item.gd` 里只有金币 / 花园植物 / 巧克力、**没有阳光**，阳光的 5 个生成点全都过 `GlobalUtils.sun_spawn_gate` 且都推 `SUN_SPAWNED` ⇒ 客户端每颗都有主机编号。命令那条路只管"多一颗 / 少一颗"的**事件**，没有东西纠正"现在场上到底有几颗"，所以交给快照兜底 |
| 不删刚出生的 | 本地有、主机没有的实体要**连续缺席 90 帧**才删，否则主机包还没到，客户端刚出生的僵尸会闪一下 |
| 位置平滑 | `lerp(目标, 0.5)` —— 直接吸附会一格一格跳 |
| **动画状态由主机下发** | 僵尸的动画**整份由主机下发**（`z_anim`）：`is_death` / `is_attack` / `is_swimming` / `is_idle` + `walk_status` / `idle_status` / `death_status` 三个变体。动画由 AnimationTree 的 `advance_expression` **直接读本体这几个字段**（见 `zombie_norm.tscn`），所以写回它们就等价于"照主机演" —— **不必另发明一套动画协议**，也**不需要**在本地跑 AI 才有动画 |
| ⚠️ 连"变体"也要发 | `zombie_norm.gd` 在 `_ready()` 里 `randi_range(1, max)` 各挑一个变体，**两端挑的不是同一个**。两个变体都合法所以不算错，但两端画面不一致 —— 要一致就得发 |
| ⚠️ 变体字段不是每类僵尸都有 | `walk_status` 等只在 `Zombie001Norm` 上（其它僵尸类没有）。读写都走 `_has_prop()` 兜底，`set()` 到不存在的属性会**报错** |
| 7 个字段挤成 1 个 int | 7 条数组 × 4 字节 = 一只 28 字节，而快照贴着 MTU。挤位后一只只占 4 字节。`z_lane` 因此回到**纯行号**，不存在"解错了挂错行"的隐患 |
| 死亡表现由主机触发 | 主机说"它死了"而本地还活着 ⇒ 客户端补一次 `Hp_loss_death(false)`。**植物没有专门的死亡位**，用血量 ≤ 0 推断（再开一条数组要多 256 字节） |
| **★ 客户端僵尸只渲染（完全无行为逻辑）** | 客户端把僵尸的**全部行为组件**用 `E_IsEnableFactor.Netplay` 因素禁用：~~只关 attack / hurt_box~~ → **现在还包括 `move_component`（移动）、`detect_component`（索敌）、`jump_component`（跳跃）、`bomb_component_jackbox`（小丑爆炸）** ⇒ 不索敌、不移动、不啃、不被打、不跳、不爆炸。动画由上面那份 `z_anim` 驱动，所以**关掉判定不会让动画停** |
| ★ **保留的只有表现组件** | `hp_stage_change_component`（血量阶段换外观）/ `charred_component`（焦黑）/ `critical_value_component`（临界掉手掉头）—— 它们由**血量**驱动，而血量是主机下发的 ⇒ 结果一致。`drop_item_component` 不必禁（已被掉落闸门拦住） |
| ⚠️ 可选组件要**探测**再禁 | `jump` / `detect` / `bomb` 只有特定僵尸才有（撑杆 / 跳跳 / 海豚 / 小丑），直接 `z.get()` 取不存在的属性会**报错** ⇒ 走 `_optional_component()`（按**脚本**缓存探测结果） |
| ⚠️ **关掉移动会丢的表现**（这条原则的已知代价） | 移动组件顺带管着屋顶斜面 / 爬梯那部分 y 修正（`move_y_correct_slope` / 爬梯）。客户端的僵尸因此**不走斜面修正** —— 位置本身（含 y）仍是主机下发下来的，缺的只是贴合斜面的那点偏移 |
| ★ **配套：截断必须轮转采集** | 关掉移动后，"收不到位置"就没有任何东西能盖住了 ⇒ 快照截断时下一帧**从没采到的那一只接着采**（`_z_cursor` 游标停在断点上）。不轮转的话每帧都从头采、被截断的永远是排在后面那同一批 ⇒ 那几只在客户端**永远收不到位置、彻底僵住**。轮转后每只最多隔 `ceil(总数 / z_cap)` 帧必被采到一次 |
| ⚠️ 这道闸门必须是**粘的** | `disable_component` 把 Netplay 因素置 false，之后任何人 `enable_component(别的因素)` 都拉不回来（`is_enabling` 是所有因素的**与**）。否则死亡 / 魅惑 / 睡眠这些正常流程会把闸门顶开，客户端又开始自己判定 |
| ★ **不动植物（指判定）** | 植物的开火动画长在攻击组件里，停掉它植物就只剩静止贴图；"客户端不自己造子弹"已由 `GlobalUtils.bullet_spawn_gate` 兜住。但**植物的存亡归快照管**，见下 |
| **★ 快照拆两包** | ENet 不可靠包**不分片**，超 MTU（约 1400B）整包丢弃。植物补进名册、阳光进来之后，满盘一局（僵尸 25 + 子弹 20 + 植物 45 + 阳光 10）约 1900B，一包装不下 ⇒ 拆成 `state_snapshot`（僵尸 + 子弹）与 `state_snapshot_extra`（植物 + 阳光），**各自一份 1300B 预算**。两包独立丢失，丢一包只是那一类这一帧没对齐 |
| **★ 植物进名册（能补种）** | 第二包带 `p_id / p_type / p_cell / p_hp`。早先只发血量，客户端**没法补种** —— 一条种植命令迟到 / 在换关接缝被吞掉，客户端就永远少这一株。现在照名册 `PlantCell.create_plant(type)` 补出来（第三参数关掉种植特效）。**实测效果**：改之前客户端 5 株都对不上（`h=5 c=0`），改完两端 5 株编号完全一致（`max_plant_gap=0`） |
| ⚠️ `place` 不用发 | 槽位由植物自己的种植条件决定（`plant_condition.place_plant_in_cell`），`create_plant(type)` 会放对 |
| ⚠️ 误删会不会抖掉刚种的 | 不会。种植命令是 **reliable**，一个 RTT 内主机快照里就会带上它，而缺席阈值有 90 帧（1.5 秒） |
| **★ 阳光进快照** | 第二包带 `s_id / s_value / s_x / s_y`，客户端照着补 / 删。⚠️ **正在跑下落 tween 的那颗不覆盖位置** —— 命令通道那颗正在演"弹起来再落下"，快照每帧吸附会把它按死在半空；落定后位置才交回快照管。缺席阈值 30 帧（比子弹长、比僵尸短：落地要停十几秒，但被捡走是命令驱动的、客户端收到就立刻摘） |
| **★ 战斗进度条进快照** | 第二包带 `pr`（进度 0~100）+ `ws`（第一波是否已开打），客户端**不自己算**进度（见 §4.7）。⚠️ 主机采的是 `ZombieManager.get_battle_progress()` 这个**通用口径**，不是直接读波次管理器的字段 —— 进度口径可被关卡脚本换掉（外部出怪器 / 僵王血量） |
| **★ 僵王单独一类** | 第一包带 `zb_id / zb_type / zb_x / zb_y / zb_hp / zb_death`。它**不在** `all_zombies_1d` 里（挂在独立的 `%ZombieBossRoot`，`ZombieManager` 明确"僵王不加入普通僵尸列表"）⇒ 照僵尸那套遍历**一只都采不到**，少这一类僵王关（5-10 / 迷你 20）就等于完全没同步 |
| ⚠️ 僵王的**类型必须随快照发** | `ZB000Base` 上**没有任何类型字段**（实测 `z_b_000_base.gd` 里没有），客户端补种时无从知道该造哪一种，只能由主机告诉它。⚠️ 已知限制：取的是关卡参数 `game_para.boss_type`（自动出场那只的类型），**僵王卡牌**召唤出来的那一只若本关没配自动出场就拿不到类型 ⇒ 客户端补种不了（宁可不显示，也不能造错一种） |
| ⚠️ 僵王遍历**根节点**而非 `get_living_bosses()` | 后者会把**已死**的过滤掉，于是主机那只正在演死亡动画的僵王一条都发不出来 ⇒ 客户端永远收不到"它死了"，只能等缺席 90 帧把它凭空删掉，**死亡演出整个丢掉**。所以走 `_boss_list()` 遍历 `%ZombieBossRoot` |
| ⚠️ 补种走**卡牌召唤**入口 | `try_create_boss_from_card(type)` 每次返回新实例；自动入口 `create_boss()` **每关只成功一次**（registry 的 `_auto_boss_spawned` 挡着），客户端补种时那一次早被主机用掉了 |
| **★ 玩家阳光总量进快照** | 第二包带 `sv`。钱包里那个数**不是**"场上飘着的那一颗"：一颗阳光谁捡到都是**各自钱包各加一次**，两端本该始终相等；可它靠一条条 `pick_sun` 命令堆出来，丢一条就**永久分叉**。⚠️ 只在值不同时才写回 —— `sun_value` 的 setter 会遍历每张卡重判"阳光够不够"，每帧白跑不值当。⚠️ 本关没有出战卡槽时**不发**（照默认 `0` 取值会把钱包清零） |
| ⚠️ **卡片冷却刻意不同步** | 两端各有自己的出战卡槽、各点各的卡，**没有任何一个事件会同时影响两端的冷却**，拉平反而打乱玩家自己的节奏。同一个判据下阳光总量属于**战斗域**（一颗阳光两端都加钱，必须一致），而卡槽冷却是**本地域** |

★ **编号必须由主机下发**：两端各自自增分配出来的 `entity_id` 会错位（谁先多生一颗阳光就整体错开），
于是快照会把整波僵尸判成"主机有、本地没有"而**再生成一遍 —— 场上僵尸直接翻倍**。

这一条现在**自动成立**：客户端不再自己开波出怪（§4.7），场上每一只僵尸都是快照补出来的，
补出来那一下就用 `assign_entity_id()` 贴上主机的号 —— 不再需要 `wave_next` 额外带 `z_ids`
（那个参数已随"客户端不出怪"一并去掉）。

> 还剩的（阶段四尾巴）：**暂停语义 / 断线重连**没进快照；僵王的**技能状态机**仍会分叉 ——
> 只同步了位置 / 血量 / 死亡，客户端那只僵王自己 `select_skill()` 选出来的技能与主机的不是同一个。
> ⚠️ **卡槽冷却 / 太阳花费已判定为「不该同步」**（本地域，见上表），不再算缺口。
> 客户端仍在跑自己的战斗模拟（只被快照拉齐，没有预测 / 回滚），所以手感仍有约半个 RTT 的延迟。
> ⚠️ 但**僵尸已经不再是"跑自己的战斗模拟"**了 —— 见上面"客户端僵尸只渲染"：
> 它的判定组件被整体关掉，只按主机下发的动画演。剩下来还跑本地模拟的只有植物与僵尸的移动。

### 4.11 子弹同步：把客户端转成真正"只渲染"的最后一块

踩到的死结：客户端植物若停火 ⇒ 场上**没有豌豆**；若照旧开火而僵尸受击框被禁 ⇒
豌豆**穿过僵尸飞出屏幕**。两头都不对 —— 所以子弹必须纳入同步，
在它进快照之前，"客户端不处理战斗逻辑"这条纪律**不能**真正落地。

工厂已经现成：`Global.bullet_registry.create_bullet(BulletType)`（类型 → 场景，
见 §三），所以快照只要带 `编号 / 类型 / 位置`，客户端就能照着造一颗。

```
host   采快照：b_id / b_type / b_x / b_y
client 收到 ⇒ 按编号对齐：缺的照类型造一颗（create_bullet + init 位置）、位置覆盖、
       连续缺席的删（子弹活得短，缺席阈值可以比僵尸小得多）
```

| 要点 | 说明 |
|---|---|
| ⚠️ 编号不能照抄角色的做法 | `Bullet000Base` 有 **7 个子类重写 `_ready()`**（bowling / cactus / cob_cannon / norm_base / parabola_base / pea_fire / track_base / winter_melon）。在基类加"`_ready()` 里自动领号"会**静默失效**：没调 `super()` 的那一批拿不到编号 ⇒ 不进快照 ⇒ 不同步**且无任何报错**。这正是 §4.8"闸门装了没人读"的同款坑 |
| ✅ 实际做法 | 领号放在**唯一的创建口** `BulletRegistry.create_bullet()` 里（全部 9 处调用方都过这里），一处覆盖、绕开 `_ready()`；客户端随后用 `assign_entity_id()` 改成主机的号 |
| ⚠️ 重建必须绕过闸门 | 客户端自己占着"不造子弹"的闸门，而重建路径也走 `create_bullet()` ⇒ 不绕过就**一颗都造不出来**（场上完全没有豌豆）。故 `create_bullet(type, is_ignore_gate)`，只有 `NetplayStateSync` 传 true |
| 客户端不开火，动画照旧 | 闸门只拦**造子弹**：`AttackComponentBulletBase._shoot_bullet()` 拿不到子弹就返回，但开火动画仍由本地攻击组件驱动。判定与表现不能一起停 —— 停掉攻击组件会连发射动画一起没了 |
| ✅ 字节预算（MTU） | 光靠"条数上限"算不出真实体积：40 只僵尸 + 64 株植物就已经 1472B **超了**。改成按 `BYTE_BUDGET` 先到先得，并给后面的类留保底（否则僵尸一多植物就一条都发不出去 ⇒ 客户端植物永远死不了） |
| ✅ 截断时不回收 | 填不下就截断并打上 `z_cut` / `b_cut`；客户端见到截断**不回收** —— 本地那几颗只是"主机这一帧没采到"，不是"主机那边没有了"。⚠️ 这是**顺手修掉的既有 bug**：加子弹之前，僵尸超过 40 只时客户端就会把多出来的那些误删 |
| 子弹是**木偶** | 客户端造出来的子弹 `set_physics_process(false)`：位置每帧由快照写，它自己不再算飞行与命中。⚠️ 代价：子弹自身的动画 / 旋转（如抛物线的翻滚）不走了 —— 待办 |

> 到这一步，"客户端不处理战斗逻辑"的三样前置（死亡状态、动画状态、子弹）**全部齐了**。
> 剩下真正落下那一刀：把客户端的 `move` / `attack` / `detect` / `hurt_box` 用
> `E_IsEnableFactor` 整体 `disable_component()` —— 实测这四个**都真的检查 `is_enabling`**
> （`ready_show()` 就是靠它让展示僵尸站着不动的）。这一刀留到下一轮，因为它会**改变运行时行为**，
> 得单独验。

### 4.12 出卡同步：传送带流过来的是哪一张，由主机说了算

为什么必须下发：传送带是从**随机池**里抽的 —— `CardRandomPool.get_random_reference()` 用的是
**全局 `randi_range`**（不是 `GameRng`），两端各跑各的，抽出来的**不是同一张卡**。
客户端手里那一张主机没有 ⇒ 点下去主机重放时认不出它（`execute()` 找不到这一张），
这一下操作就**凭空消失**了。

```
host   传送带出了一张 ──▶ `card_created` ──▶ battle_op(card_spawn: 卡的身份) 下行
client 收到          ──▶ `spawn_card_by_reference()` 照着重建同一张
client 自己          ──▶ `create_card_gate` 恒 false，本地一张都不出
```

本体留的三个通用口（都不带联机字样，见 §六-2）：

```gdscript
# card_slot_conveyor_belt.gd / card_slot_seed_rain.gd
var create_card_gate: Callable = Callable()      # 返回 false = 这一次不许本地出卡
signal card_created(reference, index)            # 出了一张卡
func spawn_card_by_reference(reference) -> Card   # 按**指定身份**出一张：不经闸门、也不走随机池
```

| 要点 | 说明 |
|---|---|
| 身份怎么过网络 | `ResourceCardReference.to_dict()` 三个标量（`card_type` / `content_id` / `is_imitater`）直接进 RPC，客户端 `from_dict()` 还原 |
| ★ 只接管传送带 | 种子雨（天降卡）是迷你游戏 04 的**一关专属玩法**，节点由关卡脚本自己挂（`minigame_04_seed_rain.gd`）⇒ 联机不碰（一次性玩法归关卡脚本，硬约束 §1-8）。本体那一侧的通用槽位照样留着，谁想用谁用 |
| 客户端 | `create_card_gate` 恒 false + 出卡定时器一并停掉（双保险）；收到命令才照着重建 |
| 关卡固定顺序照旧 | 关卡配了 `conveyor_order` 的那几张本来就不走随机池、两端天然是同一张 —— 主机照样下发，省得再判一次"这一张要不要发" |
| 接线时机 | 与其它 sync 同一条纪律：`setup()` 里 `call_deferred` 到帧末 —— 传送带卡槽是 `ConveyorBeltController` 现场 instantiate 的，装配那一刻它还没进树 |

> 为什么不是"两端都改走 `GameRng`"：出怪那条线已经证明了"两端各算一遍"的脆弱性
> （共享序列一端多调一次就全串位，而且**没有任何报错**，只表现为两端的怪不一样）——
> 出卡是同一类问题，既然"生成"一律归主机这条纪律已经立起来了，直接归主机更省事。

## 六、边界规则（联机模组同样要守）

1. **本体不 import 模组**：本体只认 `ModManager.is_mod_enabled(ModIds.NETPLAY)`，不出现 `Netplay*` 类名 / 路径。
2. **本体给的是通用槽位**：`GameRng` / `entity_id` / 拦截器 / 出怪器接口 / **`xxx_gate` 问询口**
   （**玩家操作的统一口 `GlobalUtils.player_action_gate`** + `MgmSaveManager.level_success_write_gate`、
   `MainGameManager.choose_card_start_gate`、`ZombieWaveManager.start_next_wave_gate`、
   `GlobalUtils.enter_level_gate` / `sun_spawn_gate` / `drop_gate` / `bullet_spawn_gate`）
   都不带"联机"字样 —— 与
   `PlantCell.move_*`（手套模组用）、`HandComponentBase.E_HandComponentType.Glove`（枚举槽位）同一套路。
3. **模组内部不走 `ConstEventName`**：自己的连线用信号（`session_log` / `command_received` 等）；
   `ConstEventName` 是本体常量表，往里塞联机事件等于本体化。
4. **现场装、随场景灭**：会话挂 root（跨场景存活），每局的同步节点 / 网关在 `install_to_main_game()` 里
   `add_child` 到本局上，随场景一起灭；它们占住的本体闸门（含 `GlobalUtils.player_action_gate`）
   一律在 `_exit_tree()` 里还回去，换局 / 断线都不会漏。
5. **日志一律 `Log.*`**（硬约束 §1-6）。

## 七·五、踩坑（这次真踩到的）

1. **`is_connected()` 撞 `Node` 的引擎方法** —— `NetplaySession extends Node`，而 `Node.is_connected(signal, callable)`
   已存在，写个无参 `is_connected()` 会直接报
   `The function signature doesn't match the parent. Parent signature is "is_connected(StringName, Callable) -> bool"`。
   → **正解**：改名 `is_linked()`。**给挂在 Node 上的类起方法名前，先想一遍引擎有没有同名方法**。
2. **模组在 autoload 的 `_ready()` 里装，`add_child` 会被拒** —— 那一刻 `SceneTree.root` 还在装配子节点，
   报 `Parent node is busy setting up children, add_child() failed`，节点进不了树 → `multiplayer` 与 RPC 全废。
   → **正解**：`tree.root.call_deferred("add_child", node)` 推到帧末再挂。
3. **编译门禁抓不到这两类错误** —— 门禁只编译"被某个资源引用到"的脚本，没人 import 的新脚本会整份漏掉
   （`test/check_scripts.ps1` 头部 KNOWN LIMITATION 1 已写明）。
   → **正解**：新脚本写完就配一个探针跑一遍（或至少在编辑器里看一眼实时下划线）。

## 八、已知风险（做阶段三之前先看）

1. ~~**`MAIN_GAME_CLICK_CARD` 的 payload 是 `Card` 对象**~~ —— **已解决**（§4.6）：命令里换成
   `card_index + plant_type`，重放时用 `NetplayCommand.battle_cards()` 取回那张 `Card` 再推本体的事件。
   顺带修掉一个坑：`card.get_index()` 是 **Node 的兄弟下标**，不是"第几张出战卡"，
   现在一律用 `curr_cards.find(card)`（与 `card_slot_norm.gd` 的口径一致）。
2. ~~**阳光拾取**：`EventBus` 上只有"加了多少阳光"，没有"点了哪一颗"。~~
   **已解决**（§4.8）：阳光也加了 `entity_id`，拾取命令带的是编号 ——
   两端摘的是同一颗，客户端自己长的（向日葵产 / 僵尸掉）没有编号，照单机那样本地生效。
3. **`TreePauseManager` 是全树 `paused`** —— 一端暂停不影响另一端（两个进程），但**主机暂停时客户端会继续跑自己的局面**，
   阶段四的快照要带上暂停语义。
4. **存档**：`Global.global_game_state`（金币 / 通关卡）两端各存各的，先不做跨端同步，避免档案打架。
5. **导出包里 `LevelRegistry` 可能扫到 0 关** —— 编辑器/无头跑是 108 关，某些导出包里却是
   `LevelRegistry: 扫到 0 个内置关卡`（选关页靠节点 `@export` 引用，不受影响，所以平时看不出来）。
   → 房间进关的键值因此**同时带 id 与 path**：id 优先，找不到时退回 path（仍过 `is_level_script()` 白名单）。
   真要根治就去查导出过滤为何漏了 `.gd`，别在业务里写死关卡路径（硬约束 §1-4）。
6. **进关是"整机覆盖"，不是"保存手头的局面"** —— 房主换了关，客端正打着的那一局会被直接切掉，
   没有确认弹窗、也不给回退。有正式 UI 时这里要加"房主正在把大家拉去 X 关"的提示。
7. **卡池仍是各人的存档**（解锁植物 / 卡槽数 / 种子包）—— 双实例实测：拥有 1 张植物时客户端打出
   `种子包不足,跳过选卡阶段: 卡槽数6, 拥有植物卡数1`。**跳过已解决**（§4.2.1）、**重复已避免**（§4.2.2），
   但"这一局用哪些卡"仍各读各的存档 —— 阶段三做主机权威时卡池要由房主下发。
