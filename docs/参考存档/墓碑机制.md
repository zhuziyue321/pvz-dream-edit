## 1. 原版机制速查

| # | 机制                    | 原版行为                                                              | 本仓库落点                                                                                          |
| - | --------------------- | ----------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| 1 | **数量固定**              | 每关开局固定：2-1~2-3=4、2-4=7、2-5=9、2-6=7、2-7=11、2-8=7、2-9=11、2-10=13、生存夜晚=5 | `ResourceLevelData.init_tombstone_num`，`main_game_start()` 生成                                     |
| 2 | **只在最后一大波放伏击僵尸**      | 有墓碑的**每一关**，墓碑都在**最终波**各放出一只僵尸；普通大波不冒                             | `ZombieWaveManager.start_next_wave()` 的 `E_WaveType.Final` 分支 → `call_tombstone_create_zombie()`  |
| 3 | **不是每关都补墓碑**          | 只有「会补墓碑」的关卡（生存夜晚 / 锤僵尸类）在最终波**之前**补一批新墓碑；普通冒险夜晚关卡只有开局那一批           | `ResourceLevelData.is_tombstone_respawn`（生存夜晚 = true，2-x = false）                                |
| 4 | **位置 = 草坪右侧三分之二**     | 只长第 4~9 列（0 基列 3~8）；右侧长满后才轮到左三列。**不长在坑洞上**                        | `TombStoneManager._reandom_tombstone_pos()` / `_candidates_position()`                           |
| 5 | **格子被占：只能种墓碑吞噬者**     | 墓碑格不能种普通植物；啃完清除，啃到一半被吃掉会复原                                        | `PlantCell.curr_special_state_plant[IsTombstone]`、`plant_grave_buster.gd`                    |
| 6 | **清除后掉钱**             | 掉一个银币（$10），偶尔掉更值钱的（金币 / 巧克力 / 钻石 / 禅境花园植物）                        | `tombstone.gd::tombstone_death()` → `EventBus "create_coin"`                                     |

补充细节（同源）：

- 伏击僵尸种类只有**普通 / 路障 / 铁桶**三种（wiki "The only zombies that are possible to come out of them are the Zombie, the Conehead Zombie and the Buckethead Zombie"）→ 本仓库 `ZombieWaveManager.zombie_type_candidate_tombstone`（场景里配成 `[1, 3, 5]`）。
- 僵尸从墓碑出来后**墓碑仍在**（墓碑不会被消耗）。
- 锤僵尸关（冒险 2-5「打地鼠」/ 迷你游戏 Whack a Zombie）是**另一套**：墓碑持续放僵尸，每大组结束补墓碑（<5 补到 5，否则 +1），只长第 4~9 列 → 本仓库由 `HammerZombieManager` 管，不走 `ZombieWaveManager`；该出怪器不再常驻主场景，
由这关的玩法规则装配进 `ZombieManager`（见 [特殊关卡.md](特殊关卡.md) 与 `LevelRuleHammerZombie`）。

## 2. 本仓库的开关与调用链

```
关卡脚本 _init()                       init_tombstone_num / is_have_tombston / is_tombstone_respawn
      ↓
main_game_manager.main_game_start()    开局按 init_tombstone_num 生成墓碑
      ↓ PlantCellManager.create_tombstone
TombStoneManager.create_tombstone()    位置 = 右侧 2/3 草坪，跳过已有墓碑与坑洞
      ↓
ZombieWaveManager.start_next_wave()
      ├ Final 波（curr_wave == max_wave-1）且 is_have_tombston → call_tombstone_create_zombie()
      └ Flag 波（生存夜晚 is_tombstone_respawn）                → call_tombstone_create_zombie()
             ├ is_tombstone_respawn：先 push "create_tombstone"（补 1~3 个），等 1 秒
             └ 遍历 tombstone_list，每个墓碑 create_new_zombie()
```

关键判据：

- **「最终波」是 `curr_wave == max_wave - 1`**（`E_WaveType.Final`）。生存模式每结束一轮 `max_wave += max_wave_one_round`，所以**每轮都有自己的最终波**。
- **为什么生存夜晚要在 Flag 波也触发**：生存模式一轮里「每 10 波的最后一个大波」就是那一轮的最终波；而冒险 20 波关卡（2-2 / 2-4 / 2-7 / 2-9 / 2-10）的第 9 波只是普通大波，**原版不冒僵尸**，所以只有 `is_tombstone_respawn` 的关卡才在 Flag 波触发。

## 4. 改这里要过哪些回归

- 探针：`powershell -ExecutionPolicy Bypass -File test/run_autopilot.ps1 -Scenario probe_night -Windowed`
  → STEP1 逐关核对开局墓碑数 / 是否中途生长 / 波数，STEP3 实机进 2-1 看墓碑数，STEP4 墓碑种植判定，STEP6 生存夜晚三个关卡的墓碑开关。输出 `[NIGHT] result=PASS`。
- 探针：`-Scenario probe_hammer_spawn_trace -Windowed`（输出 `[HAMMERTRACE] result=PASS`）
  → **锤僵尸关改造必跑**。它按 2 秒一格打点 `wave/小组、墓碑数(忙碌数)、累计出怪数`，
  能看出出怪器有没有推进。**「只出第一组僵尸然后整局停摆」这类故障，`probe_hammer_zombie` 是抓不到的**
  （那条探针只验「25 秒内出现过僵尸」和「清场出奖杯」，第一组僵尸就够它过）。
- 探针：`-Scenario probe_tombstone_respawn -Windowed`（输出 `[TOMBSPAWN] result=PASS`）
  → 墓碑出怪可用性：手工驱动一块墓碑，出怪 → 冒头途中把僵尸打死 → 验这块墓碑还能再出一只。
- 人工：进 2-1（4 个墓碑）打到最后一波，看「一大波僵尸正在接近」后每个墓碑各冒一只僵尸；中途大波（2-2 这类 20 波关的第 9 波）**不冒**。
- 人工（锤僵尸关）：进迷你游戏 15，不开挂、纯看，**应该**持续不断地从墓碑冒僵尸，每 10 小组停一次并多一块墓碑；
  若墓碑数量在涨、但僵尸不再冒，就是出怪循环断了。

## 5. 踩坑

### 5.1 运行期 instantiate 的出怪器，Timer 信号不一定还在

`HammerZombieManager` 场景里只有一个 `HammerZombieTimer` 子节点，**没有连 `timeout` 信号**
（`zm_hammer_zombie_manager.tscn` 里连 `[connection]` 段都没有），而 `_ready()` 也没 `connect`。

后果：`start_first_wave()` 手动调一次 `_on_hammer_zombie_timer_timeout()` 出一小组僵尸，
之后 `hammer_zombie_timer.start()` 触发的 timeout **没有任何接收者**，整局再也不出怪 ——
墓碑完好无损地立在那儿，一只都不冒。这在 `probe_hammer_zombie` 上是**全绿**的，只有 `probe_hammer_spawn_trace`
那种按时间打点的观测才看得出来（`wave/小组` 永远停在 `0/0`）。

修复写在 `_ready()` 里显式 `connect`（不要指望去改 `.tscn`：出怪器本来就是运行期 instance 出来的，
显式连接更抗改）。**同理 caution：凡是「场景 + 代码」两处协作的定时器，先确认信号真的连上了。**

### 5.2 别用「协程跑完没有」判断墓碑占用

`TombStone.create_new_zombie()` 早先靠 `await new_zombie.zombie_up_from_tombstone()` 收尾把 `new_zombie` 置空，
用 `if not new_zombie` 判断墓碑空不空。冒头表现会 await 到 body 节点上的一个 tween，
僵尸在冒头途中被销毁时那个 tween 随之消失、**finished 不会发**，协程**不再返回**，收尾那句就到不了。

实测：僵尸 `queue_free()` 后引用变成「已释放对象」，`is_instance_valid()` 转 false，
所以墓碑**不会**永久锁死 —— 但解锁时机取决于何时销毁，**不该**依赖它。
现在改成 `is_creating_zombie()` 实时判定（僵尸还在树上且没死 = 占用），不再依赖协程收尾；
返回 bool 让调用方知道这一只到底放没放出去。

连带：`HammerZombieManager.create_one_group_min_zombie()` 以前是在所有墓碑里 shuffle 后取前 N 个，
抽到正在冒头的那块会被**静默跳过**（日志一行 debug），本组实际出怪数比配置少；
现在只从空闲墓碑里挑，并且 `await` 它（内部没墓碑时会先补墓碑等 2 秒）。
