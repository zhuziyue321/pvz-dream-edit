# 重构拆分方案（场景 / 脚本）

> **[面向 AI Agent]** ｜ **触发条件**：准备对某个 `.gd` 或 `.tscn` 做**重构 / 拆分 / 提组件**之前；或有人问「这块代码该拆成什么样」
> **读完你能**：①知道全仓 356 个 `.gd` / 212 个 `.tscn` 里哪些是真胖子、哪些只是数量多；②拿到每个候选的**具体拆分动作 + 边界 + 风险**；③沿用仓库既有拆分范式（`xxx_manager/xx_*` 子目录 + `MainGameSubManager` 抽象基类）而不是自创一套
> **强制级别**：**参考**（不做也不打回） ｜ **不读的风险**：拆错方向（把数据表拆成代码、把 `.tres` 依赖打断、拆完跑不起来）
> **关联**：硬约束 [../项目规范.md](../项目规范.md) §1 ｜ 组件化细则 [规范细则存档.md](规范细则存档.md) ｜ 验证 [../验证流程.md](../验证流程.md) ｜ 组件清单 [杂项存档.md](杂项存档.md)

> 本文是**分析 + 方案**，不是规范。所有「建议」都按批次独立可交付，拆一个验一个。

## 2. 仓库既有拆分范式（必须沿用，不要自创）

1. **子目录 + 前缀**：`zombie_manager/zm_*`、`game_item_manager/gim_*`、`drop_item_manager/dim_*`、`hand_manager/component/hand_component_*`。
2. **父管理器当调度器**：父脚本 `@onready var x: X = $Child`；子脚本 `extends Node`、不持有 `game_para`，通过 `owner` / `%UniqueName` 取主引用。
3. **抽象基类**：需要统一生命周期的子管理器 `extends MainGameSubManager`（`src/managers/main_game_sub_manager.gd`），在 `_enter_tree` 解析 `main_game`，实现 `@abstract init_manager()`。
4. **节点挂点**：`src/main/main_game_base.tscn` 的 `Manager` 树下加子节点；按需场景运行时 `new()` + `manager.add_child()`（`main_game_manager.gd:51-53` 就是这么加 TutorialManager 的）。
5. **动画外置**：`animation/character/{plant,zombie}/*.tres` 已有 469 个，内联动画是**历史遗留**，不是约定。

## 5. 每次拆分的 SOP

1. **先确认它不是数据表**：`level_data.gd` / `character_registry.gd` 这类「行数大但都是数据」的，拆前先问一句收益。
2. **沿用 §2 的范式命名**，不新开目录结构；新组件挂到对应 `src/entities/character/components/` 或 `Manager` 子树。
3. **只准加引用方式，不准删**：老方法保留 1-2 个版本做转发，或者一次性全局替换后跑一次全仓 `grep`。
4. **移动 / 重命名连 `.uid` 一起走**，且**必须先关 Godot 编辑器**（硬约束 §1-5）。
5. **验证**：按 [验证流程.md](../验证流程.md) §1 判定。涉及玩法行为 → 打开游戏带窗口实测（[AI调试通道.md](../AI调试通道.md)）；只挪文件不动逻辑 → 可免验证，但反馈里写清人工验证方法。
6. **收尾**：行为或约定变了同步改文档；踩坑按 E-04 即时沉淀；按 E-05 在 [工作记录/](../工作记录/README.md) 建一条记录 + 索引补行。

**三条推翻原文的结论（做的时候才发现）**：

1. **「手套搬运 / 特殊状态拆成子模块」这条从方案里划掉** —— 见 B3 的理由。判据：一段代码如果**只操作宿主自己的字段**，就别拆成节点。
2. **别去统一子弹里的 `get_first_be_hit_plant_in_cell`** —— `bullet_parabola_base` 是 Norm > Shell > Down，`bullet_linear_base` 是 Shell > Norm > Down，顺序不同（可能是有意为之，也可能是 bug），合并会改行为。已在 `detect_target_strategy.gd` 头部写了「不要合并」的警告。
3. **僵尸 / 罐子这类「宿主状态很重」的块，用 static util 而不是组件节点** —— 26 个僵尸场景要挂组件就得逐个改 `.tscn`，代价远大于收益；而且 GDScript 没有 partial class，状态搬不出去时组件只能 `get_parent()` 回头改宿主。static util + 显式传 `self`/`pcm` 是这条约束下唯一不动场景的拆法（B4/B5/B6 统一用这个模式）。

**踩坑**：

1. 新建 `.gd` 后必须跑一次 `--headless --import`，否则 Godot 报 `Could not find type "XXX"`（全局类来自 `.godot/global_script_class_cache.cfg`）。
2. **删大块代码后要 grep 一遍被删函数的名字** —— 依赖它们的调用点可能藏在别处（`B6` 漏了 `start_next_game_plant_cell_manager_update()` 里的一处 `init_plant_cell_row_on_zombie_row_type()`，import 才报出来）。ripgrep 结果超过上限会被截断，**被截断时换个更窄的 pattern 再查一次**。
3. GDScript 的 lambda 对外部局部变量是**值捕获**：`func(): flag = true` 改不到外面的 bool，探针里要用字典当盒子回传，否则会假失败。
4. `SceneTreeTimer` 不随节点释放而取消：把「等 0.5 秒再做事」换成绑在节点上的 `Tween` 后，节点被 `queue_free` 时整条 Tween 一起被杀，不会再出现「对象已释放还去改它」的报错。
