## 1. 目录结构（参考）

### D-01 目录与文件命名

**适用范围**：全项目新增的文件与目录名。

**要求**

- **建议**全小写 snake_case，单词间下划线。
- **建议**不出现大写字母、空格、中文，例外仅限：
  - 约定俗成的文档名：`README.md`、`LICENSE`；
  - `docs/` 下的中文文档名；
  - `data/levels/params/` 下的中文关卡名（该名字会显示给玩家）。

**正例**：`src/entities/character/components/hp_component/component_hp.gd`

**反例**：`src/Character/Components/ComponentHP.gd`、`docs/新 规范.md`

**自动检查**：无（靠评审；改名后按 [M-01](#m-01-res-引用与改名) 全文搜 `res://` 确认）。

### D-02 编号前缀（已废弃：编号是注册表 id，不写进文件名）

**适用范围**：同类成组资源（角色、子弹、关卡、主场景）。

**要求**：**建议**文件名**只写语义名，不带数字编号前缀** —— 编号属于注册表（`CharacterRegistry` / `BulletRegistry` / `MainSceneRegistry`），不是文件名的一部分（2026-10-03 全量去前缀）。

| 类型  | 命名模板                | 实例                                                                    |
| --- | ------------------- | --------------------------------------------------------------------- |
| 植物  | `plant_<name>`      | `plant_pea_shooter_single`、`plant_imitater`                           |
| 僵尸  | `zombie_<name>`     | `zombie_norm`、`zombie_winter_melon`（僵王不是僵尸角色，例外叫 `zombie_boss`）      |
| 子弹  | `bullet_<name>`     | `bullet_pea`、`bullet_bowling`                                         |
| 关卡  | `<模式>_<关卡编号>_<名>`   | `adventure_01_01`、`minigame_02_bowling`（这里的编号是**关卡号**，要显示给玩家，保留）      |
| 主场景 | `<name>`            | `start_menu`、`store`、`main_game_base`                                 |

> 反例：`plant_pea_shooter_single.gd`、`start_menu.tscn`、`animation/character/plant/011_fume_shroom/`。
> 例外：需要**顺序**或**显示给玩家**的编号才保留（关卡号、教程步骤 `step_01`、对话 `opening_000`）。

### D-03 顶层目录职责

| 目录                            | 职责                                                    |
| ----------------------------- | ----------------------------------------------------- |
| `addons/`                     | 第三方插件。**不修改、不参与本规范**                                  |
| `animation/`                  | R2Ga_PVZ 转换出的动画资源，按 `character/plant\|zombie/<角色名>/`、`item/`、`garden/` |
| `assets/`                     | 图片、音频、字体、reanim 等美术素材（版权原因不在仓库中）                      |
| `data/`                       | 数据层：`.tres` 资源及其资源脚本 `.gd`（`character/` `map/` `dave/` `save/` `ui/` `almanac/` `strings/` `levels/params/`） |
| `docs/`                       | 说明文档（`docs/images/` 放 README 展示图）                      |
| `shaders/` `shaders/materials/` | 着色器与材质                                                |
| `src/`                        | **代码与场景的唯一根目录**：`.gd` 与 `.tscn` 按功能就近放置（见 D-04）        |
| `test/`                       | 自动回归探针与调试通道                                           |
| `tools/`                      | 仓库外工具脚本（`.ps1`，非 Godot 资源，如 `merge_alpha.ps1` 离线烘焙蒙版） |

### D-04 src/ 的组织方式

**要求**：**建议**按功能域分目录，**同一功能的 `.gd` 与 `.tscn` 放同一个目录**（不再分 `scripts/` 与 `scenes/` 两棵平行树）。

| `src/` 子目录                | 内容                                              |
| ------------------------- | ----------------------------------------------- |
| `core/`                   | `autoload/`（单例 + 类型注册表）、`consts/` 全局枚举常量、`utils/` 工具 |
| `entities/`               | `character/`（base / components / plant / zombie）、`bullet/` |
| `levels/`                 | 内置关卡（`mode_adventure/` `mode_minigame/` `mode_puzzle/` `mode_survival/`）+ `core/` 基类与时间轴 |
| `managers/`               | 主游戏各子管理器（波次、卡槽、手持物、格子、掉落）                       |
| `ui/`                     | 界面（卡片 / 卡槽 / 金币 / 关卡内 HUD / 菜单）                 |
| `world/`                  | `background/` 背景、`camera/` 相机                   |
| `main/`                   | 主战斗场景入口 `main_game_base.tscn`                   |
| `menus/`                  | `start_menu/` 主菜单、`choose_level/` 选关            |
| `items/` `fx/` `garden/` `store/` `almanac/` `dave/` | 按功能分目录（道具、特效、禅境花园、商店、图鉴、疯狂戴夫） |

> 新增功能域时**可以**在 `src/` 下新建一个功能目录，`.gd` 与 `.tscn` 同置（**参考**）；分成两个平行目录也能跑，只是找文件要多搜一次。

### D-05 组件的落位

**适用范围**：所有 `*Component` 脚本。

**要求**

- **建议**放在 `src/entities/character/components/<功能域>_component/` 下，一个组件一个目录：
  - 功能域单一、只有一份实现 → 直接 `src/entities/character/components/component_xxx.gd`（如 `component_sleep.gd`）；
  - 有多份变体（基类 + 子类）→ 建目录 `<功能域>_component/`，文件 `component_<功能域>.gd` + `component_<功能域>_<变体>.gd`。
- **建议**让 `src/` 侧有对应位置：组件作为**子节点**挂在角色 / 管理器场景里。

**正例**（多变体）

```
src/entities/character/components/attack_behavior_component/
├── component_attack_base.gd              # class_name AttackComponentBase
├── component_attack_bullet_base.gd       # class_name AttackComponentBulletBase
├── component_attack_bullet_split_pea.gd  # class_name AttackComponentBulletSplitPea
└── component_attack_zombie_norm.gd       # class_name AttackComponentZombieNorm
```

**反例**：把 `component_attack_bullet_split_pea.gd` 丢在 `src/entities/character/plant/` 里 —— 组件与角色脚本混层，复用与查找都会退化。

### D-06 data/ 的组织方式

**要求**：**建议**每种资源一个目录，**资源数据（`.tres`）与其脚本（`.gd`）同目录**（不再单独建 `script/` 子目录）。

```
data/
├── character/              # 角色属性：plant_condition/ 种植条件、body_change/ 掉血掉头外观
├── map/                    # 地图资源 ResourceMapData + 脚本
├── dave/                   # 戴夫对话：dialog/ 剧本 + dialog_detail/ 台词
├── save/                   # 存档资源
├── ui/                     # Theme 主题、卡片背景 card_bg/、按钮样式 button_styles/
├── almanac/                # 图鉴数据 almanac_data.json
├── strings/                # 文案表 lawn_strings.txt
└── levels/params/          # 玩家可见的自定义关卡参数（ResourceLevelData）
```

> 植物种植条件资源**建议**位于 `data/character/plant_condition/` —— 这是被代码路径依赖的硬约束。
> 内置关卡不在 `data/` 下，见 `src/levels/`。

### D-07 关卡脚本 vs 游戏本体（一次性机制的落位）

> 带 ※：本卡片与硬约束 [§1-8](../项目规范.md) 重叠，**「一关专属机制不进本体」那部分是硬约束**，其余（上浮顺序、怎么写）是参考。

**适用范围**：新增 / 修改「只有某几关才有」的机制 —— 专属胜利与失败判定、专属场地物品、专属格子限制、一次性演出、只在这一关出现的敌人编排。

**术语**

| 词 | 指 |
|---|---|
| **游戏本体** | 与具体关卡无关的系统代码：`src/managers/`（含 `main_game_manager.gd`）、组件、角色、UI、注册表。**本体不认识任何具体关卡 id / 玩法名** |
| **关卡脚本** | `src/levels/mode_*/<关卡>.gd`，继承 `LevelScriptBase`：**一关 = 一个 `.gd`（属性 + 流程）**，见 [关卡格式V2.md](关卡格式V2.md#32-逃逸层level_script-钩子p2) |

**判据：这个机制被几关用**

| 复用面 | 落位 |
|---|---|
| 只 1 关用 | **必须**写在关卡脚本里 |
| 2~3 关用、且形态不稳定 | **建议**仍留在各关脚本（允许少量重复），或抽成时间轴事件 / prefab 由关卡脚本调用 |
| 一整类玩法都在用（传送带 / 砸罐子 / 锤僵尸 / 僵王 / 保龄球…） | 才上浮进本体：关卡数据字段 + 枚举（`ConstLevelData`）/ 组件 / 规则层 `rules[]` |

> 宁可在关卡脚本里重复一段，也**不建议**为了让代码「不重复」提前把它抽象进本体 —— 抽象错了就是往通用代码里钉死一条只服务于少数关卡的分支。

**一关不止一个脚本时：落位与命名（必须）**

一关**只有一个脚本是关卡本体**（`mode_*/<关卡>.gd`，继承 `LevelScriptBase`）。其余只服务这一关的脚本（场景节点 / 绘制层 / UI / 进度条数据源 / 一次性演出）**必须**：

1. 与关卡本体脚本放在**同一个 `mode_*/` 目录**下 —— 不进 `core/`、也不另开子目录；
2. **文件名以关卡本体的文件名为前缀**（关卡 `minigame_07_seeing_stars.gd` → `minigame_07_seeing_stars_progress_provider.gd`）。

**正例**

```
src/levels/mode_minigame/minigame_07_seeing_stars.gd                    # 关卡本体
src/levels/mode_minigame/minigame_07_seeing_stars_progress_provider.gd  # 本关进度条数据源
```

**反例**

```
src/levels/mode_minigame/seeing_stars_progress_provider.gd  # 看不出属于哪一关
src/levels/script/mini_game/beghouled/xxx.gd                # 与关卡本体分家，找文件要猜
```

> **被 ≥2 关共用的不算「某一关专属」**：这时不硬套关卡名前缀，按玩法分子目录放进 `src/levels/core/<玩法>/`
> （先例 `core/zomboss/`，现有 `core/beghouled/`、`core/hammer_zombie/`）；只有 1 关用才按上面两条进 `mode_*/`。

> 前缀只是**给人看**的约定，不是识别依据：注册表认关卡**只认继承链**（见下），
> 带前缀的辅助脚本不会被误登记成假关卡；反过来也别指望「名字像关卡」就能被扫进表。

**关卡的识别：白名单（不是前缀黑名单）**

`LevelRegistry` 扫 `src/levels/` 下的 `.gd`，判据是**白名单**：沿 `get_base_script()` 链往上走，
继承链上出现 `LevelScriptBase` / `ResourceLevelData`（常量 `LEVEL_BASE_CLASS_NAMES`）**才是关卡**，
其余一律不登记 —— 见 [关卡格式V2.md §3.4](关卡格式V2.md#34-关卡注册表-levelregistryp0-已落地)。

- **不**按文件名前缀判：辅助脚本按上面的约定**也带关卡名前缀**，前缀分不出「关卡」与「辅助脚本」。`mode_adventure/adventure_05_05_bungi_blitz.gd`（`extends Node`）以前正是被前缀判据误登记成假关卡的。
- **不**用 `get_instance_base_type()` 判：它返回的是**原生**基类（关卡脚本一律是 `Resource`），要认的是脚本链上的 `class_name`。

**关卡脚本里能写什么**（`LevelScriptBase` 的三个落点）

```gdscript
func _init() -> void: ...                              # 本关属性：出怪表 / 卡槽 / 地图 / 阳光 / 模式枚举
func run_flow(mg: MainGameManager) -> void: ...        # 本关流程：await 串基类上的流程方法，if/for/while 随便用
func init_level_items(mg, item_root) -> void: ...      # 本关专属场景物品 / 给格子打规则标记
func get_zombie_init_para_extra() -> Dictionary: ...   # 本关给僵尸的额外初始化参数（E_ZInitAttr → 值），由 ZombieManager 并表
is_curr_level_success() -> bool: ...                   # 快捷工具：本关有没有通关过（查本关存档 IsSuccess）
is_level_success(关卡存档名) -> bool: ...               # 快捷工具：按存档名查某一关有没有通关过
```

**正例**

- 僵王生成：整体搬成时间轴事件 `LevelTimelineEventSpawnZomboss`，由 `adventure_05_10.run_flow()` 调用 —— 本体只保留「跑时间轴」这一件事（2026-10-03 已这么做）。
- 观星的星星轮廓这类专属物品：走 `init_level_items()`，不在 `gim_other.gd` 里加分支。
- 迷你游戏 06「隐形战争」的僵尸隐形：走 `get_zombie_init_para_extra()` 返回 `{ E_ZInitAttr.IsInvisible: true }`，
  `zombie_manager.gd` 里只有一行「并表」，不出现玩法名（2026-10-04）。

**反例**

```
gim_other.gd          if is_seeing_stars: ...          # 通用物品管理器里出现具体玩法名
main_game_manager.gd  match level_id: "adventure_05_10": ...   # 本体里出现关卡 id
zombie_manager.gd     加一条只有 5-10 才走的出怪分支
```

**自检**：改完在 `src/` 下全局搜本关 id 字符串 / 玩法名 —— 只要出现在 `src/managers/`、`entities/`、`ui/` 里，就说明机制漏进本体了。

**上浮顺序**（真要上浮时，从轻到重选最前面的够用项）

1. 关卡脚本内部私有函数 → 2. 时间轴事件脚本（`src/levels/core/timeline_event/`）→ 3. `LevelScriptBase` 上的流程方法 → 4. 关卡数据字段 + 枚举 → 5. 组件 / 角色 / 注册表 → 6. `rules[]` 规则层

## 2. 组件化开发规范（参考）

> 本项目的**主扩展手段是组件组合，不是继承**。  
> 角色根节点只保留：基础属性、动画、body、以及与本体高度耦合无法拆分的特殊功能  
> （土豆雷准备、大嘴花吞噬、魅惑），**其余一律做成组件**。

### K-01 组件的定义与边界

**适用范围**：任何准备写成组件的功能。

**要求**

- **建议**满足「可独立增删」：把组件节点从场景里删掉，角色应仍能运行（只是失去该能力），不宜空引用崩溃。
- **建议**单一职责：一个组件只回答一个问题（移动 / 血量 / 检测 / 睡眠…）。出现"顺便也管一下 X"就可以拆成第二个组件。
- **建议**自持状态：组件自己的状态（`is_sleeping`、`curr_be_attack_status`…）由组件内部维护，**宿主不宜直接改**。
- **可以**对宿主暴露「只读转发属性」。宿主给外部读的状态用 `get` 转发，不复制字段：

```gdscript
## plant_base.gd —— 宿主只做转发，状态本体在组件里
## 是否正在睡觉（由睡眠组件拥有）
var is_sleeping: bool:
	get:
		return is_instance_valid(sleep_component) and sleep_component.is_sleeping

## 是否在花园水族馆（由花园组件拥有）
var is_garden_aquarium: bool:
	get:
		return is_instance_valid(garden_component) and garden_component.is_garden_aquarium
```

**反例**

```gdscript
## ❌ 宿主自己存一份，和组件里的状态各自演化，两边迟早不一致
var is_sleeping := false
func _on_sleep_started() -> void:
	is_sleeping = true          # 组件里也有一份 is_sleeping
```

**为什么**：副本状态是这类项目最贵的 bug 来源 —— 症状是"看起来没睡但动不了"，排查成本极高。

### K-02 组件基类与命名

**适用范围**：所有组件脚本。

**要求**

| 项            | 规定                                                                                              |
| ------------ | ----------------------------------------------------------------------------------------------- |
| 基类           | **建议**继承 `ComponentNormBase`（`src/entities/character/components/component_norm_base.gd`），或继承其已有的抽象子类 |
| `class_name` | **建议**包含 `Component`，两种合法形式二选一；**建议** PascalCase                                                |
| 文件名          | **建议** `component_<功能域>[_<变体>].gd`                                                              |
| 节点名          | **建议**与 `class_name` 同名（便于 `%` 唯一名引用与编辑器里辨识）                                                    |
| 抽象           | 不直接实例化的基类**建议**标 `@abstract`                                                                    |

**`class_name` 的两种合法形式**

| 形式                       | 何时用                 | 实例                                                                             |
| ------------------------ | ------------------- | ------------------------------------------------------------------------------ |
| 后缀式 `<功能域>Component`     | 该功能域只有一份实现，或变体用后缀区分 | `SleepComponent`、`HpComponentPlant`、`GardenComponentSprout`                    |
| 前缀式 `<功能域>Component<变体>` | 同族变体多、后缀容易被压扁成一长串   | `AttackComponentBulletSplitPea`、`BombComponentJalapeno`、`AnimComponentBobsled` |

> 同一功能域内部**建议**统一，不要 `AttackComponentBulletBase` 与 `BulletAttackComponent` 混用。

**正例**

```gdscript
# 后缀式：src/entities/character/components/component_sleep.gd
extends ComponentNormBase
class_name SleepComponent

# 前缀式：src/entities/character/components/attack_behavior_component/component_attack_zombie_norm.gd
class_name AttackComponentZombieNorm

# 抽象基类
# src/entities/character/components/component_norm_base.gd
@abstract
extends Node2D
class_name ComponentNormBase
```

**组件目录里的非组件脚本**：`drop_body/`、`iron_node/` 这类辅助节点脚本不是组件，  
不受上述命名约束（如 `ZombieDropBase`、`IronNode`、`JacksonStateMachine`），  
但**可以**在文件头注释里写明「本文件不是组件」，避免被误当成组件改名。

**`ComponentNormBase` 提供的统一能力**（不要重复实现）

- `is_enabling` / `is_enable_default`：启停总闸。
- `E_IsEnableFactor` 枚举：**建议**用它说明"为什么被禁用"（`Sleep`、`Scaredy`、`Death`、`HandItem`…）。
- `enable_component(factor)` / `disable_component(factor)` / `change_is_enabling(value, factor)`：多因子独立记账，任一因子为 false 即整体禁用。
- `owner_update_speed(speed_product)`：宿主改速度时统一回调，组件按需重写。

**反例**：组件自己写 `var is_active := true` 做启停 —— 绕过了多因子机制，睡眠解除后会错误地把"因死亡禁用"的组件一起打开。

### K-03 组件通信方式

**适用范围**：组件之间、组件与宿主之间。

**要求**：**建议**只用下面几种方式，**不宜**发明新的（尤其不建议向下改宿主私有字段）。

| 方式                         | 何时用                      | 方向                |
| -------------------------- | ------------------------ | ----------------- |
| **A. 组件内自洽**               | 只影响自己的逻辑                 | 组件内部              |
| **B. 内建 `owner` 反向引用宿主**   | 组件需要读宿主属性 / 调宿主方法、访问兄弟节点 | 组件 → 宿主           |
| **C. 信号**                  | 事件通知（"我睡着了""我开始攻击了"）     | 组件 → 宿主 / 其他组件    |
| **D. `@export` 引用 + 公开方法** | 配置与协同（"我影响这些组件"）         | 宿主 → 组件 / 组件 → 组件 |
| **E. `EventBus`**          | 跨模块、不关心谁在听的事件            | 任意 → 全局           |


**A. 组件内自洽**

```gdscript
# component_sleep.gd —— 睡眠状态、动画、判定全在组件里，宿主不参与
func start_sleep() -> void:
	is_sleeping = true
	visible = true
	anim_sleep.play("zzz")
	signal_is_sleep.emit()
```

**B. 反向引用宿主 —— 一律用内建 `owner`，不用 `get_parent()`**

```gdscript
# component_move.gd —— owner 是 Godot 内建的"场景根"，节点被 reparent 也不会断
@onready var owner_zombie: Zombie000Base = owner

# component_hp.gd
@onready var owner_character: Character000Base = owner

# component_detect.gd —— 用 owner 的类型分支决定检测层
if owner is Plant000Base:
	update_curr_collision_lay(1)
elif owner is Zombie000Base:
	update_curr_collision_lay(2)
```

> `get_parent()` **只允许**用于「真的要脱离宿主 / 挂到宿主父节点」的场景，  
> 例如 `component_charred.gd` 的 `reparent(owner_character.get_parent())`。

**C. 信号 —— 组件发、宿主连**（连接位置见 [K-05](#k-05-组件信号连接)）

```gdscript
# component_sleep.gd（组件侧：只声明 + emit，不关心谁听）
signal signal_is_sleep
signal signal_not_is_sleep
```

**D. `@export` 引用 + 公开方法 —— 需要"被谁影响"时用导出数组，避免组件写死路径**

```gdscript
# component_sleep.gd：睡眠影响哪些组件由场景里配置，组件自己不认识它们
## 睡眠影响的节点,在植物本体中调用 judge_is_sleeping() 使对应节点 disable
@export var sleep_influence_components: Array[ComponentNormBase]
```

```gdscript
# plant_base.gd：宿主做"接线员"
for sleep_influence_component in sleep_component.sleep_influence_components:
	sleep_component.signal_is_sleep.connect(
		sleep_influence_component.disable_component.bind(ComponentNormBase.E_IsEnableFactor.Sleep))
	sleep_component.signal_not_is_sleep.connect(
		sleep_influence_component.enable_component.bind(ComponentNormBase.E_IsEnableFactor.Sleep))
```

**E. `EventBus` —— 唯一的全局事件通道**

```gdscript
# hand_manager.gd
EventBus.subscribe("main_game_progress_update", _on_main_game_progress_update)
# event_bus.gd 提供 subscribe / subscribe_once / unsubscribe / push_event（含优先级、once、filter、历史）
```

**要求**：**建议**只在"发布者不该知道订阅者"时用 `EventBus`；组件与宿主之间用信号就够了，  
滥用全局事件会让依赖关系彻底不可追踪。

**反例**

```gdscript
# ❌ 组件沿场景树向上抓宿主并改它的字段：删掉/挪动组件立刻崩，也读不出依赖关系
get_parent().get_parent().is_sleeping = true

# ❌ 组件之间硬编码绝对路径：换个场景树结构就断
get_node("/root/MainGame/PlantCell/Plant/NormPlant/HpComponent").take_damage(20)
```

**替代写法**：需要"最左敌人"这类跨组件查询，**建议**由宿主或管理器的公开方法提供（如 `update_first_enemy()`），组件通过 `@export` / `@onready` 持有引用后调用。

### K-04 组件与宿主的职责划分

| 谁                | 负责                                        |
| ---------------- | ----------------------------------------- |
| **组件**           | 自己的状态、自己的行为、自己的定时器与动画播放                   |
| **宿主（角色 / 管理器）** | 组件引用的获取、**信号连接**、初始化顺序编排、对外只读转发、无法拆分的特殊逻辑 |
| **管理器**          | 组件注册与事件派发（如 `HandManager`），**不实现**具体手持物行为 |

**要求**

- **建议**由宿主在 `_ready` 链路里连接信号（见 [K-05](#k-05-组件信号连接)）。
- **建议**让 `_ready()` 只做"按初始化类型分派"，不要在里面堆逻辑：

```gdscript
# plant_base.gd —— 只分派，不堆逻辑
func _ready() -> void:
	super()
	if plant_type == 0:
		push_error(name, "植物类型未赋值")

func ready_norm() -> void:
	super()
	garden_component.queue_free()          # 正常出战不需要花园组件
	be_attack_status_component.init_status()
	sleep_component.judge_is_sleeping()     # 是否睡觉由组件自己判断
```

- **建议**让子类重写 `ready_norm()` / `ready_show()` / `ready_garden()` / `ready_norm_signal_connect()`，**不宜**重写 `_ready()`。
- **建议**在 `add_child()` 之前用 `init_*()` 给角色赋值（行、初始化类型等），因为 `_ready` 时已需要这些值。
- **建议**通过 `ZombieManager.create_norm_zombie()` 创建僵尸，不要自己 `instantiate + add_child`。

**正例**（子类扩展点，全项目 87 处同类写法）

```gdscript
# plant_sun_flower.gd
func ready_norm() -> void: ...
func ready_norm_signal_connect() -> void: ...
```

**反例**：在某个植物脚本里重写 `_ready()` 并 `super()` 后追加初始化 —— `_ready` 里的分派逻辑会被执行两次或漏执行，且父类后续改动会静默破坏子类。

### K-05 组件信号连接

**适用范围**：角色类信号（角色本体与组件、组件与组件）。

> 目标：**避免信号漫天飞**。任何"谁连了谁"都应能在角色脚本里一眼读完。

**要求**（按优先级从高到低判断，命中即按其执行）

| # | 场景                            | 连接位置                                                       |
| - | ----------------------------- | ---------------------------------------------------------- |
| 1 | 角色类**自身 Timer 节点**的 `timeout` | **可以**在编辑器中直接连                                             |
| 2 | 组件**自身 Timer** 的 `timeout`    | **建议**连到该组件本体                                              |
| 3 | 父组件 ← 子组件（如攻击组件 ← 攻击检测组件）     | **建议**由**父组件**连接                                           |
| 4 | 受角色速度影响的组件                    | **建议**在角色根节点 `@export` 该组件，并在角色信号连接函数中连                    |
| 5 | 组件对组件的**禁用**影响（睡眠、胆小…）        | **建议**在**发起禁用**的组件里 `@export` 被影响的组件，由角色信号连接函数连            |
| 6 | 以上之外的所有自定义信号                  | **建议**由角色本体在 `_ready()` 对应的 `ready_*_signal_connect()` 中连接 |

**正例**

```gdscript
# plant_base.gd::ready_norm_signal_connect()
## 发射子弹攻击组件影响植物眨眼
var attack_component: AttackComponentBulletBase = get_node_or_null(^"AttackComponent")
if attack_component:
	attack_component.signal_change_is_attack.connect(
		## 可以攻击时禁用眨眼
		func(value): blink_component.change_is_enabling(not value, ComponentNormBase.E_IsEnableFactor.Attack))
```

**反例**

```gdscript
# ❌ 组件自己在 _ready 里跨节点连别的组件：依赖关系藏进组件，宿主读不出来
func _ready() -> void:
	get_parent().get_node("BlinkComponent").disable_component(...)
```

**自动检查**：无（靠评审）。新增组件时请对照本表逐条确认。

### K-06 组件化角色组装

**适用范围**：新增 / 修改植物、僵尸。

**要求**

- **建议**让根节点只保留基础属性、动画、body、以及 [K-01](#k-01-组件的定义与边界) 允许的不可拆分功能。
- **建议**让每个新能力优先问一句「这是不是能做成组件」——能，就做组件。
- **建议**用统一名（`%UniqueName`）或 `get_node_or_null()` 获取组件引用：

```gdscript
# plant_base.gd
@onready var sleep_component: SleepComponent = %SleepComponent
## 可挂载梯子组件（只有可挂梯子的植物挂载，可能为空）
@onready var ladder_component: LadderComponent = get_node_or_null(^"LadderComponent")
```

> 可选组件（可能不存在）**建议**用 `get_node_or_null()` + `is_instance_valid()` 判空；  
> 必需组件用 `%` 并在缺失时让编辑器尽早报错（`%` 找不到节点会直接报错，这是期望行为）。

- **建议**在新增组件后更新角色场景 `.tscn`，并把该组件登记进受影响角色的信号连接函数。
- **建议**让组件用内建 `owner` 拿宿主引用，宿主用 `%` / `get_node_or_null()` 拿组件引用（双向写法见 [K-03](#k-03-组件通信方式)）。

**反例**：为一个植物写 40 行特判塞进 `plant_base.gd` —— 基类会随植物数量线性膨胀，正确做法是做成组件或重写 `ready_norm()`。

### K-07 新增能力（技能 / 手持物）的三步扩展

**适用范围**：新增一类"当前有几种、以后会更多"的能力。手持物是本项目已落地的参考实现。

**要求**：**建议**满足「加能力不动管理器」—— 扩展点是枚举 + 组件脚本 + 场景节点，**不宜**在管理器里加 `match` 分支。

| 步 | 动作                                             |
| - | ---------------------------------------------- |
| 1 | 在能力类型枚举里加一个值（如 `E_HandComponentType`）          |
| 2 | 写一个继承对应 `*ComponentBase` 的组件脚本，实现"我建议实现的那几个函数" |
| 3 | 在管理器节点下加一个挂该脚本的 `Node2D` 节点                    |

> 管理器侧的**推荐范式**（`HandManager` 已落地）：遍历自己的子节点，按组件自声明的类型建表，  
> 之后一律查表派发 —— 不写任何逐个能力的 `if` / `match`。  
> 同一个管理器内部用 `get_children()` 做注册是允许的（见 [§8 红线](#8-原红线清单参考) 第 3 条只不建议拿宿主）。

**正例**：`src/managers/hand_manager/component/hand_component_base.gd` 用注释把这三步直接写在类头，`HandManager` 只做注册 / 派发 / 切换三件事；新增锤子、手套无需改 `HandManager`。

**反例**

```gdscript
# ❌ 每加一个手持物就要改管理器：组件化没做干净
func use_hand() -> void:
	match curr_hand_type:
		"shovel": ...
		"hammer": ...   # 又来一个分支
```

**完整示例见** [手持物实现.md](手持物实现.md)。

### K-08 启停规范

**要求**

- **建议**用 `E_IsEnableFactor` 说明禁用原因，不要自造布尔开关。
- **建议**保证启停**幂等**：同一因子重复 enable/disable 不产生副作用。
- **建议**在 `disable_component` / `enable_component` 里同时收敛该组件负责的**界面显隐**（如手持物组件重写后调 `refresh_ui()`）。

```gdscript
# hand_component_base.gd —— 复用 ComponentNormBase 的启停机制，顺带刷新界面
func enable_component(is_enable_factor: E_IsEnableFactor) -> void:
	super(is_enable_factor)
	refresh_ui()
```

### K-09 生命周期与清理

**要求**

- **建议**让 `exit_*` / `end_*` 之类的退出函数**幂等**：可能未进入就被调用，也可能被连续调用两次。
- **建议**在组件被 `queue_free()` 或角色换代时断开自己建立的连接（或用 `bind` 后由信号源回收，避免悬空回调）。
- **可以**让临时状态在 `exit_*` 中复原，而不是依赖"下次进入时重置"。

```gdscript
# hand_component_base.gd
## 退出手持态
## 必须幂等：可能在没有 enter_hand 的情况下被调用，也可能被连续调用两次
func exit_hand() -> void: pass
```

> 反例场景：轮次切换 / 游戏结束时手持物残留 —— 根因就是退出路径不幂等或未被调用。  
> 对应回归项见 [验证流程.md](../验证流程.md) 人工清单的「手持物」一行。

### S-02 日志必须走 Log

**适用范围**：全部脚本。

**要求**：**建议**不使用裸 `print()` / `printerr()`，统一走自动加载单例 `Log`（`src/core/autoload/logger.gd`）。

```gdscript
Log.debug("生成罐子数量:", curr_pot_num)    ## 调试信息，发布版本默认不输出
Log.info("开始新的一轮")                     ## 常规信息
Log.warn("随机罐子数量超过剩余格子，已跳过")  ## 警告（含「错误/失败/异常/不存在」等关键词的场景）
Log.error("存档写入失败: " + path)           ## 错误，走 stderr
```

| 控制项                     | 说明                                                   |
| ----------------------- | ---------------------------------------------------- |
| 参数拼接                    | 与 `print` 一致，**不加分隔符**，最多 4 个额外参数                    |
| `Log.level`             | 最低输出级别：编辑器内默认 `DEBUG`，导出发布版默认 `INFO`，静音设 `Level.OFF` |
| `Log.with_level_prefix` | 输出 `[DEBUG]`/`[INFO]` 等前缀                            |
| `Log.with_timestamp`    | 输出毫秒时间戳                                              |

**反例**

```gdscript
print("debug: ", x)      # ❌ 发布版无法关闭
printerr("failed")       # ❌ 绕过级别控制
```


**登记例外**（仅此两处，新增例外**建议**同时改检查器的豁免表）

| 文件                                | 豁免范围          | 原因                                              |
| --------------------------------- | ------------- | ----------------------------------------------- |
| `src/core/autoload/logger.gd` | 整个文件          | `_write()` 建议直连引擎原生 `print`/`printerr`，否则递归爆栈   |
| `test/autopilot_report.gd`        | 仅 `line()` 函数 | 报告正文要原样落进 stdout 供粘贴，不能带级别前缀、不能被 `Log.level` 截断 |

> ⚠️ `logger.gd` 的 `_write()` 内部**建议**用引擎原生 `print`/`printerr`，  
> 绝不能再调 `Log.*` —— 曾因此 `_write → debug() → _write` 无限递归爆栈，  
> 而编辑器全量扫描 PROBLEMS=0、资源自检通过，静态检查完全抓不到。  
> 这类"编译得过、一跑就炸"的问题只有**打开游戏**能发现。

**自动检查**：无（仓库已无静态检查器）。靠评审 + 打开游戏实测：  
控制台里出现不带级别前缀的裸输出即为违规。

### S-03 UI 屏幕坐标避坑

**适用范围**：任何"点到某个 Control"或"判断鼠标压在哪个 Control 上"的代码。

**要求**：**建议**用屏幕坐标（含画布变换）—— 即 `get_global_transform_with_canvas()`；  
**不建议**用 `global_position` / `get_global_rect()` 做命中或定位。

```gdscript
## 正确：控件在屏幕上真正能点到的中心
var screen_center := control.get_global_transform_with_canvas() * (control.size * 0.5)

## 错误：不含画布变换（相机），只有相机完全不动且原点为 (0,0) 时才碰巧对
var wrong := control.get_global_rect().get_center()
```

**原因**：鼠标命中测试与合成鼠标事件走的都是 `get_global_transform_with_canvas()`，  
而 `global_position` / `get_global_rect()` 给的是**不含画布变换**的坐标。  
本项目关卡有 `Camera2D`（`/root/MainGame/Camera2D`，位置 (120, 0)，**入场时还会移动**），  
草坪实测两者相差 **150 像素** —— 用错就稳定点偏，且偏移**不是常数**，不能靠"量一次到处减掉"糊过去。

反向操作（判断鼠标在不在控件里）**建议**在**局部空间**比：

```gdscript
c.get_rect().has_point(c.get_local_mouse_position())   ## plant_cell.gd::is_mouse_in_ui() 就是这么写的，是对的
```

> 把 `get_global_rect()` 和屏幕坐标混着比才是错的。  
> 完整根因、实测数据与排查手法见 [AI调试通道.md](../AI调试通道.md) 第六、七节。

### S-04 单位与数值

**要求**

- **建议**让速度 / 时间类参数走既有乘积机制（`owner_update_speed(speed_product)`），不要各组件自己改 `speed_scale`。
- **建议**让与屏幕尺寸相关的硬编码暴露为 `@export` 并写明适用分辨率：

```gdscript
## 静态迷雾 _ready() 会删除该区域之外的迷雾；改屏幕尺寸时必须同步调整
@export var del_fog_postion_area: Vector2 = Vector2(650, 700)
```

**反例**：在 `_ready()` 里直接写 `Vector2(650, 700)` 且无注释 —— 宽屏适配时无人知道这个数是什么意思。

- **不建议**让 `GridContainer` 的容器宽大于内容宽（列宽之和 + 分隔之和）：
  `GridContainer` 不会把多余宽度分给列，多出来的部分全落在容器**右侧** —— 容器居中了，内容却偏左
  （冒险选关的关卡块就偏了 35px）。容器宽**建议**写成「内容宽」，或按需改 `columns` / 分隔。

- **不建议**把与屏幕尺寸相关的位置**写进 `.tscn` 的开场动画轨道**（例如 `NodePath("BG_Right:position")` 的 `values`）：
  这类值既不在脚本里、也不在节点的静态 offset 里，改分辨率时按「节点属性」搜是搜不到的，
  运行期只表现为「元素被屏幕边缘裁掉」（主菜单墓碑被裁就是这么来的）。
  能只动画 `:y`（`NodePath("BG_Right:position:y")`）就把 x 交给锚点算；确实要写死时，旁边务必留一处记录说明适用分辨率。

### S-05 渲染层级

**要求**：**建议**按 [项目目录说明.md](项目目录说明.md) 的 CanvasLayer / `z_index` 表取值，**不宜**在脚本里新造层级数字。

| 用途           | 取值                                                                                     |
| ------------ | -------------------------------------------------------------------------------------- |
| 背景 / 卡槽 / 前景 | `-10` / `10` / `5`                                                                     |
| 临时种植（虚影、铲子）  | `20`                                                                                   |
| 全屏特效         | `30`                                                                                   |
| UI / 控制台     | `50` / `60`                                                                            |
| 行内元素         | `z_index = lane * 50 + <行内偏移>`（PlantCell 10 / ZombieRow 30 / LawnMover 40 / Bullet 45） |
| 特效弹道         | `BulletTrack 4000`、`Bombs 4001`、`Suns 4002`                                            |

### S-06 字典读取一律用 get()

**适用范围**：读取「按枚举 / 槽位存可选对象」的字典，典型是 `PlantCell.plant_in_cell`（`Dictionary[PlacePlantInCell, Plant000Base]`）。

**要求**

- **建议**用 `Dictionary.get(key)` 读取，或走封装好的安全访问器（`PlantCell.get_plant(place)`）；  
  **不建议**写 `dict[key]` 直接下标 —— 键缺失时会抛 `Out of bounds get index 'N'`，  
  而且 `is_instance_valid(dict[key])` 这种"先判空"写法**拦不住**：异常发生在 `[]` 取值那一刻。
- **建议**给槽位型字典配一个安全访问器，新增读取一律走它，不要各自散落 `get()`。
- **可以**用 `dict[key] = value` 写入：写入不存在的键会新建键，不会越界。
- **可以**用 `for k in dict: dict[k]` 遍历：键来自字典自身，必然存在。

**正例**

```gdscript
# src/items/plant_cell.gd —— 唯一的读取入口
func get_plant(place: CharacterRegistry.PlacePlantInCell) -> Plant000Base:
	return plant_in_cell.get(place)

# 调用方：src/entities/character/components/detect_component/component_detect.gd
var shell:Plant000Base = cell_plants.get(CharacterRegistry.PlacePlantInCell.Shell)
if is_instance_valid(shell):
	return shell
```

**反例**

```gdscript
# ❌ 槽位键可能是缺的；先判空也没用，异常在 [] 取值时就抛了
if is_instance_valid(plant.plant_cell.plant_in_cell[CharacterRegistry.PlacePlantInCell.Imitater]):
	return plant.plant_cell.plant_in_cell[CharacterRegistry.PlacePlantInCell.Imitater]
```

> 真实事故：`plant_in_cell` 默认只登记 `Norm/Shell/Down/Float` 四个槽位，`Imitater` 键被注释掉，  
> 僵尸检测到「格子里只有花盆（`Down`）」时执行到 `Imitater` 分支 → `Out of bounds get index '4'`。  
> 这个潜伏 bug 是在屋顶索敌修好、僵尸第一次真正检测到植物之后才暴露的。

**自动检查**：无（靠评审）。

### S-07 类型化形参不接「可能被释放的对象」

**适用范围**：形参可能收到**上一帧缓存的角色引用**的函数（索敌、目标锁定、持续追踪一类），
典型是 `DetectTargetStrategy.pick_enemy_for_track_bullet()` 的 `curr_enemy`。

**要求**

- **不建议**给这类形参写具体类型（`Character000Base` / `Plant000Base` / `Node`）：
  传进来的是已 `queue_free` 的对象时，GDScript 在**调用那一刻**就抛
  `Invalid type in function 'xxx' ... (previously freed) is not a subclass of the expected argument class`，
  函数体里的 `is_instance_valid()` **根本轮不到执行**（和 S-06 的 `dict[key]` 同一个时序问题）。
- **建议**形参保持无类型（Variant），进函数第一件事用 `is_instance_valid()` / `x is Character000Base` 归零；
  返回值同理，**不建议**把可能已释放的局部变量直接 `return` 给声明了类型的返回类型。
- **建议**调用方也在传参前清一次：`if not is_instance_valid(field): field = null`
  （尤其是「缓存了目标但没连它死亡信号」的组件，例如全局检测组件 `DetectComponentGlobal`）。
- **可以**用 `x is SomeClass` 判已释放对象：对 freed 实例 `is` 返回 `false`，不会抛异常；
  **不建议**用 `x != null` 判存活 —— 对 freed 对象它仍是 `true`。

**正例**

```gdscript
# DetectTargetStrategy.pick_enemy_for_track_bullet —— 形参无类型 + 入口归零
static func pick_enemy_for_track_bullet(all_enemy: Array[Character000Base], curr_enemy, camp) -> Character000Base:
	if not (curr_enemy is Character000Base):
		curr_enemy = null
	...
	return curr_enemy if is_instance_valid(curr_enemy) else null
```

**反例**

```gdscript
# ❌ 形参带类型：目标被 queue_free 后调用直接抛错，函数体里的判空没机会跑
static func pick_enemy_for_track_bullet(all_enemy: Array[Character000Base], curr_enemy: Character000Base, camp) -> Character000Base:
	if not is_instance_valid(curr_enemy):   # 到不了这里
		...
```

> 真实事故：追踪子弹（香蒲）锁定的僵尸被打死后被释放，全局检测组件没连它的死亡信号，
> `enemy_can_be_attacked` 残留已释放引用 → 下一次索敌调用即报
> `Invalid type in function 'pick_enemy_for_track_bullet' ... argument 2 (previously freed)`。

**自动检查**：无（靠评审）。

### S-08 类型化数组形参不接「`as Array[T]` 转换来的数组」

**适用范围**：形参是 `Array[int]` / `Array[Node]` 一类**类型化数组**，实参来自 Dictionary / Variant / `get()` 返回值的地方
（典型：动作队列 `{"act": ..., "types": [...]}`、配置字典里取出的数组）。

**要求**

- **不建议**用 `x as Array[int]` 给无类型 `Array`「补类型」：`as` 对数组只做引用转换，
  **不会**校验也不会补写元素类型，转换结果仍是 `Array`，传进 `Array[int]` 形参时在**调用那一刻**抛
  `Invalid type in function 'xxx' ... The array of argument 1 (Array) does not have the same element type as the expected typed array argument`。
- **建议**实参侧就写成类型化字面量（`var types: Array[int] = [ ... ]`），**或**写一个显式转换小函数逐元素 `append`：
  从 Dictionary 取出的值一律先过一遍它。
- **可以**保持形参为无类型 `Array`，函数体内用 `int(e)` 转元素 —— 但**不建议**为此把已有的 `Array[int]` 形参改回无类型，
  显式转换函数对调用方更友好。

**正例**

```gdscript
func _int_array(v: Variant) -> Array[int]:
	var out: Array[int] = []
	if v is Array:
		for e in v as Array:
			out.append(int(e))
	return out

_do_spawn(_int_array(act.get("types", [])))   # 无论 Dictionary 里存的是 Array 还是 Array[int] 都安全
```

**反例**

```gdscript
# ❌ as 不会给 [] 打上元素类型，运行时在函数调用处报错
_do_spawn(act.get("types", []) as Array[int])
```

> 真实事故：`zombie_boss.gd` 里随机轮组「`{"act": ACT_SPAWN, "types": [_pick_spawn_type(POOL_LATE)]}`」
> 是无类型 `Array`（开局剧本走 `_batch()` 建的是 `Array[int]`），`_do_spawn()` 一到随机轮就报上面的错。

**自动检查**：无（靠评审）。

## 5. 资源引用（参考）

### M-01 res:// 引用与改名

**适用范围**：脚本、场景、资源中的一切引用。

**要求**

- **建议**使用 `res://` 绝对路径。
- 移动 / 重命名资源时**建议**同步完成：
  1. 全局搜索旧路径字符串并全部替换（Godot 4 优先按 `uid://` 解析，路径错也能打开，**但导出会报错**）；
  2. 移动 `.gd` / `.gdshader` 时**连同同名 `.uid` 一起移动**（否则 Godot 重新分配 uid，场景引用失效）；
  3. **先关闭 Godot 编辑器**再批量重命名 —— 编辑器会把瞬时消失的 `.uid` 当孤儿文件删除（本项目曾一次性被删 17 个）。
- **建议**不手工编辑或提交伪造 `.uid` 内容。
- **建议**验证：全文搜 `res://`，确认引用文件真实存在。
- **建议** autoload 脚本里引用**大场景**时写 `var X = load(...)`，**不宜**写 `const X = preload(...)`：
  2026-10-04 实测 `SceneRegistry` 里 `const ZOMBIE_BOSS = preload("…zombie_boss.tscn")`（50 张 reanim 贴图 + 23 段动画）
  在 autoload 阶段解析成了一个**空 PackedScene** —— `get_path()` 为空、`instantiate()` 返回 null、
  报 `Failed to instantiate scene state of ""`，而同一进程里 `load()` 与 `SceneRegistry.get("ZOMBIE_BOSS")` 拿到的都是完好的场景；
  同文件其它 10 个常量全部正常，只有这个最大的中招，且**不打任何编译错误**（最难查的一类）。
  改成 `var ZOMBIE_BOSS: PackedScene = load(...)`（与 `TOMBSTONE` / `TROPHY` / `SUN` 一致）即恢复。
  现象（僵王进不了场）→ 原因（preload 常量为空）→ **正解**（改 load，并在该常量上留注释说明为什么不能改回 preload）。

**正例**：改名后全文搜旧路径字符串确认已全部替换，再打开游戏走一遍相关界面。

**反例**：只改文件名，靠编辑器"能打开"就以为没事 —— 导出时才发现 `ext_resource` 丢失。

**自动检查**：无（仓库已无静态检查器）。改名后**建议**自己全文搜 `res://` 确认引用存在、  
确认 `.uid` 跟着走了、没有留下孤儿 `.uid`。

### M-02 资源与脚本的配对

**要求**

- **建议**让自定义资源脚本与它的 `.tres` 数据同目录（脚本进该目录的 `script/`，见 [D-06](#d-06-resources-的组织方式)）。
- **建议**给资源类加 `Resource` 前缀（`ResourceLevelData`、`ResourcePlantCondition`、`ResourceSaveGame*`）。
- **可以**让「相同配置」共用同一份 `.tres`，而不是复制多份。

### M-03 注册表登记

**适用范围**：新增角色、子弹、道具、卡片等"按类型取场景"的对象。

**要求**：**建议**在对应注册表登记，**不宜**在业务代码里散落 `preload` 映射。

| 注册表                                                             | 位置                                               | 登记内容                                                   |
| --------------------------------------------------------------- | ------------------------------------------------ | ------------------------------------------------------ |
| `CharacterRegistry.PlantType` + `CharacterRegistry.PlantInfo`   | `src/core/autoload/character_registry.gd`  | 枚举值 + 信息表（名称、冷却、阳光、场景、种植条件资源…），经 `get_plant_info()` 读取 |
| `CharacterRegistry.ZombieType` + `CharacterRegistry.ZombieInfo` | 同上                                               | 枚举值 + 信息表（名称、场景、行类型…），经 `get_zombie_info()` 读取         |
| `BulletRegistry.BulletType` + `BulletTypeMap`                   | `src/core/autoload/bullet_registry.gd`     | 枚举值 + `preload` 场景                                     |
| `MainSceneRegistry.MainScenesMap`                               | `src/core/autoload/main_scene_registry.gd` | 主场景路径                                                  |
| `AllCards`                                                      | `src/core/autoload/all_cards.tscn`                 | 卡片预制（运行时从它复制）                                          |

> `ItemRegistry`（`src/core/autoload/item_registry.gd`）目前是空占位类，  
> 道具注册尚未落地 —— 新增道具时若需要注册表，应先把它建起来，而不是另开一份散乱映射。

**正例**

```gdscript
# bullet_registry.gd
enum BulletType {
	Bullet001Pea = 1,        ## 豌豆
	Bullet1001Bowling = 1001, ## 保龄球
}
@export var BulletTypeMap: Dictionary[BulletType, PackedScene] = {
	BulletType.Bullet001Pea: preload("res://src/entities/bullet/bullet_pea.tscn"),
}
```

**反例**：在植物脚本里 `if plant_type == 45: scene = preload(...)` —— 类型分派分散到各处，注册表失去意义。

**自动检查**：无（仓库已无静态检查器）。打开游戏后 DebugChannel 报告会列出注册表条目数，  
用它核对新增条目是否真的注册上了。

### M-04 alpha 蒙版必须离线烘焙

**适用范围**：`assets/` 下任何「底图 + 同名带下划线蒙版」的素材对（`<name>.jpg` + `<name>_.png`，黑=透明 / 白=不透明）。

**要求**：**建议**用 `tools/merge_alpha.ps1` 先把通道合成到一张 RGBA PNG，**不建议**在游戏运行时再做 alpha 合成（shader 采样蒙版图、`Image.get_pixel()` 逐像素写 alpha 都不行）。

- **建议**保留 `<name>_.png` 蒙版作为源素材：它是重新烘焙的输入，不要当成「没人引用的垃圾」删掉。
- **建议**让 Godot 侧只引用烘焙产物（`.png`），不引用未合成的底图（`.jpg`）。
- **可以**在白天 / 黑夜等变体没有自己的蒙版时**复用**同一张蒙版（用 `-Mask` 显式指定），前提是两张底图尺寸一致（如 `pool_base` 与 `pool_base_night`）。

**正例**

```
powershell -ExecutionPolicy Bypass -File tools/merge_alpha.ps1 -Name assets/image/background/pool_base
powershell -ExecutionPolicy Bypass -File tools/merge_alpha.ps1 -Name assets/image/background/pool_base_night -Mask assets/image/background/pool_base_.png
# src/items/pool.gd
const POOL_BASE = preload("res://assets/image/background/pool_base.png")
```

**反例**：在 `.gdshader` 里 `uniform sampler2D mask_texture; c.a *= texture(mask_texture, UV).r;` —— 每帧多一次采样，且蒙版图还得跟着进包。

**自动检查**：无自动化校验；路径是否存在按 [M-01](#m-01-res-引用与改名) 自己全文搜 `res://` 确认。

### M-05 手工编辑 `.tscn` 不写注释

**适用范围**：直接改文本格式的 `.tscn` / `.tres`（加节点、调 offset）。

**要求**：**不建议**在 `.tscn` 里写 `##` / `#` / `//` 注释 —— Godot 的文本资源解析器只认 `;` 开头的注释，
其它写法会被当成属性行解析失败，**后面的整个节点段被静默丢弃**（不报 Parse Error），
表现是「场景能打开、但新加的节点不存在」，脚本里 `get_node()` 拿到 `null` 才炸。
要留说明就写在对应 `.gd` 的注释里。

**踩坑实例**：给 `store.tscn` 加蜗牛 / 巧克力行时写了两行 `## 原版货架顺序…`，
结果 `GoodsStinky`、`RowGardenChocolate` 两个节点段全被吞掉，探针报
`Invalid access to property or key 'visible' on a base object of type 'null instance'`，
排查一轮才发现是注释惹的祸。

**自动检查**：改完 `.tscn` 后**建议**至少实例化一次确认节点在（无头脚本 `load(...).instantiate()` 打印子节点名即可）。

## 6. 验证与交付（参考）

### V-01 改动较小可免验证

**要求**：改完代码先做一次判定，而不是无脑跑流程。

**免验证**（改完直接交付）—— 满足任一即可：

- **改动较小**：注释、文案、`docs/` 文档、单个函数内部的局部逻辑；
- **确定不会出问题**：改动路径没有其它调用方，没动公共签名 / 枚举 / 注册表 / 资源引用；
- 能明确说出「只影响 X，而 X 不受这次改动影响」；
- **验证成本过高、不值得脚本化**：触发条件极难凑（要先通关 N 关 / 手改存档 / 等低概率随机事件）、  
  单局耗时长、或只能靠肉眼手感判定 —— **允许跳过验证，但建议在反馈里给出人工验证方法**，  
  见 [验证流程.md §1.1](../验证流程.md#11-验证成本过高时可以不验证但建议在反馈里给出人工验证方法)。

**建议打开游戏（带窗口）实测**：

- 新增 / 改动单位：植物、僵尸、子弹、手持物、组件、关卡；
- 改了公共签名、枚举、注册表、autoload、资源路径（含改名）；
- 改了 `ready_norm()` / `ready_norm_signal_connect()` 链路、组件挂载与启停；
- 改了任何玩法行为（出怪、波次、教程、掉落、存档…）；
- **拿不准** —— 拿不准就按「要验证」处理。

> 判定看**改动面**，不看行数：改 1 行但改的是 `Global` 的公共方法，就要验证。
>
> 仓库**已无静态验证脚本**（原 `test/verify.ps1` 及其驱动的 `standard_check` /  
> `script_check` / `project_checker` / `runtime_smoke` / `autoload_smoke` 已删除）。  
> 静态检查只能证明「没坏」，**打开游戏才证明「能玩」**；无头跑批只证明「跑得完」，  
> 不能用来排查（见 [AI调试通道.md](../AI调试通道.md) 第〇节）。

怎么打开游戏实测、各模块的回归清单见 [验证流程.md](../验证流程.md)。

## 7. 扩展本规范（参考）

> 这一节是给**以后要改规范的人**的：规范本身也要可扩展。

### E-01 新增一条规范

**要求**

1. **建议**判断它属于哪一节：目录结构 `D-` / 组件化 `K-` / 命名 `C-` / 代码风格 `S-` / 资源引用 `M-` / 验证 `V-` / 规范自身 `E-`。
2. **建议**分配下一个空闲编号（**不复用**已删除编号，避免历史引用失效）。
3. **建议**复制下面的卡片模板，缺项写「无」而不是省略标题。
4. **建议**在 [§0.1 速查表](../项目规范.md) 加一行"我要做 X → 卡片编号"。
5. **可以**尽量给出**真实存在于本仓库**的正例路径与代码片段。

**卡片模板**（复制后填空）

````markdown
### <前缀>-<编号> <一句话标题>

**适用范围**：<什么时候需要看这条>

**要求**

- **建议**/ **可以**/ **可以** <可判定的要求，一条一句>

**正例**

    ```gdscript
    <能直接抄的代码，注明文件路径>
    ```

**反例**

    ```gdscript
    <错在哪、会坏成什么样>
    ```

**自动检查**：<具体步骤，或"无（靠评审）">
````


**为什么这么规定**

- 固定字段 → 读的人不用重新理解结构，写的人不用重新设计结构。
- 「正例建议真实」→ 卡片即模板，新增功能可以照抄，规范不会和代码漂移。

### E-02 把规范变成自动回归

**要求**：一条规范若要自动兜底，**可以**做成**行为回归探针**，而不是留在文档里靠人记。

> 仓库**不再有静态检查器**：原 `test/verify.ps1` 及其驱动的 `standard_check` /  
> `script_check` / `project_checker` / `runtime_smoke` / `autoload_smoke` 已删除。  
> 静态扫描只能证明「没坏」，证明不了「能玩」，故统一走「打开游戏」这条线。

| 档位               | 做法                                                                                 | 适用                      |
| ---------------- | ---------------------------------------------------------------------------------- | ----------------------- |
| **行为回归（现状唯一档位）** | 加一个 `test/scenarios/probe_*.gd`，用 `run_autopilot.ps1 -Scenario <name> -Windowed` 跑 | 种植、手持物、教程、夜晚关、推车保护等玩法行为 |
| 打开游戏实测           | 按 [验证流程.md](../验证流程.md) §3 人工回归清单逐条过                                               | 画面、时序、手感 —— 探针断言不到的一切   |
| 评审               | 写进本文档对应卡片                                                                          | 命名、目录、签名类静态约定（本就自动化不了）  |

**接线步骤**

1. **建议**让探针输出**一行纯 ASCII** 汇总标记：
   ```
   [XXX] passed=<n> failed=<n> result=PASS|FAIL
   ```
2. **建议**在 [验证流程.md](../验证流程.md) §3 人工回归清单里登记这个 `-Scenario` 与它的标记名。
3. **建议**把探针的**豁免清单**（哪些情形被允许不达标）写在探针顶部常量里，  
   并在对应卡片里登记 —— 允许例外但不登记，等于把检查做成摆设。
4. **可以**在本文档 [附录 B](#附录-b-规范--自动检查索引参考) 同步一行。

**正例**：`-Scenario probe_hand` 覆盖 [K-07](#k-07-新增能力技能--手持物的三步扩展) /  
[K-08](#k-08-启停规范) / [K-09](#k-09-生命周期与清理) 三条组件规范。

**反例**：写一个只在无头模式下跑、靠纯文本扫描断言的"检查器" ——  
它绿了不代表能玩，反而给人「全绿即通过」的错觉。

### E-03 规范与文档的边界

**要求**

- **建议**让本文档只写**约束**（怎么写）；机制、原理、历史踩坑放到对应专题文档，用链接互指。
- **不建议**在本文档重复专题文档的内容 —— 两处都写必然漂移，且读者不知道该信哪一份。
- **可以**在发现"同一个坑被踩第二次"时，把它升级成一张规范卡片（并尽量配自动检查）。

## 10. 经验与流程的沉淀（参考）

> 这一节管两件事：**知识别丢**（E-04）和**路径别重复摸索**（E-05）。  
> 两者都不是风格偏好：文档是本仓库唯一的跨 Agent 记忆，回复里说过的话下一个 Agent 看不到。

### E-04 踩坑与经验即时沉淀

**适用范围**：本次任务里踩到任何坑、学到任何非显然经验的那一刻 —— 报错与排查结论、机制陷阱、工具 / 脚本用法、某个方案为什么不行。

**要求**

- **建议**在**本次任务内**写进文档，**不建议**「下次再说 / 记在心里 / 只在回复里讲一遍」：回复不被下一个 Agent 继承，等于这条经验从未发生。
- **建议**按内容类型选落点，同一件事**只在一处**写：
  - 约束（该怎么做 / 不建议怎么做）→ 本文档新增一张卡片（按 [E-01](#e-01-新增一条规范) 取号）；
  - 机制 / 原理 / 一次性排查过程 → 对应专题文档（[项目目录说明.md](项目目录说明.md)、[子弹说明文档.md](子弹说明.md)、[AI调试通道.md](../AI调试通道.md)…）或本目录里本次记录文件的「踩坑」一节 里本次记录文件的「踩坑」一节；
  - 从 wiki / 外部来源取的数值 → 按 [AI查wiki避坑.md](AI查wiki避坑.md) 带来源注释写进代码与文档。
- **建议**写成**三段式**：现象 → 原因 → 正解。只写结论不写现象的条目，后来者无法对上号。
- **可以**在发现「同一个坑第二次被踩」时，把它升级成本文档的一张规范卡片（[E-03](#e-03-规范与文档的边界)）。
- **不建议**新建「规范」文档（规范只进本文档）、**不建议**把约定写在代码注释里就当已沉淀。

**正例**

```markdown
### S-06 字典读取一律用 get()

**踩坑背景**：`plant_cell.dict[key]` 在槽位键缺失时直接抛异常，先判空也没用。
```

（卡片本体见 [S-06](#s-06-字典读取一律用-get)；机制细节只写在那一张卡里。）

**反例**

```
只在对话回复里写「注意：改名时 .uid 要一起带走，否则引用全断」。
下一个 Agent 不会读到这段回复，会再断一次。
```

**自动检查**：无（靠评审）。自检问一句：**本次任务的改动里有没有 `.md`？** 踩了坑却没有文档变更，就是漏了。

### E-05 工作流程归档（每次任务结束必做）

**适用范围**：任何一次有实质产出的任务收尾时（改代码 / 改资源 / 排查 / 改文档 / 改配置）。

**要求**

- **建议**在 [docs/工作记录/](../工作记录/README.md) 新建**一个文件**：`docs/工作记录/<YYYY-MM-DD>_<主题>.md`（模板见该目录 README §3，命名规则见 §4）。
- **建议**在 [docs/工作记录/README.md](../工作记录/README.md) §2 索引表**补一行**（不补 = 后来者捞不到这条）。
- **建议**写全必要信息：目标、步骤（**含走过又被否掉的弯路**）、关键决策与理由、踩坑（现象 → 原因 → 正解）、验证方式、耗时与成本、推荐度、任务类型、**给后来者的最简路径**（逐项含义见该目录 README §3 的表格）。
- **建议**标「推荐度」（**推荐** / 可用 / 不推荐）与「任务类型」—— 后来者靠这两个字段比较多条流程、选**最适合 / 最简单**的那条。
- **可以**在开工前先查该目录索引里的同类条目，**优先复用**已验证的最简路径，而不是重新摸索。
- **建议**在发现某条记录已过时（路径 / 脚本 / 命令已不存在）时，在记录文件顶部标注 `已过时 + 失效原因 + 替代做法`，**不建议**留着误导后人、**不建议**删改他人已归档的事实。
- **可以**在收尾时给同类旧记录追加「补充 / 评价」区块（做法见 [docs/工作记录/README.md §5](../工作记录/README.md#5-给旧记录追加补充--评价)）：  
  **只追加不改写**原文、**双向引用**（旧记录 ←→ 本次记录两端都放链接）、**不占索引新行**（索引只登记主记录）；  
  结论推翻旧评价时**可以**改索引该行的「推荐度」，**不建议**改日期 / 任务类型 / 目标 / 文件名 —— 那些是原始事实。
- **不建议**另建 `agent_notes*.md` / `docs/我的流程.md` 之类散落文件 —— 记录**只落在 `docs/工作记录/` 这一个目录**。

**正例**

```
docs/工作记录/2026-10-01_资源改名-plant_002.md     ← 一次任务一个文件
docs/工作记录/README.md                            ← 索引补一行
```


```markdown
> **任务类型**：资源改名 ｜ **推荐度**：**推荐** ｜ **耗时**：约 3 轮，开了游戏
## 步骤
1. 关编辑器 2. 连 .uid 一起移动 3. 全局替换 res:// 4. 打开游戏实测
## 踩坑
1. 只改路径字符串 → 场景报 missing resource → **正解**：.uid 同步移动
```

**反例**

- 只在对话里总结「我先试了 A 不行，后来用 B 成了」，不落文件 —— 下一次还得重新试一遍 A。
- 把记录写进 `docs/我的工作流程.md`，或堆在一个大文件里按天追加 —— 后来者要么找不到，要么要在长文件里翻。

**自动检查**：无（靠评审）。自检：**本次交付是否在 `docs/工作记录/` 新建了记录文件，并在 README 索引补了行？**

**为什么这么规定**

- 仓库没有静态检查器，靠打开游戏实测兜底，成本不低 —— **记录哪条路径最省事**，比每次重新摸索便宜得多。
- **一次任务一个文件**：单文件按天追加会无限变长（检索靠锚点、合并易冲突），而按任务拆文件后，索引表一行就能定位，也便于标注某条「已过时」。
- 记录是积累型数据，混进本规范会让规范越读越长，故单开目录（[E-03](#e-03-规范与文档的边界)）。

### E-06 细枝末节规则的强制级别判定

**适用范围**：① 觉得某条规范太琐碎、不值得强制时 ② 新增规范前判断「该不该定成硬约束」时。

**要求**

- **可以**把**纯风格类**条目定为**参考意见**：原文搬进 [参考意见存档.md](../参考意见存档.md)（按该文件 §2 的 `R-<编号>` 编号），本文档只留一行指向链接。
- **建议**按下面这张表判定，**不建议**凭"我觉得不重要"随意定为参考：

| 违反后的后果                                                 | 结论        |
| ------------------------------------------------------ | --------- |
| 会崩 / 会静默出错 / 会让引用与依赖断掉（日志、坐标、注册表、`.uid`、字典读取、验证、组件边界…） | **定为硬约束** |
| 只是「看起来不一致」，功能与依赖关系完全一样（缩进、BOM、换行、注释样式、变量后缀、目录同名…）      | **定为参考**  |

- **建议**改强制级别时**一次改全**，不留强制痕迹：原卡片标题标「参考」+ [§8 红线清单](#8-原红线清单参考)摘掉 + [附录 B](#附录-b-规范--自动检查索引参考) 摘掉 + [附录 A](#附录-a-常用约定速查参考) 同步标注 + [§0.1 速查表](../项目规范.md) 同步 + [V-02](#v-02-提交前自检清单) 同步 + [../AGENTS.md](../../AGENTS.md) 硬约束速查同步。  
  留着任何一处「必须 / 禁止」，等于把同一条规则变成了"说是参考但还有一处必须"。
- **建议**在本文件原位置保留指向新出处的链接 —— 否则后来者会以为规则凭空消失，又去猜一遍。
- **不建议**为了对齐参考意见而批量改写既有文件（大 diff、易冲突、收益为 0）；参考意见只对**新写的代码**起作用。
- **可以**在来源记录表（[参考意见存档.md](../参考意见存档.md) §3）写一行：对应卡片 → 参考条目编号 → 理由。

**正例**

```markdown
### S-01 格式与注释（参考）

> **本条为参考，不强制**（E-06）：排版不影响功能，.editorconfig 已配好。
> 原文见 参考意见存档.md R-01。
```

（同时把原红线 9「不建议 4 空格缩进、BOM、CRLF、行尾空格」从 §8 移除并更新红线计数。）

**反例**

- 只在 [参考意见存档.md](../参考意见存档.md) 抄一份原文，规范里的「建议」原封不动 —— 两处都有，评审时按哪份？
- 把 [S-02](#s-02-日志必须走-log)（日志建议走 `Log`）也定为参考 —— 发布版关不掉日志、绕过级别控制，属于会静默出错的行为约束，**不宜**。

**自动检查**：无（靠评审）。自检：**改完强制级别后，全仓 grep 该条目的关键词，是否还有「必须 / 禁止」字样？**
