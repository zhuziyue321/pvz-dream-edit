# 僵尸热注册（运行期注册僵尸）

> **[面向 AI Agent]** ｜ **触发条件**：要在**运行期**（模组 / 自制关卡 / 控制台 / 关卡脚本）加一只僵尸，或改热注册相关的入口
> **读完你能**：知道热注册的入口在哪、一只热注册僵尸由「本体 + 脚本」怎么拼出来、防具该写在哪、编号怎么取、能被哪些入口生成
> **强制级别**：**参考** ｜ **不读的风险**：把热注册的僵尸塞进 `ZombieInfoData.ZOMBIE_INFO`（那是 const 公共基础表，改它等于改全仓出怪基线）
> **关联**：注册表 `CharacterRegistry` ｜ 配方 `ZombieRuntimeRecipe` ｜ 装配钩子 `Zombie000Base.build_runtime_parts()` ｜ 防具 [防具.md](防具.md) ｜ 模组 [模组机制.md](模组机制.md)

---

## 1. 一句话

**运行期注册一只僵尸 = 一个本体 + 一个脚本，交给 `CharacterRegistry.register_runtime_zombie()`。**
防具不在配方里 —— 由那个脚本自己在 `build_runtime_parts()` 里用 `add_armor()` 挂，想挂几层挂几层。

内置的二十多只僵尸是「一个 `.tscn` 一只」：本体、防具、行为脚本全写死在场景里，
加一只要新开 `.tscn` 并在 `zombie_info_data.gd` 登记一行 —— 那是**编译期**的事，运行期没有编辑器可用。

```
src/entities/character/zombie/zombie_runtime_recipe.gd   ## ZombieRuntimeRecipe：本体 + 脚本 + 注册表信息
src/core/autoload/character_registry.gd                   ## 热注册入口 / 撤销 / 统一实例化入口
src/entities/character/zombie/zombie_base.gd              ## build_runtime_parts() 钩子 + add_armor()
```

## 2. 三步注册一只僵尸

### 第 1 步：写脚本（行为 + 防具都在这里）

```gdscript
## user://mods/my_mod/my_zombie.gd
extends Zombie001Norm
class_name MyZombie

## 【热注册】装配钩子：本体已就位、组件都已就绪，在这里挂防具
func build_runtime_parts() -> void:
	super()
	## 一类（头顶那件）
	add_armor(ConstArmor.E_ArmorType.Cone, 370)
	## 二类（举在身前那件，二类在外、先挨打）
	add_armor(ConstArmor.E_ArmorType.ScreenDoor, 1100, ConstArmor.E_ArmorClass.Armor2)
```

防具的**特殊效果**（浮空 / 破防暴走 / 免疫减速…）照旧由防具组件自己定义 —— 要就传 `armor_script`：

```gdscript
	add_armor(ConstArmor.E_ArmorType.Balloon, 20,
		ConstArmor.E_ArmorClass.Armor1,
		preload("res://src/entities/character/components/armor_component/component_armor_balloon.gd"))
```

`add_armor()` 返回那一层 `ArmorComponent`，还要改破损外观 / 受击音效 / 铁器节点就接着在返回值上改：

```gdscript
	var armor := add_armor(ConstArmor.E_ArmorType.Bucket, 1100)
	armor.sfx_be_attack = SoundManagerClass.TypeBeAttackSFX.Metal
	armor.body_change = [preload("res://data/.../stage_1.tres"), ...]
```

### 第 2 步：配配方（本体 + 脚本）

```gdscript
var recipe := ZombieRuntimeRecipe.new()
recipe.base_scene = preload("res://src/entities/character/zombie/zombie_norm.tscn")  ## 本体
recipe.zombie_script = preload("user://mods/my_mod/my_zombie.gd")                ## 脚本
recipe.zombie_name = &"MyZombie"
recipe.sun_cost = 125
recipe.row_type = CharacterRegistry.ZombieRowType.Land
recipe.spawn_power = 2      ## > 0 才能进按战力预算的生成
recipe.spawn_weight = 1000  ## > 0 才能进自然出怪的基础权重池
```

配方是 `Resource`，可以在编辑器里存成 `.tres`，也可以纯代码 new 出来。

### 第 3 步：注册

```gdscript
Global.character_registry.register_runtime_zombie(recipe)
var new_type := recipe.zombie_type   ## id 留 Null 时由注册表自动分配（`runtime_zombie_1` 起）
```

之后它和内置僵尸没有区别：`ZombieManager.create_norm_zombie(new_type, ...)`、
图鉴 / 开局预览（`CharacterShowFactory.create_show_zombie()`）都认它。

## 3. id：热注册僵尸带 `runtime_zombie_` 前缀

僵尸编号改成字符串 id 之后（2026-10-14），**没有编号段这回事了**：热注册的僵尸 id 由
`CharacterRegistry.RUNTIME_ZOMBIE_ID_PREFIX`（`runtime_zombie_`）+ 自增序号拼出来 ——
`runtime_zombie_1`、`runtime_zombie_2` …，再也不用担心「段用完」。

- 配方里 `zombie_type` 留 `Null` → 注册表自动分配下一个没被占用的 id（**推荐**）；
- 手动指定 → 不能撞内置僵尸已用的 id（`ZombieIds` 里有就会报错拒绝）；
  建议带模组自己的前缀（如 `&"more_armor_copper_bucket"`），比自增号更能看出是谁注册的；
- 想知道某只是不是热注册的：`CharacterRegistry.is_runtime_zombie(id)` / `get_runtime_zombie_types()`。

内置僵尸的 id 见 `ZombieIds`（`src/core/consts/zombie_ids.gd`）。

## 4. 为什么单独存一张运行期表

`ZOMBIE_INFO` 是 `const` 表，注释里写明「各出怪系统复制后独立调整，不修改公共基础数据」——
往里写等于改所有关卡的出怪基线，而且撤不掉。所以热注册的条目存在 `CharacterRegistry` 的三个
运行期字典里：`runtime_zombie_recipes` / `_runtime_zombie_info` / `_runtime_zombie_spawn_*`，
`unregister_runtime_zombie()` 一把摘干净。

查询侧的收口（改过这几处，别再绕回去直连静态表）：

| 该走这个                                | 别再写这个                                                     |
| ----------------------------------- | --------------------------------------------------------- |
| `get_zombie_info()`                 | `ZombieInfo[type]`                                          |
| `has_zombie()`                      | `ZombieInfo.has(type)`                                      |
| `instantiate_zombie()`              | `get_zombie_info(..., ZombieScenes).instantiate()`          |
| `can_instantiate_zombie()`          | `scene.can_instantiate()`                                   |
| `get_zombie_spawn_power()`          | `ZombieSpawnPower.get(type, -1)`                            |
| `get_zombie_spawn_weights()`        | `ZombieSpawnWeights.duplicate()`                            |

> ⚠️ **热注册的僵尸没有场景文件**：`ZombieInfoAttribute.ZombieScenes` 那一格是**故意留 null** 的，
> 实例化一律走 `instantiate_zombie()`（由配方现场组装），拿那一格去 `instantiate()` 会拿到 null。

## 5. 装配时序（防具为什么挂在 `build_runtime_parts()` 里）

组件比宿主先 `_ready()` ⇒ `HpComponentZombie.component_ready()` 收集防具表时，
本体子节点的防具已经都在了 —— 但**运行期才挂上来的不在那张表里**。

所以时序是：

```
Zombie000Base.ready_norm()
  └─ build_runtime_parts()      ## 脚本在这里 add_armor()
  └─ activate_armor_effects()   ## 每件还在的防具触发一次 on_armor_equip()
```

`add_armor()` 内部挂完会调 `HpComponentZombie.collect_armors()` 重收一遍 ——
**少了这一步那一层根本不参与伤害结算，而且是静默的（没有任何报错）**。
展示态（`ready_show()`，图鉴 / 开局预览）同样会走 `build_runtime_parts()`，好让图鉴里的僵尸戴着它的防具。

## 6. 换脚本时会发生什么

`Object.set_script()` 会**重建脚本实例**，本体场景里配的导出值会被清回脚本默认值
（编辑器里「改脚本」会帮你补回来，运行期没人补）。`ZombieRuntimeRecipe._apply_script()`
因此先把「会存进场景」的导出项抄一份、换完再灌回去，口径与编辑器一致。

⚠️ 唯一抄不回来的是**节点引用类**导出项（如 `iron_node`）：本体还没进树，路径解析不了，
读回来是 null，写 null 反而会把场景里那条路径冲掉。要做铁器防具就在 `build_runtime_parts()` 里自己补：

```gdscript
	var armor := add_armor(ConstArmor.E_ArmorType.Bucket, 1100)
	armor.iron_node = get_node("Body/BodyCorrect/Anim_bucket") as IronNode
```

## 7. 怎么让它真的出场

- **自然出怪**：配方里 `spawn_power` / `spawn_weight` 都要 > 0（**成对生效**，缺一个两头都撤），
  并且关卡数据 `ResourceLevelData` 的刷新类型表里带上这个编号；
  权重在 `ZombieWaveCreateManager.init_zombie_wave_create_manager()` 里按注册表重取一次，
  所以「关卡开局之后才注册」的僵尸也要能进本关的池子。
- **点名生成**：不走权重池也行 —— 关卡脚本 / 技能直接 `create_norm_zombie(new_type, ...)`。
- **想在选卡界面里亲手放一只**：还要再插一张**僵尸卡** —— `ZombieRuntimeKit`（本体侧，
  与植物的 `PlantRuntimeKit` 对称）一次做完三件事：往 `AllCards` 插卡并 `rebuild()`、
  从这只僵尸自己身上取卡面、把它加进已解锁名单（`GlobalGameState.curr_zombie`，**每局补一次**）。
  热注册只负责「这只僵尸存在」，卡片是另一件事（细则见 [卡片与选卡流程.md](卡片与选卡流程.md)
  「运行期注册的角色也能有卡」）。
  那页只在「僵尸卡可用」时生成：总开关或控制台「调试模式」打开即可。
