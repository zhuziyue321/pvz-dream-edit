# 关卡格式 V2 —— 脚本驱动 × 数据驱动

## 0. V1 的三条裂缝（V2 要解决的）

V1 已经**半混合**了：时间轴「一种事件 = 一个脚本」（见 [关卡时间轴.md](关卡时间轴.md)）。但缺的是**组合能力**：

| # | 裂缝 | 表现 |
|---|---|---|
| 1 | **时间轴是纯线性数组，没有控制流** | 想做「第 3 波插一段戴夫」「循环 3 批罐子」「满足条件才执行」，只能新建事件脚本把逻辑硬塞进 `run()` —— 想自定义就必须写代码，且这份代码无法被别的关用数据复用 |
| 2 | **`.tres` 存不了条件** | `wait_until(condition: Callable)` 的条件是脚本，资源里存不下 `Callable`，这是数据驱动表达力的硬天花板 |
| 3 | **玩法分支硬编码在各 manager 里** | 加一种玩法要动 `zombie_manager.gd:124` / `card_manager.gd:64,88,101` / `plant_cell_manager.gd:82,167` / `main_game_manager.gd:645` 及若干 UI 脚本 |

另有两个次生问题：`ResourceLevelData` 是 84 字段的扁平大杂烩；共性配置重复（生存 10 关各持一份时间轴副本）。

## 1. 设计原则：四条通道，各解决一件事

| 通道 | 面向 | 解决什么 | 要不要写代码 | 状态 |
|---|---|---|---|---|
| **数据层** | 所有人 | 数值：出怪表 / 卡槽 / 地图 / BG / 阳光 | 否 | V1 已有，沿用 |
| **编排层** | **玩家自制关** | 关卡内事件编排：分支 / 循环 / 条件等待 | 否，纯 `.tres` | ⬜ 待做（P1） |
| **逃逸层** `level_script` | 作者 / 模组 | 无限自定义：响应运行时事件、覆盖判定 | 是，`.gd` | ⬜ 待做（P2） |
| **规则层** `rules[]` | 新玩法 | 玩法可插拔，消掉散落的 `match` 分支 | 否（复用现成规则） | ⬜ 待做（P3） |

**为什么「编排层」必须存在**（不能只做逃逸层）：玩家自制关卡是把 `.tres` 丢进 exe 同级目录（见 `src/menus/choose_src/levels/custom_choose_level.gd`）。**要求自制关卡必须写代码，生态就起不来**。所以纯数据也要能表达复杂流程。

## 2. 版本与兼容

```gdscript
@export var format_version: int = 1   # 1 = 旧格式；2 = V2
```

| 版本 | 含义 | 迁移 |
|---|---|---|
| **1** | 扁平字段；存档键由选关场景**遍历顺序**现场拼出 | 不动，一个字段都不用改 |
| **2** | `save_key` 显式化 +（后续）`level_script` / `rules[]` / 控制流事件 | 逐关迁移，改 `format_version = 2` 即可 |

**版本只分派「哪些字段有效、怎么读」，不要求全量迁移。** `level_data.gd` 里所有 V2 字段都留安全默认值，`format_version == 1` 的关卡行为与迁移前完全一致。

### 已落地（P0）

| 字段 | 作用 |
|---|---|
| `format_version` | 版本标记 |
| `save_key` | 存档键显式化，**留空时回退旧拼法**（`str(game_mode)_str(level_page)_str(level_id)`） |

`set_choose_level()` 的兼容写法：

```gdscript
if save_key != "":
    save_game_name = save_key
    return
save_game_name = str(game_mode) + "_" + str(level_page) + "_" + str(level_id)
```

**存档键为什么不能推算只能 dump**：它依赖选关场景遍历节点的顺序（`choose_level.gd:31 generate_level_id()`），推算错了玩家的老存档就找不回来。用 `test/scenarios/tool_dump_save_keys.gd` 真跑一遍选关场景读权威值，再交给 `tool_write_save_keys.gd` 写回。

## 3. 各层规格

### 3.1 编排层：控制流事件（P1）

在现有 `timeline_event/` 12 个事件脚本旁新增结构型事件，与「一种事件 = 一个脚本」同构：

| 事件脚本 | 参数 | 语义 |
|---|---|---|
| `..._sequence.gd` | `sub_timeline: ResourceLevelTimelineData` | 跑一条子轴。**可外引独立 `.tres` → 这是复用的关键** |
| `..._repeat.gd` | `times: int` + `sub_timeline` | 循环 N 次；`times = -1` 循环到关卡结束 |
| `..._branch.gd` | `condition` + `then_events[]` / `else_events[]` | 二分支 |
| `..._wait_until.gd` | `condition` + `timeout` | 条件等待（现在只能靠写脚本） |

**条件资源化**（新增 `condition/` 目录，与 `timeline_event/` 同构）：`ResourceLevelCondition` 基类 + `WaveReached` / `ZombieCountBelow` / `SunAtLeast` / `PotOpenedAtLeast` / `PlantTypePlaced` / `RoundAtLeast` / `TimeElapsed`，加 `Not` / `And` / `Or` 组合器。

预期收益 —— 4-5 砸罐子现在平铺的 8 条事件收敛成一条：

```
Repeat(3):
  ├─ DaveDialog        # 内容仍取 crazy_dave_dialog_next_round，按轮自动取
  ├─ StartBattle(until PotAllOpened)
  └─ ClearField
```

生存 10 关可共用**同一份** `survival_loop.tres`（现在各自一份副本）。

**不建议**把 `Parallel` 放进第一批：Godot 协程并行 + 时间轴 `_run_id` 顶轮机制叠加，调试成本高，等真有需求再加。

### 3.2 逃逸层：`level_script` 钩子（P2）

> **硬约束 [§1-8](../项目规范.md)**：只有一关（或极少数关）用到的特殊机制**必须**写在关卡脚本里
> （`_init()` 属性 / `run_flow()` 流程 / `init_level_items()` 专属物品），**不进游戏本体**；
> 被 ≥2~3 关复用时才上浮成通用字段 / 组件 / 规则。细则见
> [规范细则存档 D-07](规范细则存档.md#d-07-关卡脚本-vs-游戏本体一次性机制的落位)。

```gdscript
@export var level_script: Script = null   # 继承 LevelScriptBase；null = 纯数据关
```

钩子清单（基类给空默认，全可选实现）：

| 类别 | 钩子 |
|---|---|
| 生命周期 | `on_init(para)` / `on_start(mg)` / `on_round_start(mg, round)` |
| 时间轴 | `build_timeline(para) -> ResourceLevelTimelineData`（返回非空则**覆盖**数据轴） |
| 波次 | `on_wave_start(mg, wave, is_big_wave)` / `modify_wave_list(mg, wave, list) -> Array` |
| 运行时 | `on_plant_placed` / `on_zombie_spawned` / `on_zombie_killed` / `on_sun_changed` / `on_pot_opened` |
| 判定覆盖 | `is_battle_finished(mg) -> int`（**`-1` = 走默认**，`0/1` = 覆盖） |
| 胜负 | `on_win(mg)` / `on_lose(mg)` |

> `bool` 表达不了「未实现」，判定覆盖用 `int` 三态。

### 3.3 规则层：`rules[]`（P3）

> `LevelScriptBase.create_wave_zombies()` 负责把「这批僵尸怎么进场」问给关卡脚本，

### 3.4 关卡注册表 `LevelRegistry`（P0 已落地）

`src/levels/core/level_registry.gd`，静态类（**不做 autoload**，避免第 10 个 autoload 的初始化顺序风险）。

- **id = `.tres` 文件名 basename**（`adventure_01_01`）—— 与自制关卡现有约定一致（`custom_choose_level.gd` 用的 level_id 就是文件名），内置关与自制关共用一套 id 规则
- 内置关**扫目录自动登记**（约定 > 配置，不维护 95 行大表，加一个脚本就自动进表）
- **识别走白名单**（2026-10-06 改）：一个 `.gd` 只有在继承链上出现 `LevelScriptBase` / `ResourceLevelData`（`LevelRegistry.LEVEL_BASE_CLASS_NAMES` / `is_level_script()`）才算关卡，**其余一律不登记** —— 不再按「文件名以模式名为前缀」判，因为关卡专属辅助脚本按约定也带关卡名前缀，前缀分不出关卡与辅助脚本（实测 `adventure_05_05_bungi_blitz.gd` 是 `extends Node`，旧判据会把它们登记成假关卡）
- API：`all_ids()` / `ids_by_mode(mode)` / `get_level_path(id)` / `get_level(id)` / `has_level(id)` / `register_custom(id, path)` / `rescan()`
- **不缓存实例**：`get_level()` 直接 `load()`，与「同一路径 = 同一实例」的引擎语义一致。关卡资源是**有状态**的（`init_para()` / `set_choose_level()` 会改字段），自己缓存容易与场景引用不一致

## 6. 踩坑

1. **`.tres` 的属性是「按顺序」设置的** —— 新字段插在 `[resource]` 之后、`script = ExtResource(...)` **之前**时，资源还没挂上脚本，字段会被当成未知属性**静默忽略**（文件里明明有，加载回来是默认值，且不报错）。
   → **正解**：插入位置必须在 `script =` 那一行**之后**（`tool_write_save_keys.gd:_write_fields` 已处理）。

2. **static 方法名撞内建方法** —— `LevelRegistry.get_path()` 被调用时报 `Invalid call to function 'get_path' in base 'GDScript'. Expected 0 argument(s)`：`Resource`/`Script` 有内建 `get_path()`，同名的 static func 会被解析成内建方法。
   → **正解**：改名 `get_level_path()`。同理 `has()` 改成 `has_level()`。

3. **新建 `.gd` 的 `class_name` 不是立即可用** —— 刚创建的脚本，下一次 Godot 启动前全局类表里没有它，跑无头脚本会报 `Identifier "LevelRegistry" not declared`。
   → **正解**：新建带 `class_name` 的脚本后，**先随便跑一次引擎**让它进全局类表，再写引用它的代码。

4. **同进程内 `CACHE_MODE_REPLACE` 顶不掉仍被引用的资源** —— 写回 `.tres` 后立刻 `ResourceLoader.load(path, "", CACHE_MODE_REPLACE)` 回读，拿到的仍是旧值（该资源正被选关场景引用）。
   → **正解**：回读**另起一个进程**跑（这就是 `probe_save_key.gd` 独立于 `tool_write_save_keys.gd` 的原因）。

5. **不要用 Godot 重新保存关卡 `.tres`** —— 会冲掉文件里 `;` 开头的原版考据注释（出处见 [关卡时间轴.md](关卡时间轴.md)）。迁移工具一律**文本级按行改写**。

6. **探针是 `RefCounted`，没有 `get_tree()`** —— 用 `a.get_tree()`（autopilot 是 Node）。
