# 模组机制（原版之外的功能一律做成模组）

> **[面向 AI Agent]** ｜ **触发条件**：要新增 / 改动一个**原版没有的玩法**，或要开 / 关手套这类"同人加的"功能时
> **读完你能**：知道模组放在哪、入口脚本要继承什么、什么时候被装载、本体里允许留什么；照三步新增一个模组
> **强制级别**：**参考**（机制说明，不做也不打回） ｜ **不读的风险**：把非原版玩法直接写进本体，之后"关掉它"要在 5 个文件里各堵一层分支（手套就是这样走过一遍的）
> **关联**：仓库入口 [../../AGENTS.md](../../AGENTS.md) ｜ 硬约束 [../项目规范.md](../项目规范.md) §1 ｜ 手持物 [手持物实现.md](手持物实现.md) ｜ 目录地图 [../README.md](../README.md)

---

## 一、为什么要有模组这一层

本仓库的目标是**复刻原版**。凡是原版没有的玩法（关卡内手套、选卡界面僵尸卡片…）都不该长在本体里 ——
长进去之后，"临时下线"就只能在各处堵分支。

手套就是活教材：2026-10-04 为了隐藏手套，在 5 个本体文件里各加了一层
`ConstFeatureSwitch.GLOVE_ENABLED` 判断（卡槽按钮 / G 键 / 组件订阅 / 解锁判定 / 4-6 戴夫对话），
还顺带把两个探针改成跳过（见 [工作记录 2026-10-04_隐藏关卡内手套功能](../../docs/工作记录/2026-10-04_隐藏关卡内手套功能.md)）。
改成模组之后：**关 = 不装载**，本体零分支、零节点、零常量。

一句话判据：

> **原版有 → 写在本体；原版没有 → 做成模组。**

## 二、目录与文件

### 三处位置：两个加载源 + 框架（先分清再动手）

模组有**两个加载源**，`user://mods/`（玩家那份）**优先**，那里没有这个模组时才用
`res://mods_builtin/`（内置源）。

- 两个源**不互相复制**（2026-10-15 起）：内置源**不会**在启动时铺到 `user://mods/`。
  想改内置模组，自己把它**整个目录**拷到 `user://mods/` 下再改 —— 拷过去才生效，没拷就跑内置那份。
  （早先的「自动复制 + 内容指纹决定要不要重铺」已撤销：它会把玩家改过的文件冲回去，
  也多一份「到底跑的是哪边」的解释成本；现在哪边有就跑哪边，一眼可判。）
- 内置源**永远齐全**，所以「只给玩家一个游戏文件」时模组也不会静默失效；
  玩家那份**读不出来**时（导出把脚本二进制化后引擎认不出的形态）也会退到这里再试一次。

| 位置                    | 是什么                                                                                | 谁在用它                    |
| --------------------- | ---------------------------------------------------------------------------------- | ----------------------- |
| `mods_builtin/`       | **内置加载源**（工程内，导出后躺在包里）：玩家目录里没有这个模组时加载它                               | 开发时改这里 / 默认加载源           |
| `user://mods/`        | **优先加载的那份**：玩家可以放自己的模组，也可以整目录拷内置模组过来改                                  | 游戏运行时（有就优先）             |
| `src/mods/`           | **框架**：`mod_manager.gd`（autoload）+ 基类 `mod_base.gd` + `mod_ids.gd` / `mod_config.gd` / `mod_category.gd` 三份契约 —— 全是 `res://` 资源，模组源码不在这里 | 引擎 autoload / 本体编译引用 |

> **加载根怎么定的**（`ModManager._resolve_mod_roots()`）：按**模组**判定 ——
> `user://mods/<入口脚本>` 在 → 整个模组从 `user://mods/` 加载；不在 → 从 `res://mods_builtin/` 加载。
> **一个模组只从一个根加载**：模组内部靠 `preload("相对路径")` 互相引用，
> 一半 `user://`、一半包里会错位报错。所以拷内置模组请拷**整个目录**；
> 拷漏了**不**退回内置源（改了不生效更难查），而是启动打一行 warn 列出缺哪些文件。
> **基类不在根里**：`mod_base.gd` 只有 `src/mods/` 那一份，模组入口一律
> `extends "res://src/mods/mod_base.gd"`（绝对路径在两个根下都指到同一份），拷模组目录时不用带它。
> 每次启动会打一行 `ModManager: 模组加载根 —— 玩家目录 N 个 [...]，内置源 M 个 [...]`，读那一句就知道走的哪根。

## 2.1 模组存档文件（`user://<用户名>/mod_config.ini`）

开关与**模组自己的设置**放在同一份文件里，一个模组一个段（段名 = 模组 id），
段里的 `enabled` 是开关，其余键是这个模组自己的设置：

```ini
[glove]
enabled = true
cooldown_enabled = false
cooldown_time = 5.0

[netplay]
enabled = false
target = "127.0.0.1:8912"
send_rate = 60.0
```

- **一人一份**：与 `config.ini` 同目录（用户在开始菜单里切，存档就换一份）。
  换用户时 `ModManager` 自己盯 `UserManager.signal_users_update` 重读，模组跟着补装 / 卸载。
- **改的入口是模组页面**（§七）：点一下开关就落盘，不用来回改 `data/` 里的资源
  （那在导出后是 pck 内的只读文件，本来也写不回去）。
- **`data/mods/mod_config.tres` 退成工程默认**：只有在这个用户的存档文件**不存在**时照它播种一份，
  之后一律以存档文件为准 —— 想让**所有新用户**默认开某个模组，改它；只改自己这一个用户，去模组页面。
- **模组读 / 写自己的设置**走 `ModManager`（不用给 `ConfigService` 加字段、也不用自己管存盘）：

```gdscript
var value := ModManager.get_mod_value(ModIds.GLOVE, "cooldown_time", 5.0)
ModManager.set_mod_value(ModIds.GLOVE, "cooldown_time", 7.0)   # 改内存 + 帧末落盘
```

  想立刻落盘（不排队）就调 `ModManager.save_mods()`。

## 2.2 模组自己的素材（贴图 / 场景）怎么读

**放模组自己目录里，一律走管理器的口子读，别往本体 `assets/` 塞文件。**

```gdscript
## 模组入口（ModBase 子类）—— rel_path 相对**模组目录**
var tex := load_asset("tongtong.png")          # 等价 ModManager.load_mod_asset(get_mod_id(), rel_path)

## 角色 / 组件 / 规则脚本（不是 ModBase 子类）：直接找管理器
var tex := ModManager.load_mod_asset(ModIds.MORE_ARMOR, "tongtong.png")
```

`load_mod_asset()` 内部：
- 按本模组**当前加载根**（`user://mods/` 优先 / `res://mods_builtin/` 兜底）+ 模组自己的目录
  拼出完整路径（`_mod_root()` 给的是**父目录**，别漏了 `<id>/` 这一层）；
- `res://` 下的图片走引擎导入管线（`load()` 直接得 Texture2D）；
- `user://` 下的图片**没有 `.import`**（引擎只对 `res://` 跑导入），自动退回
  `Image.load_from_file()` + `ImageTexture.create_from_image()`；
- 结果按「模组 + 相对路径」缓存，重复读只解码一次。

**为什么不能 `preload("res://assets/...")`**：那是把模组素材塞进**本体**目录 ——
模组不自包含（整目录拷到 `user://mods/` 时贴图不跟着走），导出后 `user://` 那份更读不到。
历史遗留见 `more_armor`（原先 10 张桶贴图裸放在 `assets/` 根，已移入模组目录）。

⚠️ **`user://` 下的图片不能 `preload`、也不能在 `.tscn` 里写相对路径**：
- `preload` 是编译期常量，只能指 `res://`；`user://` 那份一律运行期用 `load_mod_asset()` 读。
- `.tscn` 里的 `ext_resource` 贴图引用跑不了 GDScript，只能写**绝对** `res://mods_builtin/<id>/...`
  （**不能**写相对 `xxx.png` —— 相对路径在 `user://` 加载根下会指到**没被导入**的 png，读不出来）。
  所以「模组场景 + 同目录贴图」时，场景里引用的是**包里内置源**那份（永远齐全、已导入）。
  ⚠️ 这条只在**同一个模组**内成立；跨模组的脚本 / 素材（如 `pvz2/` 依赖 `pam/`）一律走
  `ModManager.get_mod_asset_path()` / `load_mod_asset()` 在运行时取（先例 `pvz2/pam_bridge.gd`，
  见 §6.7.0）。

## 2.3 模组依赖（声明 → 打开时补开 → 页面末尾列出）

一个模组可能要用到**另一个模组**的东西（比如"招笑版改过的伤害按明日方舟的公式结算"）。
原版没有"模组依赖"这个概念，所以在本框架里**显式声明**：

**声明**：入口脚本重写 `ModBase.get_mod_dependencies()`，返回 `ModIds` 常量数组：

```gdscript
func get_mod_dependencies() -> Array[StringName]:
	return [ModIds.ARKNIGHTS]
```

默认空数组 = 不依赖任何模组。**只用来表达"缺了它就装不起来 / 跑不对"** ——
"顺便建议开哪个模组"别写在这里：打开本模组会把依赖的开关**强行改掉**（见下）。

**打开本模组 = 依赖一并打开**（`ModManager.set_mod_enabled()` 里递归补开，带环保护）：
模组页面上打开一个声明了依赖的模组时，依赖在**同一瞬间被补开**，存档文件里也是开着
（下次启动照旧）。启动 / 换用户时也会补一遍（`_ensure_dependencies_enabled()`）——
存档文件可能被手改过、或 `data/mods/mod_config.tres` 的工程默认漏开了依赖，
留着"开着却跑不起来"的状态不如启动时补齐。

| 情形 | 口径 |
|---|---|
| **关依赖** | 只补开、**不连锁关**：关掉被依赖的模组不会连带关掉依赖者（那是玩家自己的选择 —— 他会在详情末尾的依赖列表里看到哪个依赖"未启用"） |
| **依赖成环**（A 依赖 B、B 依赖 A） | 打一行 error，环上的开关不自动补开，不卡死 |
| **依赖未登记的 id**（写歪了 / 模组删了） | `ModManager.get_mod_dependencies()` 打一行 error 后剔除，页面不显示它；自己依赖自己也这么处理 |
| **旧版入口脚本**（`user://mods/` 下没跟着升级的那份） | 没有这个方法 = 空数组，不影响装载 —— 本体侧一律 `has_method()` 防御式转调 |

**模组页面**（§七）详情**末尾**有一块「依赖的模组」（页面自己造，不归模组）：
每个依赖一个按钮（名字 + 开 / 关状态），**点了跳过去**看那个模组的详情
（分类过滤会一并清掉，保证列表里看得见它）。本模组关着时这块照样能点 ——
它是页面自己的导航，与模组开不开无关。

## 三、装载时机

```
游戏启动（autoload）
  ModManager._ready()
    ├─ 定每个模组的加载根：user://mods/<入口脚本> 在就用玩家那份，否则用内置源（见 §二）
    ├─ 读工程默认 data/mods/mod_config.tres
    ├─ 读用户存档 user://<用户名>/mod_config.ini（覆盖上面的默认；文件不在就播种一份）
    ├─ 为每个 id 创建 ModBase 实例（不论开关）
    ├─ 已启用模组缺的依赖一并补开（get_mod_dependencies()，见 §2.3）
    └─ 对已启用的调 install()（全局一次性安装）

每局主游戏
  MainGameManager.init_manager()
    ├─ background / card / plant_cell / game_item 的 init_manager()
    ├─ ModManager.install_mods_to_main_game(self)   ← 模组在这里装
    └─ hand_manager.init_manager()                  ← 之后才登记手持物组件

重读全局存档（启动 / 换用户）
  Global.reload_session_for_current_user()
    └─ ModManager.notify_session_reloaded()         ← 已启用模组补回写进存档态里的东西
                                                       （ModBase.on_session_reloaded()）
```

不是每个模组都要进主游戏：自制关卡模组只走 `install()`（菜单层：注入选关场景路径 + 挂主菜单入口按钮），
它没有 `install_to_main_game()` —— 那是给「关卡内玩法」用的。

`install_to_main_game()` **必须排在 `hand_manager.init_manager()` 之前** ——
`HandManager` 是在 `init_manager()` 里遍历 `get_children()` 登记组件的，晚加的组件登记不进去。

## 四、新增一个模组的三步

1. `ModIds` 加一个常量（`const XXX := &"xxx"`）。
2. `ModManager.MOD_SCRIPT_PATHS` 加一行（id → 入口脚本路径）。**这是唯一允许出现 id → 脚本映射的地方**（硬约束 §1-4）。
3. `mods_builtin/<id>/` 下写入口脚本（`extends "res://src/mods/mod_base.gd"`）与该模组自己的脚本 / 场景：

```gdscript
## ⚠️ 两行都不能照原版模组的老写法来（原因见 §2.0 与下面「在 `user://` 下写代码的规矩」）：
##   · 不能写 `class_name XxxMod` —— `user://` 下的脚本不注册全局类
##   · 不能写 `extends ModBase`   —— 同上；基类用**框架那一份的绝对路径**指过去
extends "res://src/mods/mod_base.gd"

func get_mod_id() -> StringName:
	return ModIds.XXX

func get_mod_name() -> String:
	return "某某玩法"

func get_mod_description() -> String:
	return "一句话写清它改了什么、为什么不属于原版"

## 每局安装：要挂节点就在这里挂（本体场景里没有你的一席之地，全靠现场装）
func install_to_main_game(main_game: MainGameManager) -> void:
	var 挂载点 := main_game.get_node_or_null("%某个本体唯一名节点")
	if 挂载点 == null:
		Log.error("某某模组：主游戏缺少挂载点，本局不安装")
		return
	...
```

### 在 `user://` 下写代码的规矩（照抄现役模组即可）

`user://` 下的脚本 **`class_name` 不会注册成全局类**（实测 Godot 4.6.2），所以下面这些写法**一律编译不过**：

| 不能写                          | 改成                                                                 |
| ---------------------------- | ------------------------------------------------------------------ |
| `extends ModBase`            | `extends "res://src/mods/mod_base.gd"`（基类只有框架一份，绝对路径；同目录其它脚本仍用相对路径） |
| `class_name XxxMod`          | 删掉（别处要引用就 `const XxxMod := preload("xxx_mod.gd")`）                 |
| `var m: ModBase` / `-> ModBase` | 去掉类型标注；`ModBase` 常量只用来取 `DETAIL_REFRESH_META` 这类常量               |
| `GloveMod.CONST` / `X.new()` | 先 `const GloveMod := preload("xxx.gd")` 再用                          |
| 两个文件互相 `preload`             | **会成环**，把两边都要读的东西抽成第三个文件（如 `glove_settings.gd` / `hammer_settings.gd`） |

两条实测结论（已写进 `mod_manager.gd` 的类注释）：

- `user://` 的脚本**不走资源缓存**，每次 `load()` 都是新对象 → `Script.instance_has()` **恒为 false**，
  判断「是不是 ModBase 子类」要沿 `get_base_script()` 基链**比路径**。
- `res://` 的脚本**可以** `preload("res://mods_builtin/<id>/xxx_mod.gd")`，`test/scenarios/` 下的探针就靠这个引用模组
  （preload 要编译期常量，写不了「当前加载根」，探针一律指内置源那份）。

**例外**：`mod_ids.gd` / `mod_config.gd` / `mod_category.gd` **保留 `class_name`** —— 它们是本体 ↔ 模组的契约，
`res://` 侧（`adventure_04_06.gd`、`data/mods/mod_config.tres`、模组页面）要按名字编译引用；
三份都在 `src/mods/`（与 `mod_base.gd` 同一处）。

要开它：模组页面（主菜单 → 选项 → 控制台 →「模组」）里点开关即可（存进存档文件，见 §2.1）；
想让它**对所有新用户默认就开着**，才往 `data/mods/mod_config.tres` 的 `enabled_mods` 里加 `&"xxx"`。

**可选第 4 步**：重写 `ModBase.create_detail_control()`，让**模组页面**（§七，主菜单 → 选项 → 控制台 →「模组」）
右侧显示这个模组自己的说明 / 开关 / 状态 —— 页面只保证名称、开关、说明三样，剩下全交给模组。
想放勾选框 / 按钮 / 滑条 / 输入框 / 只读行就接着用 [`ConsoleEntryControl`](控制台.md)
（一个实例造一堆控件、`refresh()` 一次刷全部值）；**模组自己的设置一律存进模组存档文件**
（`ConsoleEntry.bind(getter, setter)` 里读写 `ModManager.get/set_mod_value()`，见 §2.1）——
不走 `ConsoleEntry.bind_config()`：那是控制台的通用键值区，与模组开关不在一份文件里。

**可选第 5 步**：本模组要用到**另一个模组**的东西时，重写 `ModBase.get_mod_dependencies()`
声明依赖（打开本模组会把依赖一并打开、页面末尾列出它们，见 §2.3）——
现役内置模组一个都没声明，这是给将来的模组 / 玩家自己的模组用的口子。

> **模组的界面已经不在控制台里了**（2026-10-11）：`ModBase.register_console_entries()` 钩子与
> `ModManager` 在「模组」组里放的 `mod_switch_*` 开关都已删除，控制台只剩本体那三组 ——
> 别再去写那个钩子，它没有调用方。

## 五、边界规则（这几条决定了"模组是不是真的模组"）

1. **本体不 import 模组**：本体文件里不许出现模组里的类名 / 路径。
   本体只调 `ModManager.is_mod_enabled(ModIds.XXX)`。
2. **模组可以用本体的一切**：注册表枚举槽位、格子 API、单例、输入动作（`ShortcutKeys_*`）——
   模组是装在现有扩展点上的，反过来不行。
3. **本体留给模组的槽位可以有名字**：例如 `HandComponentBase.E_HandComponentType.Glove`
   这个枚举值就是给手套模组留的手持物类型槽位（没有它模组没法注册手持物）。
4. **模组自己的事件不走 EventBus 常量表**：`ConstEventName` 属于本体，模组往里塞事件名等于本体化。
   模组内部连线用**信号**（如 `UIGlove.glove_clicked` → `HandComponentGlove.on_click_glove`）。
5. **模组建的节点不能写 `@onready %同名`**：场景唯一名只对场景里本来就有的节点生效，
   运行时 `add_child` 的节点要由模组**注入引用**（见 `HandComponentGlove.set_visual_nodes()`）。
6. **本体 API 不带模组的名字**：`PlantCell` 的搬运 API 叫 `move_*` 不叫 `glove_*`
   —— 它是通用能力（手套模组与僵尸迷阵三消共用），名字里有手套就等于本体认识手套。
7. **跨模块复用的美术 / 演出资源留在原处**：如 4-6「戴夫送手套」的台词与戴夫手上举的手套
   （`data/dave/dialog/adventure_04_06_glove.tres`、`src/dave/hand_item/hand_glove.tscn`）属于关卡内容，
   由关卡脚本自己持有 ——
   让关卡脚本去 `preload` 模组目录里的文件，会造出一条"本体 → 模组"的硬依赖，删模组就编译不过。
   （手套改成"与商店园艺手套同时获取"之后，这段赠礼演出已不再播，见 [手持物实现.md](手持物实现.md) §五。）
8. **模组内部不靠 `class_name` 互相认**：入口脚本在 `user://` 下，`class_name` 不注册成全局类，
   同目录 / 跨目录一律 `const X := preload("xxx.gd")` + `extends "xxx.gd"`（规矩清单见 §四）。
   `ModIds` / `ModConfig` 是例外，它们保留 `class_name` 供本体引用。
9. **要改"判定方法"就得换资源，本体留的是通用口子**：能不能种植写在
   `ResourcePlantCondition` 的**方法**里（`judge_is_can_plant()` / `judge_purple_card_can_plant()`），
   改字段改不动，所以本体 `CharacterRegistry.set_runtime_plant_condition()` 允许运行期**整份换掉**
   某种植物的条件资源（`clear_runtime_plant_condition()` 换回来）—— 与 `register_runtime_zombie()`
   同一思路（静态表是编译期数据，运行期要改就走覆盖表）。
   紫卡直接种植模组（§6.5）就是这么装的：本体里没有一句关于该模组的分支，只有这个口子。
   换的时候**造新实例**，不要改原对象 —— 条件资源是共享的（多种植物共用同一份 `.tres`）。
10. **新增一只植物 = 一张配方 + 运行期登记，本体不认识它**：`PlantInfoData.PLANT_INFO` 是
    const 表、运行期写不进去，又不能预先在里面 `preload` 模组的场景（本体不 import 模组）。
    所以新增植物走三步：模组填一张 `PlantRuntimeRecipe`（场景 / 冷却 / 阳光 / 地形 / 卡面），
    交给 `PlantRuntimeKit.install()` —— 登记注册表、插卡并画卡面、解锁这一串都由 Kit 收着
    （`uninstall()` 反向全撤）；**本体不必再留 `PlantIds` 空槽位**，字符串 id 自己起即可
    （留空则由注册表分配 `runtime_plant_N`）。还想让玩家在**选卡界面**里挑到它，装完再自己登记一页
    `AllCards.register_plant_choose_page([...])` —— 注册 / 解锁都只是「这株植物存在」，
    页里的格位 / 顺序由模组自己排（见 [卡片与选卡流程.md](卡片与选卡流程.md) 的「选卡页」）。
    DLC 植物模组（§6.4 的水盆，2026-10-18 起并入该模组）就是这么装的，完整接口清单见 [运行期植物.md](运行期植物.md)。
11. **底部植物（花盆 / 睡莲那一层）自己声明地形位**：`Plant000DownBase.own_condition_bit`
    非 0 时，`PlantCell.down_plant_change_condition()` 按它改格子地形（种下 = 加该位，
    移除 = 还原），为 0 走原版那两套（水池行按睡莲、其它行按花盆）。
    原版之外的底部容器（水盆）靠这个口子落地，本体的格子里没有一句关于它的分支。

## 六、现役模组

### 6.1 手套（`mods_builtin/glove/`）

`GloveMod.install_to_main_game()` 现场造三件套（本体场景里一个手套节点都没有）：

| 装的东西         | 挂到哪                                       | 说明                                            |
| ------------- | ----------------------------------------- | --------------------------------------------- |
| `HM_Glove`    | `HandManager` 下                           | 手持物组件 `HandComponentGlove`，随后被登记为 `Glove` 类型   |
| `UIGlove`     | `ShovelContainer`（以 `%UIShovel` 为锚点取它的父节点） | 卡槽按钮，来自 `glove_slot.tscn`；G 键由它自己收             |
| `RealGlove`   | `%CanvasLayerTemp`                        | 跟随鼠标的真手套                                       |

另外三件跟着模组走的东西：

- **解锁**：与商店里的**园艺手套**同时获取 —— `GloveMod.is_unlocked()` 读的是商店的买断记录
  （`GardenManager.E_GardenTool.GardeningGlove`，$1000，需先通完 5-4 解锁禅境花园才上架），
  买下它 = 关卡内手套到手。旧口径是 `UNLOCK_ADVENTURE_LEVEL = 35`（通关 4-5），已改掉；
  无论哪个口径都归模组，本体不再有"手套解锁"这个概念。
- **搬运逻辑**：`src/items/plant_cell.gd` 的 `move_*` API 留在本体（三消也要用），
  搬运状态机在模组的 `HandComponentGlove` 里。
- **冷却设置**（原版没有，默认**关**）：搬完一株之后才能再用，两种口径二选一 ——
  **按秒数**（搬完等几秒）或**按波数**（连波次管理器的 `wave_started`，每开一波减 1，减到 0 冷却好）。
  开关 / 方式 / 时长 / 波数在**模组页面**里设（四条 `ConsoleEntry`：`glove_cooldown_enabled` /
  `glove_cooldown_time` / `glove_cooldown_by_wave` / `glove_cooldown_wave`），
  值落在**模组存档文件**的 `[glove]` 段（键名 `cooldown_enabled` / `cooldown_time` /
  `cooldown_by_wave` / `cooldown_wave`，读写走 `ModManager.get/set_mod_value()`，不走 `ConfigService`）；
  读值口是 `GloveMod.is_cooldown_enabled()` / `is_cooldown_by_wave()` / `get_cooldown_time()` /
  `get_cooldown_wave()`（静态，每局组件读它）。
  计时在 `HandComponentGlove._process()`（**不是** `hand_process()` —— 那个只在手套拿在手上时才被调到，
  而冷却恰恰发生在放下之后）；按波数时不倒数，等 `_on_wave_started()` 逐波扣。
  关卡没有波次（`E_MonsterMode.Null` 之类）时按波数冷却不生效（否则玩家会被永久锁住）。
  冷却中点手套只有一声 `buzzer`，卡槽图标盖一层遮罩随剩余时间 / 剩余波数往回收。

玩法细节见 [手持物实现.md](手持物实现.md) §五。

### 6.2 自制关卡（`mods_builtin/custom_level/`）

原版没有「玩家自制关卡」这个功能，所以整条链路（选关界面 / 关卡按钮 / 主菜单入口）都在模组里。
`CustomLevelMod.install()` 装两样东西，本体场景里一个自制关卡节点都没有：

| 装的东西 | 怎么装 | 说明 |
|---|---|---|
| 选关界面路径 | `MainSceneMap[MainScenes.ChooseLevelCustom] = custom_choose_level.tscn` | `ChooseLevelCustom` 是本体留的枚举槽位（边界规则 3），**路径由模组注入** —— 本体不许出现模组里的路径 |
| 主菜单入口按钮 | 监听 `SceneTree.root.child_entered_tree`，认出主菜单就把 `custom_level_entry_button.tscn` 挂到 `BG_Right` | 与手套的 `UIGlove` 同款：现场装。主菜单每次重新加载都会补一次 |

- 关卡目录约定（`user://custom_level`，编辑器与导出后同址）见 [关卡格式V2.md](关卡格式V2.md) §3.5 —— 扫描器现在在 `mods_builtin/custom_level/custom_choose_level.gd`。
- **所有模组都可以自带关卡**（2026-10-17 加）：每个模组在自己目录下放一个 `levels/`
  （`CustomChooseLevel.MOD_LEVEL_DIR`），摆法与玩家目录完全一样（关卡包优先、散装 `.gd` 亦可）。
  扫描时一起扫掉（`get_mod_level_dirs()`：登记表里的全部模组**不论启用与否**，
  外加 `user://mods/` 下未登记模组目录兜底），目录随各模组加载根走
  （`user://mods/<id>/levels` 优先、`res://mods_builtin/<id>/levels` 兜底，与 §2.2 素材同一口径：
  整目录拷到 `user://mods/` 时自带关卡跟着走）。**同 id 时玩家目录优先**。
  典型用法：某个模组带几个演示关卡 / 玩法关卡，玩这个模组的人顺带就能玩到。
- 本体侧已清干净：主菜单没有自制关卡按钮、`choose_level.gd` 没有 Custom 分支、
  `LevelRegistry` 不再有 `register_custom()`（自制关不进内置注册表）。
- **默认关闭**：要玩自制关卡就在模组页面里把它打开（存进存档文件，见 §2.1）。
- 验证探针：`test/scenarios/probe_custom_level_mod.gd`（开 / 关两端都验）。

### 6.3 更多的防具（`mods_builtin/more_armor/`）

原版的桶只有铁桶一种，本模组按矿石阶梯再加三种：**铜桶 / 钻石桶 / 下界合金桶**，
各配一只戴桶的僵尸。**防具血量全是 1100，与铁桶一致** —— 特殊效果另算，不靠血量堆。

**铜桶 = 铁桶 + 氧化**（其余与铁桶完全一致）：
铜会氧化，所以桶一路上锈、一路变脆 —— 两条表现同属一件事，都挂在"在场时间"上：

| 表现                    | 落在哪                                                         | 口径                                                        |
| --------------------- | ----------------------------------------------------------- | --------------------------------------------------------- |
| **易伤（仅对防具有效）**       | `armor_copper_bucket.gd`（`ArmorComponent` 子类，模组自己那层防具）          | 在场 30 秒内易伤倍率 1.0 → 2.0；**只放大本层防具吃掉的那部分**，往下传的永远是原始伤害没被吃完的部分 |
| **贴图变成铜锈色**          | `zombie_copper_bucket.gd`（外观归宿主）                              | 按氧化进度把三张桶精灵（头上 / 被吸走 / 掉地上）从铜色 `lerp` 向铜锈色                |

**钻石桶 = 铁桶 + 20 击后变身**（其余与铁桶完全一致）：
钻石的特殊点不在血量、而在「中途换装」—— 血量跟铁桶一样是 1100，
但是头上那层挂的是模组自己的 `armor_diamond_bucket.gd`（不是基类防具），
它累计挨打次数，满 20 次就发个 `sig_need_transform` 信号，宿主推到帧末（`call_deferred`）
把整层防具换成下界合金桶那层、贴图也换、hp 接着用。

| 表现                           | 落在哪                                            | 口径                                                                 |
| ---------------------------- | ---------------------------------------------- | ------------------------------------------------------------------ |
| **挨打次数累计 + 变身信号**           | `armor_diamond_bucket.gd`（`ArmorComponent` 子类）       | 每次 `absorb_damage()` 命中累计 `+1`，满 20 次 emit `sig_need_transform`；不算「桶已经破了」与「触发过」 |
| **换装：贴图 + 防具 + 血量继承**         | `zombie_diamond_bucket.gd`（宿主）                 | 帧末把整层防具换成下界合金桶那层，**上限与当前血量都沿用旧防具**（血条比例连续、破损阶段不跳变），贴图换三张（头 / 吸走 / 掉地）    |
| **为什么不在 `absorb_damage()` 里直接换** | ——                                              | 伤害系统此刻正在 ② 加工阶段遍历防具链，改遍历目标会跳 / 重复，`call_deferred()` 推到帧末才安全                          |

**下界合金桶 = 铁桶 + 50% 减伤**（其余与铁桶完全一致）：
下界合金是三层里最硬的一层 —— 自身血量跟铁桶 / 钻石桶一样是 1100，但本层防具有 50% 减伤，
实际能挡的伤害 ≈ 2200。贴图四张，破损分四段（比铁桶多一层过渡）；**钻石桶变身后也是这个样子**。

| 表现              | 落在哪                                          | 口径                                                                              |
| --------------- | -------------------------------------------- | ------------------------------------------------------------------------------- |
| **本层 50% 减伤**  | `armor_netherite_bucket.gd`（`ArmorComponent` 子类） | 打到本层的伤害先按 0.5 折小再交给父类去扣血；**只减本层吃掉的那部分**，往下传按原始伤害口径算（与铜桶「只放大、不外溢」同源）    |
| **破损四段**        | `OreBucketZombieBase._apply_armor()`（公共装配）    | 贴图四张（完好 / 受损 / 更损 / 打烂），比铁桶多一层过渡                                                                  |

- **为什么易伤 / 减伤都长在防具上**：伤害沿防具链往下走（② 加工阶段逐层调
  `ArmorComponent.process_damage()`），
  本体拿到的永远是"防具没吃掉的那部分"，所以"只影响防具"只能发生在防具自己吃的那一步
  （`ArmorComponent.absorb_damage()`）—— 正是防具组件的地盘（[防具.md](防具.md) §4）。
- **为什么不放大 / 减免往下传的量**：防具一破，多出来的伤害会顺着溢到本体，"仅影响防具"就不成立，
  连磁力菇吸个桶（`break_armor()` 走的也是伤害管线）都要啃掉僵尸本体一大截血。
- **固定伤害（保龄球 / 锤子）与原样下传（穿透的二类）不打折**：那几条的口径是"打多少就是多少"。
- **换防具而不是改脚本**：铁桶僵尸本体上那层是基类防具，运行期 `set_script()` 会把场景里配好的
  类别 / 铁器 / 音效清回默认值，所以照热注册那条路 `add_armor()` —— 先抄下旧那层的配置、
  摘掉它，再挂一层新的上去（`_equip_copper_armor()` / `_equip_diamond_armor()` / `_equip_netherite_armor()` 同款）。
- **三只各有一张僵尸卡**（`ZombieRuntimeKit`）：插卡 + 从这只僵尸自己身上取卡面 +
  进已解锁名单，想在选卡界面里亲手放一只就靠这三张 —— 那页在**模组页面「调试模式」**打开后出现
  （僵尸卡的总开关默认关，见 [卡片与选卡流程.md](卡片与选卡流程.md)）。

**一只僵尸 = 一个本体 + 一个脚本**（走 [僵尸热注册](../../../src/entities/character/zombie/zombie_runtime_recipe.gd)）：
本体复用 `zombie_bucket.tscn`（桶精灵 / 铁器节点 / 掉落物 / 破损外观整套现成），
脚本只做「换贴图 + 改防具血量 + 重切破损段」，公共部分在 `OreBucketZombieBase`；
编号由注册表从 9001 起自动分配，本体不写死任何编号。

| 时机 | 做了什么 |
|---|---|
| `install()`（启动一次） | `CharacterRegistry.register_runtime_zombie()` 热注册三只 |
| `on_level_para_ready()`（每局一次） | 把三只追加进 `game_para.zombie_refresh_types` —— 自然出怪只认这一张表，不加就是「注册了却永远不出场」 |

- 铁器：三只都留着铁桶那套 `IronNode`，磁力菇照样能把桶吸走。
- 贴图：10 张桶贴图在**模组目录**里（`more_armor/tongtong*.png` / `zuanshitong*.png` /
  `xiajiehejintong*.png`），僵尸脚本用 `ModManager.load_mod_asset(ModIds.MORE_ARMOR, "x.png")`
  运行期读（见 §2.2）—— 不再裸放在本体 `assets/` 根。
- 设置：「加入本关出怪表」一个开关（默认**开**），落在模组存档文件的 `[more_armor]` 段。
- 验证探针：`test/scenarios/probe_more_armor_mod.gd`（自己开模组 → 三只注册上 / 血量 / 贴图 / 破损段数 / 铁器节点
  + **铜桶专属**：换上了铜桶那层防具 / 氧化进度随时间涨 / 完全氧化后是铜锈色 /
  易伤倍率拉满时防具掉双倍血且**本体一滴不掉**
  + **下界合金桶专属**：换上了下界合金桶那层防具 / 100 伤害下防具掉 50 且**本体一滴不掉**
  + **钻石桶专属**：挨打 20 次后防具换成下界合金桶那层、贴图也换、上限与当前血量都沿用；
  之后再挨一发改验下界合金桶 50% 减伤
  + **三张僵尸卡**：有卡位 / 在已解锁名单里 / 卡面画出来了 / 能按身份造出一张卡；
  关掉模组后卡位与解锁一并撤掉）。
  ⚠️ 这些脚本**只在模组装载时才被 `load()`**，编译门禁的**第一关**（`--import`）覆盖不到；
  **第二关**（`test/check_scripts.ps1` 里的 autopilot）能覆盖到 —— 它启动 Godot 时会跑 autoload，
  `ModManager` 把所有登记的入口脚本都 `load()` 一遍，有解析错误会当场报出来。

### 6.3 锤子（`mods_builtin/hammer/`）

原版没有「点一下草坪就锤一片僵尸」这个玩法（原版锤子只属于「锤僵尸」迷你游戏，
见 [手持物实现.md](手持物实现.md) §六），所以整条链路都在模组里。
与迷你游戏的锤子**互不相干**：那边是 `src/items/mini_game/hammer.gd` + 手持物类型 `Hammer`
（单锤 1800、只打最左边一只、是那两关的空闲手持物）；
这边用手持物类型枚举**末尾**新开的 `HammerMod` 槽位（加了新类型要与现役 `Hammer` 区分开，
否则 `HandManager` 会报「类型重复」并跳过登记）。

`HeadHammerMod.install_to_main_game()` 现场造三件套（本体场景里一个模组锤子节点都没有）：

| 装的东西          | 挂到哪                                       | 说明                                            |
| ---------------- | ----------------------------------------- | --------------------------------------------- |
| `HM_HammerMod`   | `HandManager` 下                           | 手持物组件 `HandComponentHammerMod`，随后被登记为 `HammerMod` 类型 |
| `UIHammer`       | `ShovelContainer`（手套右侧，140~210）        | 卡槽按钮，来自 `hammer_slot.tscn`；H 键（`ShortcutKeys_Hammer`）由它自己收 |
| `RealHammerMod`  | `%CanvasLayerTemp`                        | 跟随鼠标的真锤子（美术与挥锤动画复用迷你游戏锤子的贴图与 `.tres` 动画） |

- **交互**：点卡槽 / 按 H 拿到手上 → 点草坪任意格子 → 挥一锤（`click_cell` 返回 true，挥完自动回空手）；
  右键或点空白由 `HandManager` 统一取消。
- **命中判定**：与迷你游戏锤子同一套路 —— 真锤子身上的 Area2D 监测僵尸受击框（`collision_mask = 4`，
  与 `hammer.tscn` 同一个 mask；半径按设置每挥都重设），挥锤那一刻 `get_overlapping_areas()`
  圈出名单，`owner is Zombie000Base` + `BulletCampConfig.is_enemy(Plant, 僵尸)` 过滤（魅惑僵尸是自己人）。
- **伤害结算**：在组件里做 —— 秒杀开关开 = `be_attack_to_death()`；
  关 = `DamageInfo.create(僵尸, 数值, Norm, Hammer)` + `apply_damage()`。
- **七项设置**（模组页面，落在模组存档文件 `[hammer]` 段，读写走 `ModManager.get/set_mod_value()`）：
  `kill_mode`（一键秒杀）/ `damage_value`（伤害数值 100~5000）/ `radius`（范围半径 40~240 像素）/
  `cooldown_enabled`（冷却开关，默认关）/ `cooldown_time`（冷却时长秒）/
  `cooldown_by_wave`（冷却按波数算）/ `cooldown_wave`（冷却波数，每开一波减 1）——
  冷却计时与手套同一套 `_process` + `wave_started` 写法（含「关卡没有波次时不生效」的兜底）。
- **解锁**（2026-10-13 起，与手套同款）：`HammerSettings.UNLOCK_ADVENTURE_LEVEL = 14` ——
  光装着还不够，要**通关冒险 2-4** 之后锤子才归玩家，从 2-5 起可操作草坪的关卡卡槽里才有它。
  判定写在组件里：`HandComponentHammerMod.is_can_has_hammer()` = `game_para.is_shovel` **且**解锁进度够，
  没解锁时卡槽那一整块不显示（H 键也一起失效 —— 按钮 `visible = false` 时不收键）。
  模组页面右侧多一行通关进度（照手套的 `_progress_text()` 写法）。

### 6.4 水盆（`mods_builtin/dlc/waterbowl/`，由 DLC 植物模组兼收）

原版**没有「水盆」这只植物** —— 它是一只新增的**战斗植物**（编号 `P050WaterBowl`）：

### 6.5 紫卡直接种植（`mods_builtin/purple_direct_plant/`）

原版紫卡（升级植物）**只能种在它的基座植物上**：判据在
`ResourcePlantCondition.get_preplant_purple()` —— 机枪射手要种在双发豌豆上、
玉米加农炮要种在两株玉米投手上。"直接种在空地上"是原版没有的玩法，所以做成模组。

**规则**：没有基座时那一格付 **紫卡原价 + 基座植物的阳光 + 惩罚阳光（默认 50）**；
种在基座上（原版那样）价格一分不变。

| 文件 | 作用 |
|---|---|
| `purple_direct_plant_mod.gd` | 入口：给 `CharacterRegistry.AllPrePlantPurple` 里每一张紫卡换一份条件资源（原版那份存下来，关掉模组换回去）；订 `HAND_CARD_TAKE` / `HAND_CARD_RELEASE` 记住"手上那张卡" |
| `purple_direct_plant_rule.gd` | 规则与运行期状态：价格公式、当前手持卡、惩罚阳光的设置。**单独一份**是因为入口与两个条件资源都要用它，互相 `preload` 会成环（同 `glove_settings.gd`） |
| `condition_purple_direct.gd` | 紫卡的种植条件：有基座走原版那条路；没有基座按**普通植物的落位条件**判（地形符合 + 该位置为空）+ 阳光够付惩罚价；并把 `judge_purple_card_can_plant()` 放开（原版要求场上有基座才点亮卡片） |
| `condition_purple_direct_cob_cannon.gd` | 玉米加农炮那一份：它是**特殊紫卡**，判据在 `judge_special_plants_condition()` 另一支；没有两株玉米投手时要求**后轮两格都空着**（加农炮自己占住后轮那一格，见 `Plant048CobCannon.ready_norm()`） |

**价格是跟着鼠标走的**：手上拿着紫卡时，鼠标进格子 → `judge_is_can_plant()` 顺手把手上那张卡的
`sun_cost` 改成"这一格种下去的价"（种在基座上就改回标准价），卡面立刻显示出来；
点下去由 `CardSlotBattle.card_use_end()` 照 `card.sun_cost` 扣 —— **卡面上看到的数就是扣的数**。
放下卡片（`HAND_CARD_RELEASE`）时把价格刷回标准价。

- **默认关闭**：模组页面里打开；惩罚阳光（0~300，步 25）在同一页可调，存进 `[purple_direct_plant]` 段。
- 只改**出战卡槽**里的卡：传送带上的卡不花阳光（`sun_cost` 恒为 0），也不判阳光够不够。
- **被依赖**：生态版声明依赖本模组（见 §6.6）—— 打开生态版时本模组会被一并打开；
  生态版把吸金磁从 50 调到 150，这个新价就是本模组直种公式里的「紫卡自己的价格」（照注册表现读）。
- 本体这边只多了一个通用口子 `CharacterRegistry.set_runtime_plant_condition()`（见 §五 第 9 条），
  本体没有任何 `if 紫卡直接种植` 的分支。

### 6.6 生态版（`mods_builtin/eco/`）

前面的几个模组都是「**加**东西」（加植物 / 加手持物 / 加玩法），本模组是「**改数**」：
把**原版已有的数值**改成同人口径（也含一条原版没有的「格子光照」），不加植物、不加卡、不加节点。
原版数值是多少就该是多少 —— 这类同人调整同样不属于原版，所以做成模组：**关掉 = 数值回到原版**。

| 文件 | 作用 |
|---|---|
| `eco_mod.gd` | 入口：装 / 卸 + 每局接线 + 模组页面上的**清单**（一行一条「原版多少 → 现在多少」） |
| `eco_settings.gd` | 数值表：**新值 + 原版值**成对放；单独一份是为了 `preload` 不成环 |
| `eco_plant_patcher.gd` | 改**数据层**（装一次全局生效）：三种植物的阳光、仙人掌子弹的穿透数 |
| `eco_wiring.gd` | 改**实例层**（每局接一次）：光照、寒冰菇伤害、机枪连发、卷心菜索敌行、吸金磁吸铁器 |

**为什么不直接改 `PlantInfoData.PLANT_INFO`**：那张表是 `const`，而 **Godot 4.4 起常量字典是只读的**
（实测就地写会报 `ERROR: Dictionary is in read-only state.`）。所以这类「改原版数据」的事，
一律走本体的**通用覆盖口子**（下面那张表），模组只管往覆盖表里写，撤得掉（清掉就是原版）。

### 本体为本模组开的通用口子（都不是为生态版开的，默认行为零变化）

| 口子 | 位置 | 谁用 |
|---|---|---|
| `set_runtime_plant_stat(植物, 属性, 值)` / `clear_runtime_plant_stats()` | `CharacterRegistry` | 改三种植物的阳光（`get_plant_info()` 里覆盖表优先） |
| `set_runtime_bullet_stat(子弹, 属性, 值)` / `clear_runtime_bullet_stats()` | `BulletRegistry` | 仙人掌子弹 `max_attack_num = 3`（能穿 3 个） |
| `PlantCell.light_level` / `add_light_level()` / `set_light_level()` | `PlantCell` | 格子的光照等级（原版没有这个属性，恒为 0） |
| `get_plant_cell_cross(格子)` | `PlantCellManager` | 火炬树桩照亮的十字四格（与旧的 `get_plant_cell_surrounding()` 是一对） |
| `add_extra_ray_area(区域)` | `DetectComponent` | 卷心菜索敌三行（复制本行那块检测区到上下两行） |
| `burst_num` / `burst_extra_num` | `AttackComponentBulletBase` | 机枪 6 连发（原版 4 发写在射击**动画**里，动画不能改，只补差额 2） |
| `max_iron` | `MagnetComponent` | 吸金磁一次吸 3 件铁器（默认 1 = 原版磁力菇口径） |

三条必须守住的规矩：

- **改完注册表必须 `AllCards.rebuild()`**（卡模板上的阳光是 `rebuild()` 时照注册表重读的，见 `all_cards.gd`）；
- **实例层那几条靠 `PlantCell.signal_plant_create` / `signal_plant_free`**（照明植物被铲掉范围要收），
  重算一律**全场从零算一遍**（几十个格子，成本可忽略，且天然幂等，不会算错）；
- **光照的口径**：火炬树桩照十字四格、路灯花照周围八格，**都不含自己那格**；向日葵按所在格子的
  光照等级每级 +5（没被照到就是原版的 25）。

- **默认关闭**：模组页面里打开；开关落在 `mod_config.ini` 的 `[eco]` 段。
- **依赖**：声明依赖「紫卡直接种植」（`get_mod_dependencies()`，见 §2.3）—— 打开生态版会把它一并打开。
  理由：生态版唯一改到的**紫卡**是吸金磁（50 → 150；它自己是紫卡、基座是磁力菇），而紫卡直种的价
  = 紫卡原价 + 基座植物的阳光 + 惩罚阳光，两项都照注册表**现读** ⇒ 两个模组是同一套经济口径。
- **生效时机**：数据层（阳光 / 子弹）装完当场生效；实例层（连发 / 索敌 / 光照 / 伤害 / 吸铁）
  在**下一局**生效 —— 场上已有的植物不会被追溯改动。
- **回归**：`test/scenarios/probe_eco_mod.gd`（无头可跑，装前装后各验一遍，failed=0）。

### 6.7 PVZ2（`mods_builtin/pvz2/`）+ PAM 动画播放器（`mods_builtin/pam/`）

的植物 —— 原版没有这几株，连美术都不是同一套格式（PVZ2 是 **PAM / XFL**，不是原版的 `.reanim`），
所以整件东西做成模组：**关掉 = 回到原版**。

**2026-10-23 重写**：五株**全部**改走「一张 1536 图集 + 一个 `.pam.bin` + 播放器模组」，
菜问原先那条「烘焙成 `.tscn` + `AnimationPlayer`」的路子已废（产物 4.8 MB、加一株就得重跑一次转换器）；

| 动画数据 | `pvz2/<植物>/<植物>.pam.bin` | 每株一个：图集 + 每帧全量快照（几百帧几百 KB） |

| 项 | 取值（菜问） |

- **默认关闭**：模组页面里打开；开关落在 `mod_config.ini` 的 `[pvz2]` 段。
- **依赖**：`get_mod_dependencies()` 返回 `[ModIds.PAM]` —— 打开 PVZ2 会一并打开播放器（§2.3）。
- **图鉴**：条目由**模组自己登记 / 摘掉**（本体不认识模组），落在图鉴第 3 页「扩展植物」。
- **回归**：`test/scenarios/probe_pvz2_pam.gd`（无头可跑：五个 bin 都能解析 / 部件全部绑上贴图 /
  脚本引用的状态名真的存在且帧数对得上 / 播放会推进 / 单次状态只报一次结束 / 打印各株待机包围盒）。

#### 6.7.0 为什么动画挂点上**没有脚本**

模组有两个加载根（`user://mods/` 优先、`res://mods_builtin/` 兜底），而 `.tscn` 里的脚本 / 贴图路径是
**写死的绝对路径**。播放器现在住在**另一个模组**里，场景一旦写 `res://mods_builtin/pam/...`，
玩家把 pvz2 拷进 `user://mods/` 之后就会指到「另一份」（可能是旧版）。所以：

1. 场景里只放一个**空 Node2D**（只标名字与节点位置）；
2. `character_ready()` 里调 `pam_bridge.gd` 的 `attach()`：脚本按
   `ModManager.get_mod_asset_path(ModIds.PAM, "runtime/pam_animator.gd")` 取，bin / 图集按
   `ModIds.PVZ2` 取，然后把 `binary_path` / `hidden_parts` / `pivot_offset` / `texture_override` 塞进去；
3. 播放器变量声明成**无类型**（`var _anim = $Body/XxxAnim`）—— 写成 `Node2D` 会编译不过
   「Node2D 没有 set_state()」（它不是全局类，没有可写的类型名）。

⚠️ 顺序：**先 `set_script()` 再 `set()`**。空 Node2D 上设 `binary_path` 不报错，只是静默丢掉，
症状是「节点挂上了但什么都不发生」。脚本是进树之后挂的，所以 `_ready()` 不会自动跑 ——
`attach()` 里手动 `set_process(true)` + `load_bin()`；少了前者就是「画出第一帧然后一动不动」。

#### 6.7.1 播放器为什么单独做成模组（`mods_builtin/pam/`）

PVZ2 的植物、子弹、僵尸、特效**都要播 PAM**，将来别的模组（联机同步的敌人 / 自制关卡里摆一只 PVZ2 单位）
也会用同一套。播放器跟着「内容」走的话，第二家就得复制一份 —— 拆出来之后，播放口径
（状态机 / 循环 / 单次 / 部件显隐 / 包围盒 / 贴图覆盖）只在这里维护一次。

| 项 | 落点 |
|---|---|
| 入口 | `mods_builtin/pam/pam_mod.gd`（能力模组，**不加玩法**，`get_mod_categories()` 返回空 = 未分类） |
| 播放器 | `pam/runtime/pam_animator.gd` —— 一个 `Node2D` 在 `_draw()` 里画四边形，**没有** `Sprite2D` / `AnimationPlayer` |
| 数据类 | `pam/runtime/pam_anim_data.gd` / `pam_image_def.gd` / `pam_instance_state.gd` / `pam_binary_reader.gd` |
| 定格渲染 | `pam/runtime/pam_static_frame.gd`（`extends "pam_animator.gd"`，`_process()` 顶成空实现 ⇒ 永远同一帧） |
| 公开 API | 切状态 / 循环与单次 / 状态内帧回调 / 部件显隐与查询 / `get_render_rect()` / `get_sprite_position()` |
| 贴图覆盖 | `texture_override`：bin 里内嵌的 `res://` 路径只是**烘焙痕迹**，运行时一律由调用方塞贴图 |

三条会反复踩的坑：

1. **导出包要给 `include_filter` 加 `*.pam.bin`**：`export_presets.cfg` 里是 `export_filter="all_resources"`，
   非资源文件（`.bin`）默认不进 PCK，加进 `include_filter` 才随包发出去（两个预设都加了）。
2. **装扮和本体塞在同一条时间轴里**：PVZ2 把帽子 / 外套 / 围巾当普通部件画，全开就会同时戴好几件。
   各株脚本里的 `HIDDEN_PARTS` 就是关它们的地方（名单按部件名筛，重新烘焙后要复核）。
3. **PAM 的 `change.transform` 是部分更新**：6 元 = 完整矩阵、3 元 = `(旋转弧度, x, y)`、2 元 = 只改平移
   （旋转与缩放沿用上一次）。按「一律 6 元整体替换」烘会把旋转件打飞（`tools/bake_pam_bin.py`
   的 `apply_transform()` 就是这个口径）。

#### 6.7.1.1 摆放常量怎么量（`pivot_offset` / `scale`）

播放器把画布中心对齐节点原点（PVZ2 画布 390×390，地面线在 y≈240）。`scale` 与 `pivot_offset`
**不是猜的**，是跑 `test/scenarios/probe_pvz2_pam.gd` 打印 `get_render_rect()` 量的：

- `scale ≈ 92 / 包围盒高度`（格子 76×95）；
- `pivot_offset.y = 原 pivot.y - rect.end.y` —— 让包围盒**底边**落到节点原点。
  ⚠️ 这个值**越小画面越靠上**（脚悬空就要把它**调大**），方向搞反的症状是「整株飘在半空 / 陷进地里」。

#### 6.7.2 潜伏芹菜（Celery Stalker）：从「动画」变成「可种植物」（玩法 + 卡面）

**玩法一句话**：平时缩在地里（僵尸从它头上走过去，**不吃它**），**左边一有僵尸就从土里冒出来照着后背连打，
左边空了才缩回去**。它**只往左打**（僵尸从右往左走，走到它左边才叫「到了背后」）。

**状态机的判据只有一个**（和仙人掌 `plant_cactus.gd` 那种「按条件起落」同一个路子）：
`_find_target()` **有 → 起身 / 一直打；没有 → 低头**。没有「打够几拳就收」这种计数。
场上循环：`idle_down*` ⇄ `up` → `attack` → `attack_loop`（循环打）→ `attack_end` → `down`。

| 项 | 落点 / 取值 |
|---|---|
| 植物 id | `&"pvz2_celerystalker"` |
| 场景 | `celerystalker/plant_celerystalker.tscn` = `plant_base.tscn` + `Body` 下挂 PAM 播放器 + 左侧检测框 + `ScanTimer` |
| 脚本 | `celerystalker/celerystalker_plant.gd`（四段状态机：藏着 / 冒头 / 出拳 / 缩回） |
| 配方 | `celerystalker/celerystalker_recipe.gd`（`extends PlantRuntimeRecipe`，**只覆盖卡面**，见下） |
| 数值 | 阳光 50 / 冷却 15s（RTON `PacketCooldown`）/ 每拳 100（RTON `CeleryStalkerProps`）/ 往左够 130 px |

**17 段状态怎么分工**（名字之外的含义是照烘焙数据量出来的，重新烘焙后按这三条复核）：

| 状态 | 帧 | 用途 |
|---|---|---|
| `idle` ~ `idle4` | 50 | 站在地上的待机（图鉴 / 展示态用） |
| `down` / `up` | 32 | 缩回 / 冒出（各 1.07 秒，带扬土） |
| `idle_down` ~ `idle_down3` | 50 | **缩在地里**的待机三段接龙（只剩贴地那一小截） |
| `attack` | 8 | 朝左打一拳，**第 4 帧**手伸到最远 |
| `attack_loop` | 21 | 朝左连打两拳（**第 7、16 帧**是两次伸展顶点），循环段 |
| `attack_end` | 18 | 收势，不造成伤害 |
| `attack_special` / `plantfood*` / `water` | — | 本株**不用**（能量豆 / 浇水 / 特殊攻击都没做） |

四条口径（踩过才知道）：

1. **藏着时怎么做到「僵尸不吃它」**：关受击盒（`hurt_box_component.change_is_enabling(false, E_IsEnableFactor.Character)`）。
   僵尸挑「啃哪株」靠它自己 `DetectComponent` 的 Area2D 与植物受击盒重叠，`monitorable = false`
   之后根本重叠不到。**别**走「受击状态位」（`BeAttackStatusComponentPlant`）那条 —— 那条会一直生效，
   冒头时它必须能被啃。
2. **冒头之后不能一直关着受击盒**（那就无敌了）：出拳期间每 0.1 秒按目标位置重判 —— 目标走到
   **32 px** 之外才开。32 是量出来的：僵尸啃食框在身前、宽 50 且中心偏 -13 ⇒ 有 12 px 伸到自己身后，
   植物受击框半宽 20 px，12 + 20 = 32。比这更近时开着就等于「刚冒头就被目标回头啃」（伏击白做）；
   走开之后它是正常植物：**右边**新来的僵尸照样能啃它（它打不到右边）。
3. **命中帧要按数据对**，别用「播完打一次」：`attack` 只在第 4 帧手伸出去，`attack_loop` 是第 7、16 帧。
   走 `state_frame_changed` 打，比按时间猜稳。
4. **卡面不能走通用取帧**：`PlantRuntimeRecipe.build_card_face()` 用 `AnimationFrameUtil`，那条路找的是
   `AnimationPlayer`；PAM 播放器没有播放器节点 —— 取帧**不报错**，只会返回一棵什么都画不出来的树
   （卡面全空、手持报「卡片静态角色为空」拿不起来）。所以**五株都有**配方子类覆盖 `build_card_face()`，
   用 `pam_bridge.gd` 的 `create_static_frame()` 造一个定格节点（`pam_static_frame.gd`，
   `_process()` 顶成空实现 ⇒ 永远定格在 `idle` 第 0 帧），外面再套一层 `card_face_scale` 的挂点。
   `_process` 顶空而不是 `set_process(false)`：卡面会被 `duplicate()` 复制到待选区 / 手持 / 整列虚影，
   脚本级行为一定跟着走，节点级开关不一定。

- **摆放**：`pivot_offset = (0, -45)`（画布地面线 y≈240）+ `scale = 0.55` ⇒ 实测整株 85×94 px（格子 76×95）。
  数是 `probe_pvz2_pam.gd` 打印的待机包围盒量的，口径见 §6.7.1.1。
- **回归**：`test/scenarios/probe_pvz2_pam.gd`（状态名 / 帧数 / 播放推进 / 单次只报一次 / 包围盒）。

#### 6.7.3 火焰豌豆射手 / 豌豆荚：直线射手与叠层射手

两只都是**普通的直线射手**（本行右边有僵尸才打），动画与芹菜同一条 `.pam.bin` 路线；
区别在「打什么 / 怎么打」，以及豌豆荚会用到本体的**同格叠层**口子。

| 项 | 火焰豌豆射手 | 豌豆荚 |
|---|---|---|
| 植物 id | `&"pvz2_firepeashooter"` | `&"pvz2_peapod"` |
| 场景 / 脚本 | `firepeashooter/plant_firepeashooter.tscn` / `firepeashooter_plant.gd` | `peapod/plant_peapod.tscn` / `peapod_plant.gd` |
| 配方 | `firepeashooter/firepeashooter_recipe.gd`（只覆盖卡面） | `peapod/peapod_recipe.gd`（只覆盖卡面） |
| 数值 | 阳光 175 / 冷却 5s / 攻击间隔 1.4s / 一发 40 | 阳光 125 / 冷却 5s / 攻击间隔 1.5s / 每颗 20 / 最多 5 层 |
| 子弹 | `BulletIds.PEA_FIRE`（火豌豆，会取消冰冻） | `BulletIds.PEA`（按层数连发 1~5 颗） |
| 主要状态 | `idle` / `idle2`（待机接龙）、`attack`（第 8 帧喷火） | `idle`~`idle5`（1~5 层待机）、`attack`~`attack 5`（1~5 层攻击） |

三条口径：

1. **不用本体的 `AttackComponentBulletBase`**：那条路的攻击节奏靠
   `AnimationTree.set("parameters/OneShot/request")` 驱动，而 PAM 播放器没有 `AnimationTree`
   （组件里的 `@onready var animation_tree = $"../AnimationTree"` 会在场景加载时报 Node not found）。
   所以这两只照菜问的做法自己挂 `DetectComponent` + `AttackCdTimer`，发射走 `BulletRegistry`，
   参数口径与 `AttackComponentBulletBase.get_bullet_paras()` 一一对应（行 / 位置 / 方向 / 双方掩码 / 阵营 / 攻击力）。
2. **发射按帧号，不按时间猜**：火焰豌豆在第 8 帧；豌豆荚在第 8 / 11 / 14 / 17 / 20 帧各一颗，
   并且按「到这一帧为止该发几颗」补发（卡顿跳帧也不会少发）。帧号是对着烘焙数据的包围盒量的。
3. **豌豆荚的叠层走本体通用口子**（本体不认识豌豆荚）：
   - `Plant000Base` 加 `max_stack_layers`（默认 1）+ `can_stack_up()` / `try_stack_up()`（默认不支持）；
   - `ResourcePlantCondition.judge_is_can_plant()`：同格已有植物时，**同种 + 还能叠**才放行（手持虚影同理）；
   - `PlantCell.create_plant()`：同种 + `try_stack_up()` 成功时**不新建第二株**，直接返回已有那株；
   - 层数进存档：豌豆荚覆盖 `gat_save_game_data_plant()` / `load_game_data_plant()`。

- **摆放**（`probe_pvz2_pam.gd` 量的）：火焰豌豆 `pivot_offset = (-24, -50)` / `scale = 0.44`
  ⇒ 实测 73×92 px；豌豆荚 `pivot_offset = (-31, -72)` / `scale = 0.40` ⇒ 87×92 px（格子 76×95）。
- **回归**：`test/scenarios/probe_pvz2_pam.gd`。

#### 6.7.5 数值来源：解包资源的 RTON

阳光 / 冷却 / 血量 / 近战伤害 / 子弹伤害**全部取自** `..\2代解包资源`（桌面，与仓库同级）的 RTON，
不是照 wiki 抄的：

| 数据 | 文件 | 读法 |
|---|---|---|
| 阳光 / 卡片冷却 | `PACKAGES/PLANTTYPES.RTON` + `PLANTPROPERTIES.RTON`（`SunCost` / `PacketCooldown`） | `tools/rton2json.py` 转 JSON 后取 |
| 近战伤害 / 攻击矩形 | `PLANTPROPERTIES.RTON`（`Actions`） | 同上 |
| 子弹伤害 | `PACKAGES/PROJECTILETYPES.RTON`（`BaseDamage`：`PeaDefault` 20 / `FirePeaDefault` 40 / `PoisonPeaDefault` 10） | 同上 |
| 图集矩形 | `PROPERTIES/RESOURCES.RTON`（`ax/ay/aw/ah` + `parent`） | 同上，给 `bake_pam_bin.py --atlas-id` |

`tools/rton2json.py` 是本仓库写的 RTON 解码器（字节码表在文件头，已用 `COLORS` / `PLANTTYPES` /
`PLANTPROPERTIES` / `RESOURCES` 四份实测）。两条会咬人的细节：

1. **根对象不带 `0x85`**：键值对直接从文件头之后开始，遇 `0xff` 结束，再跟 `DONE`；
2. **同一个 image id 在 `*_768` 与 `*_1536` 两个资源组里各有一份矩形**（数值差一倍），
   所以 `bake_pam_bin.py` **必须**给 `--atlas-id`（或用 `tools/bake_pvz2_assets.py` 的清单），
   给错的表现是「每块都还在图里，但位置全错」。

⚠️ 伤害是 PVZ2 口径原样搬的：本作僵尸血量比 PVZ2 低，会比原版更快被打死。要平衡就改各株
`*_plant.gd` 顶部的 `@export`（场景里也能改），**别改 `pvz2_mod.gd` 里的常量**。

### 6.8 招笑版（`mods_builtin/zhaoxiao/`）

改**向日葵**与**豌豆射手**两只植物，各是一套原版没有的演出（所以做成模组；**关掉 = 回到原版**）。

#### 6.8.1 向日葵 → 「朝阳葵」

| 改了什么 | 落在哪 | 口径 |
|---|---|---|
| **改名**：向日葵 → 「朝阳葵」 | `zhaoxiao_mod.gd` 的 `_rename_plant()` | 改的是图鉴数据里那一行的**「名字」字段**（图鉴页 / 商店卡说明 / 「获得新植物」提示都读它），**键（= 注册表 `PlantName`）原样不动** —— 图鉴页是拿 `PlantName` 当键去查 `Plant` 段的，键一改就查不到那一条。只改内存里的字典，`data/` 里那个 json 不动，关掉模组按原名还原（原名按图鉴键记在 `_original_names` 里，两只植物共用同一套） |
| **集体转头（只转头）** | `zhaoxiao_sunflower.gd`（每株挂一个观察者） | 一到产光时间，产光那株遍历观察者组广播一次；其余朝阳葵**只转头**看它：转的只有花瓣（`SunFlower_*`）与脸（`Anim_*`）那几张贴图，**花茎与叶子（`Backleaf*` / `Stalk_*` / `Frontleaf*`）一点不动**，整株 `Body` 也不碰。口径：目标在**左边**就把花头**镜像**过去（`scale.x` 取负、围绕花心的竖线翻），再旋转到「右侧对准目标」（镜像时转「目标角度 + π」，归一化后仍是个小角）。 |
| **流汗** | 同上，`_start_sweat()` | 产光那株的花心上冒一颗汗滴：**借本体禅境花园那颗「缺水」水珠贴图**（`res://assets/image/garden/waterdrop.png`，原版素材），**循环滴**（淡入 → 往下淌 + 淡出 → 回起点再来一趟） |
| **两者都是持续的** | 同上 | 转到目标方向就停在那儿（**不转回来**），汗滴一直循环滴；直到**下一株**产阳光时，全体改看新的那株（旧的停汗、花头摆正 —— 它自己成了产光者） |

- **「只转头」是怎么做到逐帧改在动画之上的**（6.8.1 这一半的技术坑）：
  那几张贴图的 `position / rotation / scale / skew` 全被 `AnimationTree` 的待机动画
  **逐帧写回**，插一个父节点又会让动画的轨道路径（`Body/BodyCorrect/<贴图名>`）断掉。
  所以走 `_process()`：**排在 `AnimationTree` 之后**（`process_priority = 100`，同优先级下按树序、
  观察者本来也是后挂的），每帧拿动画刚写好的原始姿态，再绕**花心**（= 花瓣视觉中心的平均，

- **回归**：`test/scenarios/probe_zhaoxiao_mod.gd`（无头可跑：改名与还原 / 两株都挂上观察者 /

|---|---|---|
| **停下** | `zhaoxiao_fall.gd` 的 `_stop_move()` | 移动因素 `IsCharacter` 置位（本体留给「特殊角色自己定」的那个因素）⇒ 僵尸停在事故原地；走路动画照播（腿还在原地倒腾，图一乐）。**每帧摁住**而不是只摁一次（与烟熏每帧摁啃咬伤害同一个路子） |
| **趴下** | 同上，`_fall_down()` | `Body` 绕脚根倒 90°（`rotation = -FALL_LIE_ANGLE × direction_x_root`：朝左走倒向左、朝右走倒向右），同时把身体往上抬 `FALL_SINK_Y` 看着才是趴在地上；Tween 倒下去（`TRANS_BACK` 带一点回弹） |
| **起来** | 同上，`_get_up()` / `_stand_up_done()` | 到点先把身体转回 0°（`TRANS_SINE`，不往回弹），**转完才放开**移动因素 ⇒ 僵尸站起来继续走（原先在啃的植物，起来接着啃） |
| **死亡时转回来** | 同上，`_on_death()` | 接 `hp_component.signal_hp_component_death`：身体**立刻**转回站姿（死亡动画是按站姿画的），本状态当场撤掉；移动因素保留置位（死了正好别动） |

- **为什么不改动画状态机**：本体的僵尸状态机里没有「趴下」这个状态；硬跳 `Idle` 会连带两个坑（`Idle` 没有出向 `Death` 的转移 —— 趴着被打死就不播死亡动画；起来还得还 `is_idle`）。所以动画一行不动，只转 `Body` 自己 —— `Body` 的 `rotation / position` 没有任何动画轨道写它（轨道写的都是 `BodyCorrect` 底下的部件，见 `component_anim_norm.gd` 顶部的结构说明）。
- **数值是目眯的**：`FALL_SINK_Y`（30）按普通僵尸的身材眯的（绕脚根转平后身体中线压到地面以下，抬这一下才像趴着）；小僵尸按体型缩，大僵尸不缩。想趴得再平 / 再沉改 `zhaoxiao_settings.gd` 那一处。
- **谁挂它**：绊倒路障僵尸走到第 4 列时挂一次；后来走到「掉在草坪上的路障」身上的僵尸也被挂一次。挂之前都先查 `FallStatus.NODE_PATH`，不重复挂。

**绊倒路障僵尸**（`zhaoxiao_cone_zombie.gd`，走僵尸热注册，本体复用 `zombie_cone.tscn`）—— 戴路障的普通僵尸变种，四件事：

| 改了什么 | 落在哪 | 口径 |
|---|---|---|
| **速度 = 普通僵尸 10 倍** | `zhaoxiao_cone_zombie.gd` 的 `ready_norm()` | 与闪电掉头僵尸同一招：`random_speed_range` 设 10，让基类 deferred 的 `init_random_speed()` 读到 10 倍 |
| **无视植物** | 同上，`ready_norm()` 里 `attack_component.disable_component(Character)` | 禁用攻击组件会顺带禁用它的 `detect_component` ⇒ 永不啃食、永不因植物停下，直接穿过去（植物照样能打它） |
| **走到第 4 列摔倒** | 同上，`_process()` + `_compute_fall_x()` | 从僵尸入场一侧（右侧）数第 `CONE_ZOMBIE_FALL_COLUMN_FROM_RIGHT` 列的中心 x 作为摔倒点，朝左走到那（含 10 倍速的每帧 overshoot）就摔倒 + 掉路障；口径同闪电掉头僵尸的掉头列，想改成「从房子一侧数」改一处公式即可 |
| **路障掉在地上、永久存在** | `zhaoxiao_cone_drop.gd` | 挂在僵尸行节点上（与本体掉落物同一个父节点，见 `ZombieDropBase.acitvate_it()`）⇒ 跟着这一行活到关尾；**没有**着地动画、**没有**淡出（本体那些掉落物弹一下是会淡出的，见 `zombie_drop_base.gd` 的 `fade_and_delete()`）。贴图借本体 `zombie_cone.tscn` 里那套「路障掉地上」的 `Zombie_cone3.png` |
| **后来走到路障上的僵尸也被绊倒** | 同上，`_physics_process()` | 每物理帧扫 `ZombieManager.all_zombies_2d[lane]`（本体自己也在用的按行僵尸表）：与路障的 \|x 差\| ≤ `CONE_TRIP_RANGE`（26 像素）就挂一个摔倒状态。朝左走来的 / 朝右走来的（魅惑僵尸）都绊；天上（气球）和地下（矿工）的碰不到它；已经摔着的不重复绊；**每只僵尸只被同一根路障绊一次**（掉下它的那只自己也不算「后来的」—— 否则它起来那一下还压在路障上，会立刻再摔一次） |

- **头上的路障怎么摘的**：不走 `break_armor()`（伤害管线会顺带播场景里那个「弹一下淡出」的掉落节点 `Body/NodeDrop/Node2D_Arm1_Drop`，与「永久留在草坪上」不是一回事）。照 more_armor 换防具那招：藏起 `Body/BodyCorrect/Anim_cone`（本体防具打掉时藏的也是这一处）+ `remove_child` + `queue_free` + `hp_component.collect_armors()` 重收一遍（防具表是血量组件一次性收集的，少了这一步那一层还挂在表里 —— 而且是静默的）。
- **摔倒的僵尸照样能被植物打**（受击框没动）—— 只是走不动、腿还在原地倒腾；如果它在摔着的时候被打死，身体会立刻转回来再播死亡动画。
- **注册 / 出怪**：与闪电掉头僵尸同一套（`install()` 热注册、`on_level_para_ready()` 追进本关出怪表、`uninstall()` 注销）；入口脚本上多一个 `get_cone_zombie_type()` 给探针按类型号造僵尸。**默认关闭**：模组页面里打开后才会出现。
- **回归**：`test/scenarios/probe_zhaoxiao_fall.gd`（无头可跑 29 条断言：摔倒机制的「挂上 / 趴平（rotation ≈ 90°、身体抬到地面）/ 摔着一步不挪 / 到点自己站起来（rotation 与 y 都还回去）/ 继续走」+ 绊倒路障僵尸的「热注册 / 走到第 4 列摔倒（位置对上）/ 路障 sprite 藏掉 / 防具摘掉 / 摔倒点留下路障（x 与行地面 y 都对上）/ 它自己也爬起来继续走」+ 后来的僵尸「走到路障上被绊倒 / 就绊在路障那儿 / 爬起来走过去了 / 不被同一根绊第二次 / 路障永久留着」+ 关模组后注销）。
  ⚠️ 探针里踩到两个坑（都写在文件头 / 注释里）：**僵尸行节点在原点**（`zombie_manager.gd` 的 `create_zombie_rows_from_map_data()`），摆僵尸的 y 必须取 `zombie_create_position` 的世界 y（= `get_row_base_global_y()`），取行节点自己的 y 会把僵尸飘到半空；**本体走路是「爆发式」位移**（`MoveComponent` 跟着动画里的 `_ground` 标记走，标记有停顿段），「站起来后继续走」这类断言要轮询等，固定等 1 秒可能刚好卡在停顿段（实测差 0.2 像素假失败过一次）。

### 6.9 明日方舟（`mods_builtin/arknights/`）

把《明日方舟》的战斗数值规则搬进本作：**防御力 / 法术抗性**、**物理 / 法术伤害分类**、
**植物精英化**。它们都是原版没有的概念，且默认数值全为 0、关掉模组即整套消失，所以做成模组
（分类 `OVERRIDE_RULE`）。

| 文件 | 作用 |
|---|---|
| `arknights_mod.gd` | 入口：`modify_damage()` 伤害修饰器 + 精英副本登记 / 每局接线 + 模组页面只读说明 |
| `arknights_stats.gd` | 共享契约：伤害类型标记、防御 / 法抗数值表与单实例覆盖、两条减免公式（单独一份防 `preload` 成环，照 `hammer_settings.gd` 的拆法） |
| `arknights_elite.gd` | 精英化规则：id / 命名、加成数值表、普通关判据、实例层加血 / 加伤 / 加法抗、种子包「精英化」标记（`mark_card()`） |
| `elite_icon.png` | 种子包标记的原图（30x20 纯白，代码里染蓝 `ICON_COLOR`）；走 `load_mod_asset()` 读，模组整目录拷到 `user://mods/` 也跟着走 |

**伤害类型与减免**（三条规则）：

1. **伤害类型是随包便签**：发起方在 `apply_damage()` 前调 `ArknightsStats.mark_attack(info, TYPE_PHYSICAL / TYPE_SPELL)`，写 `effects["meta_dmg_type"]`；修饰器在 ②-c 读它决定用哪套公式。**未标记 = 物理** —— 原版的子弹 / 啃食 / 爆炸 / 碾压一概不写这个便签，天然全走物理，本体一行不用改。
2. **减免公式**：物理 `amount = max(0, amount - 目标防御力)`；法术 `amount = round(amount × (100 - 目标法抗%) / 100)`（法抗夹 0~100）。**秒杀**（`is_instant_kill`）不看减免，与「秒杀不过防具吸收规则」同口径。
3. **减免发生在修饰器链（②-c），排在防具吸收之后**：只影响打本体那部分，防具那一层照旧 —— 口径见 [伤害系统.md](伤害系统.md) §10 的警告。框架在 `install()` 之后自动注册、`uninstall()` 之后自动注销（见 `ModBase` 的修饰器链段）。

数值配在哪：`arknights_stats.gd` 的 `PLANT_STATS` / `ZOMBIE_STATS`（key = `PlantIds` / `ZombieIds`，填 `defense` / `spell_resist`；没填 = 0），或运行期 `set_instance_defense()` / `set_instance_spell_resist()` 做单实例覆盖（写进 `Character000Base.mod_custom_effects`，本体给模组留的容器，效果结束 `clear_instance_stats()` 清掉）。

**植物精英化**（`arknights_elite.gd`）：每种内置植物（排除模仿者 / 萌芽 / 保龄球三兄弟，见 `EXCLUDED_PLANT_TYPES`）在 `install()` 时登记一个**精英副本** = 运行期植物（`PlantRuntimeRecipe` + `PlantRuntimeKit`，id 带 `arknights_elite_` 前缀）：

| 层 | 精英副本是什么 |
|---|---|
| 卡面 / 数据层 | 复用原版场景；名字加 `_Elite` 后缀、阳光 ×0.8、冷却 ×0.8、卡面借原版那张卡的脸；**跟随原版植物的解锁状态**点亮（普通关里同步解锁）。**不登记选卡页** —— 精英副本不自己占格子，出场靠下面的原位替换 |
| 数值层 | 普通关里场上植物按**原版类型**一视同仁加精英数值：血量 ×2、子弹 / 爆炸 / 大嘴花伤害 ×1.5、+15 防御、+15% 法抗（`ELITE_STATS` 可按植物覆盖） |

**区分标记**（`EliteMark`，`ArknightsElite.mark_card()`）：只在**种子包卡面**上贴，场上植物不加。

- 挂点：**卡面那株植物**下（`card.character_static` 的第 0 个孩子）。卡面本来就是本体精灵树的
  缩小图片（`all_cards.tscn` 里同一套 `CharacterStatic → PlantXXX → Body`，缩 0.5），挂这里
  标记跟着 0.5 一起缩、落点就是「植物右下角」；挂在卡面植物下（不是 `CardBg`）才能跟着整卡的
  `duplicate()` 走进待选区候选格 / 图鉴 / 出战卡槽。
- 位置 / 外观：`ICON_POSITION = (27, 0)`（植物根节点在脚下，碰撞盒 `(0,-40)` / `40x80`，
  见 `plant_base.tscn`：x 压到右脚外侧、y 落在脚下水平线），`ICON_SCALE = (1,1)` 跟着卡面缩到 15x10；
  原图纯白**染成蓝色**（`ICON_COLOR`，modulate 是乘法）—— 卡片底图是浅绿 / 紫，白色看不清。
- ⚠️ 卡面是帧末才画的（`_build_card_face.call_deferred()`）：`mark_card()` 也推到帧末、
  且晚于它入队（同帧按入队顺序执行），那时植物那一枝已经在卡上了。
- 图标走 `ModManager.load_mod_asset()`：模组可能从 `user://mods/` 加载，那里的图片不走导入管线，
  `preload` 拿不到 Texture2D。

为什么按原版类型判而不是按精英 id 判：**精英副本复用原版场景，场景根节点烘焙的 `plant_type` 就是原版 id**
（连 `signal_plant_create` 发的也是它）—— 实例上区分不出「这张卡是精英卡」。所以普通关的替换分两路，
合起来才是完整的「代替」：

1. **选卡界面**（`on_level_para_ready()`）：普通关用 `AllCards.set_plant_choose_replacement(原版, 精英)`
   让精英副本**原位顶掉原版那一格**（表见 [卡片与选卡流程.md](卡片与选卡流程.md) 的「原位替换」一节）——
   **不是**另开一页登记它：待选区的页数 / 位置与只排原版时完全一致，玩家看到的还是原来那一格，
   只是内容换成了精英卡。特殊关 `clear_plant_choose_replacement()` 撤回，原版植物回到自己那一格
   并反过来禁掉精英副本。
   ⚠️ 原版植物**照样进 `banned_plant_types_in_choose_card`**：选卡列表里它已经没有格子（禁单对显示无影响），
   但「冒险模式全锁 / 前 N 槽随机」是照 `curr_plant` 抽的（`level_data.gd` 的 `_resolve_locked_random_cards()`），
   不剔掉会抽出没有卡位的原版占位。本关自己禁掉的植物，连它的精英副本一起禁。
2. **实例数值**（`install_to_main_game()` 接格子 `signal_plant_create`，照 `eco_wiring.gd` 的接线法）：
   普通关里按原版类型给**每一株**种下的植物加精英数值 —— 选卡界面走精英卡来的、系统预选卡
   （`prechosen_cards`，`is_valid()` 只认内置 id，运行期 id 过不了那道门禁，见 [卡片与选卡流程.md](卡片与选卡流程.md)）
   发原版 id 来的，都按精英数值结算；加成幂等（标记写实例自己的 `mod_custom_effects`）。

**普通关 / 特殊关判据**（`is_general_level()`，无单一现成字段，按数据拼）：
冒险模式 + `card_mode == Norm` + 非砸罐子 / 我是僵尸 / 僵王 / 种子雨 / 保龄球 / 传送门 / 锤僵尸。
传送带关（1-5 / 1-10 / 2-10…）算**特殊关**（传送带是特殊关卡机制）。另有一份显式注明名单
`LEVELS_USE_ORIGINAL`（预置蹦极闪电战 `adventure_05_05` —— 本体没有数据字段标记它），
「特殊的关卡注明使用原版植物」就往这里加 level_id。

将来加干员（植物侧，走 [运行期植物.md](运行期植物.md)）与新僵尸（走 [僵尸热注册.md](僵尸热注册.md)）时，它们的攻击便签发 `mark_attack()` 即可接进这套减免；模板数值填进两张表或实例化时覆盖。想让新植物也有精英副本，确认它的 id 在 `PlantInfoData.PLANT_INFO` 且进了 `PlantIds.ALL` 即可（目标清单是自动枚举的）。

**验证**：`test/check_scripts.ps1` 必过；`test/scenarios/probe_arknights_mod.gd`（公式 / 便签 / 登记 / 真僵尸实例端到端）与 `test/scenarios/probe_arknights_elite.gd`（id 映射 / 判据 / 登记 49 株 / 普通关禁单与加成 / 特殊关不动数值 / 解锁同步 / **原位替换**：选卡列表长度与只排原版时一致、原版不进列表、精英只出现一次、特殊关撤表、种子包卡面的 `EliteMark` 标记：挂在卡面植物下 / 右下角 / 金色 / 场上植物不带），无头可跑（`run_autopilot.ps1 -Scenario <name>`，failed=0）；打开游戏在模组页面开启后进普通关（选卡界面每一格应换成精英卡、页数不变，植物更强）与 1-5（应全是原版数值）。

### 6.10 调试模式（`mods_builtin/debug/`）

原版没有任何调试功能 —— 僵尸卡片、四株隐藏植物、事件追踪、Ctrl+Q 调试窗口都是同人加的。
2026-10-23 之前它们长在本体里（控制台「调试」分组的一个 `debug_mode` 开关 +
`GlobalGameState.is_debug_mode`），关掉只能在每个读它的地方各判一次；现在整块做成模组：
**关掉 = 不装载，本体零节点、零分支**。

| 文件 | 作用 |
|---|---|
| `debug_mod.gd` | 入口：`install()` / `uninstall()` 开 / 关全部副作用；`on_session_reloaded()` / `install_to_main_game()` 各补一次植物解锁 |
| `debug_window.gd` | Ctrl+Q 面板：七页 + 搜索 + 拖动调宽 + 动作反馈 + 日志页（见 [调试窗口.md](调试窗口.md)） |
| `debug_window_entries.gd` | 面板里的条目（原 `src/ui/debug/`，整份搬来，去掉 `class_name`）+ 搜索索引 + 植物无敌 / 无限阳光状态 |
| `debug_damage_modifier.gd` | 「植物无敌」用的全局 `DamageModifier`：只放行 `Death` / `Script` 来源（铲子 / 关卡脚本强杀） |

装 / 卸各做四件事（全在 `_set_debug_mode()` 一处，别散着改）：

| 能力 | 落地 | 卸掉时 |
|---|---|---|
| 僵尸卡片（含僵王） | `GlobalGameState.set_runtime_zombie_card_enabled(true)` | 置 false + 清 `selected_cards` 里的僵尸条目 |
| 四株隐藏植物（三保龄球 + 反向双发） | `unlock_plants(ConstPlantUnlock.APPENDED_PLANT_TYPES)` | 逐株 `lock_plant()`（必须真删，存档按 `curr_plant` 重建） |
| 事件追踪（死事件检测） | `EventBus.is_trace_pushed_events = true` | 置 false |
| 调试窗口 | `DebugWindowScript.new()` + `Global.add_child()` | `set_window_visible(false)` 后 `queue_free()` |

**本体只为它开了通用口子**（一个模组名字都没出现，本体自己从不置真）：

| 口子 | 位置 |
|---|---|
| `set_runtime_zombie_card_enabled()` / `is_runtime_zombie_card_enabled()` | `GlobalGameState`（`is_zombie_card_enabled()` 是唯一判据） |
| `unlock_plants()` / `lock_plant()` | `GlobalGameState`（原本就是留给模组的） |
| `EventBus.is_trace_pushed_events` | 普通 bool（默认 false） |
| `ConstPlantUnlock.APPENDED_PLANT_TYPES` | 本体植物名单：原版流程拿不到的几株，供 `AllCards.is_appended_plant()` 判断「别当常规植物排」 |

**读档之后要补一次**：`Global.reload_session_for_current_user()` 会用存档覆盖 `curr_plant` /
`selected_cards`，而模组并没有被卸载（开关没变）—— 所以框架新增了

### 6.12 僵尸卡（`mods_builtin/zombie_card/`）

「我是僵尸」关卡要靠**僵尸卡**开局（玩家挑一张僵尸卡 → 放到草坪上吃植物），但本体那条僵尸卡通道
是**关着**的（`ConstFeatureSwitch.ZOMBIE_CARD_ENABLED = false`，见
[卡片与选卡流程.md](卡片与选卡流程.md) §僵尸卡片）—— 原版 PVZ1 没有「在关卡里直接放僵尸」这件事。
不解决它，「我是僵尸」关卡发不出牌、也判不了负（没有僵尸卡时
`MgMLoseManager.get_min_zombie_sun_cost()` 返回 0 = 不判负）。

**为什么不直接打开那个总开关**：它是**全局**的 —— 一打开，普通关卡的选卡界面也会冒出僵尸页，
玩家能在正常关里放僵尸。所以本模组**不去动它**，改成在需要僵尸卡的关卡里**直接把僵尸卡发进出战卡槽**。

模组名原来是「僵尸卡（我是僵尸）」，2026-10-25 起玩家对战也用它，去掉后缀。
生效范围 = **两类关卡**，按 `install_to_main_game()` 里的判据选装（别的关卡一行代码都不走）：

| 关卡 | 判据 | 装什么 |
|---|---|---|
| 「我是僵尸」 | `game_para.is_zombie_mode` | 下表全套（`zombie_card_wiring.gd`） |
| 「玩家对战」 | `game_mode == ChooseLevelPlayerBattle`（玩家对战模组 §6.11 的关卡） | **12 槽合一**的接线 + **银行视图** + 选僵尸卡面板（见下，`zombie_card_pvp_wiring.gd`）—— 场上没有脑子，脑光 / 脑子阳光不装 |

**「我是僵尸」侧**：

| 做了什么 | 怎么做的 |
|---|---|
| 发僵尸卡 | `CardSlotBattle.set_cards()`（本体给的公共口子：按身份复用 / 缺的照模板补 / 多的退回去）。关卡自己写的僵尸预选卡优先，没有就用默认四张（普通 / 路障 / 撑杆 / 铁桶，见 `zombie_card_settings.gd`） |
| 换卡槽外观 | 出战卡槽的 `panel` 样式换成 PVZ2 的 `ZombieSeedBank`（446×87，边距照原版那张） |
| 换卡面外观 | 僵尸 / 僵王卡的 `CardBg` 换成 PVZ2 的 `Seeds_ZombieSun`（50×70）—— **全模组共用的同一张**，常量在 `zombie_card_settings.gd` 的 `ASSET_ZOMBIE_CARD_BG`（「我是僵尸」与玩家对战都读它，别各留一份） |
| 换选卡界面背景 | 待选区（`CardSlotCandidate`）换成 PVZ2 的 `SeedChooser_Background_I_Zombie`（465×513，与原版那张同尺寸） |
| 脑光 | 脑子旁边挂一颗粉色星芒（PVZ2 的 `BrainGlow`）：被啃一口闪一下，脑子被吃掉时爆一下。⚠️ 脑光挂在**脑子的同级**上 —— 挂脑子底下的话，脑子被吃掉时那一爆会跟着 `queue_free()` 一起没了 |
| 脑子阳光 | 天上掉下来的阳光换成 PVZ2 的 `BrainSun`（只换外观：收集 / 飞向计数器 / 数值都不动）。靠订阅 `ConstEventName.SUN_SPAWNED` 拿到刚生成的阳光 |

**「玩家对战」侧（12 槽合一 + 银行视图 + 选僵尸卡面板，2026-10-25 加，同日改合一）**：

对战里只有**一个**出战卡槽（本体那张，关卡配 12 格）——前 6 格植物、后 6 格僵尸 / 僵王，
卡与冷却都存在同一份 `curr_cards` 里，「卡槽第几格」是**整槽 12 格**的口径（与联机的合并卡表
同一套思想：眼前是两块，存储是一份）。本体为这套加了三个**通用口子**（都不带对战字样，
见 `card_slot_battle.gd`）：`card_type_blocks` / `block_sizes`（分块：每类卡进自己那块的
第一个空位，取消只清自己那格）、`currency_of_card` / `on_card_cost`（分池：每张卡判钱 / 扣钱
问哪个池）、`shortcuts_enabled`（整槽不占数字快捷键）。空位（null）进槽后，本体各读点都补了
空位容忍。

入口有两条：

1. 主菜单 → 「选项」→ **「控制台」** → 入口页最后一个**「模组」**按钮
   （页面实例挂在控制台按钮下面：`StartMenuOptionDialog/Button4/ModPage`，
   控制台的 `@export var mod_page_path` 指向它，见 [控制台.md](控制台.md)；
   2026-10-11 之前它是选项面板里的一个独立按钮）。
   点开后页面**盖在控制台上**，关掉它（右下角「关闭」）回到控制台入口页。
2. **Ctrl+M**（2026-10-25 起）：任何时候都能直接呼出 / 收起本页面，
   **游戏内那条路就靠它** —— 游戏内的控制台没挂模组页面（入口页也就没有「模组」按钮）。
   热键在 `ModManager`（`src/mods/mod_manager.gd` 末尾 `#region 模组页面（Ctrl+M）`）：
   它 `process_mode = PROCESS_MODE_ALWAYS`，所以**树被菜单暂停时按得出来**
   （挂在 `Global` 上不行 —— 那里是 PAUSABLE，同一个坑见 `debug_window.gd` 头部注释）。
   用的页面是**场景里挂的那份**（`ModPage._ready()` 里 `register_mod_page()` 登记上来）；
   当前场景没挂（游戏内）时，`ModManager` 现造一份挂在自己下面（layer 128，盖在游戏 UI 上）。

| 文件 / 钩子                                        | 作用                                          |
| --------------------------------------------- | ------------------------------------------- |
| `src/ui/mod_page/mod_page.tscn` + `mod_page.gd` | 页面本体：左列列表 + 右侧详情 + 关闭，打开时整体重建一次             |
| `ModBase.create_detail_control()`              | **详情里模组自己那一块**（返回 null = 只有名称 / 开关 / 说明）   |
| `ModBase.create_detail_label()`                | 给模组用的一行正文（换行的样式统一在这里，模组只管 add_child）        |
| `ModBase.DETAIL_REFRESH_META`                  | 详情控件的刷新回调 meta 键（值在外面变了，页面替模组调一次）           |

页面**不认识任何一个具体模组**（与控制台同一个道理）：

- **左列** = `ModManager.all_mods`：登记了几个就列几条，按钮上带开 / 关状态，选中的那个前面加箭头；
- **右侧** = 名称 / 开关 / 说明这三样（页面自己造）+ `create_detail_control()` 返回的那一块（**模组自己造**）
  + **末尾**一块「依赖的模组」（页面自己造）：`get_mod_dependencies()` 声明了几个就列几个按钮
  （名字 + 开 / 关状态），**点了跳过去**看那个模组（分类过滤一并清掉）；没有依赖写一句
  「不依赖其它模组」。这块不跟着「模组没启用」禁用 —— 它是页面自己的导航（见 §2.3）；
- 那个开关**直接落进存档文件**（`ModManager.set_mod_enabled()` → `save_mods()`，见 §2.1）：
  点了就永久生效，下次启动照旧，`data/mods/mod_config.tres` 只在没有存档文件时才起作用；
- 模组**没启用**时，右侧它自己那一块**整块禁用**（`ModPage._set_controls_enabled()` 递归关掉
  按钮 / 勾选框 / 输入框 / 滑条）、整块压暗，并在上面写一句「先启用上面的开关」。
  关着的模组下一局根本不装载，那块里的设置改了也不生效，索性让它点不动
  （模组**不用**自己判「我开没开」—— 页面统一处理；联机面板里那句「启用之后这里就是联机面板」
  是它自己额外写的说明，两码事）。

所以新增一个模组不用碰页面；想让右侧有内容，就在自己的 `ModBase` 子类里重写：

```gdscript
func create_detail_control() -> Control:
	var box := VBoxContainer.new()
	box.add_child(ModBase.create_detail_label("解锁：通关冒险 4-5 之后戴夫把它交给你"))
	return box
```

值会变的那一块（如联机的状态栏）挂一个刷新回调，页面在 `ConsoleRegistry.values_changed` 时会调它一次：

```gdscript
box.set_meta(ModBase.DETAIL_REFRESH_META, func() -> void: builder.refresh())
```

想直接复用控制台那套控件（勾选框 / 按钮 / 滑条 / 输入框 / 只读行）就用 `ConsoleEntryControl`
—— 联机正是这么做的：**一份条目**（`_build_panel_entries()`）只喂给模组页面，
「控制台「联机」栏」这个第二现场已经撤销（曾经两边共用同一批条目）。

## 八、验证

改动较小 → **免验证**（判定见 [验证流程.md](../验证流程.md) §1）。

要验证就**打开游戏**（带窗口）跑探针，见 [AI调试通道.md](../AI调试通道.md)：

```powershell
powershell -ExecutionPolicy Bypass -File test/run_autopilot.ps1 -Scenario probe_glove_unlock -Windowed
powershell -ExecutionPolicy Bypass -File test/run_autopilot.ps1 -Scenario probe_hand -Windowed
powershell -ExecutionPolicy Bypass -File test/run_autopilot.ps1 -Scenario probe_mod_page -Windowed
```

- `probe_mod_page`：验模组页面（入口：主菜单「控制台」按钮挂着页面 / 列表条数 = 登记数 /
  详情里模组自己那一块 / 开关能真的开 / 关模组）。**无头就能跑**（纯 Control 界面，不涉及渲染）。

  （模组默认关，不打开整支必挂 —— **写新探针时最容易漏这一步**）。
- `probe_hand`：模组关着时第 7 节跳过，且断言 `HandManager` 只有 4 个本体组件
  （装了手套模组才是 5 个）。
