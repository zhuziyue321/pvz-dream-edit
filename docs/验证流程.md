# 验证流程

> **[面向 AI Agent]** ｜ **触发条件**：改完代码、准备交付之前  
> **读完你能**：① 判断本次改动**要不要验证**（改动较小 / 确定不会出问题 → 免验证；**验证过于艰难耗时 → 也可不验证，但必须在反馈里给出人工验证方法**，见 §1.1）；② 要验证时知道怎么**打开游戏**实测；③ 按模块认领人工回归清单  
> **强制级别**：**按需**（交付前先过 §1 的判定） ｜ **不读的风险**：该测的没测（运行期故障漏到线上），或不该测的也去开一遍游戏（浪费时间）  
> **关联**：仓库入口 [../AGENTS.md](../AGENTS.md) ｜ 文档地图 [README.md](README.md) ｜ 打开游戏取证 [AI调试通道.md](AI调试通道.md)

本文件定义改完代码后的验证方式。

**本项目的验证方式只有一种：打开游戏（带窗口）实测。**

原静态验证流水线 `test/verify.ps1` 及其驱动的 `standard_check` / `script_check` /  
`project_checker` / `runtime_smoke` / `autoload_smoke` **已全部删除**。  
原因：静态检查只能证明「没坏」，证明不了「能玩」—— `logger.gd` 曾经在 `_write()` 里  
误用 `Log.debug()`，导致 `_write → debug() → _write` 无限递归爆栈，  
而编辑器全量扫描与资源自检**全是绿的**。  
反过来，为了跑那套脚本付出的等待与误报成本却是实的。  
验证一律回到「打开游戏」。

## 1. 先判断：这次要不要验证

**免验证（改完直接交付）** —— 满足任一情形即可：

| 情形                        | 例子                                                 |
| ------------------------- | -------------------------------------------------- |
| 改动较小、没有外溢影响               | 注释、文案、`docs/` 文档、单个函数内部的局部逻辑                       |
| 确定不会出问题                   | 改动路径没有其它调用方；没动公共签名 / 枚举 / 注册表 / 资源引用               |
| 能明确说出影响面                  | 「只影响 X，而 X 不受这次改动影响」                               |
| **验证成本过高、不值得脚本化**（见 §1.1） | 要凑出触发条件得先通关 N 关 / 改存档 / 等几分钟随机事件；或探针断言不出来，只能靠肉眼与手感 |

**必须打开游戏实测**：

- 新增 / 改动单位：植物、僵尸、子弹、手持物、组件、关卡；
- 改了公共签名、枚举、注册表、autoload、资源路径（含改名）；
- 改了 `ready_norm()` / `ready_norm_signal_connect()` 链路、组件挂载与启停；
- 改了任何**玩法行为**：出怪、波次、教程、掉落、存档…；
- **拿不准** —— 拿不准就按「要验证」处理。

> 判定看的是**改动面**，不是改动行数：改 1 行但改的是 `Global` 的公共方法，就要验证。

### 1.1 验证成本过高时可以不验证但必须在反馈里给出人工验证方法

有些改动**理论该验，实际验不动** —— 光是把游戏推进到能触发它的状态就要几分钟甚至几十分钟，  
或者它本身就是「手感 / 时序 / 画面」这类脚本断言不出来的东西。  
**允许跳过脚本验证**，但**不允许悄悄跳过**：跳过的前提是把验证成本转交给人类，  
在交付反馈里写明「怎么自己验一遍」。

**适用（示意，不穷举）**：

- 触发条件极难凑：要先通关若干关 / 手改存档 / 等一个低概率随机事件才有机会复现；
- 单局耗时长：一次验证要盯几分钟的真实对局；
- 只能靠肉眼判定：动画时序、手感、UI 观感，探针断言不出来；
- 环境与成本明显不成比例（例如为了 1 行改动专门写一个新探针）。

**不适用（不能拿这条当挡箭牌）**：

- 改动就是「跑一遍就能看出对不对」的常规玩法改动；
- 已有现成探针（§3 清单里带 `-Scenario xxx` 的）能覆盖的场景；
- 拿不准影响面的改动 —— 那按「必须打开游戏实测」处理。

**跳过后，交付反馈必须包含下面三块**（缺一块视为未交付）：

1. **结论**：明确写「本次未做脚本验证，原因：……（成本过高 / 需人工肉眼判定）」。
2. **人工验证方法**：可照做的步骤 —— 进哪关 / 用什么存档 / 点哪些按钮 / 看什么现象算对。  
   有现成探针就附上完整命令：`powershell -ExecutionPolicy Bypass -File test/run_autopilot.ps1 -Scenario <name> -Windowed`，  
   并说明 `result=PASS` 算通过。
3. **预期结果与判据**：什么现象 = 通过，什么现象 = 坏了（最好再给一条「坏了怎么回退」）。

模板：

```
验证状态：未验证（成本过高）
原因：<为什么脚本化不划算>
人工验证方法：
  1. <准备：进 X 关 / 用 Y 存档 / 需要已通关 Z>
  2. <操作：点 A → 点 B → 等 C 秒>
  3. <判据：看到 D = 通过；看到 E = 坏了，回退方式是 …>
（可选）现成探针：powershell -ExecutionPolicy Bypass -File test/run_autopilot.ps1 -Scenario <name> -Windowed → [XXX] result=PASS
```

> 这条只**转移**验证责任，不**免除**验证责任。  
> 「没验证」必须连同「怎么验」一起交付，不能只写「未验证」三个字。

## 2. 怎么验证：打开游戏

由轻到重三档，按需选：

1. **自己玩**：Godot 打开项目 → F5 运行 → 按 §3 清单里对应模块逐条过；控制台不刷错即通过。
2. **Agent 自己开游戏取证**：见 [AI调试通道.md](AI调试通道.md) —— 带窗口启动真实游戏、  
   模拟操作、取回结构化状态（`a.observe` / F10 快照 / `debug_channel_log.txt`）。
3. **探针回归（可选）**：
   ```powershell
   powershell -ExecutionPolicy Bypass -File test/run_autopilot.ps1 -Scenario <name> -Windowed
   ```
   探针输出 `[XXX] result=PASS|FAIL`。**必须带 `-Windowed`**：不带是无头 CI 回归，  
   只证明「探针问过的那几件事过了」，**不能**用来判定行为对不对。  
   报告落在 `%TEMP%\pvz_autopilot\ap_out.txt`，存档同样被重定向，不会碰真实存档。

> ⚠️ 探针 PASS ≠ 改动没问题。探针只覆盖它自己断言过的点；  
> 画面、时序、手感只有真窗口里看得见。

## 4. 调试通道（运行期取证）

打开游戏实测只能覆盖「已知的检查点」。  
当遇到**只有在真实对局里才复现**的问题时，用调试通道把现场录下来。

### 设计原则

**默认完全静默** —— 不带参数启动时，它只在启动时做一次判定就什么都不做，  
不影响正常游戏、不写任何文件。只有满足以下任一条件才激活：

1. 命令行带用户参数：`-- --debug-channel` 或 `-- --debug-channel-level`
2. 存在开关文件 `user://debug_channel.on`

### 用法一：正常游玩时录制（**排查首选：打开游戏**）

双击 `test/debug_channel.bat`：

1. 游戏正常启动，**你自己玩**
2. 想记录现场时按 **F10**，会把当前状态快照追加进报告
3. 玩完关掉游戏
4. 把生成的 **`debug_channel_log.txt`** 发我

日志里同时包含：Godot 自身所有 `print`/错误输出 + 调试通道的结构化报告。

### 用法二：全自动跑一关（无头 CI 回归，**不用于排查**）

双击 `test/debug_channel_auto.bat`：

- 无窗口（`--headless`）启动
- 自动载入 `adventure_01_01.tres` 并切到主游戏场景
- **自动跳过选卡**（调用 `main_game_start()`，否则游戏会永远停在选卡阶段，僵尸不刷）
- 跑 45 游戏秒，期间每 120 帧采样一次
- 出报告后自动退出

自定义时长：`set SECONDS=90` 后再运行。

**这个流程不会碰你的存档** —— `.bat` 里把 `%APPDATA%` 重定向到了 `%TEMP%\pvz_debug_userdir`。

> ⚠️ 无头跑批没有画面、视口是强设的假尺寸、帧率不受限，  
> 只能证明「跑得完」。**要排查就回到用法一**，  
> 或用 [AI调试通道.md](AI调试通道.md) 的 `run_autopilot.ps1 -Windowed` 打开游戏再驱动。

### 报告里有什么

| 区块    | 内容                                                             |
| ----- | -------------------------------------------------------------- |
| 环境    | 引擎版本、平台、渲染方式、视口、时间缩放、main_scene                                |
| 自动加载  | 8 个核心单例是否都注册（缺哪个直接列出）                                          |
| 日志自检  | 四级日志各调一次 —— **曾经这里会无限递归爆栈**，看到「正常」即为通过                         |
| 注册表   | 角色（植物/僵尸条数）、子弹、AllCards 卡牌数、SceneRegistry 抽检                   |
| 运行时状态 | 当前场景、`Global.main_game` 是否有效、植物格子行列数与**失效引用数**、场上僵尸数与**失效引用数** |
| 采样    | 每 120 帧：frame / fps / 节点数 / **孤儿节点数** / 静态内存 / 场景 / 场上僵尸数      |

「失效引用数」和「孤儿节点数」是排查**对象泄漏与悬空引用**最直接的两个指标，  
正常情况下应始终为 **0**。

### 已知的正常现象

- 无头模式下 `视口尺寸` 显示 `(0, 0)`、`fps` 会跑到 140+（无垂直同步），都不是问题。
- 自动关卡模式强制退出时可能打印 `ObjectDB instances leaked at exit` ——  
  这是**中途掐断对局**造成的，手工正常退出不会出现，属预期。
- stderr 里必然有一行 `[调试通道] error 级自检` —— 那是故意触发的，用来验证 error 级能正确走 stderr。
- 本机还会固定出现 `Failed to read the root certificate store`（没有可读的根证书库），属环境噪声，不是项目问题。

### 不要它了怎么移除

1. 删掉 `project.godot` 里 `[autoload]` 下的 `DebugChannel=...` 一行
2. 删掉 `src/core/autoload/debug_channel.gd`（含 `.uid`）
3. 删掉 `test/debug_channel*.bat`

## 5. 维护这些工具时注意

1. **批量重命名文件/目录前先关 Godot 编辑器**：编辑器会把瞬时消失的 `.uid` 当孤儿文件删除  
   （本项目曾一次性被删掉 17 个 `.uid`，靠备份恢复）。
2. 往项目里加 `print()` 之前先看 [参考存档 S-02 日志走 Log](参考存档/规范细则存档.md#s-02-日志必须走-log) —— 一律走 `Log`（[项目规范.md](项目规范.md) §1 第 6 条，硬约束）。
3. **不要用 `Start-Process` 起 Godot**：部分受限环境直接 `Access is denied`，  
   而 Godot 在 Windows 是 **GUI 子系统程序**，不重定向就完全抓不到 stdout。  
   统一用 `cmd.exe /c '"<godot>" <args> > out.txt 2> err.txt'`（`run_autopilot.ps1` 已改）。
4. 新增的启动步骤，若是「启动场景但不是玩游戏」，记得带 `-- --no-autopilot`。
5. **写探针断言时不要依赖随机结果**：本项目大量逻辑用 `randi_range` / `pick_random`  
   （僵尸随机外观就是逐项 `pick_random`，全 false 的概率 1/8）。  
   断言只写**确定性**判定，随机值放到 detail 里打印 —— 否则探针会随机翻车，  
   让人误以为是代码坏了。`test/scenarios/probe_init.gd` 里有正反面示例。
